# 不使用 ByteTrack 会失去什么？

## 结论

可以不使用 ByteTrack。

只要保留“无手稳定快照 → 前后快照对比 → 更新库存”的主流程，系统仍能完成主要任务：

```text
放入
取出
食材是否存在
粗粒度分类
遮挡物品仍保留在库存中
```

最主要的损失是：对【整理 / 移动】的判断会变差。


## 没有 ByteTrack 时，整理会怎样？

例如苹果从左边移到右边：

```text
旧稳定快照：左边有苹果 A
新稳定快照：左边没有苹果，右边有苹果 B
```

没有中间轨迹证据时，系统无法高置信地证明 A 和 B 是同一颗苹果。
最保守的结果会是：

```text
左边苹果 A → OUT（取出）
右边苹果 B → IN（放入）
```

这会产生一对不够准确的事件，但最终库存数量通常还是正确的：

```text
操作前：1 个苹果
操作后：1 个苹果
```

如果当前阶段可以接受“整理偶尔被拆成取出 + 放入”，那完全可以先不用 ByteTrack。


## ByteTrack 还提供哪些作用？

| 作用 | 不用它会怎样 | 是否必须 |
| --- | --- | --- |
| 区分整理与“取出 + 放入” | 整理可能被拆成两条事件 | 不必须，但这是它最有价值的作用 |
| 记录物品移动过程 | 只能看操作前后，无法知道中间路径 | 不必须 |
| 手遮挡后连接移动前后 | 手挡住物品后，更难证明它被放到哪里 | 不必须；最终快照仍可判取出/放入 |
| 临时检测连续性 | 短暂漏检时可保留一小段轨迹 | 快照投票和遮挡状态已能承担大部分作用 |
| 画面显示 | 可以在画面上显示 `Track#12` 等轨迹号 | 仅调试用途 |

所以对这个项目来说，ByteTrack 不是库存系统的必需基础，而是“提高整理识别准确度”的可选增强模块。


## 没有 ByteTrack 时，必须保留什么？

不要因为去掉 ByteTrack，就同时去掉以下核心逻辑：

```text
1. 连续无手、稳定后才生成快照
2. 快照多帧投票，过滤 YOLO 单帧抖动
3. InventoryItem / item_id，保存库存状态
4. visible / occluded / out 三种库存状态
5. 遮挡物品不能直接出库
6. 新稳定快照与 baseline 快照的差异判断
```

这些才是库存准确性的主干；ByteTrack 只是旁路证据。


## 一个很适合当前阶段的简化方案

建议第一版先采用：

```text
稳定快照主导库存
整理暂时允许拆成 OUT + IN
不让任何逐帧轨迹直接修改库存
```

这样流程更简单、性能开销更小，也更容易测试。

后续若发现“整理被拆成事件”确实影响演示或后端业务，再补一个更简单的移动辅助模块即可；不一定要保留现在这套完整的 ByteTrack + HELD 代理设计。


一句话总结：

```text
没有 ByteTrack，系统仍能管理库存；
只是更难知道同一件物品是否从一个位置整理到了另一个位置。
```
