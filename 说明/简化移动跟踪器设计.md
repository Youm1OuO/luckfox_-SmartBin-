# 极简 ByteTrack + 快照设计：每件物品只记录起点和终点

## 结论

你现在的想法更简单，也更适合这个项目。

不需要复杂的 `HeldProxyEvidence`、完整轨迹数组、多级分数或跨快照冻结。
在一次“旧稳定快照 → 新稳定快照”的操作期间，每个被跟踪的库存物品只保留：

```text
Start_Box：操作开始时的位置
End_Box  ：目前最后确定/估计的位置
```

等快照发现：

```text
旧快照：A 消失
新快照：出现同类 B，且 A / B 大小接近
```

才检查：

```text
A 对应轨迹的 End_Box 是否靠近 B.box？
```

靠近且候选唯一，就判【整理】；否则回退为【OUT + IN】。


## 最小轨迹结构

```cpp
# 轨迹模式 (即：轨迹目前的情况)
enum class TrackMode {
    OBJECT,      // 物品仍被 YOLO 检测到
    HAND_PROXY,  // 物品被手完全挡住，暂时跟随手位移
    INVALID,     // 冲突或断轨，不能用于判整理
};

struct ItemTrack {
    int item_id;             // 这条轨迹属于哪个库存物品
    int cls_id;              // 物品类别
    int object_track_id;     // 物品自己的短期 track_id
    int hand_track_id;       // HAND_PROXY 时的手 track_id；否则 -1

    BBox start_box;          // 从 baseline 快照得到的旧位置
    BBox end_box;            // 当前最后位置：真实物品框或手代理估计框
    BBox hand_start_box;     // 切换代理时，手的位置

    TrackMode mode;          // 当前的轨迹模式
    bool valid;              // 能否作为整理证据
};
```

这就是全部核心数据。没有完整路径数组；每帧只覆盖更新 `end_box`。


## 一次操作如何运行

### 1. baseline 快照建立

假设稳定快照中有：

```text
item#1：苹果，在左边 L
item#2：牛奶，在中间 C
item#3：苏打罐，在右边 R
```

本轮操作开始后，每个物品可按需建立一条 `ItemTrack`：

```text
苹果被看到并匹配到 item#1：
    start_box = L
    end_box   = L
    mode      = OBJECT
    valid     = true
```

`start_box` 必须使用 baseline 中的物品位置，而不是 Track 刚创建时的随机位置。


### 2. 物品完整可见或部分遮挡但仍被 YOLO 识别

只要 YOLO 仍能检测到苹果，简单 ByteTrack 就让相邻帧的苹果检测框维持同一个 `object_track_id`。

```text
苹果在 L → M：
    ItemTrack.end_box = M

苹果被部分挡住，但 YOLO 仍识别到：
    ItemTrack.end_box = 当前较小的苹果框
    mode 仍为 OBJECT
```

部分遮挡时框大小会变小，所以“是否是同一条轨迹”的匹配不能只看严格 IoU；可以使用：

```text
同类
且（IoU 有重叠，或中心距离仍很近）
```

只要匹配连续，最终 `end_box` 就会随着物品移动到新位置。


### 3. 被手完全挡住时，物品轨迹改为遵从手的位移

当满足：

```text
手与 item#1 的当前 end_box 明显重叠；
随后 item#1 的 YOLO 检测消失；
手仍连续被跟踪。
```

就把同一条苹果 `ItemTrack` 切换为：

```text
mode = HAND_PROXY
hand_track_id = 当前手的 track_id
hand_start_box = 手刚遮挡苹果时的框
```

之后苹果的 `end_box` 跟随手的**位移**更新：

```text
手从 H0 移动到 H1：
    dx = H1.center_x - H0.center_x
    dy = H1.center_y - H0.center_y

苹果 end_box = 遮挡前苹果框，整体平移 (dx, dy)
```

这就是“物品轨迹遵从手轨迹”的正确含义。

不要直接写：

```text
苹果 end_box = 手的 bbox
```

因为手框和苹果框大小不同；直接覆盖后，苹果的 `end_box` 很可能无法和新快照中的苹果 B 做大小/位置比较。

正确结果是：

```text
苹果仍保持苹果原来的框大小；
只是它的中心随着手的中心移动相同距离。
```


### 4. 手离开后，等待新稳定快照

移动期间不生成库存快照。

手离开后，物品可能在新位置重新被 YOLO 检测到，也可能其新 `object_track_id` 已经变了；这不影响已有的 `ItemTrack`：

```text
ItemTrack.item_id = 1
ItemTrack.start_box = L
ItemTrack.end_box = 手代理推算出的 R 附近位置
```

只要画面连续无手、稳定 N 帧，生成新稳定快照。


## 快照对比时才使用轨迹

快照 diff 得到：

```text
A：旧快照中左边消失的苹果，对应 item#1
B：新快照中右边出现的苹果
```

此时使用 `item#1` 直接找到：

```cpp
ItemTrack track = tracks_by_item_id[1];
```

判整理只需要检查以下条件：

```text
1. A.cls_id == B.cls_id
2. A.box 与 B.box 的大小、宽高比接近
3. track.valid == true
4. track.start_box 靠近 A 的旧位置
5. track.end_box 靠近 B 的新位置
6. B 是唯一合理的同类新物品候选
```

全部满足：

```text
item#1 判定 MOVED
item#1.anchor_box / visible_box 更新为 B.box
```

有一项不满足：

```text
A OUT
B IN
```

没有 PendingRelocation，也不需要一堆低/中/高分支。


## 冲突时唯一的处理原则

只有两类冲突需要处理：

```text
一只手明显盖住多个物品；
同类 B 候选有多个，无法唯一对应。
```

遇到任一冲突：

```text
track.valid = false
```

然后老老实实回退 `OUT + IN`。

这条规则能替代复杂的抢占、候选分数和多层状态机。


## 它和旧方案相比删掉了什么

不需要：

```text
- 保存每一帧的完整 object trajectory
- 保存完整 hand proxy trajectory
- candidate_held / confirmed_held 多层集合
- 复杂 ReID 分数
- PendingRelocation
- 长时间 LOST 队列
- track_id 作为库存长期字段
```

只保留：

```text
物品的 Start_Box
物品的 End_Box
完全遮挡时的手位移代理
快照 diff 时的一次终点核对
```


## 最短例子

```text
baseline：item#1 苹果在 L

操作中：
  苹果可见时：End_Box 跟着苹果从 L 到 M
  苹果被手挡住：End_Box 跟着手位移从 M 到 R

stable：左边苹果消失，右边出现同类苹果 B

检查：item#1.End_Box 靠近 B.box，且 B 唯一
结果：item#1 MOVED 到右边
```

一句话总结：

```text
每个物品只保存 Start_Box 和 End_Box。
可见时 End_Box 跟物品；完全遮挡时 End_Box 跟手的位移。
快照出现 A 消失 + B 出现时，只核对 End_Box 是否到达 B。
```
