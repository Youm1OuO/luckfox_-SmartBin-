# 快照与库存对比的规则

这份规则用于手离开后的一份稳定 Snapshot，与正式 `InventoryDB` 比较并确认：整理、取出、放入、遮挡、露出。

## 1. 前提与临时数据

只有满足下面条件才允许改正式库存：

```text
已经得到 N 帧连续无手的稳定 Snapshot；
operation_pending == true（本轮确实出现过手）。
```

若 `operation_pending == false`，不做出入库或状态变化，只刷新正常匹配物品的 `last_seen_box`。

比较时不直接改 `InventoryDB`：

```text
planned = InventoryDB 的副本；
initial_status[item_id] = 比较开始前的状态；

每个 SnapshotItem B：
    binding[B] = -1；
    role[B] = NONE；
```

`initial_status` 必须保留。因为“本轮刚改成 OUT/OCCLUDED”不等于“原本就是 OUT/OCCLUDED”。

每个 B 最终只能有一个 `item_id`、一个角色：

```text
DIRECT    原位置仍可见
MOVED     Track 已证明整理
REVEALED  原本 OCCLUDED 的旧物品露出
RETURNED  原本 OUT 的旧物品放回
NEW_ITEM  真正新放入
```

一个 B 一旦有角色，后续不能改写为另一个身份。

---

## 2. 身份匹配：普通框与局部框

### 2.1 NORMAL_MATCH：普通身份匹配

```text
类别相同；
中心距离接近；
宽、高接近。
```

这是默认匹配方式，先尝试它。

### 2.2 PARTIAL_MATCH：局部框身份匹配

普通匹配失败后，允许判断“B 是某个可靠完整参考框 `R` 被遮挡后留下的小框”。

```text
直接身份匹配时：R = A.anchor_box；
Track 整理匹配时：R = Track.release_box 或可靠 Track.proxy_box。
```

规则：

```text
1. A.cls_id == B.cls_id；
2. R 必须是可靠完整框；
3. B 的面积小于 R；
4. B 几乎被 R 包含：
   intersection(R, B.box) / min(areaR, areaB) 足够高；
5. B 的中心在 R 内部或附近；
6. 所有同类库存项中，只有 A 唯一满足。
```

方向不能反过来：

```text
小框 B 被可靠完整框 R 包含
    → 可以是 A 的局部框。

大框 B 包含 R
    → 不能仅凭包含关系认作同一物品。
       它可能把邻居或背景也框进去了。
```

`A.last_seen_box` 比 `anchor_box` 小，说明 A 上一轮可能已是局部可见；它可以提高匹配可信度，但**不是 PARTIAL_MATCH 的必要条件**。

因为本轮可能刚发生：

```text
上一轮：A 完整可见，last_seen_box ≈ anchor_box；
本轮：新物体挡住 A，当前 B 变成小框。
```

身份不唯一时，不强行认领：

```text
一个小苹果框同时被两个旧苹果 anchor_box 包含
    → 不做 PARTIAL_MATCH。
```

### 2.3 PARTIAL_MATCH 成功后的更新

```text
A.status = VISIBLE；
A.last_seen_box = B.box；
A.anchor_box 不修改；
A.anchor_valid 保持 true。
```

`VISIBLE` 的含义是“当前还能被 YOLO 识别到”，不要求一定是完整框。

若新物品第一次出现时只能看到局部小框：

```text
last_seen_box = B.box；
anchor_valid = false；
```

以后看到更可靠的完整框后，才确认它的 `anchor_box`。

> N 帧快照投票聚类也要兼容“完整框 / 被包含的小框”属于同一物品；但同类物品身份不唯一时不能合并。

## 3. 固定处理顺序

```text
1. 原位置仍可见
2. Track 已证明的整理
3. 剩余旧可见物品消失：取出 / 遮挡 / 露出
4. 剩余当前快照物品：露出 / 放回 / 新放入
5. 遮挡计数器
6. 最终检查并一次性提交
```

比较期间只改 `planned`；最后才提交正式库存。

---

## 4. 第一步：原位置仍可见

对每个 B，与开始时 `VISIBLE` 的库存项 A 做一对一身份匹配：

```text
先 NORMAL_MATCH；失败后再尝试 PARTIAL_MATCH。
```

成功：

```text
binding[B] = A.item_id；
role[B] = DIRECT；
planned[A].status = VISIBLE；
planned[A].last_seen_box = B.box；
```

若是 `PARTIAL_MATCH`，不得把 `anchor_box` 缩成 B 的小框。

---

## 5. 第二步：Track 证明整理

处理尚未原位匹配的 `VISIBLE` 旧物品 A，与尚未绑定的同类 B。

```text
Track 有 release_box：
    B 必须唯一匹配 release_box；对不上就不退回 path。

Track 没有 release_box：
    B 必须唯一匹配 Track.path 中某个代理框。
```

匹配 B 时，同样允许 `NORMAL_MATCH` 或 `PARTIAL_MATCH`：

```text
若 B 是完整框：
    anchor_box = B.box。

若 B 是局部框：
    last_seen_box = B.box；
    anchor_box = 与 B 匹配的完整 release_box / proxy_box；
    不能把 anchor_box 缩成 B.box。
```

整理成功后立刻检查两处：

```text
A 旧位置附近：
    若 C 唯一匹配“原本 OCCLUDED”的库存项 I：
        C → I.item_id，role = REVEALED，I → VISIBLE。

B 新位置附近：
    若原本 VISIBLE 的 D 消失：
        D → OCCLUDED。
```

所有 C、D 都要扫描；已认定 `REVEALED` 的 C 不能再当未知遮挡物。

---

## 6. 第三步：剩余旧可见物品 A 消失

此时 A 没有原位匹配，也没有被 Track 证明整理。

扫描 A 旧位置附近的所有当前快照物品 C，分成两类：

```text
revealed_C：
    C 能唯一匹配“开始时就是 OCCLUDED”的库存项 I。
    → 预留 C → I.item_id；role[C] = REVEALED；I → VISIBLE。

unknown_C：
    C 不能唯一匹配任何原本 OCCLUDED 的库存项；
    或 C 的身份本身不唯一。
```

然后再决定 A：

```text
附近没有 C：
    A → OUT。

附近只有 revealed_C，没有 unknown_C：
    A → OUT；
    revealed_C → VISIBLE。

附近存在至少一个 unknown_C：
    A → OCCLUDED。
```

这一步的关键禁止事项：

```text
不能只因附近有 C，就直接 A → OCCLUDED。

必须先判断 C 是否是原本 OCCLUDED 的旧物品露出。
若是，C 是“露出”，不是“新的遮挡物”。
```

若附近同时有 `revealed_C` 和 `unknown_C`：

```text
revealed_C 仍可露出；
A 保守保持 OCCLUDED。
```

---

## 7. 第四步：剩余当前快照物品 B

只处理仍未绑定的 B：

```text
1. 唯一匹配 initial_status == OCCLUDED 的库存项：
       B → REVEALED，继承 item_id。

2. 唯一匹配 initial_status == OUT、且未过期的库存项：
       B → RETURNED，继承 item_id。

3. 都不匹配：
       B → NEW_ITEM，分配新 item_id。
```

禁止用本轮刚改变状态的物品做第 1、2 项匹配：

```text
本轮 A → OUT 后，不能立刻让另一个同类 B 恢复 A；
否则“拿出 A + 放入 B”会被错误合并。

本轮 A → OCCLUDED 后，也不能立刻被 B 恢复。
```

---

## 8. 计数器、检查与提交

所有身份和状态确定后，才处理最终仍为 `OCCLUDED` 的物品：

```text
只在本轮 operation_pending == true 时增加一次计数；
不按每帧、也不按静止快照重复增加。
```

提交前检查：

```text
每个 B 都绑定到唯一 item_id，且该 item 最终为 VISIBLE；
一个 item_id 不会被两个 B 绑定；
每个原本 VISIBLE 的 A 都已有最终状态：
DIRECT / MOVED / OCCLUDED / OUT；
没有相互矛盾的 planned 修改。
```

```text
检查通过：planned 一次性提交给 InventoryDB。
检查失败：整轮不提交，正式库存保持不变。
```

提交后清空本轮 Track、Candidate、临时绑定，并令：

```text
operation_pending = false。
```

---

## 9. 例子：移开苏打罐，露出橙子

比较前：

```text
item#10 soda_can：VISIBLE，右边；
item#11 orange：OCCLUDED，右边。
```

当前 Snapshot：

```text
B1：左边 soda_can；
B2：右边 orange。
```

```text
Track 成功：
    item#10 → MOVED 到左边；
    item#11 → REVEALED。

Track 失败：
    B2 唯一匹配原本 OCCLUDED 的 item#11；
    item#11 → REVEALED；
    item#10 → OUT；
    B1 → NEW_ITEM。
```

Track 失败时允许退化成 `OUT + IN`，但不能留下一个不存在的“右边被遮挡的 item#10”。

---

## 10. 信息不足时的原则

```text
同类物品身份不唯一；
多个候选同样匹配；
YOLO 把冰箱外物品也识别进来；
多件物品同时移动且 Track 不唯一。
```

这些情况不强行判整理、露出或放回：

```text
附近有身份不明物体 → 优先 OCCLUDED；
身份绑定检查失败 → 本轮不提交。
```
