# 从开门第一帧开始的完整运行过程

这一节说明一次开门会话中，每一帧做什么、Track 如何工作、稳定快照如何和库存比较。

### 7.1 开门：初始化本次临时状态

冰箱门打开时，先从后台读取已经确认的库存表：

```text
InventoryDB：唯一正式状态
item_id=1：苹果，VISIBLE，anchor_box=L，last_seen_box=L
item_id=2：牛奶，VISIBLE，anchor_box=R，last_seen_box=R
item_id=3：饮料，OCCLUDED，anchor_box=M，last_seen_box=M
```

然后只清空本次开门的临时状态：

```cpp
ProcessStore {
    no_hand_buffer = 空;
    current_stable_snapshot = 空;
    tracks = 空;
    operation_pending = false;   // 用于判断是否要处理【遮挡】物体的计数器
}
```

此时不会复制或修改库存。库存表就是本次比较的旧基准。

### 7.2 所有帧都先做的事情

无论是否有手，每一帧都执行：

```text
1. 摄像头取一帧图像；
2. 输入 YOLO，得到本帧 Detection 列表；
3. 得到手框 hand_box（若有手）；
4. 对 Detection 做类别筛选、框坐标统一；
5. 更新本次 ProcessStore；
```

单帧 Detection 只有：

```cpp
Detection { cls_id, box, score }
```

它没有自己的 `item_id`。只有在本帧处理时，程序才会尝试让它临时关联到：

```text
某条活动 Track，或某个 InventoryItem。
```

注意：无论这一帧匹配是否成功，都不能立刻改 `InventoryDB`。正式库存只在稳定快照比较结束后修改。

### 7.3 手在画面中：更新 Track，不生成快照

只要检测到手：

```text
operation_pending = true;
清空 no_hand_buffer；
本帧不参与稳定快照；
```

此时库存中的 `anchor_box`、`last_seen_box`、`status` 都保持不变。

Track 只用来证明“原有库存物品是否被整理”；新放入、拿出等情况仍交给稳定快照与库存比较。因此 Track 使用下面三个状态：

```cpp
enum class TrackState {
    TRACKING_VISIBLE,      // YOLO 仍看得到物品：可以完整可见或部分被手遮挡
    FULL_HAND_OCCLUDED,    // YOLO 看不到物品，只能按手位移估计
    PLACED                  // 已确认物品放下，不再跟随手
};
```

一条 Track 主要保存：

```cpp
Track {
    track_id;                    // 本次开门的临时编号
    bound_item_id;               // 所引用的库存物品
    cls_id;
    start_box;                   // 从 anchor_box（或 last_seen_box）复制来的起点
    proxy_box;                   // 当前完整物品位置的估计框
    optional<BBox> last_yolo_box;// 最近一帧物品 YOLO 框，可为局部框
    last_hand_box;
    path;                        // 本次操作中每次更新后的 proxy_box
    optional<BBox> release_box;  // 已确认放下位置；未确认时为空
    state;
}
```

#### 7.3.1 手刚碰到一个原有物品

例如库存中有苹果：

```text
Inventory item_id=1：apple，anchor_box=L，anchor_valid=true
```

手进入后，YOLO 还能看到苹果的一部分：

```text
Detection：apple，box=L_part
```

处理顺序是：

```text
先尝试匹配已有活动 Track；
若没有匹配的 Track，再与库存中 VISIBLE 的同类物品比较；
要求 cls_id 相同、物品在手附近，且局部框与 last_seen_box / anchor_box 有较强包含关系；
匹配到 item_id=1 后，创建一条临时 Track。
```

```cpp
Track {
    track_id = 1;         // 本次开门的临时编号
    bound_item_id = 1;    // 引用库存苹果
    cls_id = apple;
    start_box = item#1.anchor_box;
    proxy_box = item#1.anchor_box;     // 当前完整物品位置的估计框
    path = [item#1.anchor_box];
    last_yolo_box = 当前苹果检测框;
    last_hand_box = 当前手框;
    release_box = 空;
    state = TRACKING_VISIBLE;
}
```

这里 `Track` 是复制 `anchor_box` 的值，不是一直读取库存框。`proxy_box` 始终表示“完整物品的最新估计框”；`last_yolo_box` 则是最近一帧 YOLO 输出的原始框，允许是局部小框。因此手移动期间，库存框始终冻结，Track 自己的 `proxy_box` 和 `path` 才会变化。

#### 7.3.2 手在移动，YOLO 仍能看到物品

当前帧苹果已经被移动到中间位置：

```text
Detection：apple，box=M_part
```

先看所有当前物品 Detection，不只看手附近；因为苹果可能已经放下，手正在转去拿牛奶。对同类候选 Track，按状态选择比较对象：

```text
TRACKING_VISIBLE 或 PLACED
→ D.box 与 Track.last_yolo_box 比较。

FULL_HAND_OCCLUDED
→ D.box 与 Track.proxy_box 比较。
```

若当前 `Track#1.state == TRACKING_VISIBLE` 且匹配成功：

```cpp
object_delta = Center(current_detection.box) - Center(track.last_yolo_box);
track.last_yolo_box = current_detection.box;
track.last_hand_box = current_hand_box;

if (物品连续两帧位移很小 &&
    手已不再覆盖物品 &&
    (!item.anchor_valid || SimilarSize(current_detection.box, item.anchor_box))) {
    track.state = PLACED;
    track.proxy_box.center = Center(current_detection.box); // 宽高保持原样
    track.release_box = track.proxy_box;
} else {
    track.proxy_box = Move(track.proxy_box, object_delta);
}

track.path.push_back(track.proxy_box);
```

也就是说：局部 YOLO 框通常只用于计算位移，不能直接覆盖完整的 `proxy_box`；但确认已放下时，可以用当前较可靠 Detection 的中心校正 `proxy_box`。

若当前 `Track#1.state == FULL_HAND_OCCLUDED`，而苹果重新出现：

```cpp
// D.box 先与 proxy_box 匹配成功
track.last_yolo_box = current_detection.box;
track.last_hand_box = current_hand_box;
track.state = TRACKING_VISIBLE;
// 本帧没有相邻的物品 YOLO 框，不计算 object_delta，不移动 proxy_box
track.path.push_back(track.proxy_box);
```

下一帧才恢复用相邻 YOLO 框的位移更新 `proxy_box`，或满足条件后确认 `PLACED`。

若 Track 已是 `PLACED`，正常情况下只更新 `last_yolo_box`、记录路径，不移动 `proxy_box`。若手再次覆盖它、且物品框又明显移动：

```cpp
object_delta = Center(current_detection.box) - Center(track.last_yolo_box);
track.state = TRACKING_VISIBLE;
track.release_box.reset();
track.proxy_box = Move(track.proxy_box, object_delta);
track.last_hand_box = current_hand_box;
track.last_yolo_box = current_detection.box;
track.path.push_back(track.proxy_box);
```

库存 `item_id=1` 仍留在旧确认位置 L，直到本次操作最终被确认。

#### 7.3.3 手完全挡住物品，YOLO 看不到物品

例如苹果 Detection 消失，但手仍连续出现。

```text
Track#1 不删除；
Track#1.bound_item_id 仍为 1；
```

此时用手框的位移作为代理：

```cpp
if (track.state == PLACED) {
    // 刚再次拿起的第一帧没有可靠 hand_delta
    track.release_box.reset();
    track.last_hand_box = current_hand_box;
} else {
    hand_delta = Center(current_hand_box) - Center(track.last_hand_box);
    track.proxy_box = Move(track.proxy_box, hand_delta);
    track.last_hand_box = current_hand_box;
}

track.state = FULL_HAND_OCCLUDED;
track.last_yolo_box.reset();
track.path.push_back(track.proxy_box);
```

这一步只在手仍靠近 `proxy_box` 时执行；若手已经远离该 Track，则不再让它跟随手。物品估计框仍保持完整框的大致尺寸，只是位置跟着手移动。手离开时，不再继续追加手的离开路径；Track 保留当前已有路径，等待后面的稳定快照使用。

若手一进入就完全盖住库存物品，当前没有物品 Detection，也可以创建候选 Track：

```cpp
track.bound_item_id = item.item_id;
track.start_box = item.anchor_valid ? item.anchor_box : item.last_seen_box;
track.proxy_box = track.start_box;
track.last_yolo_box = 空;
track.last_hand_box = current_hand_box;
track.path = [track.proxy_box];
track.release_box = 空;
track.state = FULL_HAND_OCCLUDED;
```

第一帧只记录手框；下一帧才有 `hand_delta` 可以计算。

#### 7.3.4 新放入的物品

若手中出现一个库存中没有对应项的物品，不创建用于证明整理的正式 Track。它是否为新物品，等手离开、稳定快照与库存比较后再决定；确认放入时才分配新的 `item_id`。

### 7.4 手离开：连续无手帧生成一份稳定快照

手消失后，每帧仍继续 YOLO；此时开始填充 `no_hand_buffer`：

```text
第 101 帧：无手，加入缓冲
第 102 帧：无手，加入缓冲
...
第 N 帧：无手，且结果连续稳定
→ 生成一份 current_stable_snapshot
```

若中途又检测到手或明显移动：

```text
清空 no_hand_buffer；
回到“手在画面中”的处理；
```

稳定快照中的每个物品，是同一位置附近多个检测框投票、融合后的结果：

```cpp
SnapshotItem {
    cls_id;
    box;          // 本次稳定观察框
    score;
    vote_count;
}
```

此时 `box` 还不是库存的 `last_seen_box`；只有比较确认并提交后，它才会写入对应库存项。

### 7.5 用“当前稳定快照”直接比较 InventoryDB

比较前建立本轮临时结果：

```cpp
planned_changes = 空;
每个库存项和 SnapshotItem 都标记为 unprocessed;
```

整个比较过程中不直接修改 `InventoryDB`。

#### 第一步：匹配未移动、仍可见的库存物品

对每个当前 `SnapshotItem B`，尝试匹配库存中状态为 `VISIBLE` 的同类物品 A：

```text
优先比较：B.box 与 A.last_seen_box
必要时参考：A.anchor_box（仅 anchor_valid=true 时）
```

匹配规则仍使用统一的框匹配方法：类别相同、中心距离接近、宽高接近；同一个 A 和 B 只能一对一匹配。多个候选无法唯一确定时，先不强行匹配，留给后续步骤处理。

若匹配成功，表示 A 仍在原位置附近：

```text
B 临时关联 A.item_id；
planned_changes[A.item_id].last_seen_box = B.box；
planned_changes[A.item_id].status = VISIBLE；
```

若 `B.box` 基本包含 `A.anchor_box`，还可以按已约定的规则补强：

```text
planned_changes[A.item_id].anchor_box = B.box；
planned_changes[A.item_id].anchor_valid = true；
```

这一步不使用手部 Track，因为它们是“原位置直接匹配成功”的物品。

#### 第二步：处理整理（物品从旧位置移动到新位置）

这时会留下两类未匹配对象：

```text
库存中原本 VISIBLE、但当前快照没有在旧位置匹配到的物品 A；
当前快照中新出现、尚未匹配库存的物品 B。
```

对每个 A：

```text
查找 bound_item_id=A.item_id 的活动 Track；

如果 Track 有 release_box：
    先检查 B.box 是否与 release_box 唯一匹配。
    匹配成功，才可证明整理。
    不匹配或无法唯一匹配时，不再退回使用 path；
    此时“确认放下的位置”和当前快照互相矛盾，按普通拿出、放入或遮挡流程处理。

如果 Track 没有 release_box：
    说明手离开太快，尚未来得及确认放下；
    再检查 B.box 是否与这条 Track.path 中某个物品估计框唯一匹配。
```

若 A、B 和 Track 三者唯一对应：

```text
这是整理：库存 item_id 不变；
B 临时关联 A.item_id；
```

并写入计划：

```cpp
planned_changes[A.item_id].last_seen_box = B.box;
planned_changes[A.item_id].anchor_box = 与 B 匹配的 release_box 或 Track 路径点;
planned_changes[A.item_id].anchor_valid = true;
planned_changes[A.item_id].status = VISIBLE;
```

这里更新 `anchor_box` 是操作结束、整理已经确认后的提交计划，不是手移动过程中修改库存。

整理成立后，还要检查两个位置：

```text
旧位置 A 附近：原来被遮挡的库存物品是否在当前快照重新可见？
新位置 B 附近：原来可见的库存物品是否在当前快照消失并被 B 遮挡？
```

前者计划改为 `OCCLUDED → VISIBLE`，后者计划改为 `VISIBLE → OCCLUDED`。处理过的对象做好标记，避免后续重复处理。

#### 第三步：处理剩余“原来可见、现在没有匹配到”的物品

此时某个库存物品 A 原本 `VISIBLE`，但没有原位置匹配，也没有被 Track 证明整理。

以 A 的 `anchor_box` 为旧位置参考，检查当前快照中是否有物品 C 出现在附近：

```text
附近没有 C
→ A 大概率被拿出，计划 A → OUT。

附近有 C，且 C 能关联到原来 OCCLUDED 的库存物品
→ C 重新可见，计划该库存物品 → VISIBLE；
  A → OUT。

附近有其他 C
→ C 可能是新放入物品，也可能是另一个原有物品移动过来；
  保守地计划 A：VISIBLE → OCCLUDED。
```

这一步不使用 Track 判断“拿出”或“遮挡”；Track 只负责证明整理。

#### 第四步：处理剩余“当前新出现、仍未匹配”的物品

对还没有关联 `item_id` 的当前快照物品 B：

```text
1. 尝试匹配库存中剩余的 OCCLUDED 物品：
   成功 → B 重新可见，继承原 item_id。OCCLUDED → VISIBLE

2. 尝试匹配尚未过期的 OUT 物品：
   成功 → 恢复该 item_id。out → VISIBLE

3. 都不匹配：
   确认是新放入；
   这时才分配新的 item_id，VISIBLE，并计划新增库存项。
```

### 7.6 遮挡计数器与统一提交

所有匹配和判断完成后，才根据最终计划状态检查遮挡物品的计数器。

只要本次开门确实发生过手部操作，即：

```cpp
operation_pending == true
```

才对最终仍为 `OCCLUDED` 的库存物品检查其 `anchor_box` 附近：

```text
附近没有可见物品
→ no_occluder_count + 1；duplicate_count 清零。

附近严格只有一个可见物品
→ duplicate_count + 1；no_occluder_count 清零。

附近情况不明确或有多个候选
→ 两个计数器都清零。
```

计数器 no_occluder_count 达到阈值后，才计划该物品 `OCCLUDED → OUT`。
计数器 duplicate_count 达到阈值后，才计划该物品 `OCCLUDED → VISIBLE`。
这样不会因为用户只开门查看、系统重复生成稳定快照，就不断累加计数。

最后一次性执行：

```text
planned_changes → InventoryDB；
InventoryDB → 后台；
清空 tracks、no_hand_buffer、current_stable_snapshot；
operation_pending = false；
```

新的 InventoryDB 立刻成为下一次稳定快照比较的唯一基准。

## 8. 常见情况速览

| 用户操作 | 稳定快照与库存的结果 | 最终库存结果 |
| --- | --- | --- |
| 什么也没动 | 每个快照物品都直接匹配原 VISIBLE 库存项 | 只更新 `last_seen_box`，必要时补强 `anchor_box` |
| 拿出苹果 A | A 没有对应快照物品，旧位置附近也没有新物品 | A → `OUT` |
| 放入新苹果 B | B 无法关联任何库存项 | 分配新 `item_id`，新增 B |
| 将苹果 A 从左整理到右 | A 未在旧位置匹配；B 优先匹配绑定 A 的 `release_box`，没有时才匹配 Track 路径 | A 的 `item_id` 不变，位置更新到右侧 |
| 新物品 C 挡住苹果 A | A 未匹配；A 原位置附近出现 C | A → `OCCLUDED`；C 后续作为新物品入库或关联旧库存项 |
| 移走遮挡物，苹果 A 重新露出 | 当前 B 匹配库存中 A 的 `OCCLUDED` 记录 | A → `VISIBLE`，恢复原 `item_id` |
| 拿出苹果 A，同时放入另一颗苹果 B | A 的 Track 路径不能唯一匹配 B | A → `OUT`；B 获得新的 `item_id` |
| 同一次手部操作先移动 A、再移动 B | 有多条绑定不同 `item_id` 的 Track | 每条 Track 只在唯一匹配时证明各自整理；不唯一就保守按遮挡/拿出/放入处理 |
