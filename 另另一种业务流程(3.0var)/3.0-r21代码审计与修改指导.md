# 3.0-r21 代码审计与修改指导

> 审计日期：2026-08-07  
> 审计对象：`tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n`  
> 当前构建标识：`3.0-r21`  
> 本文件是后续修改的工程约束和回归清单，不是本次审计对生产状态机的直接修改。

## 1. 结论先行

当前 `3.0-r21` 已经实现了你基础思想中大部分最重要的约束，不应该推倒重写。它已经是“一次手部操作的事务”模型，而不是旧的快照/track-id diff 模型。

```text
原始 detection
    -> 旧 C / 暂定 D 的身份与一对一归属
    -> 已确认前景事件的 blocker 关系
    -> visibility/proof 计划
    -> OUT 证据
    -> 排序事件 + replace_all() 原子提交
```

但是，还有一个 P0 的职责边界违反，以及若干个 P1 的边界风险。它们集中在“手期临时证据”与“无手期正式遮挡生命周期”之间仍有字段混写、歧义应该阻止遮挡/OUT 证据却没有完整传递，以及多层 blocker 没有做到固定点求值。

本文中：

- **P0** 表示与最新业务文档直接冲突，下一轮状态机修改前必须收敛。
- **P1** 表示存在明确的控制流缺口或未覆盖的高风险边界，应先写回放再改。
- **P2** 表示可维护性、构建边界或文档的债务，不应和核心业务改动混在同一个大提交中。

## 2. 业务文档的正确阅读顺序

`完整操作流程说明.md` 是最基础的业务目标：它规定一次完整手部操作中 C、D、移动、放入、取出、遮挡与提交的意义。`细节1-21总结.md`、`细节22.md` 与 `超参数位置与调节说明.md` 是你根据实机问题对实现机制的继续收紧、补全，不是另一套相互替代的目标。

后续代码修改必须同时满足下面的不变式：

```text
1. inventory_ 只能在 replace_all() 的原子提交时改变。
2. detection 不等于库存身份；HAND_*/CONTACT/D 都是操作期证据，不是正式事件。
3. 未确认 D、HAND 框、预测框和低分重复框绝不能成为正式 blocker。
4. 身份 -> blocker 关系 -> visibility/proof -> OUT -> 事件/提交的顺序不得倒置。
5. block_ids 是已确认事件驱动的目标侧前景关系，不是逐帧几何相交缓存，也不等于 OCCLUDED。
6. OCCLUDED 必须有可检查的 proof；OUT 不能在遮挡解释之前抢跑。
7. 身份歧义不既能生成 disappearance proof，也不能让普通 OUT 强行结案。
```

`细节9.md` 是上述第 7 条的一个有意识的狭义例外：**仅在手已离开、同类旧物品数量持续大于可见可靠框数量的最终无手结算中**，采用“一框一物品”的可观察库存语义。这是单摄像头的产品取舍，不应被误认为普通的身份分配规则。

## 3. 已经正确实现的部分：修改时不可退化

| 能力 | 已有实现与证据 | 修改约束 |
|---|---|---|
| 事务库存 | `session.cc` 维护 `inventory_` / `working_inventory_` / `operation_start_inventory_`；`session_settlement.cc` 在最后才调用 `replace_all()` | 不要让 HAND 期提前写 `inventory_`，不要恢复快照提交 |
| 无手每帧结算 | `SessionManager::process_frame()` 对手离开后的每帧依次调用 `observe_no_hand_frame_()` 和 `settle_no_hand_frame_()` | 不做多帧框平均、多数投票或回到稳定快照模型 |
| C/D 身份防线 | `session_ownership.cc` 中旧 C 优先、一对一 owner、C-D alias/quarantine、严格重复框提示都已拆分 | 不要让遮挡结论反向决定 detection 的身份 |
| D 入库防线 | `session_hand.cc` 和 `session_no_hand.cc` 已有 suspect 连续自匹配、POST_HAND_REVEAL_D 窗口、无手确认、未绑定框不自动 IN | 不能把单帧未匹配框变成 IN |
| 遮挡逻辑分层 | `session_occlusion.cc` 已有纯几何 `CoverageEvaluation`、event-driven blocker graph、proof 校验、lifecycle decision | 继续保持几何、关系图、结算的分层，不把新 if 全部堆回 `session_settlement.cc` |
| 事件顺序 | 结算先生成 `MOVED/OUT/IN`，再生成 `OCCLUDED/REVEALED` | 保持前景自身事件在受影响目标的 visibility 事件之前 |
| 手微小移动 | 手框静止只在没有活动 HAND/CONTACT 轨迹时才跳帧 | 不要把“手腕不动”误当成“对象不可能被推动” |
| 已有回放 | `tests/session3_replay_main.cc` 调用 70 个主机场景，包含 D、同类、CONTACT、遮挡、reveal、OUT 等 | 每一次状态机修改都必须全量通过 |

## 4. 已确认的问题

### P0-1：HAND 阶段仍然直写正式遮挡字段

**证据**

- `src/session_hand.cc:477-510` 的 `confirm_rearrange_()` 直接写 `status = VISIBLE` 并 `block_ids.clear()`。
- `src/session_hand.cc:513-551` 的回滚路径同样直写 `VISIBLE` 和清空 blocker。
- `src/session_hand.cc:554-580` 的 `release_not_held_()` 直接将工作库存的 status 写为 `VISIBLE/OCCLUDED`。
- `src/session_hand.cc:1896-1941` 的 `apply_suspect_cover_evidence_()` 在手期 D 已提升且 `drop_confirmed` 后，直接将 C 写为 `OCCLUDED` 并 `block_ids.insert(d.item_id)`。

这与 `细节22.md` 第 7.2 节的明确要求直接冲突：HAND 期只能留下 provisional evidence，`block_ids` / `status` / `proof` 的唯一正式写入点应是无手 `OcclusionLifecyclePlan` 的应用。注意：这些写入当前的目标是 `working_inventory_` 而不是 `inventory_`，因此它们没有立即破坏正式库存；但它们仍将尚处于手期的临时判断写进了后续结算会读取的字段，破坏了两个证据层的边界。

**修改目标**

1. 增加 operation-local `PendingFrontEvidence`（或同等的运行时结构），建议包含：`target_id`、`candidate_front_runtime_key`、`candidate_front_item_id`、`hand_box`、`front_box`、`是否完整覆盖`、`frame_id`、`证据来源`。
2. `apply_suspect_cover_evidence_()` 只记录/更新这个证据，仍可用它来维护 `hold_evidence_count` 与 `not_hold_evidence_count`，但不得写 C 的 `status` 或 `block_ids`。
3. D 的身份、放下、无手直接观察都确认后，再仅在 `session_settlement.cc` 通过 blocker graph 将它转化为正式关系。
4. `confirm_rearrange_()` 和回滚路径仍可更新操作期的终点、`confirmed_moved_ids_`、轨迹与 runtime state，但不应借 `block_ids.clear()` 表达“移动物品已经不被其他物品遮挡”。关系在目标侧，只能由统一关系图更新。

**必须新增的回放**

- D 在手期已提升、还有放下候选证据，但首张无手帧没有確认 D：C 不得提交 `OCCLUDED`、不得留下正式 `block_ids`、也不得直接 OUT。
- D 在无手帧完成身份+放置确认且稳定覆盖 C：才允许在同一次原子提交中产生 `OCCLUDED(C)` 和对应 proof。
- 移动 A 本身在旧位置被 B 遮挡的情况：不得因 `confirm_rearrange_()` 直接清空 A 的目标侧 blocker 关系而误丢状态。

### P1-1：未被唯一绑定的身份歧义没有正确传递到遮挡决策

**证据**

`src/session_settlement.cc:702-710` 先计算了 `target_observation_conflict`，但它将 plan 字段写成：

```cpp
plan.observation_conflict = target_observed && target_observation_conflict;
```

如果 C 存在 `no_hand_candidate_ambiguous`、被更强 owner 预约，或存在未解决 C-D alias，导致某个同类框没有被绑定到 C，那么 `target_observed` 为 false，`plan.observation_conflict` 却被写成 false。后续 `decide_occlusion_lifecycle()` 可以把这张实际上有歧义的帧当成“无歧义的消失”，进而累计 `DISAPPEARANCE_SUPPORTED` 候选证据。
问题还不止于该一行：如果该对象也被纳入可见数量缺额候选，`has_unresolved_no_hand_state_()` 对 visible-count candidate 会在检查 runtime 歧义前继续处理。所以单纯把上述条件改成 `target_observation_conflict` 还不够；歧义必须让 lifecycle plan 产生“不累计遮挡、也不累计 OUT、defer commit”的结论。

**修改目标**

1. 将“有合法 direct observation”和“当前帧身份歧义”拆为两个独立事实；`observation_conflict` 不得以 `target_observed` 为前提。
2. 对 operation-start 为 `VISIBLE` 的 C，一旦存在 owner/alias 歧义，plan 应返回可区分的 pending 结论：不建立 disappearance candidate，`OUT disposition = HOLD_FOR_PENDING_OCCLUSION`，并让结算延后。
3. `update_pending_occlusion_evidence_()` 应在歧义帧自动清除已有的该 C 的 pending disappearance 证据，确保不能把“歧义帧 + 后续清晰帧”拼成两帧连续遮挡证明。
4. 只有歧义解除且后续无手帧重新满足连续性时，才重新开始 disappearance 或 OUT 计数。

**必须新增的回放**

```text
无手帧 1：已确认前景 A 近完整覆盖 C，
          但同类 B 对 C 的 owner 不唯一。
          -> 不应留下 disappearance 计数，不应 OUT，不提交。
无手帧 2：歧义消失，A 仍是同一个连续前景。
          -> 计数从 1/2 重新开始，不得直接 OCCLUDED。
无手帧 3：同样的无歧义帧。
          -> 才允许生成 DISAPPEARANCE_SUPPORTED 或其他已满足的 proof。
```

### P1-2：移动目标自己的历史 blocker 可能被无依据地保留

`src/session_occlusion.cc:130-210` 的 graph 从 operation-start 的关系出发。对 `confirmed_moved_ids` 它只执行“从所有目标的 blocker 集合中移除这个移动物品 A”：

```cpp
erase_blocker_from_all(&graph.effective_by_target, moved_id);
```

若 A 在操作开始时是目标，并有历史 `A.block_ids = {B}`，A 移到与静态 B 不再相交的新位置后，当前实现没有一条路径将 B 从 A 的集合中去掉：B 未移动、又不是新建的 confirmed front，因此旧边会留下来。
这是高置信度的源码级风险，但修改前必须先写窄回放锁死前景深度语义。二维交集本身不能证明静态 B 在 A 新位置仍然处于前景；不应以“有交集”强行保留旧关系。

**修改目标**

- 保持“移动 A 是旧位置 remove + 新位置 add”的原子语义，但对所有受影响 target（包括 A 自己）根据事件 delta 重算关系。
- 不要修成 `confirm_rearrange_()` 里粗暴的 `block_ids.clear()`；那会丢掉 A 在新位置仍可能存在的合法关系。应在纯 graph plan 中把“旧 target 关系失效”与“新位置是否用已确认事实建立新关系”分开。

**必须新增的回放**

1. 上一操作：B 正式遮挡 A，且 A 有合法 proof。
2. 本次操作：A 自身被确认移到远离 B 的位置。
3. 无手帧里不能无故保留 `A.block_ids={B}`。若 A 已正式直接被观测，需按生命周期决定 VISIBLE/REVEALED；若未被观测，进入 pending reveal/OUT，不发假 REVEALED。
4. 反向对照：A 移动后仍有已确认前景关系可解释它被遮挡，必须保留那条有因果的关系。

### P1-3：OUT 与多层 blocker 只做了有限次重算，不是稳定固定点

`src/session_settlement.cc:1186-1214` 在 visible-count 推出 pending OUT 后重算一次，在 `advance_occlusion_loss_out_evidence_()` 又改变 pending OUT 后再重算一次。这能覆盖一部分两层场景，但不能保证 `A -> B -> C` 等多层关系不依赖执行顺序。`细节22.md` 第 5.4 节要求的是对 pending OUT 集合做有限、单调的固定点求值，直至集合不再变化。

**修改目标**

1. 将“计算计划”与“应用 `pending_out_ids_`”分离；循环内使用局部的 `candidate_out_ids` 而非直接删改存成员。
2. 每一轮计算同一份 blocker graph + lifecycle plan，将被 confirmed/pending occlusion 保护的 OUT 候选从集合中移除。
3. 直到 `candidate_out_ids` 不变再一次性应用 `final_items`、事件和 `replace_all()`。如果结果仍无法由既有证据打破，必须 defer，而不是按 map/item_id 顺序强行结案。

**必须新增的回放**

- 三层 `A -> B -> C`：A 的 OUT 使 B 的 proof 失效，B 也作为 C 的 blocker。使用不同 item_id 顺序、不同 detection 顺序运行，结果必须一致。
- 同帧多个 OUT 候选，其中一个被遮挡 plan 保护：不得因另一个候选先删除而产生不同结果。

### P1-4：正式库存不保证 OCCLUDED proof 不变式

`InventoryDB::replace_all()`（`src/inventory.cc:67-81`）只保证 `VISIBLE` 记录不保留 proof，但没有验证：

```text
OCCLUDED
    => proof.kind != NONE
    => proof.witness_blocker_ids 非空
    => proof.witness_blocker_ids 是 block_ids 的子集
```

`refresh_confirmed_blockers_()` 对老数据做了保守的补证明（`src/session_settlement.cc:721-735`），但在无法补证时仍可保留 `OCCLUDED + proof == NONE`。这比直接改成 VISIBLE 安全，但它使“正式 OCCLUDED 必有 proof”变成无法被系统检查的约定。

**修改目标**

- 增加一个无副作用的 `validate_committed_inventory_invariants()`，在结算 plan 应用后、`replace_all()` 前调用。
- `replace_all()` 作为防御性边界也应有一次校验。这里不建议无声自动修改所有异常记录；应将非法新记录拒绝提交/延后提交并打出明确 trace。
- 对升级前的 `OCCLUDED + NONE` 记录要显式建模或显式记录 `legacy-unverified-occlusion`；先用历史几何尝试补齐 proof，无法补齐时保守地保留但不得假装是有效正式 proof。不要简单把它改回 VISIBLE。

**必须新增的测试**

- `VISIBLE + 任意 proof` 提交后 proof 必为空。
- `OCCLUDED + NONE`、空 witness、witness 不是 `block_ids` 子集的三种非法输入，必须有明确的拒绝/延后/旧数据诊断行为。
- 合法的 `STRICT_UNION`、`EDGE_RESIDUAL_UNION`、`DISAPPEARANCE_SUPPORTED` proof 均可通过，并在 witness 移动/OUT 后触发正确的 reveal 或 pending 路径。

## 5. 尚未被现有回放完整证实的风险

### P1-R1：`DISAPPEARANCE_SUPPORTED` 的连续 witness 集与最终 proof witness 集可能不一致

当前 `refresh_confirmed_blockers_()` 用 `current_front_witnesses` 保存 disappearance 连续性，但真正参与几何的集合是 `effective_with_geometry`。如果历史 blocker 也参与了覆盖，候选的“同一 witness”判定与最后 proof 记录的 witness 集合就有可能不一致。

修改前应写一个“新前景 A + 历史 blocker B 联合近完整覆盖 C”的回放，明确决定连续性需要追踪什么：

- 若 `DISAPPEARANCE_SUPPORTED` 的语义是“本轮已确认前景 A 持续解释 C 消失”，那应将 A 作为必须连续的核心 witness，B 是辅助当前几何。
- 若 proof 需声明所有实际覆盖者，则 pending 容器也必须追踪完整的 witness 集合与每个框的连续性。

不应在未定义这个语义前直接改队列结构。

### P2-R2：同类绝对平局的 item_id 决胜是已接受的局部业务取舍，但文档应更明确

`tests/session3_replay_ownership.cc` 的 `test_mature_same_class_tracks_keep_shared_b_ambiguous_until_no_hand_count_settlement()` 断言完全等价时保留 `item#1`、`OUT(item#2)`。代码也在 `prepare_visible_count_settlement_()` 里以 item_id/detection index 作为完全同价的稳定决胜。
这不应被当成一般 C -> B 的身份争抢。`细节9.md` 已经明确接受了“稳定无手画面只剩一个同类框时，库存按一个可见实例结算”的取舍。建议在 `细节1-21总结.md` 的“不得按 item_id 强行选择”之后追加一句明确注释：“细节9的最终可见数量结算是狭义例外”。代码修改不应无意中删掉这个有意识的单摄像头取舍。

## 6. P2 可维护性与构建债务

### 6.1 追踪日志默认开启与参数说明不一致

`include/fridge_config.h:266` 将 `FLOW3_DEBUG_TRACE_LOG` 设为 `true`，但 `超参数位置与调节说明.md` 将默认值记为 `false`。全量主机回放会产生大量 trace，在板端默认开启会影响性能、日志存储和定位可读性。

建议：发布默认改为 `false`，保留编译期或运行时可控的诊断开关；同时更新参数说明。这不应与 P0/P1 状态机修改混合。

### 6.2 构建边界仍将旧 snapshot 代码编入正式可执行文件

`tools/luckfox_pico_rkmpi_example/CMakeLists.txt:59-72` 使用 `file(GLOB "${SRC_DIR}/*.cc")`，只额外排除了 `tracker.cc`。当前 `main.cc` 和 `SessionManager` 不使用 `SnapshotBuffer`，但 `snapshot.cc` 仍会被编入类似的业务可执行文件。

建议分两步处理：

1. 先为主机回放加一个显式构建目标或最小脚本，使 70 个场景可被 CI/CTest 稳定运行。
2. 再将正式 3.0 业务源文件显式列出，或拆成 `fridge_session_core` 静态库。旧 `snapshot`/`tracker` 代码可作为独立兼容目标保留，但不应通过 GLOB 悟合到主业务编译单元。

### 6.3 `ARCHITECTURE.md` 已经与真实运行路径不符

`ARCHITECTURE.md` 仍描述 `snapshot + ByteTrack + 稳定切片 + track_id diff`，甚至提到已不存在的 `evict_long_occluded()`。它和 `src/main.cc` 中实际的 `SessionManager::process_frame(food_dets, hand_boxes, ...)` 路径相反，会误导下一位维护者。

建议在一个独立文档提交中更新为：YOLO 业务输入 -> 手/无手 `SessionManager` -> C/D 归属 -> 遮挡 lifecycle -> 原子提交 -> 事件/上传。旧架构若有保留价值，应明确标记为“历史骨架，不参与当前业务路径”。

## 7. 推荐的实施顺序

### 第 0 步：先冻结基线

1. 不改任何阈值。不调大 `FLOW3_CONFIRMED_OCCLUSION_EDGE_RESIDUAL_PX`，不改 YOLO/NMS，不降低 D/MOVED/OUT 连续帧数。
2. 先增加上文 P0-1、P1-1、P1-2、P1-3、P1-4 的窄回放。如果现有代码应该失败，要明确写出“旧行为”与“新期望”，而不要先改代码再写测试。
3. 将这些测试按职责放置：HAND 证据放 `session3_replay_hand_contact.cc`，身份歧义放 `session3_replay_ownership.cc`，遮挡/OUT 生命周期放 `session3_replay_no_hand.cc`，纯关系图可新建 `session3_replay_occlusion.cc`。

### 第 1 步：收紧手期证据边界

1. 在 `OperationTrack` 附近或 `SessionManager` 内设置 `PendingFrontEvidence` 容器；它与 `pending_in_ids_`、`pending_out_ids_` 一样只存在于本次操作。
2. 让 `session_hand.cc` 只写 runtime/轨迹/证据字段，移除对 `InventoryItem.status`、`InventoryItem.block_ids` 的直写。
3. 每次手重新进入、D 置信度失效、目标自身有独立移动/出库证据时，清除相关临时证据。
4. 保留 `placed_box`、`confirmed_moved_ids_`、D 的连续自匹配、C-D alias 已有语义，不要为了清理字段而弱化身份防线。

### 第 2 步：让无手 plan 成为唯一的正式决策来源

1. `observe_no_hand_frame_()` 只产出当帧身份事实：owner、无手自匹配、alias 状态、已确认 D/MOVED 资格。
2. 用纯 `OcclusionLifecyclePlan` 同时计算：historical/effective blocker、before/after coverage、proof、visibility、OUT disposition。
3. 将 owner 歧义作为独立输入传给 plan，不以“当帧是否绑定到 C”掩盖它。
4. 在 plan 的 OUT disposition 已决定之后，才调用 visible-count、direct-missing、occlusion-loss 的证据推进逻辑。
5. 最后一次性写 `final_items.status`、`final_items.block_ids`、`final_items.occlusion_proof`、`pending_out_ids_`。不要重新引入“先把 observed item 写成 VISIBLE，后面再修正”的反向流程。

### 第 3 步：将 blocker 图与 OUT 实现为稳定计划

1. 从 operation-start 的正式关系出发，仅用已确认 `IN/MOVED/OUT` delta 增删边。
2. 确认 `MOVED(A)` 要对旧位置的所有受影响 target 移除 A，再对新位置的受影响 target 增加 A；包括处理 A 作为 target 时旧 blocker 是否仍有效。
3. 用 `candidate_out_ids` 的单调固定点循环计算，到稳定后再应用。
4. 计划不稳定或身份歧义时延后提交；不能以 timeout、遍历顺序或 ID 来收敛核心身份解析。

### 第 4 步：最后再做数据库边界和非业务清理

1. 加入 proof 不变式验证、旧数据诊断和对应回放。
2. 再更新 `ARCHITECTURE.md`、CMake 的显式源文件边界、主机测试目标，以及 trace 默认值与参数说明。
3. 业务修正、构建改造和文档清理尽量拆为不同提交，便于出现回归时定位。

## 8. 回归测试清单

除上文的窄回放外，后续任何涉及遮挡的修改都要覆盖下表。

| 场景 | 必须断言 |
|---|---|
| 确认移入的 A 遮挡 C | `MOVED(A)` 后才有 `OCCLUDED(C)`，C 不得 OUT，proof witness 正确 |
| blocker 移出后 C 被合法直接观察 | `MOVED/OUT(A)` 在 `REVEALED(C)` 之前，C 不得异常继续 OCCLUDED |
| blocker 移出但 C 仍未被合法观察 | 不发假 REVEALED，OUT 从 proof 失效后重新计数 |
| 多 blocker 联合遮挡 | 移走其中一个仍完整覆盖时，C 继续 OCCLUDED，witness 更新正确 |
| 近完整外边残余 | 只有已确认 front + 连续可比无手帧 + 无歧义 + 无独立 exit 证据才能产生 `DISAPPEARANCE_SUPPORTED` |
| 手重新进入 | 清除 pending disappearance 、visible-count 缺额和静态无手证据，不得跨段拼接 |
| 未确认 D / alias D | 不能成为正式 blocker，不能发 IN/OCCLUDED，也不能绕过 C 的未决问题 |
| 同类两独立框 | 两个 C 均保留；移动的对象必须走自己的 MOVED 链 |
| 同类持续只剩一框 | 仅在细节9的无手、数量不足、连续帧前提下执行一框一物品结算 |
| 事件乱序输入 | 交换 item_id 、map 插入顺序和 detection 数组顺序后，结果不变 |

当前审计实测结果：

- 上述普通主机回放编译并运行成功。
- ASAN + UBSAN 回放退出码为 `0`，未发现 AddressSanitizer 或 UndefinedBehaviorSanitizer 报告。

每次修改之后还应执行：

```bash
git diff --check
git status --short
```

最后还需要板端实机验证：橙子移入遮住苹果，以及 blocker 移开后被遮物品重新露出。主机回放只能验证状态机语义和内存安全，不能替代模型、透视、光照和坐标变换的实机验证。

## 10. 修改时的禁止项

```text
不要为了通过一个案例而调大 edge-residual 像素容差。
不要用调高/调低 YOLO、NMS、owner、D、MOVED 或 OUT 全局阈值代替生命周期修复。
不要删除 detection、改变 detection 数组顺序或以 OSD 逻辑作为身份判定。
不要以 block_ids 非空直接代替 OCCLUDED，也不要把它当作永久 OUT 豁免。
不要让未确认 D、HAND 框、预测框或低分重复框产生正式 blocker/proof。
不要删掉现有 C-D alias、quarantine、一对一 owner、无手连续确认和同类 visible-count 结算防线。
不要以 map/item_id/detection 顺序作为普通身份歧义的决策器；细节9的窄例外除外。
```

## 11. 完成标准

后续一轮修改只有同时满足以下条件才算完成：

1. HAND 期不再直写正式 `status/block_ids/proof`；临时信息可追溯但不可提交。
2. 身份歧义会中断并清除 disappearance/OUT 证据，不会被后续清晰帧拼接。
3. blocker 关系图对移入、移出、多层 OUT 不依赖遍历顺序，并通过固定点测试。
4. 每个正式 `OCCLUDED` 都有可检查的 proof，老数据例外有显式诊断和迁移策略。
5. 新增窄回放、既有 70 个主机回放、`-Wall -Wextra -Werror`、ASAN/UBSan、`git diff --check` 全部通过。
6. 板端实机 trace 能显示 identity、front relation、coverage/proof、OUT disposition 和事件顺序，且对应两个实机例得到正确结果。
