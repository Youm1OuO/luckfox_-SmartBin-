# 旧 C 失配时的假 D 隔离、C-D 别名与无手重归属

> 本文建立在细节 8、细节 9、细节 10 之上。
>
> 本文只处理这样一类局部问题：一次操作中，原本已经在库存里的旧物品 C
> 正在被移动，但有手阶段没有把它的新检测框稳定认回 C；程序随后把同一个
> 真实物品错误建立为疑似新物品 D，导致 C 和 D 在无手帧互相阻塞。
>
> 本文不废弃细节 10。细节 10 的“静止旧 B 是排除证据，排除后继续寻找 A”
> 规则仍然正确且必须保留。新问题发生在更早的“有手阶段错误创建 D”和之后
> 的“未确认 D 被当作旧库存”两个环节。

> **实时性边界：**本文不是把识别推迟到手离开后。手存在的每一帧都必须实时
> 跟踪旧 C、疑似 D、手接触和遮挡/移动可能性；延后的只有会改变正式库存、排他
> 所有权或不可撤销事件的确认。该区分是本次实现的硬性要求。

## 0. 实时业务契约

### 0.1 “实时判断”在本项目中的准确含义

本版本先保证“一只手、一次操作”可靠；但数据结构不能把关系硬编码为“只有一件
旧物品和一个 D”，以免后续扩展一只手多个操作时需要推倒重来。

实时不等于在证据不足时立刻宣布最终事实。正确的逐帧行为是：

```text
每一张有手帧：
    立即更新旧 C 的实时状态，例如 HAND_CONTACT、POSSIBLE_MOVED、
    POSSIBLE_OCCLUDED；
    立即创建或更新新框的 PROVISIONAL_D 运行时记录；
    若 C 与 D 同类且证据冲突，立即建立 C_D_ALIAS，并继续记录双方轨迹。

手离开后的直接帧：
    不是“才开始识别”；
    而是用已有实时轨迹、当前直接画面和连续帧证据，把暂定状态升级为
    MOVED / IN / OUT / OCCLUDED_CONFIRMED，或保持未决。
```

当物品被手完全遮住时，单摄像头本来无法从该帧直接知道它是仍在手中、已移动、
已被取出还是只是被遮住。此时实时输出 `POSSIBLE_MOVED` / `POSSIBLE_OCCLUDED`
是正确的实时结论，不是“没有处理”。程序不得伪造确定的 `MOVED` 或 `OUT`；但也
不得停止跟踪或等到无手帧才创建轨迹。

所有对外实时状态都必须带有确认级别：

```text
provisional=1  可被后续帧撤销或改判的实时观察结论
provisional=0  已满足既有连续帧规则、可以提交库存和正式事件的结论
```

### 0.2 两层状态的职责

```text
实时运行层（OperationTrack / runtime key）
    每帧更新。保存位置、接触、手相贴、路径、候选、C_D_ALIAS 和实时状态。
    它可以立刻显示“可能移动”“可能遮挡”“疑似新物品”。

库存身份与结算层（operation_start_inventory_ / working_inventory_ / 事件）
    保存操作开始旧库存和必要的 staged 记录；每条记录都必须显式带有身份类型。
    只有 START_OLD_C 和已确认的 CONFIRMED_D 才能拥有排他所有权、计入正式库存
    或产生最终 IN/OUT/MOVED；PENDING_D 只是可撤销的 staged / 运行时记录。
```

同一物品在实时层有记录，不代表它已经拥有正式库存层的排他所有权。这个区别是
本次修复的核心：要保留实时能力，同时阻止假 D 反过来污染旧 C。

## 1. 已确认的结论

当前问题已经不是猜测。两次实机日志都给出了完整链路：

```text
旧库存 C 被手移动
    -> C 的 hand/reference 路径未命中真实新框，或旧候选被 YOLO 框跳动带偏
    -> 一个同 cls_id、贴手或接近手的未认领框进入 HAND_VISIBLE_D
    -> D 在有手阶段连续两帧后被 promote_suspect_() 写入 working_inventory_
    -> 手离开后，C 再看见该框时，通用“属于其他库存”判断把这个未提交 D
       也当成 another old item
    -> C 被标记 no_hand_candidate_ambiguous，D 又因 C 未解决而不能 IN
    -> 本轮操作永久 defer-commit
```

这里的 D 在真实业务上不存在，它只是移动 C 的重复身份。下文称它为：

```text
假 D / C-D 别名：同一个真实物品同时被 C 和未确认 D 两条运行时记录解释。
```

这不是“把真实新 D 强行认成旧 C”的许可。真正的 D 必须继续存在并能够
正常 IN；系统只是不能在证据仍不足时先复制出库存身份，再让这个复制身份反过来
阻塞原 C。

## 1. 本次实机日志证明了什么

### 1.1 测试错误 1：苹果 #2 与错误苹果 D #7

操作开始时，`item#2` 是已有苹果 C。用户只移动了它，没有放入新苹果。

日志先出现：

```text
frame 197
    预登记疑似新物品 D suspect#-1 cls=0

frame 198
    suspect#-1 已提升为工作库存 item#7
```

因此 `item#7` 必定是假 D。

随后无手帧出现：

```text
item=2 ... other-owner=5
action=exclude-independent-static-neighbor-and-fallback
```

这正是细节 10 的修复分支：`item#5` 是当前拥有独立严格原位框的静止苹果，
所以它被正确排除，不能再永久阻塞 `item#2`。

但紧接着又出现：

```text
result=real-path-ambiguity
reason=ambiguous-no-hand-path-candidate
block-commit pending-d=7 cls=0 unresolved-old=2
```

含义不是细节 10 失败，而是静止 `item#5` 已被排除后，错误建立的 `item#7`
仍让 `item#2` 没有一个可独立完成结算的身份。

### 1.2 测试错误 2：旧橙子 #5 与错误橙子 D #6

操作开始时只有一个旧橙子 `item#5`。用户只整理它，没有放入新橙子。

日志出现：

```text
frame 170
    预登记疑似新物品 D suspect#-1 cls=2

frame 171
    suspect#-1 已提升为工作库存 item#6
```

因此 `item#6` 也是假 D。

无手帧中旧橙子 `item#5` 反复看到：

```text
reject=strictly-belongs-to-other-old-item
result=real-ambiguity
```

开始库存根本没有第二个橙子，所以日志里所谓的 `other-old-item` 不是真正
的旧库存；它就是本轮刚被错误提升的 `item#6`。这也说明当前日志名字不够准确，
后续必须区分“操作开始前旧 C”和“本轮未提交 D”。

### 1.3 与“同类相贴 / 不同类相邻”的关系

用户观察到即使移动到不同类别物品旁边，也可能失败。这个观察是对的：

```text
失败不依赖目标邻居的类别；
真正冲突的双方始终是：移动前的旧 C 与被误建的同 cls_id D。
```

例如移动苹果到苏打罐旁，业务层仍可能产生“旧苹果 C + 假苹果 D”；
移动橙子到不同类别物品旁，仍可能产生“旧橙子 C + 假橙子 D”。

相邻同类框、手框跳动、YOLO 在完整框/局部框之间切换，都会提高 C 丢失
当前框的概率，但它们不是这次永久 pending 的唯一前提。

## 2. 当前实现中的具体漏洞

以下三点要一起修，不能只改其中一个。

### 2.1 C 的单一路径可能被手框位移带偏

`estimated_box(track)` 主要由手框累计位移推算。实机中手框常包含手臂，
它的中心移动距离、方向和被拿物品不完全一致；手指动作、检测框局部化、手框
尺寸变化也会造成明显差异。

因此，真实 C 的新框可能不落在当前 `estimated_box`、`last_seen_box` 或单个
`reappear_candidate_box` 的范围内。当前 C 没有认到该框时，D 扫描会把它当作
全新的物品。

这不是应通过增大 `FLOW3_TRACK_*` 或
`FLOW3_REAPPEAR_CANDIDATE_*` 解决的问题。全局放宽会把相邻真实同类物品、
真实新 D 也吞回旧 C，破坏已有的入库和整理能力。

### 2.2 D 扫描错误地把“C 已认到别的候选”当作“C 已解决”

`scan_or_update_suspects_()` 当前对未认领检测框扫描 D。它为了允许真正的相邻
同类 D，存在如下风险：

```text
C 已经临时认领一个检测框
    （这个框可能只是旧位置局部框、静止邻居或过期 reappear candidate）

另一同类检测框出现
    -> scan 认为 C 已有 owner，跳过“未解决同类旧 C”的防线
    -> 将第二个框建立为 D
```

这里“本帧有 owner”只代表当前暂存了一个候选，绝不等于 C 已经完成
`MOVED / STATIC / OUT / OCCLUDED` 结算。尤其当 owner 本身还只是
`reappear_candidate` 时，不能让它解除 D 防线。

### 2.3 未提交 D 被通用函数误当作“其他旧库存”

`promote_suspect_()` 在有手阶段达到两帧条件后，会立刻把 D 写入
`working_inventory_`，同时用 `pending_in_ids_` 标记它尚未正式 IN。

但是 `detection_strictly_matches_other_item()` 只遍历 `working_inventory_`，
没有区分：

```text
操作开始前就存在的旧 C
本轮刚写入、尚未提交的 pending D
已经通过无手帧确认的 D
```

于是 pending D 的框会被当成“其他旧物品”的强排除证据，最终把原 C 设为
真实歧义。这是错误的语义转换。

只把 `detection_strictly_matches_other_item()` 改成忽略 D 也不够：那会让 C
在没有证据时直接抢走一个可能是真实新 D 的框。因此必须同时引入
`C-D 别名 / 隔离` 状态与无手连续确认。

## 3. 本次修改的目标与不可退化约束

本次修复的目标是：

```text
旧 C 暂时失去自己的可靠框时，潜在同类 D 必须继续被实时记录、追踪和输出；
但在证据不足时，D 不能获得“可排除旧 C 的正式库存所有者”地位。

无手阶段利用已有的连续直接观测、一框一物品和同类可见数量规则，
把已经持续维护的 C、D 实时状态在 C、D 或真正不可分辨三种结论之间保守收尾。
```

必须遵守：

1. 不修改细节 10：独立静止旧 B 仍是 A 的排除证据，排除后仍继续 fallback。
2. 不修改细节 9：同类可靠可见框持续不足时，仍按连续直接无手帧确认 OUT。
3. 不降低 `MOVED`、`IN`、`OUT` 的连续帧门槛；首张无手帧不直接提交。
4. 不通过放宽几何阈值把远处同类物品强行归属。
5. 真正独立的新 D 必须仍能 IN；本补丁最多让“与未解决同类 C 冲突的 D”的
   **正式所有权和正式 IN** 延后确认，绝不能延后它的实时创建、轨迹更新、
   手相贴判断或暂定业务状态输出。
6. 已确认遮挡仍然保持 `OCCLUDED_CONFIRMED`，不能因为 C-D 冲突改判 OUT。
7. 不同类别的正常 IN / OUT / MOVED 流程必须维持既有时序。
8. 单摄像头下若同 cls_id 的 C 与 D 最终只有一个框、且没有独立证据，遵循
   用户确定的规则：一框一个物品；不能凭类别相同凭空生成 `OUT + IN` 两个事件。
9. 已有入库、出库、整理、CONTACT_*、同类静止邻居、D 防线回放都必须继续通过。
10. 有手阶段的每张输入帧都必须更新实时状态。不得把 `POSSIBLE_MOVED`、
    `POSSIBLE_OCCLUDED`、`PROVISIONAL_D` 或 `C_D_ALIAS` 的创建推迟到无手阶段。
11. 对外状态、调试日志和任何未来 UI/API 必须区分 `provisional=1` 与正式结论；
    暂定状态可以更新、撤销或合并，正式事件才不可撤销。
12. C-D 关系必须按 `operation_id + old C + provisional D` 保存，而不是一个全局
    bool。当前虽然只验收一只手一次操作，但这样不会阻断后续多个物品的匹配仲裁。

## 4. 新的概念：实时运行记录、正式库存身份与 C-D 别名

当前错误的根源之一，是把“存在一条实时轨迹”和“已经拥有库存所有权”混成一件事。
后续代码必须显式拆开这两个维度，不能只看对象是否位于 `working_inventory_`。

### 4.1 实时运行层：所有候选都必须立即可追踪

`OperationTrack` 或等价会话级运行时结构是实时层的唯一事实来源。它必须让以下
语义可在有手帧逐帧更新；具体枚举名字可以调整，但不能合并或省略其含义：

```text
START_OLD_C 的实时状态：
    HAND_CONTACT / POSSIBLE_MOVED / POSSIBLE_OCCLUDED /
    已回到原位的 provisional static 等。

PROVISIONAL_D 的实时状态：
    HAND_VISIBLE_D / POST_HAND_REVEAL_D / PLACED 等已有观察状态，
    并保留 runtime key、last_seen_box、手相贴、路径和连续帧信息。

C_D_ALIAS 的实时状态：
    说明 C 与同类 PROVISIONAL_D 当前可能解释同一真实物品；
    它不是删除 D，也不是把 D 强行认给 C，而是要求后续继续观察并仲裁。
```

每次状态变更应当可以实时输出给日志和上层业务，并标记 `provisional=1`。即使
冲突 D 最终被证明是假 D，也必须先完整保留它在有手期间的轨迹，这既满足实时业务，
也为无手仲裁提供证据。

### 4.2 正式库存层：只有明确类型的身份才能参与排他所有权

在正式库存层中，至少区分以下身份，而不是把 `working_inventory_` 里的所有记录
统称为“旧物品”：

```text
START_OLD_C
    operation_start_inventory_ 中已有的物品。
    它是“操作开始前旧库存身份”的唯一来源；只有它能参与细节 10 的静止旧 B
    所有权证明，也只有它能默认作为旧 C 排除证据。

PENDING_D
    本轮手操作中出现、尚未通过独立无手确认的新物品候选。
    它必须有实时运行记录。无冲突的 PENDING_D 可保持当前已经验证过的 staged
    入库链路；但它始终不能被查询函数误报为 START_OLD_C。

QUARANTINED_PENDING_D
    与未结算同类 START_OLD_C 存在 C_D_ALIAS 的 PENDING_D。
    它仍是实时可见、可追踪、可显示的 provisional 物品，但有手阶段不得写入
    working_inventory_ 取得临时 item_id，也不得成为任何 C 的 other-owner 证据。
    如上层需要显示“预计库存”，可从运行时层投影一条 provisional 项；该投影
    不能参与库存计数、排他匹配或正式事件。

CONFIRMED_D
    已满足 D 的直接无手连续确认，且不存在未解决同类旧 C 冲突，
    可以正式形成 IN 的物品。
```

再引入一个运行时关系：

```text
C_D_ALIAS
    某个 PROVISIONAL_D / QUARANTINED_PENDING_D 与一个未结算旧 C 同 cls_id，
    且在同一次手操作中
    争夺同一检测框、相邻候选框或同一段手接触路径。

    它的含义不是“D 就是 C”，而是“当前证据不足，D 不能作为 C 的
    其他库存排除证据，C 也不能单帧抢走 D”。双方仍须实时更新。
```

推荐在 `OperationTrack` 中增加可追溯字段，名字可在实现时微调，但语义必须保留：

```text
bool pending_d_quarantined_by_old_c
std::set<int> conflicting_old_item_ids       // D 记录冲突的旧 C item_id
std::set<int> conflicting_suspect_keys       // C 记录冲突的 D runtime key
int alias_no_hand_match_count                // 仅记录同一 C-D 关系的直接无手连续性
LiveObservationState live_state              // 或等价字段，逐帧实时状态
bool live_state_provisional                  // 对外输出时必须可区分暂定/正式
int live_state_last_changed_frame
std::string live_state_reason                // 或等价可追溯原因
```

不应只存一个 bool 而没有关系对象。一个操作里可能有多个同类旧 C 或多个
疑似 D；日志和一对一仲裁必须能知道到底是哪两条记录发生冲突。运行时 key 与
`working_inventory_` 的 staged item id 也必须可区分：前者立即存在以支撑实时业务；
无冲突 D 可以按现有流程获得 staged item id，但必须保持 `PENDING_D` 身份。只有
`START_OLD_C` 与 `CONFIRMED_D` 的 item id 才具有正式排他所有权语义；冲突 D 在
有手阶段只能使用 runtime key。

## 5. 有手阶段：实时跟踪，同时隔离不可靠的正式所有权

### 5.0 每帧实时处理契约

有手不等于暂停库存识别。对每张有手帧，代码必须先更新实时运行层，再决定是否
允许它影响正式库存层：

```text
旧 C：
    更新当前可见框、手接触、覆盖率、预计路径和实时状态。
    即使尚不能提交 MOVED，也必须能实时报告 POSSIBLE_MOVED 或
    POSSIBLE_OCCLUDED，并保留其理由和帧号。

新框 D：
    首次出现即创建或更新 PROVISIONAL_D runtime key；后续每帧更新其框、
    手相贴、连续性、路径及实时状态。

C-D 冲突：
    首帧发现即建立 C_D_ALIAS，并向实时层输出“同类身份未决”的暂定状态。
    不得因为进入 quarantine 就冻结 C 或 D 的位置和状态更新。
```

这里的“实时输出”可以是现有日志、回调或未来 UI/API 的状态投影；本次代码至少
必须让内部状态和 `FLOW3_DEBUG_TRACE_LOG` 逐帧可见。它与最终 `[EVENT]` 分开：
前者允许修正，后者仍遵守既有连续帧确认。

### 5.1 识别条件

在 `scan_or_update_suspects_()` 处理一个未认领、贴手或 `C_POSITION_REPLACEMENT`
候选框时，检查同 cls_id 的操作开始旧 C：

```text
同 cls_id 的 START_OLD_C 存在
且该 C 本轮仍未终态结算
且 C 当前为 HAND_* / CONTACT_* / reappearance_pending / 仍需无手结算
    -> 该检测框必须实时创建/更新为 PROVISIONAL_D，
       但不能立刻当作拥有独立正式库存所有权的 D。
```

判断“C 未结算”必须看 `operation_start_inventory_`、`resolution`、
`needs_no_hand_settlement` 和活动轨迹，不得只看：

```text
effective_known_item_owner 是否已有 C
本帧 C 是否已经 claim 了另一个框
```

因为这正是本次漏洞：C 已 claim 的可能只是过期候选，不能代表 C 已解决。

### 5.2 隔离动作

当满足上述条件时：

```text
1. 立即创建或更新 D 的 PROVISIONAL_D runtime key，保留 suspect 轨迹、
   手相贴记录、last_seen_box、连续性和逐帧实时状态。
2. 立即把 D 与该旧 C 标为 C_D_ALIAS / QUARANTINED_PENDING_D，并让 C 和 D
   的对外实时状态均带 provisional=1。
3. 不把该 D 当作 START_OLD_C 的“其他库存”参与严格排除；它也不能作为
   细节 10 的静止旧 B 证据。
4. 不在有手阶段调用 promote_suspect_() 把这个**冲突 D**写入
   working_inventory_ 并赋予 staged item id。若上层需要展示预计库存，
   只能使用明确标记 provisional 的运行时投影。
5. 不把该框直接 claim 给 C，也不把 C 单帧确认 MOVED；但 C 仍须实时更新为
   POSSIBLE_MOVED / POSSIBLE_OCCLUDED 或当前更贴切的暂定状态。
6. 不创建最终 OUT、IN、MOVED 事件；应继续输出可撤销的实时状态，等待无手
   直接帧完成确认。
```

这样真实 D 没有被删除、更没有被延后识别：它从首次出现起就有可追踪的运行时
身份和实时状态。被延后的只是“把它写成正式库存所有者”的动作，因此假 D 不会
反过来污染 `working_inventory_`，真实 D 也仍保有后来独立 IN 的全部证据。

### 5.3 为什么不能直接吞回 C

即使只有一个同类旧 C，也不能只要看见同类贴手框就把它写成 C 的新位置。
真实业务可能是：

```text
旧苹果 C 正在被手遮住
同时手放入一个新苹果 D
```

所以有手阶段必须实时保留和更新 `C_D_ALIAS`，不能凭单帧决定最终 C MOVED 或
最终 D IN。最终库存结论交给无手连续帧和同类可见数量；实时业务结论则从有手帧
开始持续存在，且可以被后续证据修正。

## 6. 无手阶段：确认已有实时判断，再处理旧 C 和隔离 D

无手收尾不是重新开始识别，而是把第 5 节持续维护的轨迹和暂定状态转为正式结论。
无手收尾顺序建议如下。这个顺序是本次修改的核心。

### 6.1 保留已有的旧 C 静态归属

先继续执行细节 10 的规则：

```text
操作开始旧 B 与当前检测框双方唯一严格原位
    -> B 的独立静态所有权成立
    -> 对移动 A 是排除证据
    -> A 清除过期 reappear candidate，并继续 fallback
```

`PENDING_D` 不得伪装成这里的静止旧 B。只有 `START_OLD_C` 才能作为
`other-owner-evidence=direct-original-mutually-unique` 的来源。

### 6.2 C 遇到 pending D 时，不再叫“真实旧 C 歧义”

为当前 `detection_strictly_matches_other_item()` 拆分语义，至少能够回答：

```text
STRICT_OWNER_START_OLD_C
STRICT_OWNER_PENDING_D
STRICT_OWNER_QUARANTINED_PENDING_D
STRICT_OWNER_CONFIRMED_D
STRICT_OWNER_NONE
```

对旧 C 的无手匹配：

```text
命中 START_OLD_C：
    按细节 10 / 细节 8 原有规则处理。

命中 QUARANTINED_PENDING_D，且 D 与 C 是 C_D_ALIAS：
    不设置 no_hand_candidate_ambiguous；
    不把它直接认作 C；
    进入“C-D 无手仲裁”，保留两条实时轨迹并继续累积直接无手证据。

命中 PENDING_D，但不存在 C_D_ALIAS：
    它不是 old C 的排除证据；保留既有无冲突 D 的独立确认链路，
    不因它位于 working_inventory_ 就把 C 直接判为真实歧义。

命中 CONFIRMED_D：
    这是已有独立库存，可作为正常排除/遮挡/冲突证据。
```

因此日志不得再把 pending D 打印为 `other-old-item`。

### 6.3 C-D 无手仲裁

对同 cls_id 的一个旧 C 与一个 quarantined D，使用已有直接无手帧和数量规则：

```text
情况 A：当前同类可靠框数等于本轮开始时的旧 C 数量
        且其他旧 C 已各自拥有独立框
        且剩余框连续出现在 C-D alias 的位置

    -> 这一个框按“一框一个旧物品”优先归给 C；
    -> 第一张无手帧仅建立/更新 C 的候选；
    -> 第二张直接无手帧连续后，C -> MOVED；
    -> 该 D 作为 C 的重复身份丢弃，不产生 IN。

情况 B：当前同类可靠框数比本轮开始旧 C 数量多
        且 C 与 D 能在两张直接无手帧中各自占用不同 detection index

    -> C 依旧走自己的 MOVED / STATIC / OUT 证据链；
    -> D 走自己的两张直接无手帧 IN 确认；
    -> 最终允许“C 的事件 + D 的 IN”。

情况 C：当前同类可靠框数少于旧 C 数量

    -> 不把 quarantined D 计入新增数量；
    -> 保持细节 9 的一框一物品和连续可见数量不足 OUT 结算。

情况 D：仍只有一个框，且 C 与 D 均无独立连续证据

    -> 保持 unresolved，不强认 MOVED、OUT 或 IN；
    -> 后续帧继续观察。
```

对于单摄像头下“取出一个旧苹果，同时放入一个新苹果，最终同类框数不变”这类
本身无法区分的情况，不能伪造两条事件。若存在本次手操作的 C-D alias，而没有
两个独立框，则遵循用户已确定的一框一物品规则，优先保留旧 C 的身份链；没有
可靠 C 路径时保持未决或按细节 9 的可见数量规则收尾，而不是自动 `OUT + IN`。

### 6.4 D 的提升时机

推荐规则：

```text
无冲突的 D：
    保持当前实时 D 链路、已有 staged 入库链路和确认时序，避免破坏已验证的
    普通入库。即使它已进入 working_inventory_ 的 staged 状态，也必须带有
    PENDING_D 身份，不能被任何所有权查询当作 START_OLD_C。

与未结算同类旧 C 冲突的 D：
    有手阶段持续保留并更新 PROVISIONAL_D / quarantine 的实时记录；
    它可以实时显示“疑似新增、同类身份未决”，但不能获得正式库存所有者权限；
    只有无手阶段证明它与 C 是两个独立连续框，或 C 已经独立结算后，
    才允许 promote_suspect_()、写入 working_inventory_ 和 pending_in_ids_。
```

这不是降低 D 的确认要求，也不是让程序等手离开才看见 D；它只是把冲突 D 的
“正式工作库存所有者权限”延后，避免假 D 成为 C 的排除证据。

```text
action=create / update / wait-second-no-hand / assign-to-old-c /
       confirm-independent-d / discard-duplicate / keep-unresolved
```

无手阶段还必须补充数量与连续性信息：

```text
[C-D-ALIAS]
old-item=<C id>
suspect=<D key>
detection=<index>
relation=shared-detection / distinct-detections
old-count=<operation-start old count>
visible-count=<current raw same-class boxes>
action=wait-second-no-hand / assign-to-old-c / confirm-independent-d / keep-unresolved
```

### 9.4 所有权日志

所有目前写作 `strictly-belongs-to-other-old-item` 的位置，必须改为或补充：

```text
owner-kind=start-old-c / pending-d / quarantined-pending-d / confirmed-d
owner-id=<item_id or suspect key>
owner-authority=static-old-evidence / provisional-runtime-only / confirmed-inventory
usable-as-other-old-item=<0/1>
```

这样下一次日志可以立刻区分：

```text
真实旧 C 身份歧义
假 D 的实时存在，但不具备阻塞旧 C 的权限
已确认 D 与旧 C 的真实冲突
```

## 10. 超参数、版本与实施限制

本次是状态、所有权语义和结算顺序修复，不是阈值问题。因此默认要求：

```text
不新增数值超参数；
不调整 FLOW3_TRACK_*；
不调整 FLOW3_REAPPEAR_CANDIDATE_*；
不调整 FLOW3_NO_HAND_*、IN、OUT、MOVED 的确认帧数；
不通过放宽几何距离让测试通过。
```

实施时：

1. `fridge_config.h` 的 `FLOW3_BUILD_TAG` 递增为下一版本，例如 `3.0-r14`。
2. 更新 `超参数位置与调节说明.txt` 的固定规则和诊断日志说明。
3. 先运行主机端全量回放；再交叉编译；最后实机复测两种错误操作。
4. 实机调试开启 `FLOW3_DEBUG_TRACE_LOG = true`；验收后恢复 `false`。

## 11. 最终验收标准

针对本次两个实机错误，修复后日志应接近：

```text
有手：
    旧 C 的 HAND_CONTACT / POSSIBLE_MOVED / POSSIBLE_OCCLUDED 状态逐帧更新，
    且都带 provisional=1
    移动旧 C 的额外同类框首次出现
    -> 创建或更新 PROVISIONAL_D runtime key
    -> quarantine-pending-d / C-D-ALIAS
    -> D 的位置、手相贴和轨迹继续逐帧更新
    -> 不 promote-suspect-to-working-inventory，不产生最终事件

第 1 张无手：
    静止旧 B 按细节 10 独立保留
    C-D alias 的最终框按一框一物品等待第二帧
    -> 不提交

第 2 张无手：
    只有一个同类最终框且数量未增加
    -> 归回旧 C，C MOVED
    -> 丢弃 alias D
    -> 无 IN、无 OUT、正常 commit
```

真正带入一个独立同类 D 时则应接近：

```text
有手：
    C 实时显示可能移动；D 从首次可见帧起就是 PROVISIONAL_D
    若短暂形成 alias，双方轨迹继续更新，不丢 D

第 1 张无手：
    C 与 D 有不同 detection index，均等待连续确认

第 2 张无手：
    C MOVED
    D IN
    -> 正常 commit
```

不应再出现：

```text
旧 C 丢失当前候选
-> 创建 PROVISIONAL_D 本身是允许且必须实时可见的
-> 但该 D 与旧 C 已形成 C_D_ALIAS 后，仍被错误 promote 到 working_inventory_
-> pending / quarantined D 被打印为 other-old-item
-> old C 被错误标为 real ambiguity
-> pending D 又被 old C 阻止提交
-> defer-commit 无限循环
```

同样不应出现以下“表面上最终正确、实际上丢失实时能力”的退化：

```text
手存在期间：没有 C 的接触/可能移动/可能遮挡状态，或没有 D 的 runtime key
手离开后：才第一次创建 C 或 D 的候选、才开始追踪其位置
最终：虽然偶然输出 MOVED / IN，却无法说明有手期间发生了什么
```

最终验收必须同时满足两件事：库存事件正确，且从手接触开始到最终提交之间的每个
关键状态都可实时追溯。不能只以最终库存数量正确作为通过条件。
