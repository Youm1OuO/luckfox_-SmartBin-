# 旧 C 失配时的假 D 隔离、C-D 别名与无手重归属

> 本文建立在细节 8、细节 9、细节 10 之上。
>
> 本文只处理这样一类局部问题：一次操作中，原本已经在库存里的旧物品 C
> 正在被移动，但有手阶段没有把它的新检测框稳定认回 C；程序随后把同一个
> 真实物品错误建立为疑似新物品 D，导致 C 和 D 在无手帧互相阻塞。
>
> 本文不废弃细节 10。细节 10 的“静止旧 B 是排除证据，排除后继续寻找 A”
> 规则仍然正确且必须保留。新问题发生在更早的“有手阶段错误创建 D”和之后
> 的“未确认 D 被当作旧库存”两个环节。

## 0. 已确认的结论

当前问题已经不是猜测。两次实机日志都给出了完整链路：

```text
旧库存 C 被手移动
    -> C 的 hand/reference 路径未命中真实新框，或旧候选被 YOLO 框跳动带偏
    -> 一个同 cls_id、贴手或接近手的未认领框进入 HAND_VISIBLE_D
    -> D 在有手阶段连续两帧后被 promote_suspect_() 写入 working_inventory_
    -> 手离开后，C 再看见该框时，通用“属于其他库存”判断把这个未提交 D
       也当成 another old item
    -> C 被标记 no_hand_candidate_ambiguous，D 又因 C 未解决而不能 IN
    -> 本轮操作永久 defer-commit
```

这里的 D 在真实业务上不存在，它只是移动 C 的重复身份。下文称它为：

```text
假 D / C-D 别名：同一个真实物品同时被 C 和未确认 D 两条运行时记录解释。
```

这不是“把真实新 D 强行认成旧 C”的许可。真正的 D 必须继续存在并能够
正常 IN；系统只是不能在证据仍不足时先复制出库存身份，再让这个复制身份反过来
阻塞原 C。

## 1. 本次实机日志证明了什么

### 1.1 测试错误 1：苹果 #2 与错误苹果 D #7

操作开始时，`item#2` 是已有苹果 C。用户只移动了它，没有放入新苹果。

日志先出现：

```text
frame 197
    预登记疑似新物品 D suspect#-1 cls=0

frame 198
    suspect#-1 已提升为工作库存 item#7
```

因此 `item#7` 必定是假 D。

随后无手帧出现：

```text
item=2 ... other-owner=5
action=exclude-independent-static-neighbor-and-fallback
```

这正是细节 10 的修复分支：`item#5` 是当前拥有独立严格原位框的静止苹果，
所以它被正确排除，不能再永久阻塞 `item#2`。

但紧接着又出现：

```text
result=real-path-ambiguity
reason=ambiguous-no-hand-path-candidate
block-commit pending-d=7 cls=0 unresolved-old=2
```

含义不是细节 10 失败，而是静止 `item#5` 已被排除后，错误建立的 `item#7`
仍让 `item#2` 没有一个可独立完成结算的身份。

### 1.2 测试错误 2：旧橙子 #5 与错误橙子 D #6

操作开始时只有一个旧橙子 `item#5`。用户只整理它，没有放入新橙子。

日志出现：

```text
frame 170
    预登记疑似新物品 D suspect#-1 cls=2

frame 171
    suspect#-1 已提升为工作库存 item#6
```

因此 `item#6` 也是假 D。

无手帧中旧橙子 `item#5` 反复看到：

```text
reject=strictly-belongs-to-other-old-item
result=real-ambiguity
```

开始库存根本没有第二个橙子，所以日志里所谓的 `other-old-item` 不是真正
的旧库存；它就是本轮刚被错误提升的 `item#6`。这也说明当前日志名字不够准确，
后续必须区分“操作开始前旧 C”和“本轮未提交 D”。

### 1.3 与“同类相贴 / 不同类相邻”的关系

用户观察到即使移动到不同类别物品旁边，也可能失败。这个观察是对的：

```text
失败不依赖目标邻居的类别；
真正冲突的双方始终是：移动前的旧 C 与被误建的同 cls_id D。
```

例如移动苹果到苏打罐旁，业务层仍可能产生“旧苹果 C + 假苹果 D”；
移动橙子到不同类别物品旁，仍可能产生“旧橙子 C + 假橙子 D”。

相邻同类框、手框跳动、YOLO 在完整框/局部框之间切换，都会提高 C 丢失
当前框的概率，但它们不是这次永久 pending 的唯一前提。

## 2. 当前实现中的具体漏洞

以下三点要一起修，不能只改其中一个。

### 2.1 C 的单一路径可能被手框位移带偏

`estimated_box(track)` 主要由手框累计位移推算。实机中手框常包含手臂，
它的中心移动距离、方向和被拿物品不完全一致；手指动作、检测框局部化、手框
尺寸变化也会造成明显差异。

因此，真实 C 的新框可能不落在当前 `estimated_box`、`last_seen_box` 或单个
`reappear_candidate_box` 的范围内。当前 C 没有认到该框时，D 扫描会把它当作
全新的物品。

这不是应通过增大 `FLOW3_TRACK_*` 或
`FLOW3_REAPPEAR_CANDIDATE_*` 解决的问题。全局放宽会把相邻真实同类物品、
真实新 D 也吞回旧 C，破坏已有的入库和整理能力。

### 2.2 D 扫描错误地把“C 已认到别的候选”当作“C 已解决”

`scan_or_update_suspects_()` 当前对未认领检测框扫描 D。它为了允许真正的相邻
同类 D，存在如下风险：

```text
C 已经临时认领一个检测框
    （这个框可能只是旧位置局部框、静止邻居或过期 reappear candidate）

另一同类检测框出现
    -> scan 认为 C 已有 owner，跳过“未解决同类旧 C”的防线
    -> 将第二个框建立为 D
```

这里“本帧有 owner”只代表当前暂存了一个候选，绝不等于 C 已经完成
`MOVED / STATIC / OUT / OCCLUDED` 结算。尤其当 owner 本身还只是
`reappear_candidate` 时，不能让它解除 D 防线。

### 2.3 未提交 D 被通用函数误当作“其他旧库存”

`promote_suspect_()` 在有手阶段达到两帧条件后，会立刻把 D 写入
`working_inventory_`，同时用 `pending_in_ids_` 标记它尚未正式 IN。

但是 `detection_strictly_matches_other_item()` 只遍历 `working_inventory_`，
没有区分：

```text
操作开始前就存在的旧 C
本轮刚写入、尚未提交的 pending D
已经通过无手帧确认的 D
```

于是 pending D 的框会被当成“其他旧物品”的强排除证据，最终把原 C 设为
真实歧义。这是错误的语义转换。

只把 `detection_strictly_matches_other_item()` 改成忽略 D 也不够：那会让 C
在没有证据时直接抢走一个可能是真实新 D 的框。因此必须同时引入
`C-D 别名 / 隔离` 状态与无手连续确认。

## 3. 本次修改的目标与不可退化约束

本次修复的目标是：

```text
旧 C 暂时失去自己的可靠框时，潜在同类 D 可以被记录，
但不能立刻获得“库存所有者”地位并阻塞 C。

无手阶段利用已有的连续直接观测、一框一物品和同类可见数量规则，
在 C、D 或真正不可分辨三种结论之间保守收尾。
```

必须遵守：

1. 不修改细节 10：独立静止旧 B 仍是 A 的排除证据，排除后仍继续 fallback。
2. 不修改细节 9：同类可靠可见框持续不足时，仍按连续直接无手帧确认 OUT。
3. 不降低 `MOVED`、`IN`、`OUT` 的连续帧门槛；首张无手帧不直接提交。
4. 不通过放宽几何阈值把远处同类物品强行归属。
5. 真正独立的新 D 必须仍能 IN；本补丁最多让“与未解决同类 C 冲突的 D”
   延后到无手阶段确认，不能删除它。
6. 已确认遮挡仍然保持 `OCCLUDED_CONFIRMED`，不能因为 C-D 冲突改判 OUT。
7. 不同类别的正常 IN / OUT / MOVED 流程必须维持既有时序。
8. 单摄像头下若同 cls_id 的 C 与 D 最终只有一个框、且没有独立证据，遵循
   用户确定的规则：一框一个物品；不能凭类别相同凭空生成 `OUT + IN` 两个事件。
9. 已有入库、出库、整理、CONTACT_*、同类静止邻居、D 防线回放都必须继续通过。

## 4. 新的概念：操作开始旧 C、pending D 与 C-D 别名

后续代码必须明确把物品分为三类，而不是只看它是否位于
`working_inventory_`：

```text
START_OLD_C
    operation_start_inventory_ 中已有的物品。
    它是“旧库存身份”的唯一来源。

PENDING_D
    本轮手操作中出现，尚未通过独立无手确认的新物品候选。
    即使当前实现已把它预写进 working_inventory_，语义上仍不是旧 C。

CONFIRMED_D
    已满足 D 的直接无手连续确认，且不存在未解决同类旧 C 冲突，
    可以正式形成 IN 的物品。
```

再引入一个运行时关系：

```text
C_D_ALIAS
    某个 pending D 与一个未结算旧 C 同 cls_id，且在同一次手操作中
    争夺同一检测框、相邻候选框或同一段手接触路径。

    它的含义不是“D 就是 C”，而是“当前证据不足，D 不能作为 C 的
    其他库存排除证据，C 也不能单帧抢走 D”。
```

推荐在 `OperationTrack` 中增加可追溯字段，名字可在实现时微调，但语义必须保留：

```text
bool pending_d_quarantined_by_old_c
std::set<int> conflicting_old_item_ids       // D 记录冲突的旧 C item_id
std::set<int> conflicting_suspect_keys       // C 记录冲突的 D runtime key
int alias_no_hand_match_count                // 仅记录同一 C-D 关系的直接无手连续性
```

不应只存一个 bool 而没有关系对象。一个操作里可能有多个同类旧 C 或多个
疑似 D；日志和一对一仲裁必须能知道到底是哪两条记录发生冲突。

## 5. 有手阶段：先隔离冲突 D，不抢 C，也不丢 D

### 5.1 识别条件

在 `scan_or_update_suspects_()` 处理一个未认领、贴手或 `C_POSITION_REPLACEMENT`
候选框时，检查同 cls_id 的操作开始旧 C：

```text
同 cls_id 的 START_OLD_C 存在
且该 C 本轮仍未终态结算
且 C 当前为 HAND_* / CONTACT_* / reappearance_pending / 仍需无手结算
    -> 该检测框不能立刻当作独立 D。
```

判断“C 未结算”必须看 `operation_start_inventory_`、`resolution`、
`needs_no_hand_settlement` 和活动轨迹，不得只看：

```text
effective_known_item_owner 是否已有 C
本帧 C 是否已经 claim 了另一个框
```

因为这正是本次漏洞：C 已 claim 的可能只是过期候选，不能代表 C 已解决。

### 5.2 隔离动作

当满足上述条件时：

```text
1. 保留 D 的 suspect 轨迹、手相贴记录、last_seen_box 和连续性信息。
2. 把 D 与该旧 C 标为 C_D_ALIAS / quarantined。
3. 不把该 D 当作 START_OLD_C 的“其他库存”参与严格排除。
4. 不在有手阶段调用 promote_suspect_() 把这个冲突 D 变成 working inventory。
5. 不把该框直接 claim 给 C，也不把 C 单帧确认 MOVED。
6. 不创建 OUT、IN、MOVED 事件；继续等待无手直接帧。
```

这样真实 D 没有被删除，只是暂时没有库存身份；假 D 也不会反过来污染
`working_inventory_`。

### 5.3 为什么不能直接吞回 C

即使只有一个同类旧 C，也不能只要看见同类贴手框就把它写成 C 的新位置。
真实业务可能是：

```text
旧苹果 C 正在被手遮住
同时手放入一个新苹果 D
```

所以有手阶段只能保留 `C_D_ALIAS`，不能凭单帧决定 C MOVED 或 D IN。
最终结论必须交给无手连续帧和同类可见数量。

## 6. 无手阶段：先处理旧 C，再解决隔离 D

无手收尾顺序建议如下。这个顺序是本次修改的核心。

### 6.1 保留已有的旧 C 静态归属

先继续执行细节 10 的规则：

```text
操作开始旧 B 与当前检测框双方唯一严格原位
    -> B 的独立静态所有权成立
    -> 对移动 A 是排除证据
    -> A 清除过期 reappear candidate，并继续 fallback
```

`PENDING_D` 不得伪装成这里的静止旧 B。只有 `START_OLD_C` 才能作为
`other-owner-evidence=direct-original-mutually-unique` 的来源。

### 6.2 C 遇到 pending D 时，不再叫“真实旧 C 歧义”

为当前 `detection_strictly_matches_other_item()` 拆分语义，至少能够回答：

```text
STRICT_OWNER_START_OLD_C
STRICT_OWNER_PENDING_D
STRICT_OWNER_CONFIRMED_D
STRICT_OWNER_NONE
```

对旧 C 的无手匹配：

```text
命中 START_OLD_C：
    按细节 10 / 细节 8 原有规则处理。

命中 PENDING_D，且 D 与 C 是 C_D_ALIAS：
    不设置 no_hand_candidate_ambiguous；
    不把它直接认作 C；
    进入“C-D 无手仲裁”，保留两条候选。

命中 CONFIRMED_D：
    这是已有独立库存，可作为正常排除/遮挡/冲突证据。
```

因此日志不得再把 pending D 打印为 `other-old-item`。

### 6.3 C-D 无手仲裁

对同 cls_id 的一个旧 C 与一个 quarantined D，使用已有直接无手帧和数量规则：

```text
情况 A：当前同类可靠框数等于本轮开始时的旧 C 数量
        且其他旧 C 已各自拥有独立框
        且剩余框连续出现在 C-D alias 的位置

    -> 这一个框按“一框一个旧物品”优先归给 C；
    -> 第一张无手帧仅建立/更新 C 的候选；
    -> 第二张直接无手帧连续后，C -> MOVED；
    -> 该 D 作为 C 的重复身份丢弃，不产生 IN。

情况 B：当前同类可靠框数比本轮开始旧 C 数量多
        且 C 与 D 能在两张直接无手帧中各自占用不同 detection index

    -> C 依旧走自己的 MOVED / STATIC / OUT 证据链；
    -> D 走自己的两张直接无手帧 IN 确认；
    -> 最终允许“C 的事件 + D 的 IN”。

情况 C：当前同类可靠框数少于旧 C 数量

    -> 不把 quarantined D 计入新增数量；
    -> 保持细节 9 的一框一物品和连续可见数量不足 OUT 结算。

情况 D：仍只有一个框，且 C 与 D 均无独立连续证据

    -> 保持 unresolved，不强认 MOVED、OUT 或 IN；
    -> 后续帧继续观察。
```

对于单摄像头下“取出一个旧苹果，同时放入一个新苹果，最终同类框数不变”这类
本身无法区分的情况，不能伪造两条事件。若存在本次手操作的 C-D alias，而没有
两个独立框，则遵循用户已确定的一框一物品规则，优先保留旧 C 的身份链；没有
可靠 C 路径时保持未决或按细节 9 的可见数量规则收尾，而不是自动 `OUT + IN`。

### 6.4 D 的提升时机

推荐规则：

```text
无冲突的 D：
    保持当前 D 链路和已有确认时序，避免破坏已验证的普通入库。

与未结算同类旧 C 冲突的 D：
    有手阶段只保留 suspect / quarantine；
    只有无手阶段证明它与 C 是两个独立连续框，或 C 已经独立结算后，
    才允许 promote_suspect_()、写入 working_inventory_ 和 pending_in_ids_。
```

这不是降低 D 的确认要求，而是把冲突 D 的“临时工作库存身份”延后，避免
假 D 成为 C 的排除证据。

先补回放，再写生产逻辑。测试必须构造有手阶段的：

```text
旧 C 已有一个过期/局部 candidate
真实移动后的 C 框成为未认领的 HAND_VISIBLE_D
```

只构造“直接把 C 的 final box 喂到无手帧”的测试不足以覆盖本次漏洞。

## 8. 必须新增或强化的回放测试

### 8.1 实机错误 1 的抽象回放：苹果 C 不得被建成苹果 D

```text
初始：多个苹果，其中 A 被手移动，B/C 静止。
有手：A 的候选先误指向静止 B 或局部框；A 的真实新框短暂作为未认领框出现。
无手：A、B、C 各有一框。

断言：
    不创建或提升假 D；
    静止 B/C 保持；
    第 1 张无手不提交；
    第 2 张无手只产生 A MOVED；
    没有 IN、没有 OUT、没有永久 pending。
```

此测试必须同时覆盖细节 10 的静止 B 排除和细节 11 的 C-D alias，防止
两次修复互相覆盖。

### 8.2 实机错误 2 的抽象回放：唯一旧橙子不得复制为 D

```text
初始：只有一个旧橙子 A。
有手：A 的预计手位移与真实物品位置偏离；一个目标框短暂成为 D candidate。
无手：只剩移动后的一个橙子框。

断言：
    不生成 IN；
    不把 pending D 当作 other-old-item；
    第 2 张直接无手确认 A MOVED；
    最终库存仍然只有一个橙子，item_id 仍是 A。
```

### 8.3 真实同类 D 与移动旧 C 同时存在

```text
初始：旧苹果 A。
有手：A 被移动，同时手带入新苹果 D。
无手：A 的新位置和 D 的位置是两个独立框，连续两张均存在。

断言：
    A -> MOVED；
    D -> IN；
    数量从 1 到 2；
    不把 D 吞成 A，不把 A 复制成 D。
```

这是本次隔离策略最重要的反向测试，保证“防假 D”不会退化为“同类真实 D 永远不能入库”。

### 8.4 同类 C-D 只有一个最终框

```text
初始：旧苹果 A。
操作后：只有一个苹果框，且该框可同时解释为 A 或 pending D。

断言：
    首张无手不产生 IN / OUT / MOVED；
    不产生两个物品；
    后续按一框一物品、C 的直接证据和细节 9 的数量规则处理；
    不得永久由“假 D 是 other-old-item”造成 defer。
```

### 8.5 非同类真实 D 保持原能力

```text
旧苹果 A 被移动，同时真正放入一个橙子 D。

断言：
    不进入同类 C-D quarantine；
    原有 D 链路继续确认橙子 IN；
    苹果仍按原有 MOVED / OUT 规则结算。
```

### 8.6 既有完整回归集

至少重跑并保持通过：

```text
test_stale_same_class_reappear_candidate_without_a_waits_then_out
```

## 10. 超参数、版本与实施限制

本次是状态、所有权语义和结算顺序修复，不是阈值问题。因此默认要求：

```text
不新增数值超参数；
不调整 FLOW3_TRACK_*；
不调整 FLOW3_REAPPEAR_CANDIDATE_*；
不调整 FLOW3_NO_HAND_*、IN、OUT、MOVED 的确认帧数；
不通过放宽几何距离让测试通过。
```

实施时：

1. `fridge_config.h` 的 `FLOW3_BUILD_TAG` 递增为下一版本，例如 `3.0-r14`。
2. 更新 `超参数位置与调节说明.txt` 的固定规则和诊断日志说明。
3. 先运行主机端全量回放；再交叉编译；最后实机复测两种错误操作。
4. 实机调试开启 `FLOW3_DEBUG_TRACE_LOG = true`；验收后恢复 `false`。

## 11. 最终验收标准

针对本次两个实机错误，修复后日志应接近：

```text
有手：
    移动旧 C 的额外同类框出现
    -> quarantine-pending-d / C-D-ALIAS
    -> 不 promote-suspect-to-working-inventory

第 1 张无手：
    静止旧 B 按细节 10 独立保留
    C-D alias 的最终框按一框一物品等待第二帧
    -> 不提交

第 2 张无手：
    只有一个同类最终框且数量未增加
    -> 归回旧 C，C MOVED
    -> 丢弃 alias D
    -> 无 IN、无 OUT、正常 commit
```

真正带入一个独立同类 D 时则应接近：

```text
第 1 张无手：
    C 与 D 有不同 detection index，均等待连续确认

第 2 张无手：
    C MOVED
    D IN
    -> 正常 commit
```

不应再出现：

```text
旧 C 丢失当前候选
-> create HAND_VISIBLE_D
-> promote-suspect-to-working-inventory
-> pending D 被打印为 other-old-item
-> old C ambiguous
-> pending D 又被 old C 阻止提交
-> defer-commit 无限循环
```
