# 细节20：低分跨类别重复框抢占移动物品身份的修复指导

## 0. 文档用途和适用范围

本文件是下一次修改 3.0 状态机前的实施指导，针对最新实机日志中新发现的一类
身份归属错误：移动中的旧物 A 已经有真实移动/reappear 证据，但目标物附近出现了
一个低分、不同类别、与高分目标框几乎完全重合的重复检测。当前代码先把这个低分
框当成 A 的原位直接证据，使 A 被错误结算为静态旧物，随后真正的 A 终点被当成新 D
并产生错误 `IN`。

本文件只补充这一类“跨类别重复框抢占身份”的问题。此前《细节18.md》和
《细节19.md》中关于正式库存、工作库存、`base_box`、`block_ids`、C-D alias、D
防线、遮挡生命周期、OUT 时序和事件事务边界的约束仍然有效。若本文件与旧文件的
旧案例描述发生冲突，以本文件对最新实机日志的确定事实为准；旧文件中已经验证的
行为和禁止项仍必须保留。

## 1. 最高优先级：当前已经实现的功能很好，绝对不能改坏

**当前代码已经实现了很多正确且重要的功能，后续修改只能做最小增量。修改这次
问题时，千万不要把原来已经做好的功能改坏。**这不是重写 3.0 状态机，也不是重做
遮挡模块；只允许在已有身份候选和无手收尾边界增加一个窄的身份仲裁门控。

下列行为必须作为不可回归的基线：

- 正式 `inventory_` 与操作期间 `working_inventory_`、`operation_start_inventory_`
  的隔离；手操作期间不能提前写正式库存；
- `NORMAL`、`HAND_PARTIAL_BLOCKED`、`HAND_FULL_BLOCKED`、`CONTACT_*` 的现有状态
  语义和转移顺序；
- 旧 C 的严格原位认领、原位 recovery、局部恢复、reappear 候选、轨迹匹配以及
  既有连续确认门槛；
- 真实旧物的 `MOVED` 确认条件、`confirmed_moved_ids_` 语义和正式事件时机；
- 新 D 的连续无手确认、quarantine、C-D alias 和“没有充分 D 证据就绝不 `IN`”
  的防线；
- 普通两帧无手 `OUT` 规则、低置信度假 `IN` 防御和小位移/YOLO 抖动容忍；
- 已经成功的遮挡、揭示、历史 `block_ids` 生命周期和矩形覆盖并集语义；
- `IN`、`OUT`、`MOVED`、`OCCLUDED`、`REVEALED` 只能在既有正式结算提交路径产生；
- 原有日志、OSD 业务输入和截图行为；身份仲裁标记不能删除检测或改变显示结果。

明确禁止用以下方式解决本问题：

- 不能全局删除所有低分框；
- 不能粗暴提高 `YOLO_OBJECT_SCORE_THRESH`、`NEW_TRACK_SCORE_THRESH` 或任何全局
  NMS/检测阈值；
- 不能把“不同类别 + 有交集”直接判定为重复；真实遮挡中不同类别物品本来就可能
  重叠；
- 不能修改全局 `strict_match_box()`、`partial_match_box()`、`track_match_box()`
  或普通 reappear 几何，使所有路径一起变宽或变窄；
- 不能让 D guard 通过强制删除 D 来掩盖旧 A 身份丢失；
- 不能恢复“跳过 old-C 冲突检查”或把临时 D 直接当作旧 A；
- 不能用遮挡几何结论反向证明 A 的身份；
- 不能为了这一个案例降低 MOVED、D、OUT 的既有确认帧数；
- 不能把所有新增逻辑塞进一个已经很大的源文件中，导致身份判断、无手流程和结算
  互相耦合。

## 2. 最新实机日志确认的事实

### 2.1 业务结果和正确结果

实际操作是：旧苹果 A 移到橙子 B 前方，B 已经正确被判为 `OCCLUDED`；随后用户
把 A 移走。正确事件应为：

```text
MOVED(苹果 A)
REVEALED(橙子 B)
```

实际事件却为：

```text
IN(苹果 D)
REVEALED(橙子 B)
```

橙子 B 的揭示成功，说明本轮遮挡关系和揭示提交主流程并没有整体失效。错误发生在
更早的同类身份归属阶段。

### 2.2 旧 A 已经有移动证据

在无手收尾前，item#1 已经记录了真实移动/重现链路，例如：

```text
hold=1
expected=(712,233,917,440)
reappear=1/2:(827,240,980,400)
```

这表示 A 不能再被普通的一张“看起来接近原位置”的框轻易结算为静态旧物。这里的
`expected_box` 或 reappear 候选本身仍不等于已确认 `MOVED`，但它们构成了比可疑原位
框更强的身份竞争证据，必须先参与仲裁。

### 2.3 低分苹果框和高分橙子框几乎是同一个框

在 frame 147/149，检测器在橙子位置同时输出了不同类别的框：

```text
orange: cls=2 score=0.696/0.699 box=(563,283,727/730,445/447)
apple:  cls=0 score=0.318/0.301 box=(561/560,283/285,729/730,445)
```

两个框的中心、宽高和覆盖区域几乎一致，苹果分数明显低于橙子。这个苹果框很可能
是橙子附近的跨类别重复/类别误判，而不是移动 A 回到原位置。它不是因为“有交集”
才可疑，而是因为同时满足“低分、异类高分框几乎同框、旧 A 已有独立移动路径”。

### 2.4 当前代码错误结算的具体位置

无手匹配在 [session_no_hand.cc] 中先查 `original_box`，再查
`reappear_candidate_box`、普通参考路径和无手 reappear。`unique_detection_for_box()`
只检查类别和几何匹配，不检查检测分数、跨类别同框重复或移动证据。

因此 frame 149 中低分苹果框先被选为：

```text
item=1 detection=4 source=ORIGINAL
release reason=ORIGINAL_DETECTION
resolution=STATIC_CONFIRMED
```

这一步会让 A 失去未完成的移动身份链，并使后续候选上下文不再把 A 视为仍待解决的
旧 C。右侧真正的苹果终点于是失去 A 的 owner，既有 C-D alias/D 连续确认流程随后
按错误前提把它提升为新 item，最终产生 `IN`。

### 2.5 这不是本轮 D guard 或 blocker 生命周期的主因

日志中 D 仍经过了 alias、连续无手和提交门控；橙子也正确 `REVEALED`。所以不能
通过重新设计 `block_ids` 或强行删除 D 解决本问题。必须先阻止低分跨类别重复框
完成旧 A 的静态原位结算，同时继续保留 D 的防假入库能力。

## 3. 本轮要建立的业务不变量

在身份仲裁层加入以下不变量：

```text
低分、跨类别、几乎同框的 detection
  在旧 A 已有更强移动/reappear 证据且存在可行替代终点时，
  不能单独完成 A 的 ORIGINAL/STATIC_CONFIRMED 结算。

它只降低当前帧的身份权威，不删除 detection，不改变 OSD，
也不直接把 detection 变成 blocker 或 D。

真正的 A 终点仍须沿已有 reappear/path、自匹配和 MOVED 连续确认链路完成。

若替代终点后来失败，临时抑制必须失效，旧 A 和该 detection 回到原有规则，
不能永久 defer，也不能永久丢弃一个可能是真实物品的框。
```

事件依赖必须保持单向：

```text
当前帧 detection 身份候选与证据分级
    -> 旧 A / 新 D 的既有连续身份确认
    -> 已确认 A/D 的最终位置
    -> 现有 blocker 重算和 C 的 OCCLUDED/REVEALED
    -> 正式结算事件
```

禁止形成循环：

```text
因为框看起来遮住橙子
    -> 所以它一定是旧苹果 A
    -> 再用旧苹果 A 证明橙子被遮挡
```

## 4. 推荐的最小实现方案

### 4.1 增加“当前帧身份可疑标记”，不要做全局过滤

建议新增一个只在当前检测帧存在的身份仲裁结果，例如一个按 detection index
索引的集合/结构：

```text
CrossClassDuplicateHint
  detection_index       // 低分候选的索引
  competing_index       // 几乎同框的另一类别高分候选
  score / competing_score
  geometry evidence     // IoU、中心差、宽高差或等价诊断值
```

名称可按现有风格调整，但语义必须是“身份权威较弱的当前帧提示”，不能把它设计成
正式库存状态。该提示应由纯函数根据当前 `detections` 计算，不写
`inventory_`、`working_inventory_`、`base_box`、`block_ids` 或事件。

### 4.2 可疑重复框必须同时满足窄条件

不能只写 `different_class && overlap > 0`。一个低分框只有在下面条件全部成立时，
才可成为“跨类别重复候选”：

1. 两个 detection 都是食品框，类别不同；手框不参与该判断。
2. 被怀疑的框属于低置信度范围，竞争框明显更可信；建议同时看绝对分数和分数差，
   不能只按输入数组顺序选择“另一个框”。
3. 两框几何上几乎是同一检测假设：IoU/交并比很高，中心偏移很小，宽高或面积比例
   接近。可以使用已有几何 helper 或新增纯几何 helper，但“普通相交”不够。
4. 低分框与某个旧 A 的 `original_box` 确实匹配；否则它不能抢走 A 的原位身份。
5. A 已有真实移动证据或有效 reappear 链路，例如既有 `hold_and_move`、真实手/CONTACT
   移动观测、已保存且连续观察的 reappear candidate。只有 `expected_box` 单独存在、
   一张低分框或宽路径命中，不足以启用抑制。
6. 同一当前帧存在 A 的另一条可行同类终点路径，且该终点与 A 原位置有实质移动差异；
   优先是 reappear candidate/真实轨迹候选，而不是从“遮挡了 B”反推出来的框。
7. 该替代终点没有被更高等级的独立旧物 owner 正式占用，也不是未经确认的 D。

第 5、6 条是安全核心：没有“旧 A 的强移动证据 + 另一条可行终点”，就不能因为
低分或跨类别重叠而否定一个原位 detection。这样可避免真实静态低分物品被全局抹掉。

### 4.3 两阶段选择：先观察候选，再决定原位框能否结算

不要直接改写通用 `unique_detection_for_box()` 的语义。推荐在旧物无手处理的窄调用
边界执行两阶段仲裁：

**第一阶段：只读收集。**

- 先找到当前 `original_box` 候选，但暂不调用 `release_not_held_()`；
- 同时查询 A 的保存 reappear candidate、动态参考路径和现有无手 reappear 候选；
- 记录每个候选的来源、类别、分数和是否满足既有连续链路；
- 对 original 候选运行当前帧的 `CrossClassDuplicateHint` 判断。

**第二阶段：窄门控。**

- 若 original 候选不是可疑重复框，完全沿现有顺序和现有逻辑处理；
- 若 original 候选可疑，且替代终点满足第 4.2 节的强移动条件，则只对该 A 的本轮
  original 证据临时降权/排除；
- 重新尝试 A 的 reappear/path 候选，令其继续沿现有 `update_reappear_candidate()`、
  连续自匹配和 MOVED 确认门槛运行；
- 可疑 original detection 不得触发 `release_not_held_()`，不得清除 A 的
  `reappear_candidate_box`、`hold_and_move`、移动观测或未决状态；
- 若替代终点找不到或不满足强条件，则撤销本轮抑制，回到原有 original 处理，避免
  因一次猜测让旧物永久未决。

在实现上可以复用现有的“本轮排除 detection index 后继续 fallback”机制，但排除理由
必须单独记录为 `cross-class-duplicate-identity-only`，不能把它当成“另一旧 C 已有
独立严格 owner”。这两种原因对 reappear 清理、静态结算和 D alias 的后续影响不同。

### 4.4 对候选上下文和 D/alias 的处理

该低分框不能被完全从候选图中删除，否则真实旧物可能失去 D guard 保护。推荐将它
分成两种权威：

```text
identity authority = weak / duplicate-suspect
conflict authority = retained
```

具体规则：

- 对已有强移动路径的旧 A：可疑框不能算作 direct original owner，不能完成
  `STATIC_CONFIRMED`；
- 对 C-D alias/D guard：可疑框仍应作为“存在未解决旧物冲突”的弱边保留，不能让
  同位置的 runtime D 因它看似独立而立即 `pending IN`；
- 可疑框不能单独完成 D 的独立 alias、不能单独进入 `pending_in_ids_`、不能单独产生
  `IN`，也不能成为 blocker；
- 若该框与旧 A 的强终点在后续帧被确认，按旧 A 的正常 MOVED 路径处理；若强终点
  失败且低分框持续出现，才允许它重新按既有静态/新 D 流程竞争；
- 同级的多个旧 C 仍保持真实歧义，不能借本标记强行选择一个 `item_id`；
- “本轮被更强 owner 排除”不等于“旧 A 已经被直接看见”，也不等于可以提前累计
  OUT。OUT 仍必须使用原有直接缺失证据。

这一步应扩展当前的 `SameClassCandidateContext` / owner evidence 语义，而不是绕过
已有的 C-D alias。若需要新增字段，优先使用本轮 map/set 或轻量结果结构，避免把
一次检测误判写入持久 `InventoryItem`。

### 4.5 不改变遮挡和 blocker 的确认边界

可疑重复标记只解决“谁拥有当前检测框”的问题。它不能直接改变：

- `block_ids`；
- `OCCLUDED` / `REVEALED` 状态；
- `fully_covered_by()` 或边缘残余容差；
- `confirmed_moved_ids_`；
- 普通 `OUT` 计数；
- 正式库存或事件。

当 A 沿已有门槛确认 `MOVED` 后，继续调用现有统一结算和 blocker 重算；此时橙子 B
才可以根据已确认的 A 终点正常露出并产生 `REVEALED`。如果 A 没有确认，遮挡结论
不能替它确认身份。

## 5. 检测分数和几何阈值的使用原则

### 5.1 不要复用显示阈值

`OSD_LOW_CONFIDENCE_OBJECT_SCORE_THRESH` 只用于显示颜色，不能被当作新的业务身份
过滤阈值。`YOLO_OBJECT_SCORE_THRESH` 是全局业务输入门槛，也不能为了本案例修改。

如果现有 `HIGH_SCORE_THRESH` 等业务候选分层足以表达“高分竞争框”，可以先复用其
既有语义；如果无法清楚表达，才新增专用参数。

### 5.2 新参数必须窄、可解释、同步文档

若需要专用常量，建议采用明确的 3.0 身份命名，例如：

```cpp
FLOW3_IDENTITY_DUPLICATE_LOW_SCORE_MAX
FLOW3_IDENTITY_DUPLICATE_PEER_SCORE_MIN
FLOW3_IDENTITY_DUPLICATE_SCORE_MARGIN
FLOW3_IDENTITY_DUPLICATE_IOU_MIN
FLOW3_IDENTITY_DUPLICATE_CENTER_NORM_MAX
FLOW3_IDENTITY_DUPLICATE_SIZE_RATIO_MAX
```

不一定要全部新增；能用现有 helper 且不改变全局语义时，应尽量少加参数。任何真正
写入 `fridge_config.h` 的新常量都必须同步更新
`另另一种业务流程(3.0var)/超参数位置与调节说明.md`，写明地址、单位、作用、调大/调小
的后果和本案例中的观测依据。不能只改头文件而不更新说明。

初始值必须先用最小回放和实机日志校验，不能为了让一条日志通过而把 IoU、中心或
分数范围放得很宽。特别要防止一个真实的部分遮挡框被误归为“跨类别重复”。

## 6. 文件和模块拆分建议

**代码没有必要、也不应该全部塞进同一个文件。按职责拆分会更容易验证和解耦。**
但拆分必须服从现有工程构建方式，不要为了形式新建大量文件或移动无关代码。

推荐职责如下：

### 6.1 `session_ownership.cc`：纯身份/候选判断

适合放：

- 跨类别重复框的纯几何/分数分类 helper；
- 当前帧 `CrossClassDuplicateHint` 或等价结果结构的生成；
- 旧 C 对 detection 的证据等级、候选上下文和双向预约；
- “可疑 original 不能作为 direct owner，但仍保留冲突边”的判断；
- 只读诊断信息和 owner 来源说明。

这里的 helper 尽量纯函数化：输入 detection、track、当前帧候选和已有只读容器，
输出分类/证据，不直接改正式库存、不发布事件、不操作 pending 集合。

### 6.2 `session_no_hand.cc`：无手流程编排和窄门控

适合放：

- 在原位认领前调用候选收集与重复提示；
- 对特定旧 A 临时排除可疑 original index，并继续尝试 reappear/path；
- 只有真实原位证据才调用 `release_not_held_()`；
- 保持现有 `claimed`、候选预约、连续自匹配和失败回退顺序；
- 输出 `source=ORIGINAL`、`source=REAPPEAR_CANDIDATE` 及抑制原因的 trace。

不要在这里重新实现几何算法，也不要把 D/遮挡提交逻辑复制进来。

### 6.3 `session_settlement.cc`：正式事务和遮挡结果

这次身份修复原则上不应改动这里的事件顺序。只有当验证发现可疑框仍绕过正式提交
门控时，才在此处补充最终 `pending_in`/事件保护。正式 `MOVED`、`REVEALED`、
`block_ids` 重算继续沿既有事务路径。

### 6.4 `session_internal.h` / `session.h`：最小声明边界

- 新结果结构和 helper 声明放在 `session_internal.h`，不要把实现塞进公共 API；
- 只有确实需要跨成员函数保存的操作状态才改 `session.h`；
- 当前帧提示优先作为函数局部结果或本轮容器，不能新增持久库存字段；
- 若新结构仅在两个实现文件使用，可放在实现文件私有命名空间，减少头文件耦合。

### 6.5 是否新建 `session_identity.cc`

如果 `session_ownership.cc` 已经因为候选仲裁过大，允许把纯身份 helper 单独拆到
`session_identity.cc`，但必须同时更新实际使用的 Make/CMake 源文件列表、测试编译
列表和依赖声明。新文件不是目的，清晰的职责边界才是目的。若工程构建不方便新增
源文件，则保留在 `session_ownership.cc` 的独立区域也可以；无论放在哪个文件，
都不能把身份分类、无手编排和正式结算揉成一个不可测试的大函数。

## 7. 必须先写的最小失败回放和对照回放

实现前先在现有 `tests/session3_replay_*` 体系中加入最新案例的确定性回放。测试应
先能证明旧代码会走错，再在修复后断言正确结果；不要直接修改生产代码后只看一条
实机日志。

### 7.1 最新失败案例

至少模拟这些帧：

1. 初始正式库存含苹果 A 和橙子 B，B 已因 A 处于 `OCCLUDED`；
2. A 的 HAND 阶段记录真实移动和 reappear candidate；
3. 无手帧同时出现右侧真实 A 终点、橙子 B 高分框和同位置低分苹果框；
4. 下一张无手帧继续出现真实 A 终点，低分重复框可出现或消失；
5. 继续到现有结算帧数。

修复后必须断言：

- 苹果 A 保留原 `item_id`，沿既有门槛产生一次 `MOVED`；
- 橙子 B 产生一次 `REVEALED`；
- 不产生新的苹果 `IN`，正式库存数量不增加；
- 低分重复框不写入 `base_box`、`block_ids` 或正式库存；
- 不提前产生 `OUT`、`OCCLUDED`、`MOVED` 或 `IN` 事件；
- 事件顺序和结算提交点符合现有事务边界。

### 7.2 必须保留的反例

至少增加或保留以下反例：

- 真实静态苹果与高分橙子部分重叠，但苹果框分数低、没有移动证据：不能仅因跨类别
  重叠就抑制它；
- 低分苹果框与橙子框位置相近但并非几乎同框：不能判为重复；
- 低分框与高分异类框同框，但旧 A 没有另一条强移动路径：不能直接删除或跳过；
- 可疑框持续多帧但真实移动终点失败：抑制最终要释放，沿原有规则收敛，不得永久
  `defer-commit`；
- 真实新 D 连续稳定出现在与旧物不同的位置：仍按既有帧数 `IN`；
- 单帧低置信度新框：仍不能 `IN`、不能成为 blocker；
- HAND/CONTACT、正常 OUT、正常 MOVED、同类强/弱 owner、历史 blocker 生命周期的
  全部既有 replay。

### 7.3 日志断言要求

回放 trace 至少要能区分：

```text
original candidate found
cross-class duplicate hint=true/false
alternative move candidate source
original evidence suppressed/skipped
reappear/path observation count
candidate-context direct/weak conflict
formal release reason
```

日志只用于诊断，不能让测试依赖 detection 数组顺序或遍历顺序。应断言 item id、
状态、事件种类/次数、`pending_in_ids_`、`pending_out_ids_` 和最终库存。

## 8. 实施顺序

严格按以下顺序进行，避免把新的身份问题与旧遮挡问题混在一次大改中：

1. 保存当前完整 replay、`-Werror`、ASAN/UBSAN 和 `git diff --check` 基线；
2. 先加入 7.1 的最小失败回放和 7.2 的对照回放；
3. 只实现当前帧重复提示和旧 A 原位证据窄门控，不改遮挡几何和 blocker 生命周期；
4. 运行已有 HAND、CONTACT、C-D alias、D、低分假框、OUT、MOVED、遮挡/揭示回放；
5. 若新增候选证据字段，再实现 candidate-context/D guard 的弱冲突保留；
6. 重新运行最新失败案例，确认 A 不再被 `STATIC_CONFIRMED`，且替代终点沿原有连续
   链路收敛；
7. 仅在必要时增加专用超参数，并立即同步 `超参数位置与调节说明.md`；
8. 最后运行完整构建、模块化 replay、ASAN/UBSAN、`-Werror` 和 `git diff --check`。

每一步若出现原有成功案例退化，应停在上一个通过点定位，而不是继续扩大阈值或
增加更多例外分支。不要因为最新实机只显示一条错误路径，就重写已经稳定的遮挡
生命周期、OUT 防线或 D 认领流程。

## 9. 验收标准

只有同时满足以下条件，才算本轮完成：

- 最新场景产生 `MOVED(苹果 A) + REVEALED(橙子 B)`，不产生错误 `IN(苹果 D)`；
- 低分跨类别同框框不能单独把有移动证据的旧 A 结算为 `STATIC_CONFIRMED`；
- 可疑提示是当前帧临时信息，不污染正式库存、`base_box`、`block_ids` 或 OSD；
- 替代移动路径失败后，旧逻辑仍能正常处理原位框/OUT/D，且不会永久 defer；
- 真实低分静态物品、真实部分遮挡物品和真实新 D 不因新规则被误删或误合并；
- D guard 仍能防止低置信度单帧假 `IN`，而且未确认 D 不能成为 blocker；
- 现有遮挡成功案例、揭示事件、历史 blocker、HAND/CONTACT、小位移和正常 OUT/MOVED
  行为均无回归；
- 完整 replay、`-Werror`、ASAN/UBSAN、`git diff --check` 全部通过。

## 10. 核心原则

```text
先把当前帧的检测框按身份证据分级，再决定谁可以认领；
低分跨类别同框只能在“旧 A 已有强移动证据且有另一条可靠终点”时降低原位权威；
它不被删除、不成为 blocker、不绕过 D 防线；
真正的 MOVED、遮挡和 REVEALED 仍使用原有连续确认与正式结算；
当前代码已经实现的功能很好，修改只能是可回退、可测试、职责清晰的最小增量。
```
