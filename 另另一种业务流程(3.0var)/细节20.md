# 细节20：以 blocker 因果驱动遮挡状态，并修正跨类别重复框身份误认

## 0. 文档用途和适用范围

本文件是下一次修改 3.0 状态机前的实施指导。它针对最新实机日志暴露出的完整
问题链，而不是只针对某一个苹果/橙子坐标添加例外：

```text
移动中的旧苹果 A 已经有真实移动/reappear 证据；
橙子 B 附近出现低分、跨类别、几乎同框的苹果重复 detection；
低分框先抢走 A 的原位身份，A 被错误静态结算；
右侧真实终点失去 A 的 owner，随后被当成新 D；
同时，橙子自己的 detection 又被直接解释成 REVEALED。
```

本轮的正确目标不是再加一个“遇到这组分数就跳过”的临时补丁，而是修正两层状态
逻辑：

```text
第一层：先正确完成 detection -> 旧物/新 D 的身份归属；
第二层：遮挡状态变化必须由已确认的 blocker 变化驱动。
```

此前《细节18.md》和《细节19.md》中关于正式库存、工作库存、`base_box`、`block_ids`、
C-D alias、D 防线、OUT 时序、矩形覆盖并集和事务边界的约束仍然有效。本文件是
对这些约束的进一步收紧和落地，不是推翻已有状态机。

## 1. 最高优先级：当前代码已经实现的功能很好，绝对不能改坏

**当前代码已经实现了很多正确且重要的功能，后续修改只能做职责清晰、可验证、可
回退的最小增量。修改这次问题时，千万不要把原来已经做好的功能改坏。**这不是
重写 3.0，也不是重做所有遮挡、D 或 OUT 逻辑。

以下行为必须作为不可回归基线：

- 正式 `inventory_` 与操作期间 `working_inventory_`、`operation_start_inventory_`
  的隔离；手操作期间不能提前写正式库存；
- `NORMAL`、`HAND_PARTIAL_BLOCKED`、`HAND_FULL_BLOCKED`、`CONTACT_*` 的现有状态
  语义、保护期和转移顺序；
- 旧 C 的严格原位认领、原位 recovery、受限局部恢复、reappear 候选、轨迹匹配和
  已有连续确认门槛；
- 真实旧物的 `MOVED` 确认条件、`confirmed_moved_ids_` 语义和正式事件时机；
- 新 D 的连续无手确认、quarantine、C-D alias 和“没有充分 D 证据就绝不 `IN`”
  的防线；
- 普通两帧无手 `OUT` 规则、低置信度假 `IN` 防御和小位移/YOLO 抖动容忍；
- 已经成功的遮挡、揭示、历史 `block_ids` 生命周期和矩形覆盖并集语义；
- `IN`、`OUT`、`MOVED`、`OCCLUDED`、`REVEALED` 只能在正式结算提交路径产生；
- YOLO 业务输入、OSD 业务输入、日志和截图行为；身份仲裁结果不能删除 detection
  或改变显示层。

以下方案禁止采用：

- 不能全局删除所有低分框，不能粗暴提高 `YOLO_OBJECT_SCORE_THRESH`、NMS 或新轨迹
  阈值；
- 不能把“不同类别 + 有交集”直接当作重复；真实遮挡中不同类别物品可以重叠；
- 不能全局改宽或改窄 `strict_match_box()`、`partial_match_box()`、`track_match_box()`、
  普通 reappear 几何；
- 不能用 `item_id` 顺序、detection 数组顺序、timeout 或“卡住太久选一个”结束身份
  歧义；
- 不能让 D guard 通过删除 D 来掩盖旧 A 身份错误，不能把未确认 D 当作 blocker；
- 不能用“目标框出现了”反向证明 blocker 已经移动，也不能用“框有交集”反向证明
  旧物身份；
- 不能为了这次案例降低 MOVED、D 或 OUT 的既有确认帧数；
- 不能把所有新逻辑塞进一个大函数或一个大源文件。身份、遮挡因果、几何和正式
  结算应保持解耦。

## 2. 本轮必须纠正的核心逻辑

### 2.1 检测事实不等于业务状态变化

必须明确区分三个概念：

```text
observation
    当前帧检测器给出的框，以及它是否被合法归属到某个 item。

formal visibility state
    正式库存中的 VISIBLE/OCCLUDED 状态。

transition event
    OCCLUDED、REVEALED、MOVED、IN、OUT 等正式事件。
```

当前代码的危险路径是：

```text
检测到旧 C 的框
    -> 直接把 C 写成 VISIBLE
    -> 只要上一正式状态是 OCCLUDED 就产生 REVEALED
```

这把“看到了一个框”和“遮挡关系已经被解除”混成了同一个事实。下一次修改必须
把这两个层次分开：当前 detection 可以先成为临时 observation，但正式状态变化和
事件必须通过 blocker 因果门控。

### 2.2 遮挡和露出必须由 blocker 变化驱动

本轮固定以下业务不变量：

```text
VISIBLE -> OCCLUDED
    必须有已确认的前景物品 A/D 在本轮进入或移动到 C 前方，
    且最终可靠框的覆盖并集完整覆盖 C.base_box。

OCCLUDED -> REVEALED/VISIBLE
    必须有已确认的 blocker 移动、出库或位置变化使覆盖不再完整，
    并且 C 在当前无手帧有合法的直接观察。
```

因此：

- 没有任何 blocker 的 `MOVED`、`OUT`、`IN` 或其他已确认位置变化，不能因为 C 自己
  出现一张 detection 就产生 `REVEALED`；
- 没有任何已确认前景物品 `IN`/`MOVED`，不能因为某个框与 C 重叠就产生 `OCCLUDED`；
- 未确认 D、低分重复框、HAND 临时框、历史推测框都不能作为这两个状态变化的因果
  依据；
- 历史 `block_ids` 可以让已经正式 `OCCLUDED` 的 C 在无关操作中继续保持遮挡，但
  历史关系本身不能在一个原本 `VISIBLE` 的 C 上凭空创建新的 `OCCLUDED`，也不能
  在一个 blocker 没有变化时凭空创建 `REVEALED`。

初始化/后台加载时依据权威库存建立初始状态属于建库流程，不属于本条的操作内状态
转换；除此之外的正式状态变化都必须遵守这个因果约束。

### 2.3 事件顺序必须服从因果顺序

状态结算可以在一次事务中完成，但事件计划不能按 `item_id` 或 map 遍历顺序随意
生成。至少要满足以下依赖：

```text
MOVED(A) -> REVEALED(C)
OUT(A)   -> REVEALED(C)
IN(D)    -> OCCLUDED(C)
MOVED(A) -> OCCLUDED(C)
```

也就是说，先确认前景物品的身份和最终位置，再重算 blocker，最后决定 C 的遮挡
状态和事件。正式事件可以仍然在一次 `replace_all()` 前集中生成，但必须按依赖关系
排序，不能出现 C 先 `REVEALED`、A 后 `MOVED` 的反向结果。

## 3. 最新实机错误的完整因果链

### 3.1 A 的原位参考本身没有错，错误在同类 detection 身份

旧苹果 A 的操作开始原框大约是：

```text
A.original_box = (527,278,732,485)
```

橙子 B 的检测框和低分苹果重复框大约是：

```text
orange cls=2: (561,283,730,447)
apple  cls=0: (560,285,730,445)
```

代码并没有把 `cls=2` 的橙子框直接匹配给苹果 A；它匹配的是另一个 `cls=0` 的
低分苹果框。这个低分框位于 A 原框内部，而且中心、宽高仍满足当前严格/局部几何
条件。由于 A 原本就在 B 前方，B 的可见检测区域天然可能落入 A 的完整原框范围。

所以当前匹配器看到的是：

```text
类别是苹果；
几何上接近 A 的 operation-start 原框；
因此可以作为 A 的 ORIGINAL。
```

它没有利用“同位置还有一个高分橙子框”和“A 已经有另一条移动终点路径”这两条
身份证据，才导致错误的 `source=ORIGINAL`、`STATIC_CONFIRMED` 和 `release`。

### 3.2 为什么橙子仍然会 REVEALED

当前结算函数会把当前橙子检测合法绑定到旧 item#4 后，将它放入本帧观察集合；随后
`refresh_confirmed_blockers_()` 对“当前直接观察到的 target”直接设置 `VISIBLE`。
最后的事件生成只比较：

```text
old.status == OCCLUDED
now.status == VISIBLE
```

于是橙子产生 `REVEALED`。这一条路径没有检查 A 是否已经确认 `MOVED`/`OUT`，也没有
检查历史 blocker 关系是否发生了变化。这正是本轮必须纠正的第二个逻辑缺口。

### 3.3 为什么旧 A 没有 OUT、右侧却出现 IN

低分苹果框已经被当成 A 的直接原位 observation，所以 A 不会进入普通缺失 OUT；
同时，A 的真正右侧终点失去了 owner，经过已有的 D 连续确认后被提升为新 item。

因此系统内部变成：

```text
旧 A：仍在库存，错误地认为位于原位置；
旧橙子 B：因自己的直接检测被错误地标记为露出；
右侧苹果：被错误地当成新的 D/IN。
```

这不是一个符合业务的“先出库再入库”流程，而是身份仲裁错误和遮挡状态转移错误
叠加后的不一致状态。单独增加一个低分阈值只能遮住这个案例，不能修正状态机的
因果关系。

## 4. 正确的两层状态机模型

### 4.1 第一层：身份计划

每个当前 detection 先得到一个只存在于当前帧的身份候选计划。它至少需要区分：

```text
strong/direct owner
    既有严格原位、合法移动终点、reappear 连续候选或其他更高等级 owner。

weak candidate
    只有宽路径、历史参考或低权威几何命中。

cross-class duplicate hint
    低分候选与另一类别高分框几乎同框，且可能只是类别重复。

conflict edge
    当前框仍可能属于未解决旧 C，因此必须继续阻止 D 草率 IN。
```

该计划不能直接修改正式库存或事件。只有经过原有连续确认门槛后，才把旧 A 放入
`confirmed_moved_ids_`，或把新 D 放入 `pending_in_ids_`。

### 4.2 第二层：blocker 因果计划

在身份计划完成后，再基于以下只读输入计算当前事务的 blocker 转移：

```text
operation_start_inventory_[C].status
operation_start_inventory_[C].block_ids
operation_start_inventory_[C].base_box
当前已确认的旧物 MOVED 集合
当前已确认的 D IN 集合
当前合法的 direct observation
当前最终可靠的 candidate base_box
正式 OUT 的 pending 结果
```

建议增加一个只存在于本轮结算的内部计划结构，名称可以按项目风格调整，例如：

```text
BlockerTransitionPlan
    historical_blocker_ids
    effective_blocker_ids
    added_blocker_ids
    removed_blocker_ids
    moved_blocker_ids
    coverage_before_full
    coverage_after_full
    coverage_changed_by_confirmed_front
    valid_target_observed
    observation_conflict
    cause_kind
    allow_occluded_transition
    allow_revealed_transition
```

这个结构是本轮局部计划，不应直接新增到持久 `InventoryItem`。它的职责是回答：

```text
当前 target 的观察是否可信？
当前 blocker 集合与覆盖是否发生了有业务原因的变化？
本轮是否允许改变 OCCLUDED/VISIBLE？
本轮是否允许生成 OCCLUDED/REVEALED 事件？
```

### 4.3 统一结算阶段顺序

推荐将无手结算明确分成下列阶段。现有 helper 可以复用，但不能跳过阶段：

1. **候选上下文阶段**：建立同类 owner、reappear、D alias 和跨类别重复提示；不写
   正式库存。
2. **观察绑定阶段**：为旧 C/D 预约当前 detection，低分跨类别重复不能直接完成
   A 的静态结算；保留既有 `claimed` 和双向唯一规则。
3. **身份确认阶段**：沿现有连续无手链路确认 `MOVED`、D `IN`、普通静态恢复或
   `OUT`，不因遮挡几何反向确认身份。
4. **blocker 差分阶段**：合并历史关系和当前已确认前景，识别新增、移除、移动和
   覆盖变化；未经确认的缺失 blocker 不能静默删除。
5. **遮挡状态阶段**：只按第 5 节规则决定 C 是否保持、进入或离开 `OCCLUDED`。
6. **OUT/遮挡失效阶段**：沿现有两帧 OUT 和 occlusion-loss 规则继续，不能因临时
   observation 直接撤销或制造 OUT。
7. **事件计划阶段**：生成带因果原因的事件，并按 blocker 依赖拓扑排序。
8. **事务提交阶段**：没有 unresolved 冲突后才 `replace_all()`，然后清理操作运行时。

任何阶段发现身份或因果冲突，都可以 `defer-commit`；但必须保留能使后续帧收敛的
证据，不能把冲突永久锁死。

## 5. Blocker 关系和状态转移的正式规则

### 5.1 `effective_blocker_ids` 的计算

对每个旧目标 C：

```text
effective_blockers(C)
    = 历史已提交 block_ids(C)
      union 当前已确认且直接出现的 IN/MOVED 前景物
      minus 已正式 OUT 的 blocker
      minus 已确认 MOVED 到不再与 C 可靠框相交处的 blocker
```

细节要求：

- 历史 blocker 仍在工作库存且仍与 C 有正面积交集时，不能因本轮暂时没有新的
  blocker detection 就清空关系；
- blocker 已移动但仍与 C 相交时，关系可以保留，必须重新用新 `base_box` 计算覆盖；
- blocker 只是当前帧漏检、尚未达到 OUT 门槛时，不能从关系中删除；应保持关系并让
  现有未决/OUT 逻辑继续；
- 未确认 D、quarantined D、低分跨类别重复框、手框和局部临时框不能进入正式关系；
- `block_ids` 是前景关系集合，不等于 `OCCLUDED`。只有覆盖并集完整时，才有完全
  遮挡资格。

### 5.2 允许 `VISIBLE -> OCCLUDED` 的条件

只有以下条件全部成立才允许从 VISIBLE 进入 OCCLUDED：

1. C 是合法的旧目标，或已经按既有建库规则拥有正式身份；
2. 当前没有合法、完整的 C 直接 observation。部分/可疑/未绑定框不能绕过这一条；
3. `effective_blockers(C)` 的最终可靠框覆盖并集完整覆盖 C 的可靠 `base_box`；
4. 至少存在一个本轮确认的前景变化原因：
   - 已确认旧物 A `MOVED` 到 C 前方；或
   - 已确认新物 D `IN` 到 C 前方；或
   - 已确认已有 blocker 在本轮移动，使覆盖从不完整变为完整；
5. 参与覆盖的每个 blocker 都经过已有身份和最终位置确认。

如果 C 原本已经是 OCCLUDED，且历史 blocker 仍有效，只需保留状态和关系，不重复
生成 `OCCLUDED`。历史关系本身不是一次新的遮挡事件。

以下情况必须拒绝新建 OCCLUDED，保持 VISIBLE 或 unresolved：

- 只有一个未确认 D 或低分 detection 与 C 框重叠；
- 只有历史 `block_ids`，本轮没有任何确认的前景变化；
- C 仍有合法直接框，只是框大小或边缘发生抖动；
- 只能靠“这个框看起来像 blocker”反推其身份；
- 仅有 `expected_box`、宽路径或一帧手框，没有现有 MOVED/IN 确认。

### 5.3 允许 `OCCLUDED -> REVEALED/VISIBLE` 的条件

只有以下条件全部成立才允许产生 REVEALED：

1. 操作开始的正式状态确实是 OCCLUDED；
2. C 当前有合法直接 observation，并且该 observation 不是未绑定框、低分跨类别
   重复提示或其他身份冲突的弱证据；
3. 使用当前最终可靠 blocker 框计算后，C 不再被完整覆盖；
4. 至少存在一个已确认的解除原因：
   - 历史 blocker A 已确认 `MOVED`，且新位置不再覆盖 C 或覆盖从完整变为不完整；
   - 历史 blocker A 已确认 `OUT`；
   - 多 blocker 中至少一个已确认移动/出库，导致覆盖并集失去完整性；
5. blocker 差分和 C 观察属于同一事务，不能仅凭 C 自己出现来推断原因。

允许 blocker 仍与 C 有部分交集：`block_ids` 可以继续保留为前景关系，但覆盖已不
完整时，C 可以变为 VISIBLE 并产生一次 REVEALED。这里的原因是 blocker 的确认
位置变化，而不是简单的“看到 C”。

以下情况禁止 REVEALED：

- C 自己出现了框，但没有任何历史 blocker 的确认移动/OUT/覆盖变化；
- A 仍处于 `POSSIBLE_MOVED`、alias、quarantine 或仅有宽路径候选；
- 当前低分苹果框和橙子框冲突，C 的 observation 还没有合法 owner；
- blocker 只是当前帧漏检，没有正式 OUT 或确认移动；
- 覆盖并集仍完整，只是检测器在内部产生了一个小框；
- 目标框出现但导致的状态变化只能依赖“遮挡物已经离开”的猜测。

没有解除原因时，建议保留 C 的正式 OCCLUDED 状态和历史关系，把当前 observation
放在本轮临时冲突结果中，并令结算保持 unresolved；不能直接把 C 写成 VISIBLE，也
不能产生 REVEALED。这样可以避免本次日志中的“旧 A 没动，橙子却无原因露出”。

### 5.4 blocker 变化与 OUT 的关系

遮挡解除和 OUT 仍是两个事件，不能互相替代：

- blocker A 确认 OUT 后，若 C 有合法直接 observation 且覆盖已解除，可以在同一事务
  中按依赖顺序产生 `OUT(A)`、`REVEALED(C)`；
- blocker A 确认 MOVED 但 C 没有直接 observation，不能产生 REVEALED；C 继续沿已有
  覆盖失效/普通 OUT 证据链处理；
- C 自己缺失不能证明 A OUT，也不能证明 C 被遮挡；
- 仍然保留原有两帧 direct-missing OUT 规则和《细节19.md》的窄 OUT 延迟保护；
- 如果 blocker 的 OUT 只是临时 pending，后续保护逻辑撤回该 OUT 时，相关 reveal
  计划也必须一并撤回，不能留下孤立 REVEALED。

### 5.5 历史 blocker 的跨操作生命周期

在无关操作中：

- C 已正式 OCCLUDED，历史 blocker 仍有效：C 继续 OCCLUDED，不重复事件；
- C 未被直接看到但 blocker 只部分变化，仍保留关系，按覆盖和 OUT 规则处理；
- blocker 确认移动到不相交处或正式 OUT：从有效关系中移除；只有 C 随后被合法
  直接观察，才生成 REVEALED；
- blocker 只是漏检或暂时未决：不能清空关系，不能提前 REVEALED。

这部分是对已有正确 blocker 生命周期的强化，不是恢复“只保留本轮 blocker”的旧
逻辑。

## 6. 第一层实现：跨类别重复框不能抢走旧 A 身份

### 6.1 当前帧身份提示，不是全局检测过滤

建议增加只存在于当前帧的内部提示，例如：

```text
CrossClassDuplicateHint
    detection_index       低分可疑框
    competing_index       几乎同框的另一类别框
    score / competing_score
    几何诊断值             IoU/IoM、中心差、宽高差等
```

它是身份仲裁结果，不是正式库存状态。不能删除 detection，不能改变 OSD，不能写
`base_box`、`block_ids` 或事件。

### 6.2 可疑重复框必须是窄组合条件

只有以下条件全部成立时才可降低其身份权威：

1. 两个 detection 都是食品框且类别不同；手框不参与；
2. 被怀疑框分数较低，另一类别框分数明显更高；不能依赖 detection 数组顺序；
3. 两框几乎是同一个检测假设：IoU/IoM 很高、中心偏移很小、宽高/面积接近；普通
   相交不够；
4. 低分框确实匹配某个旧 A 的 `original_box`；
5. A 已有真实 `hold_and_move`、CONTACT/HAND 移动证据或有效 reappear 连续链路；
6. 同帧存在 A 的另一条可靠同类终点路径，且与 A 原位置形成真实移动差异；
7. 替代终点没有被更高等级的独立旧物 owner 占用，也不是未确认 D。

第 5、6 条是关键防线。没有强移动证据和可行替代终点，不能因为低分或异类重叠
否定真实静态物品。

### 6.3 两阶段身份选择

不要改写通用 `unique_detection_for_box()` 的全局语义。应在旧物无手处理的窄调用
边界：

**第一阶段只读收集：**

- 收集原位、reappear、动态参考和无手路径候选；
- 记录来源、分数、类别、当前连续证据；
- 判断原位候选是否为跨类别重复提示；
- 暂不调用 `release_not_held_()`。

**第二阶段按身份权威选择：**

- 普通原位候选不是可疑重复时，完全沿现有顺序；
- 原位候选可疑且替代终点满足第 6.2 节条件时，只在本轮对该 A 排除该 detection
  的原位身份权威；
- 继续走 A 的 reappear/path、自匹配和既有 MOVED 门槛；
- 可疑原位框不得清除 A 的移动观测、reappear candidate、hold 证据或未决状态；
- 替代路径失败时，临时排除自动失效，回到原有规则，不能永久 defer 或永久删除
  真实 detection。

排除理由应单独记录为 `cross-class-duplicate-identity-only`，不能伪装成“另一旧 C
已有独立严格 owner”，两者对 C-D alias 和后续回退语义不同。

### 6.4 D guard 必须保留弱冲突边

低分重复框不能被完全从候选图删除，否则 D 可能反过来抢走旧 A：

```text
identity authority = weak
conflict authority = retained
```

因此：

- 它不能单独完成 A 的 `STATIC_CONFIRMED`；
- 它仍可作为“这里存在未解决旧物冲突”的弱边，阻止 D 草率 `IN`；
- 它不能单独进入 `pending_in_ids_`，不能单独成为 blocker；
- “本轮被更强 owner 排除”不等于“旧 A 已被直接观察”，也不等于可以提前 OUT；
- 真正同级的多个旧 C 仍保持歧义，不按 item id 强选。

这一层是身份逻辑的纠正，不是提高分数阈值的补丁；它必须和第 5 节 blocker 因果
计划同时存在。仅修复身份而不修复状态因果，仍可能在其他身份错误下产生无原因
REVEALED；仅修复状态因果而不修复身份，则可能得到“A 留在库存 + D IN + C 仍遮挡”的
另一种错误。

## 7. 结算实现边界和模块拆分

**代码没有必要、也不应该全部塞进同一个文件。按职责拆分会更容易验证和解耦。**
不要为了形式新建大量文件，但应把因果计划和身份计划从正式事务中分开。

### 7.1 `session_identity.cc` 或 `session_ownership.cc`

适合放：

- 跨类别重复提示的纯分数/几何判断；
- 同类 owner 证据等级和双向预约；
- `SameClassCandidateContext` 的 direct/weak/conflict 关系；
- C-D alias 完整冲突边；
- 只读身份诊断结果。

这些 helper 不直接修改正式库存、不发布事件、不写 `block_ids`。

如果新建 `session_identity.cc`，必须更新实际 Make/CMake 源文件列表、测试编译列表
和依赖；如果工程不方便新增文件，则在 `session_ownership.cc` 中保持独立区域也可。

### 7.2 `session_no_hand.cc`

适合放：

- 当前帧候选收集和两阶段 owner 选择；
- 可疑 original 的本轮排除和 reappear/path 回退；
- 只有合法身份 observation 才进入 `observed_ids` 的规则；
- 现有连续 MOVED/D/OUT 证据的推进。

不要在这里复制遮挡覆盖算法或正式事件生成。

### 7.3 `session_occlusion.cc` 或 `session_settlement.cc` 的独立区域

推荐将以下内容集中在一个遮挡职责模块中：

- `historical_block_ids` 与当前确认前景的合并/差分；
- blocker added/removed/moved 和覆盖前后比较；
- `BlockerTransitionPlan` 的生成；
- `VISIBLE -> OCCLUDED`、`OCCLUDED -> VISIBLE` 的因果门控；
- 历史关系保留、未确认 blocker 缺失的冲突处理；
- 纯几何 `fully_covered_by()`、边缘残余 helper 的调用编排。

该模块不负责分配 item id，不负责创建 D，不负责发布最终事件。若新建
`session_occlusion.cc` 不符合工程构建方式，则在 `session_settlement.cc` 中用独立
的纯 helper 区域实现，但不能把所有判断写进 `settle_no_hand_frame_()` 的一个大
条件链。

### 7.4 `session_settlement.cc`

这里负责按阶段调用身份计划、遮挡计划、OUT 计划，构造最终 `final_items` 和事件。
必须注意：

- 不能再只用 `old.status != now.status` 就生成遮挡事件；事件必须带有通过门控的
  causal plan；
- 先完成 `MOVED/IN/OUT` 的身份与最终位置确认，再重算 blocker 和遮挡状态；
- 事件要按依赖拓扑顺序排列；
- 所有 unresolved/conflict 必须在 `replace_all()` 前阻止提交；
- 正式库存、`base_box`、`block_ids` 仍只能在原有事务边界更新。

### 7.5 `session_internal.h`、`session.h` 和配置

- `BlockerTransitionPlan` 优先放在 `session_internal.h` 或实现文件私有区域；
- 不要为了当前帧计划给 `InventoryItem` 增加持久化字段；
- 只有确实跨成员函数需要保存的操作状态才改 `session.h`；
- `session_geometry.cc` 只放纯几何，不放业务因果；
- 这次因果修正原则上不需要超参数；如果身份重复判断必须新增专用参数，只能放在
  `fridge_config.h`，并同步更新《超参数位置与调节说明.md》；不能复用 OSD 显示阈值。

## 8. 事件计划的具体要求

### 8.1 不再由状态差单独生成事件

当前“旧状态 OCCLUDED + 新状态 VISIBLE = REVEALED”的状态差比较可以作为事件
候选，但必须额外满足：

```text
reveal_plan.allow_revealed_transition == true
reveal_plan.cause_kind != NONE
```

同样，`OCCLUDED` 事件必须有 `allow_occluded_transition == true` 和已确认的
front-change cause。没有原因的状态差只能记录为诊断冲突，不能提交业务事件。

### 8.2 事件依赖排序

推荐先生成带依赖的事件节点，再排序：

```text
front event:
    MOVED(A), OUT(A), IN(D)

visibility event:
    REVEALED(C), OCCLUDED(C)

dependency:
    front event -> visibility event
```

至少测试并保证：

```text
MOVED(A) before REVEALED(C)
OUT(A)   before REVEALED(C)
IN(D)    before OCCLUDED(C)
MOVED(A) before OCCLUDED(C)
```

如果同一前景事件同时影响多个 C，则先发布/记录前景事件，再按稳定但不依赖 map
顺序的方式生成多个 C 的遮挡事件。不能因为 item id 更小就让被遮挡目标先出事件。

### 8.3 当前错误案例的正确中间状态

对于最新日志，正确状态机应该允许出现这样的中间结果：

```text
橙子检测已出现，但 A 尚未完成 MOVED：
    橙子 observation 可以记录；
    但旧 OCCLUDED 状态和历史 blocker 保留；
    不生成 REVEALED；事务保持待确认。

A 的真实右侧终点通过现有连续链路确认 MOVED：
    A 进入 confirmed_moved_ids_；
    用 A 的新 base_box 重算 blocker；
    覆盖解除且橙子有合法 observation；
    依赖顺序提交 MOVED(A) -> REVEALED(B)。
```

这不是永久等待。A 的候选失败时，保护和临时 observation 必须回退到既有 OUT/D
规则；但在原因尚未确认前，不能为了尽快提交而伪造 REVEALED。

## 9. 必须新增或保留的回放

每个回放至少断言 `item_id`、状态、`base_box`、`block_ids`、事件种类/次数、事件
顺序、`pending_in_ids_`、`pending_out_ids_` 和是否提交。测试不能依赖检测数组顺序。

### 9.1 最新身份+遮挡联合案例

构造：旧苹果 A 遮挡橙子 B；A 有 HAND/reappear 移动证据；无手帧出现右侧真实 A
终点、橙子高分框和同位置低分苹果框。

断言：

- 低分苹果框不能完成 A 的 `STATIC_CONFIRMED`；
- A 保留原 item id，按既有门槛确认 MOVED；
- 橙子在 A 未确认移动的中间帧不能先 REVEALED；
- A 确认移动且覆盖解除后才产生一次 `REVEALED(B)`；
- 最终只有 `MOVED(A)` 和 `REVEALED(B)`，没有新的苹果 `IN`；
- 事件顺序为 `MOVED(A)` 在 `REVEALED(B)` 之前；
- 正式库存数量不增加，低分框不写 `base_box` 或 `block_ids`。

### 9.2 直接看到 C 但 blocker 未变化

初始 C 已正式 OCCLUDED，历史 blocker A 在本轮没有 `MOVED`、`OUT` 或其他确认
位置变化，但当前检测器又给出 C 的直接框。

断言：

- 不能仅因直接框把 C 改成 VISIBLE；
- 不产生 REVEALED；
- 历史 `block_ids` 保留；
- 该帧作为 observation/因果冲突保留，必要时 defer-commit；
- 后续 A 确认移动或 OUT 后，C 才能按正常条件 reveal。

### 9.3 VISIBLE -> OCCLUDED 的因果回放

至少覆盖：

- 旧 A 已确认 MOVED 到 C 前方并完整覆盖：产生 OCCLUDED；
- 新 D 已按原有帧数确认 IN 到 C 前方：先 IN，再 OCCLUDED；
- 只有未确认 D 或低分框重叠：不产生 OCCLUDED；
- 只有历史 `block_ids`、本轮没有 front change：不能把 VISIBLE 新改成 OCCLUDED；
- C 仍有合法直接 observation：不产生完整遮挡事件；
- blocker 移动但覆盖未完整：不产生 OCCLUDED，关系可保留为部分前景关系。

### 9.4 OCCLUDED -> REVEALED 的因果回放

- A 确认 MOVED 离开 C，且 C 直接出现：`MOVED(A)` 后 `REVEALED(C)`；
- A 确认 OUT，且 C 直接出现：`OUT(A)` 后 `REVEALED(C)`；
- 多个 blocker 中一个确认移动/OUT，覆盖并集不再完整且 C 出现：允许 REVEALED；
- blocker 移走但 C 仍未检测到：不产生 REVEALED，继续 OUT/缺失流程；
- blocker 仅当前帧漏检：不产生 REVEALED，关系保留；
- C 直接出现但没有 blocker 变化：不产生 REVEALED；
- A 仍与 C 相交但确认移动导致覆盖从完整变不完整：关系保留，允许 REVEALED。

### 9.5 历史 blocker 生命周期回放

- 无关操作中历史 blocker 仍有效：C 继续 OCCLUDED，不重复事件；
- blocker 未确认缺失：不能清关系，不能 reveal；
- blocker 正式 OUT 或确认移动到不相交处：关系移除；C 直接出现后才 reveal；
- 最后 blocker 移走但 C 未出现：不 reveal，启动既有覆盖失效/OUT 证据；
- blocker 移动到另一个仍覆盖完整的位置：C 仍 OCCLUDED，按新的关系保留。

### 9.6 身份保护和既有回归

必须保留或增加：

- 低分跨类别同框但有强移动终点；
- 真实静态低分物品与异类物品普通部分重叠但无移动证据；
- 低分框持续出现但替代移动路径失败，临时抑制最终回退；
- 真实新 D 两帧以上稳定入库；
- 单帧低分假框不 `IN`、不成为 blocker；
- HAND、CONTACT、C-D alias、正常 MOVED、正常 OUT、小位移、边缘残余和已有
  blocker 生命周期的全部回放。

## 11. 完成条件

本轮只有同时满足以下条件才算完成：

- 最新案例最终为 `MOVED(苹果 A)` + `REVEALED(橙子 B)`，没有假 `IN(苹果 D)`；
- 在 A 未确认移动前，橙子不会仅因自己的 detection 出现而提前 REVEALED；
- `VISIBLE -> OCCLUDED` 必须有确认的 front `IN/MOVED` 和完整覆盖；
- `OCCLUDED -> REVEALED` 必须有确认的 blocker 移动/OUT/覆盖解除和合法 C observation；
- 历史 blocker 在无关操作中不会被错误清空，未确认缺失不会触发 reveal；
- 事件顺序遵守 blocker/前景事件先于遮挡状态事件；
- 低分跨类别重复框只降低当前帧身份权威，不污染库存、`base_box`、`block_ids`、
  OSD 或事件；
- 替代移动路径失败时能回退到既有 OUT/D 规则，不永久 defer；
- 真实新 D、低置信度防假 IN、HAND/CONTACT、正常 OUT/MOVED、小位移和已有遮挡
  成功案例均无回归；
- 完整 replay、`-Werror`、ASAN/UBSAN、`git diff --check` 全部通过。

## 12. 核心原则

```text
先确认“这个 detection 属于谁”，再判断它能否成为前景；
先确认前景物品的 IN/MOVED/OUT 和最终位置，再重算 blocker；
遮挡状态不是由框的出现/消失直接决定，而是由 blocker 的确认变化驱动；
只有 blocker 变化导致覆盖关系变化，才允许 OCCLUDED/REVEALED；
当前代码已经实现的功能很好，修改必须是模块解耦、可测试、可回退的逻辑修正，
不能用一个只针对单条日志的分数补丁替代状态机因果约束。
```
