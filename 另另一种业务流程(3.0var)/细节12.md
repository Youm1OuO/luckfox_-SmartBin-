# 细节 12：已结算旧 C 后，消失的隔离 D 导致永久不提交的窄修复（3.0-r15 已实施）

## 0. 本文件的用途与首要约束

本文件记录本次 3.0-r15 修改的指导说明、边界和验收依据。此次只处理一个已经由实机详细日志
完全证实的收尾漏洞：一个在有手阶段创建的、与旧物品 C 形成 C-D alias 的隔离候选 D，
在手离开后没有任何独立检测证据时，当前代码会把它无限期保留为“未决”，最终让整轮
操作永远停在 `defer-commit`，不产生 `[EVENT]`，也不打印新的库存结果。

**最重要的原则：当前版本在正常入库、出库、整理、遮挡、接触、同类相邻物品等方面
已经表现很好。下一次修改必须是一个极窄的补丁，只能影响本文件明确列出的 C-D alias
终态。不得为了修复本例而放宽、重写或削弱已经成熟的主流程。**

本次目标不是“让所有未匹配候选都尽快消失”，更不是“所有同类物品都按更宽松的规则
匹配”。目标仅是：当证据已经足以说明隔离的 D 是一个过期的运行时重复解释时，正确地
清理这个假 D，使已经正确结算的旧 C 可以提交。

本次还要补齐一个直接影响排查能力的显示契约：**画面上显示的食品/手框必须与真正送入
业务状态机的检测框完全一致。** 这只统一“看见什么、状态机正在使用什么”，不等于把
业务层的低分有效证据阈值粗暴提高到当前 OSD 的显示阈值。低分但已进入业务层的框必须
显示为低置信度业务框，不能对用户隐藏。

### 0.1 r15 实施结果

`3.0-r15` 已按本文件的窄边界实现以下内容：

```text
1. 新增 alias_no_hand_missing_count；只有关联旧 C 全部已独立结算、隔离 D
   没有独立框也没有共享框的连续两张有效无手帧，才回收 runtime-only D。
2. D 被回收时只解除 alias 并删除运行时 track；不写 working_inventory_，
   不写 pending_in_ids_，不产生 IN/OUT，由原有 settlement 自然提交。
3. OSD 直接绘制 food_dets 和与 hand_boxes 同条件生成的手检测集合；每个业务
   输入框都会显示。0.50 只决定常规颜色或橙色低置信度颜色。
4. [FOOD-DETECTION] 与 [HAND-DETECTION] 会记录实际业务输入的索引、类别、分数和坐标。
5. 没有修改 .01 / .25 / .30 / .60 / 0.50 的数值，也没有修改任何 IN、OUT、MOVED、
   遮挡、CONTACT 或同类邻居的匹配与确认帧数。
```

## 1. 本次实机问题：已经确认的事实

### 1.1 操作场景

操作开始前库存有 3 个苹果：

```text
item#1：左侧苹果 A
item#3、item#4：右侧两个相邻苹果
```

用户移动了右侧靠外的一个苹果到左侧苹果附近。画面开启了镜像，因此“左/右”的口头
方向不应直接用于推断日志中的坐标方向；本次判断以日志中的状态链路为准。

### 1.2 关键日志链路

在 `讨论用/测试后的结果与发现的问题.md` 中，本次操作为 `op=20`：

```text
frame 460，HAND：
    inventory=3，但检测到 foods=4
    old item#3 与 suspect#-1 建立 C-D alias
    suspect#-1 被标记为 quarantined-pending-d

frame 466，NO_HAND：
    item#1 -> STATIC_CONFIRMED
    item#3 -> MOVED_CONFIRMED
    item#4 -> STATIC_CONFIRMED
    suspect#-1 没有匹配到独立 detection
    [C-D-ALIAS] relation=no-direct-pair action=keep-unresolved
    [SETTLE] defer-commit

frame 467 及以后：
    同一条 relation=no-direct-pair / action=keep-unresolved 重复出现
    同一条 defer-commit 重复出现
    没有 [EVENT]，没有新的库存提交
```

因此，问题不是“旧 C 没有正确完成整理判断”。日志已经明确显示旧 C 的整理结果是
`MOVED_CONFIRMED`，其余旧物品也已经稳定确认。真正阻塞提交的是 `suspect#-1`：它既
没有成为独立 D，也没有回归为与 C 共用的检测框，却没有退出未决状态。

### 1.3 重要澄清：`foods=4`、屏幕只见 3 框与 runtime D 的关系

用户确认物理冰箱中只有 3 个物品，画面中也只看见 3 个 YOLO 框。这不与以下日志矛盾：

```text
[3.0-TRACE][FRAME][op=20][frame=460][HAND] foods=4 hands=1 ...
[3.0-TRACE][C-D-ALIAS] old-item=3 suspect=-1 detection=3 ...
```

这里必须严格区分三个不同层次的“框/物品”：

| 层次 | `frame=460` 的含义 |
| --- | --- |
| 正式库存 | 操作开始前真实库存中有 3 个物品 |
| `food_detections` | 状态机入口收到 4 个经 YOLO 后处理接受的食品检测框 |
| `suspect#-1` / D | `process_frame()` 内部根据其中一个未可靠归属的框创建的运行时身份，不会生成新的 YOLO 框 |

`[FRAME] foods=4` 在 `SessionManager::process_frame()` 的入口输出，统计的是传入的
`food_detections.size()`；此时 D 尚未创建。因此它**不可能**表示“库存 3 个 + 本地 D
凑成 4 个”。`detection=3` 是从 0 开始的 detection index，进一步说明当时确有第 4 个
业务输入框。

本问题发生时 r14 的检测、NMS、业务输入和显示顺序是：

```text
YOLO 原始候选
    -- YOLO_CANDIDATE_SCORE_THRESH = 0.01 粗筛 -->
同类候选 NMS
    -- NMS_THRESH = 0.60（IoU 重叠阈值，不是分数阈值） -->
最终类别分数筛选
    -- 食品 YOLO_OBJECT_SCORE_THRESH = 0.25 --> food_dets --> process_frame()
    -- 手   YOLO_HAND_SCORE_THRESH   = 0.30 --> hand_boxes --> process_frame()
旧版 OSD 独立再筛一次
    -- OSD_OBJECT_SCORE_THRESH = 0.50 --> 才画在画面上
```

所以第 4 个食品框很可能满足 `0.25 <= score < 0.50`：它已经是 NMS 后、能够影响业务的
YOLO 输出，但因当前 OSD 的二次显示门槛而不可见。仅凭现有日志尚不能确认它的精确分数，
也不能排除用户看到的画面不是 `frame=460` 或两个框视觉上重叠；但可以确定它不是 D
在本地凭空生成的框。

这次问题因此有两层：YOLO 的短暂额外/重复候选是输入噪声；而该候选后来消失后仍让操作
永久 `defer-commit`，是状态机收尾漏洞。修复显示不一致可以让输入噪声立即可见，但不能
替代 stale alias cleanup；反过来，也不能靠把食品阈值从 `0.25` 提高到 `0.50` 来掩盖
本例，否则会丢失被手遮挡时仍有价值的低分真实证据。

### 1.4 本次问题与细节 11 的关系

这是和细节 11 同一类根因，即“手操作期间，同类旧 C 与暂定 D 可能代表同一个物理
物品，必须延迟决定身份”。但这不是细节 11 已经覆盖的两个终态之一：

| 无手阶段 C-D 关系 | 细节 11 / r14 的既有处理 | 是否是本次问题 |
| --- | --- | --- |
| C 与 D 连续共用同一个 detection | 视为重复运行时解释，D 在连续确认后丢弃 | 否 |
| C 与 D 连续拥有不同 detection | C 确认 MOVED，D 走独立 IN | 否 |
| C 已独立结算，D 没有任何自己的 detection，也没有共享 detection | 当前一直 `keep-unresolved`，永久阻塞提交 | 是 |

所以此前的思路并没有错，r15 保留 r14 的前两条修复，并补全第三种“假 D 在手离开后
消失”的终态。它是状态机收尾分支不完整的问题，不是需要重新设计入库、出库或整理规则
的问题。

## 2. 根因与必须保持的状态语义

### 2.1 根因

现有 `session.cc` 的无手收尾逻辑中，隔离 D 的处理位于约第 4478 行附近：

```text
if (D 是 is_suspect_new 且 pending_d_quarantined_by_old_c) {
    若本帧与 C 共用 detection：
        用 alias_no_hand_match_count 连续确认后丢弃重复 D；
    否则：
        alias_no_hand_match_count = 0；
        relation=no-direct-pair；
        action=keep-unresolved；
        continue；
}
```

这段逻辑正确地避免了“第一张无手帧就删掉可能真实的 D”，但它把“本帧没有共享框”
一概等同于“仍需无限等待”。当 D 根本没有独立框时，后续每张无手帧都会走相同分支，
没有任何状态可促使它被清理。

随后未确认的隔离 D 仍留在 `track_buffer_`。最终结算代码会看到它既不是已提升并确认的
入库 D，也不是可忽略的已删除运行时记录，于是持续选择 `defer-commit`。这正是日志中
“旧 C 已 `MOVED_CONFIRMED`，但没有 `[EVENT]`”的直接原因。

### 2.2 必须保持的语义

以下语义绝不能因为本次修复而变化：

```text
C-D alias：
    有手阶段的运行时身份歧义，不是正式库存物品，也不是立即可删除的噪声。

QUARANTINED_PENDING_D：
    必须继续逐帧追踪和记录；有手期间不得直接写入 working_inventory_，
    也不得被当作拥有 old C 排他权限的正式库存物品。

独立 D：
    若无手后能连续获得自己的、与相关 old C 不同的 detection，仍必须沿用现有
    staged IN / confirm-independent-d 链路，不能因本补丁而被误删。

共享框：
    若 D 与 C 在无手阶段共用同一 detection，仍必须沿用现有的连续共享框确认，
    不能在第一帧无手或第一帧丢失时直接下结论。

旧 C：
    仍由现有 strict / original / reappear / CONTACT_* / 遮挡与同类邻居仲裁逻辑
    决定 STATIC、MOVED、OUT 等结果。本补丁不能抢占或改写这些判断。
```

### 2.3 新增显示语义：看到的是状态机实际输入，不是另一套筛选结果

这里的“看到即所得”应当精确地定义为：

```text
对食品：
    某个 detection 被放进当前帧的 food_dets，状态机就能看到它；
    它也必须在当前画面上显示出来。

对手：
    某个 detection 被放进当前帧的 hand_boxes，能够使状态机进入 HAND 阶段；
    它也必须在当前画面上显示出来。

对未进入业务的原始 YOLO anchor / 被 NMS 压掉的候选：
    不要求显示。它们不是状态机实际输入，显示它们反而会制造另一层混乱。
```

画面显示的是“本帧业务有效的、NMS 后的 YOLO 输入”，不是最终库存结论。一个黄色低分框
表示“状态机正在谨慎观察这个候选”，不表示“冰箱已经多了一个物品”，也不表示已经产生
IN 事件。正式库存仍然只能由既有的多帧确认和最终 settlement 决定。

实施时必须遵守：

```text
不得为了实现看到即所得而提高 YOLO_OBJECT_SCORE_THRESH；
不得让 OSD 的 0.50 门槛继续隐藏已进入 food_dets / hand_boxes 的框；
不得把黄色低分业务框直接当作正式 D 或 IN；
不得因为低分框显示出来而改变任何 C-D alias、IN、OUT、MOVED 的确认条件。
```

推荐的视觉约定：高置信度业务框保持现有常规颜色；分数低于原 OSD 0.50、但已经进入业务
层的食品框用黄色/橙色显示，并在标签中保留 `input-index`、类别与分数，例如：

```text
#3 apple 31% [BUSINESS]
```

这样相邻或重叠的重复框不会被“看起来只有 3 个大绿框”的画面掩盖，且用户可以立即判断
`foods=4` 是一个真实业务输入事实，而非库存或 runtime D 自行膨胀。

## 3. r15 实现的唯一目标状态

为隔离 D 增加一个只服务于本终态的运行时计数，例如：

```cpp
int alias_no_hand_missing_count = 0;
```

它的含义必须非常精确：

```text
在有效的直接无手帧中：
    该 D 仍是 QUARANTINED_PENDING_D；
    与它冲突的所有 operation-start old C 都已通过既有主流程独立结算；
    D 没有自己的独立 detection；
    D 也没有与任一关联 C 共用 detection；
上述条件连续成立的帧数。
```

这个字段不能复用普通旧 C 的 `no_hand_missing_count`，也不能改变它的含义。普通旧 C
的缺失计数用于 OUT / 遮挡等已有流程；本字段只描述“已结算 C 后的隔离 alias D 没有
直接无手证据”。两者混用会把本次修复扩散到出库和遮挡逻辑，是不允许的。

### 3.1 触发条件：必须全部满足

仅当以下条件在同一帧全部满足时，才允许增加 `alias_no_hand_missing_count`：

1. 当前处于有效的直接无手处理帧，且本帧没有手；不是有手帧、过渡帧或未完成正常
   无手匹配的中间状态。
2. 当前 track 是 `is_suspect_new == true` 且
   `pending_d_quarantined_by_old_c == true` 的 D。
3. 该 D 确实仍有至少一个 `conflicting_old_item_ids`，即它是明确的 C-D alias，
   不是普通 pending D。
4. 关联的**所有** operation-start old C 都已经走完它们原有的无手判断，并且已经
   独立结算为最终结果。这里的“已结算”至少应表示：

   ```text
   旧 C 的 resolution 已是现有最终确认状态（例如 STATIC_CONFIRMED 或 MOVED_CONFIRMED）；
   旧 C 不再 needs_settle；
   旧 C 不再等待 reappear / CONTACT / alias 共享框的后续仲裁；
   旧 C 的本次结论来自自己的既有无手证据链，而不是靠 D 的未决状态强行放行。
   ```

5. D 本帧没有通过现有匹配链路取得自己的独立 `no_hand_detection_index`。
6. D 本帧没有和关联 old C 共享 detection，即
   `alias_no_hand_matched_this_frame == false`，且没有出现现有代码已经识别出的
   `shared-detection` 关系。
7. 本帧没有任何能证明 D 是独立真实物品的新直接证据。若存在符合 D 位置/类别的独立
   候选，但当前仲裁尚未完成，应继续原有 `keep-unresolved`，不得把“尚未仲裁完”误作
   “D 消失”。

只有连续满足以上 7 条、计数达到既有
`FLOW3_NO_HAND_D_CONFIRM_FRAMES`（当前为 2）时，才执行 stale alias cleanup。

### 3.2 达到阈值后的唯一动作

达到阈值时，行为必须是“丢弃过期的运行时 alias D”，不是确认一次 OUT，也不是确认
一次 IN：

```text
1. 用既有 unlink 逻辑解除 D <-> old C 的双向 alias 关系；
2. 将该 D 的 runtime key 放入现有安全的 discard / erase 路径；
3. 不把 D 写入 working_inventory_；
4. 不把 D 写入 pending_in_ids_；
5. 不产生 D 的 IN 事件；
6. 不对任何 old C 产生 OUT；
7. 保留已经由原逻辑确认的 old C 结果，例如 C 的 MOVED_CONFIRMED；
8. 在 D 被清理后，让既有 settlement 逻辑自然提交本轮操作。
```

不应直接在中途手写库存提交、手写 `[EVENT]`，也不应在此补丁中重算任何旧物品的位置。
正确方式是只移除已经证实为过期的未决运行时障碍，再由原有、已验证的收尾代码完成
提交。

### 3.3 计数必须重置的情况

以下任一情况发生时，`alias_no_hand_missing_count` 必须清零：

```text
1. 手重新出现；
2. D 获得独立的无手 detection；
3. D 与关联 C 共享 detection；
4. 任何关联 old C 重新进入未结算、等待 reappear、CONTACT、遮挡或 alias 仲裁的状态；
5. alias 关系解除；
6. D 的 runtime track 被删除；
7. 当前帧不是有效直接无手帧。
```

这个重置规则很重要。它保证“连续 2 帧无直接证据”是同一种稳定终态的证据，而不是把
两段被手打断、被共享框打断或被新证据打断的短暂缺失拼在一起。

## 4. 推荐的实现位置和顺序

### 4.0 `src/main.cc`：让 OSD 与业务输入同源

在 r14 中，`main.cc` 先从 `detections` 构建 `food_dets` / `hand_boxes`，但绘图又重新遍历
`detections` 并用旧的 `OSD_OBJECT_SCORE_THRESH = 0.50` 二次过滤。这是“业务有 4 框、屏幕
只见 3 框”的直接原因。r15 已移除这道显示过滤。

r15 将食品和手的绘制来源改成与业务完全同源的集合：

```text
食品框：直接遍历当帧将要传给 process_frame() 的 food_dets；
手框：直接遍历当帧将要传给 process_frame() 的 hand_dets_for_display / hand_boxes；
标签：输出 input-index、类别、score，并用颜色区分高分和低分业务有效框；
```

不要仅靠“把旧的 `OSD_OBJECT_SCORE_THRESH` 从 0.50 改成 0.25”实现这一点。数值相等虽然在
当前配置下大概率有效，但未来单独调整食品或手阈值后会再次悄悄分叉。显示代码应复用
`food_dets`、`hand_boxes` 或与它们完全相同的判定谓词；r15 的
`OSD_LOW_CONFIDENCE_OBJECT_SCORE_THRESH` 只作为低分颜色分界线，不得再作为食品/手业务输入
的第二道隐藏过滤。

这个显示改动只影响 OSD 和调试可观察性，不能改变 `food_dets`、`hand_boxes` 的构造内容，
更不能改变它们送入 `process_frame()` 的先后顺序或阈值。

### 4.1 数据结构

在 `include/session.h` 的 `OperationTrack` 中，紧挨现有 C-D alias 字段增加：

```cpp
int alias_no_hand_missing_count = 0;
```

现有字段的职责应保持如下：

```text
alias_no_hand_match_count：
    C-D 在无手阶段有共享框，或双方有独立框时的已有连续直接证据计数。

alias_no_hand_matched_this_frame：
    本帧是否已经出现 alias 的直接匹配/共享关系。

alias_no_hand_missing_count：
    本文件新增；所有旧 C 已独立结算后，D 连续没有任何直接无手证据的计数。
```

在 `unlink_quarantined_suspect_` 等统一解除 alias 的位置，把新增计数清零；不要只在某个
单独分支清零，以免运行时 track 被复用时带入陈旧状态。

### 4.2 无手收尾位置

修改应放在 `src/session.cc` 当前处理
`is_suspect_new && pending_d_quarantined_by_old_c` 的无手分支附近（当前约第 4478 行）。
但判断时机必须在下列工作都已完成之后：

```text
1. 本帧普通 old C 的 strict/original/reappear/contact/遮挡判断；
2. 现有 C-D shared-detection 仲裁；
3. 现有 C-D distinct-detections 仲裁；
4. 对相关 old C 的最终 resolution、needs_settle 和 detection 归属更新。
```

原因是新分支必须知道“所有关联 old C 是否真的已经独立结算”。如果过早检查，可能把
仍在等待第二帧的真实 D 或仍未确认的 C 当作 stale alias 清理，从而破坏已有的保护。

建议提取一个语义清楚的小帮助函数，而不是在循环中堆叠难以审查的条件，例如：

```cpp
bool all_conflicting_old_c_independently_settled_for_stale_alias_cleanup(
    const OperationTrack& suspect,
    const std::map<int, OperationTrack>& tracks);
```

该帮助函数只读取本轮 operation-start old C 的状态，不改变任何匹配结果。它必须对找不
到关联 old C、关联 C 仍未结算、关联 C 已被错误/异常移除等情况返回 `false`，即继续等
待而不是贸然清理。

### 4.3 推荐伪代码

下面是状态边界，代码可按现有风格实现，但语义不得扩大：

```cpp
if (is_quarantined_c_d_alias_d(track)) {
    if (d_has_shared_or_independent_direct_no_hand_evidence(track)) {
        track.alias_no_hand_missing_count = 0;
        // 完全沿用既有 shared / distinct 处理；不在这里删除 D。
    } else if (all_conflicting_old_c_independently_settled_for_stale_alias_cleanup(
                   track, track_buffer_)) {
        ++track.alias_no_hand_missing_count;
        if (track.alias_no_hand_missing_count >= FLOW3_NO_HAND_D_CONFIRM_FRAMES) {
            // 只标记 discard；在既有统一 erase 位置 unlink 并删除 runtime D。
            discard_keys.insert(runtime_key);
        }
    } else {
        track.alias_no_hand_missing_count = 0;
        // 继续现有 keep-unresolved；绝不改变普通 pending D 的行为。
    }
}
```

伪代码中的 `d_has_shared_or_independent_direct_no_hand_evidence` 不能仅用“同类检测总数
大于零”实现。它必须使用当前已有的匹配和 detection 归属结果，防止把属于其他静止旧
物品的同类框误认为 D 的证据，或反过来把尚未仲裁的独立 D 当作不存在。

### 4.4 版本与超参数

本次是状态机收尾完整性修复，不是几何阈值问题。默认要求：

```text
不新增数值超参数；
不调整 FLOW3_TRACK_*；
不调整 FLOW3_REAPPEAR_CANDIDATE_*；
不调整 FLOW3_NO_HAND_*、IN、OUT、MOVED 的确认帧数；
不通过放宽距离、IoU 或同类匹配阈值让本例通过。
```

直接复用已有 `FLOW3_NO_HAND_D_CONFIRM_FRAMES`（当前为 2），但不能修改其全局语义。
本分支只是把它作为“隔离 alias D 的连续无直接证据确认帧数”，与既有 D 连续直接证据
确认使用相同的保守时长。

本轮没有调整上述数值，并已更新 `超参数位置与调节说明.txt`：补充 `.01/.25/.30/.50`
与 NMS `.60` 的职责、旧显示/业务不一致的原因，以及“OSD 要从业务输入集合绘制”的
固定实现规则。旧的 `OSD_OBJECT_SCORE_THRESH` 已更名为
`OSD_LOW_CONFIDENCE_OBJECT_SCORE_THRESH`，只保留 0.50 的低分颜色分界职责，不能过滤业务
有效食品/手框。

## 5. 严格的不可退化边界

下一次修改前和代码评审时，必须逐项确认以下限制：

```text
1. 不得放宽 FLOW3_TRACK_*、strict match、partial match、reappear 或同类邻居的
   几何范围。

2. 不得降低 IN、OUT、MOVED、共享 C-D alias 或独立 C-D alias 的确认帧数。

   QUARANTINED_PENDING_D + C_D_ALIAS + 所有关联 old C 已独立结算 + D 连续无直接

4. 不得改变普通独立 D 的 staged IN 链路，也不得让一个真正有独立 detection 的 D
   因本分支失去 IN。

5. 不得改变细节 9 的“同类数量不足时 OUT”保护，以及细节 10 的“静止同类邻居
   fallback”保护。

6. 不得改变 CONTACT_CANDIDATE、HAND_CONTACT、POSSIBLE_MOVED、
   POSSIBLE_OCCLUDED、遮挡恢复、无手收尾、普通整理的既有时序。

7. 不得因为本次逻辑删除、放松或绕过既有回放断言；旧测试失败时，不可用一次实机
   偶然成功替代回归验证。

8. 不得根据本次日志中 item#3 / item#4 与用户口头 B/C 的可能对应关系，盲目改动
   相邻同类旧物品的主匹配流程。镜像画面与物理命名无法仅凭当前日志绝对映射；本轮
   先只修复已经完全证实的“stale alias 永久阻塞提交”。
```

如果实现发现需要修改上述任一主流程，说明补丁范围已经超出本文件目标，应先停止并重新
分析，而不是把风险扩散到现有可用功能。

## 6. 日志要求

`FLOW3_DEBUG_TRACE_LOG = true` 时，新增分支必须输出足以判断“为什么等、为什么丢弃”
的日志。建议统一使用现有 `[C-D-ALIAS]` 标签：

```text
[C-D-ALIAS]
old-item=<关联 C id 或列表>
suspect=<runtime key>
phase=NO_HAND
relation=no-direct-pair
all-conflicting-old-settled=<0/1>
old-settlement=<id:resolution:needs_settle,...>
independent-detection=<index 或 -1>
```

达到阈值并删除时，必须另有一条明确日志，至少说明：

```text
suspect=<runtime key>

working-inventory-write=0
pending-in-write=0
event=none
```

在最终 `[SETTLE]` 日志中，应能看出阻塞项已经移除并进入正常提交，而不是用一个特殊的

```text
[3.0-TRACE][FOOD-DETECTION]
input-index=<0-based index in food_dets>

score=<0.xx>
box=(x1,y1,x2,y2)
business-input=1
osd-business-visible=1
```

若本帧出现手，也应输出等价的手输入信息，或在 FRAME 日志中给出每个 `hand_boxes` 的分数
和坐标。日志中的 `osd-business-visible=1` 是新的显示契约，不是把 OSD 可见性反过来作为
业务判断条件。这样下次出现 `foods=4`、而物理上只有 3 个物品时，可以立刻确认额外框的
类别、分数、位置和是否与其它框重叠。

### 7.0 显示/业务一致性的实现验收

OSD 绘制在 `main.cc`，不适合仅靠 `SessionManager` 的纯回放断言验证，因此必须同时做以下
两类验收：

```text

    food_dets 和 hand_boxes 仍以原有方式、原有顺序送入 process_frame()。

    它消失后，画面和下一帧 food_dets 都不再包含它。
```

这项验收只证明“看见的业务输入与实际一致”，不能代替本节后续的 stale alias 状态机回放。

### 7.1 测试场景

```text

    至少两个相邻的同类 operation-start old C；
```

### 7.2 必须断言的结果


针对本次实机问题，预期日志应类似：

```text
第 1 张有效无手帧：
    item#1 -> STATIC_CONFIRMED

    suspect=-1 -> relation=no-direct-pair
    all-conflicting-old-settled=1

    action=discard-stale-alias-after-settled-old-c-no-hand-missing
    runtime D 被 unlink 并删除，无 IN、无 OUT
    [SETTLE] 正常 commit
    [EVENT] 正常输出整理结果与库存表
```

而下面两类既有正确行为必须继续保持：

```text
共享框终态：
    D 与 C 连续共用一个无手 detection
    -> 仍按现有 alias_no_hand_match_count 判断
    -> D 作为重复解释被丢弃，C 正常结算。

独立框终态：
    D 有自己的连续独立 detection，C 也有自己的 detection
    -> C MOVED，D IN，正常提交。
```

最终验收不是“某一次实机不再卡住”这么简单。必须同时证明：

```text
本次 stale alias 不再无限 defer-commit；
新的删除条件不会误删真实独立 D；
旧 C、静止同类邻居的身份和结果保持正确；
原先已稳定的入库、出库、整理、遮挡、CONTACT_* 与同类相邻回放全部不退化；
从手接触到提交的每一个关键状态都能在详细日志中追溯。
```

还必须满足新的可观察性验收：任意一帧中，画面上所有食品/手业务输入框与当帧
`food_dets` / `hand_boxes` 一一对应；不再出现“日志 `foods=4`，但 OSD 因独立 0.50
过滤只显示 3 框”的情况。

只有这些条件同时满足，才可以认为本次修复完成。
