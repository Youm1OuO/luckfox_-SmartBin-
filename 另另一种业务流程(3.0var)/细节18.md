# 细节18：3.0-r19 遮挡生命周期与同类移动归属实施指导

## 0. 文档用途

本文件是下一轮实现遮挡优化前的固定指导说明。它把《遮挡优化.md》以及
《讨论用/思路.md》中已经确认的业务思路整理成代码实施边界，重点处理两个问题：

```text
1. 上一轮操作已经确认的 blocker，在下一轮操作中被错误清空；
2. 同类物品移动后身份没有完成确认，临时 D 不能安全参与正式遮挡提交。
```

最新实机回放已经把第 2 项进一步定位到一个确定的前置缺口：同类候选检测框被
创建为 C-D alias 时，当前 alias 关系只收集了“已经拥有另一检测框”的部分旧 C，
漏掉了“没有直接框、但路径上可合理属于该候选”的旧 A。于是临时 D 会先获得
排他语义，再反过来阻止真正的旧 A 认领自己的最终框。本文件必须先修复这个
身份关系完整性，再让任何确认的 A 参与 blocker 重算。

本文件不是重写 3.0 状态机的方案。实现时必须先写最小失败回放，再做最小生产
代码修改，并在每一步保留完整既有回放和相称的构建、ASAN/UBSAN 验证。

## 1. 最重要的保护声明

当前代码已经实现并验证了大量正确功能，不能因为本次优化遮挡而改坏原有行为。
当前实现不是需要推倒重来的代码，遮挡优化应建立在现有状态机和事务边界之上。

以下能力必须原样保留，除非后续有单独的设计文件和回放证明需要修改：

- 门状态和关门行为：关门阶段不进入 YOLO、Track、快照、Session 结算或业务图片保存；
- 正式库存与 `working_inventory_` 的隔离；手操作期间不能提前写正式库存；
- 无手结算成功后才用 `replace_all()` 原子替换正式库存；
- `NORMAL`、`HAND_PARTIAL_BLOCKED`、`HAND_FULL_BLOCKED`、`CONTACT_*` 的状态语义；
- 旧 C 的严格原位所有权优先级、局部连续匹配、灰区静态恢复和 reappear 证据；
- `D` 的连续无手确认、`C-D alias` 隔离、quarantine 和“无 D 证据不自动 IN”；
- 已有 `C-D alias` 与真实新 D 的防误入库能力；本轮只能补全 alias 的候选旧 C
  关系，不能删除 alias、把临时 D 当正式 owner，或降低 D 的确认帧数；
- 正常的 `MOVED` 确认条件、`confirmed_moved_ids_` 语义和正常 `MOVED` 事件；
- 原有两帧无手 OUT 证据，不因遮挡优化降低确认帧数或放宽 OUT 门槛；
- YOLO 输入、类别阈值、NMS、手阈值以及 `fridge_config.h` 中已有参数；
- 事件的事务边界：`IN`、`OUT`、`MOVED`、`OCCLUDED`、`REVEALED` 只能在正式
  结算提交时产生，不能在手阶段或临时 D 阶段提前产生；
- 已有的矩形覆盖并集实现。`fully_covered_by()` 已经按矩形差集计算多个框的
  覆盖并集，不能重新写成简单的交集面积相加。

本轮只处理 blocker 关系生命周期、遮挡与 OUT 的排除关系，以及为当前实机案例
增加一个严格的同类残余归属出口。不得借机重写全局身份仲裁或调参。

## 2. 当前业务模型和术语

### 2.1 工作库存和正式库存

`inventory_` 是正式库存。手操作期间的所有修改只能进入：

```text
working_inventory_
operation_start_inventory_
track_buffer_
pending_in_ids_
pending_out_ids_
confirmed_moved_ids_
```

无手帧结算函数中的 `final_items` 是工作库存本轮的提交候选，它虽然是局部副本，
但遮挡重算必须在它上面进行，不能直接修改正式 `inventory_`。

### 2.2 `base_box` 和 `box`

- `box` 是最近一次确认看到的框，可以是局部框；
- `base_box` 是初次入库或已确认整理后的可靠完整位置；
- 遮挡目标和遮挡物的几何计算统一使用最终可靠的 `base_box`；
- 只有本轮已经确认 `IN` 或 `MOVED` 的物品，才能用本轮最终直接无手框刷新
  它的 `base_box`；临时手框、局部框和未确认 D 不能成为持久几何依据。

### 2.3 `block_ids` 的方向和含义

如果库存物品 C 的状态是：

```text
C.block_ids = { A, E }
```

含义是：A、E 是已经确认位于 C 前方的物品，当前遮挡关系中它们参与解释
C 的不可见。关系写在被遮挡目标 C 上，不写在移动物品 A 上。

按照《讨论用/思路.md》的业务前提：一个物品新进入库存，或一个旧物品已经
确认移动到新的最终位置时，在与旧物品发生重叠的区域中，按本业务规则把它
视为前景物品。这个前后顺序来自用户的操作语义，不是单靠二维框交集推导出的
物理深度，因此只有在 A 的身份和最终位置确认后才能使用。

`block_ids` 是前景关系集合，不等于状态枚举：

```text
block_ids 非空不必然表示 C 完全不可见；
只有 block_ids 对应框的覆盖并集完整覆盖 C.base_box，C 才能是 OCCLUDED。
```

本轮固定采用以下存储语义：只要 A 已经根据本轮操作顺序确认位于 C 前方，且
A 的 `base_box` 与 C 的 `base_box` 仍有正面积交集，就保留 A 与 C 的
`block_ids` 关系；但部分关系只是“前景关系”，不能单独代表 C 完全不可见。
`OCCLUDED` 的判断必须始终由全部关系的覆盖并集决定，不能由“有一个交集”决定。

## 3. 两层问题必须分开处理

### 3.1 第一层：同类物品身份归属

遮挡模块不能把一个尚未确认身份的 D 直接变成 blocker。当前实机日志中的顺序是：

```text
item=3（橙子）已经得到 OCCLUDED_CONFIRMED；
item=5（旧苹果）仍为 no-hand-path-ambiguous；
候选苹果被提升为临时 item=6；
pending-d=6 因 unresolved-old=5 而阻止 commit。
```

这不是应该通过“放宽 D 防线”解决的问题。若直接把 item=6 当作 item=5，可能
把“旧苹果出库 + 新苹果入库”错误地写成一次 MOVED，造成正式库存身份污染。

遮挡结论不能反向证明物品身份，不能形成循环证据：

```text
因为 A 覆盖 C，所以认为 A 是旧 item；
因为 A 是旧 item，再反过来证明 C 被 A 覆盖。
```

### 3.2 第二层：遮挡关系和状态结算

只有第一层完成后，才允许使用：

```text
pending_in_ids_ 中已满足既有 D 确认条件的物品；
confirmed_moved_ids_ 中已经满足既有 MOVED 条件的物品；
上一轮已经提交并保存的历史 block_ids。
```

这些物品才可以参加 blocker 关系重算。遮挡模块本身不负责给未决 D 分配正式
item_id，也不负责改变普通 MOVED 的确认门槛。

特别地：一个只靠自身连续帧刚进入 `pending_in_ids_`、但其 candidate-context 中仍有
未决旧 A 的 D，不是本节所说的“已满足身份条件的 D”。它不能成为 `new_fronts`、
不能让任何 C 得到正式 `OCCLUDED`，也不能以 blocker 身份影响 OUT 计数。必须先由
第 4 节完成 A/D 仲裁；本次实机中的临时 `item=6` 正是这一条要防止的对象。

### 3.3 叠放后的局部框认领：猜想部分成立，但不能全局放宽

本次测试暴露出的另一个真实风险是：原来不允许物品重叠时，旧 C 的可见框通常
接近完整框；开始叠放后，前景 A 可能只遮住 C 的一部分，检测器给 C 的框会变小，
这个小框可能不再满足旧 `base_box` 的严格原位匹配。于是“原位置没匹配 + 当前有
一个未认领同类框”确实可能让绑定变得困难，并最终让无手结算保持未决。

但“正常物品只进行严格匹配”并不是当前代码的完整事实。当前无手绑定大致是：

```text
已确认移动/轨迹终点
-> 普通严格匹配
-> 动态轨迹匹配
-> 原位置严格匹配
-> 原位置局部匹配
-> 普通局部匹配
```

`bind_mutually_unique()` 的局部阶段已经使用 `partial_match_box()`，现有阈值为
`INVENTORY_PARTIAL_IOM`。因此这次 `item=5` 没有归属，不能简单归因于“普通物品
没有局部匹配”；实机日志已经进一步确认，直接根因是第 3.4 节的 alias 冲突关系
漏掉了 `item=5`，使临时 D 先获得该候选框的排他语义。局部框问题是叠放场景新增的
独立风险，需要补上，但不能用它替代同类身份仲裁。

为此增加一个很窄的“遮挡感知静态局部认领”阶段。它的作用只是把被已确认前景
物品部分遮挡后变小的旧静态 C 认领回来，不是把所有普通物品改成宽松匹配：

1. C 必须是操作开始时的旧库存，且没有已确认 `MOVED`、未解决的 HAND/CONTACT
   动态路径或待处理 D 身份；动态物品继续走现有轨迹和严格移动规则。
2. C 必须有遮挡上下文：上一轮保存的 `block_ids` 中至少有一个仍有效的 blocker，
   或本轮已经确认 `IN`/`MOVED` 的前景物品与 C 的可靠 `base_box` 有正面积交集。
   没有这个上下文时，不能因为同类框“看起来像局部框”就启用该阶段。
3. 只对同类别、满足现有 `partial_match_box()` 的候选做绑定；item 和 detection
   两侧都必须唯一。候选不能是已经被确认移动物品、确认 D 或其他更高优先级 owner
   保留的检测框。
4. 绑定只恢复 C 的身份和当前 `box`，不能创建 `IN`、`MOVED`、新的 blocker，也
   不能用不完整的小框覆盖 C 的 `base_box`。C 直接重新出现时按现有事件边界从
   `OCCLUDED` 变为 `VISIBLE`，由正式结算产生一次 `REVEALED`。
5. 任何一侧存在第二个合理候选、同类残余仍未唯一、遮挡 blocker 尚未确认身份，
   或局部框无法通过现有几何条件时，都保持未决，继续使用现有 C-D alias、D 确认和
   OUT 保护，不用“先认一个再说”。

这个阶段应放在已确认移动/轨迹和原位置严格绑定之后、现有普通局部回退之前，或
收敛为一个等价的独立预约阶段；它必须保持双向唯一性和现有 owner 优先级。不能
把普通局部匹配整体移到所有严格匹配之前。

这里的“阶段”不要求新建第二套匹配器。当前已经存在的“原位置局部匹配”应优先
复用：把遮挡上下文和 owner 保护作为它的输入过滤，或在同一个预约位置实现受限
子集；只有现有接口无法表达这些条件时，才增加一个独立 helper，且不能让同一
item/detection 被两个局部阶段重复预约。

因此，下面两种直觉方案都不能直接采用：

- **方法 1（全局局部优先）**：会让旧 C 先抢走移动 A 的终点框、手带出的 D，或在
  同类重叠时把真实 MOVED 误判成静态；它还可能让真实新 D 无法入库。
- **方法 2（卡住后统一放宽）**：`卡住` 是结算结果而不是稳定业务状态，放宽后会
  改变 owner、D 和 OUT 的后续输入，结果容易依赖帧数、检测顺序或遍历顺序。

正确原则是：先按现有顺序完成身份预约，再只对“有已确认遮挡证据的旧静态 C”做
受限局部恢复；若仍有多个同类 owner，回到第 4 节的残余唯一归属，而不是靠遮挡
结论或全局局部匹配强行收尾。

### 3.4 当前实机案例的确定根因：C-D alias 漏掉真正移动的旧 A

这一节不是假设，是由当前测试日志和现有代码共同确认的因果链。以该轮操作为例：

```text
无手 frame=336：
  detection=0 -> item=1 的原位置直接认领成功；
  detection=2 -> item=4 的原位置直接认领成功；
  detection=1 -> 物理上是移动 A 的最终苹果框，但代码中先是 suspect=-1；
  item=5   -> 没有得到 detection=1，状态为 no-hand-path-ambiguous；
  suspect=-1 -> 在现有连续帧规则下，只对已记录的 item=1 关系完成独立性检查，
                随后提升为临时 item=6。
```

因此，`item=1` 和 `item=4` 已经各自认领自己的框；它们不是在无手帧继续抢走
`detection=1` 的原因。真正的区别是：一个检测框即使还没有被旧库存放入普通
`claimed` 集合，也可能已被临时 D runtime 在“身份语义”上占住。对 `item=5` 来说，
这个框不再是可直接认领的剩余框。

当前有手阶段创建 C-D alias 的窄分支存在以下结构性缺口：

```text
candidate d
-> 只把“已经拥有另一 detection”的活动旧 C 写进 alias_old_item_ids
-> alias_old_item_ids 非空后立刻创建 suspect D 并 continue
-> 没有直接 detection、但其 reappear/path 可到达 d 的旧 A 不会再进入后续检查
-> D 的 conflicting_old_item_ids 缺少 A
```

本次日志的 `old-item=1 ... conflicting-old-count=1` 正是这个缺口的证据：`item=5`
仍是 HAND_FULL_BLOCKED、需要无手结算且其候选路径可到达最终框，却没有被写入该
D 的冲突旧物品集合。

随后无手阶段发生两件事：

1. 临时 D 只需要证明自己与它记录的 `item=1` 检测不同，就会被当作
   `confirm-independent-d` 并提升为 `item=6`；它没有被要求同时排除遗漏的
   `item=5`。
2. `item=5` 的无手 reappear 匹配会跳过“属于另一条 suspect/pending D”的候选。
   例外只适用于该 D 的 `conflicting_old_item_ids` 已经包含 `item=5` 的情况。由于
   关系漏边，例外不生效；后续的歧义检查又把 PENDING_D 视为继续等待的证据，最终
   得到 `no-hand-path-ambiguous`。

这说明当前卡死的根因是**同类候选的 alias 冲突图不完整**，不是“B/C 没有匹配”、
不是正常物品完全没有局部匹配，也不是应该降低 D 防线。临时 D 的存在只能表示
“当前候选尚待仲裁”，绝不能使一个未被纳入 alias 的、可合理拥有该候选的旧 A
失去认领资格。

## 4. 第一层的安全收尾：完整候选冲突图与同类残余唯一归属

当前实机案例需要一个独立于遮挡的旧物品归属出口。这个出口不能只是最后发现
`pending-d` 与 `unresolved-old` 后再猜一次；它必须在 C-D alias 创建和 D 提升前，
先完整描述“这一个同类检测框可能是谁”。否则临时 D 会先成为排他 owner，后面的
唯一残余规则已经没有机会看到真正的候选框。

### 4.1 先建立候选框到全部可行旧 C 的冲突图

对每个尚未被高优先级直接 owner 占用的同类检测框 d，先建立一份仅存在于当前事务
内的候选上下文。它至少包含：

```text
direct_old_owners
  当前帧已由双方唯一、严格原位置或现有更高优先级规则直接认领的旧 C；

viable_unresolved_old_ids
  操作开始时的旧 C，当前仍活动/未决，且 d 能通过现有 reappear、track、CONTACT
  或其他已验证的路径规则合理属于它；

matching_suspect_d_ids
  当前同类别、几何上也能命中 d 的 suspect D / pending D runtime。
```

`viable_unresolved_old_ids` 的收集必须在创建新的 D 之前完成，且不能因为某一个
旧 C 已经拥有另一 detection 就停止遍历。反过来也不能把所有同类旧物品无条件塞进
集合：只有仍未决并且 d 确实通过现有路径/几何证据可属于它的旧 C 才能进入。这样
既不会让真实新 D 永久被所有同类库存阻塞，也不会再漏掉像 `item=5` 这样的无直接框
移动旧 A。

同一帧的决策顺序固定为：

```text
1. 保留现有严格、原位置和高优先级直接 owner 预约；
2. 对每个剩余同类 d，收集全部 viable_unresolved_old_ids；
3. 在完整集合基础上决定“旧 A 候选 / 多旧 C 歧义 / 独立 D”，而不是先建 D；
4. 只有身份关系稳定后，才允许该 d 进入后续 D 自匹配、MOVED 或遮挡流程。
```

决策规则如下：

1. `viable_unresolved_old_ids` 恰好为一个 A，且同类别其他操作开始旧 C 都已有
   独立直接 owner 或已是正式终态：优先把 d 预约为 A 的 reappear/移动候选。即使
   d 此前已经有临时 suspect D，也必须先将 D 回收为 A 的候选关系，禁止 D 先提升。
2. `viable_unresolved_old_ids` 有两个或以上：d 是真实同类歧义。把**全部**可行旧 C
   写入关系图，保持未决；不能创建排他 D、不能确认 MOVED、不能把任意一个旧 C
   计为 OUT。
3. `viable_unresolved_old_ids` 为空，且所有同类旧 C 都有独立直接 owner、正式终态
   或已被可靠遮挡解释：才允许按现有 D 规则创建或继续确认真正的新 D。

这里的关系图不是新的正式库存数据结构。第一步可复用/补全
`OperationTrack::conflicting_old_item_ids`，或新增仅供本轮仲裁的私有上下文；重点是
关系必须对每个 candidate 完整，不能再由“某个 C 恰好有另一个 owner”决定集合是否
存在。

### 4.2 临时 D 不能排除遗漏的旧 A

以下不变量必须在有手和无手阶段都成立：

```text
若 pending/suspect D 的当前检测 d 仍可合理属于一个未决旧 A，
则 A 必须已经在该 D 的冲突关系中，或 d 必须先被预约给 A；
不存在“D 不认识 A，但 D 可以阻止 A 认领 d”的状态。
```

因此：

- 创建 alias 后不能因为关系集合非空就直接 `continue`，而跳过同一帧尚未拥有直接框
  的活动旧 A；必须先完成该 candidate 的全量旧 C 收集。
- 既有 pending D 若在后续帧才显露出可属于旧 A 的路径，也要在调用“D 是否占用该框”
  之前补上 A 的冲突边，或降回未决 alias；不能简单把 d 从 A 的候选列表排除。
- D 的“独立”确认不能只证明它与 `conflicting_old_item_ids` 的一个子集检测不同；
  必须证明所有同类未决旧 C 都已被独立直接认领、正式结束，或不可能拥有 d。
- 只有完整关系图已经没有未决旧 A 时，D 才能变成可提升的 `pending_in_ids_` 成员。
  在此之前它只是证据 runtime，不是 A 的排他 owner，也不能成为正式 blocker。

这不是放松 C-D alias，而是使 alias 覆盖完整。已有“同一检测被 C 与 D 共享时等待
第二张无手帧、确认重复后回收 D”的逻辑必须保留；修复后它会正确地覆盖真正的旧 A，
而不是只覆盖错误选中的旧 C。

### 4.3 严格的同类残余唯一归属

完成第 4.1 节的关系图后，才允许把一个同类无手检测 d 回收到唯一旧物品 A。这里的
“未绑定”指尚无**已确认排他身份**，而不是“尚未存在 suspect/pending D runtime”。
一个临时 D 不能单独使 d 失去作为 A 残余候选的资格。

只有同时满足以下条件，才允许回收：

1. A 是本轮操作开始时的旧库存物品，且本轮确实有 HAND_*、有效手移动、
   reappear 或其他已有的移动证据；
2. 同类别的其他旧物品已经由连续、独立、严格的直接框完成归属，不能只是局部或
   路径猜测；
3. 同类别中恰好只剩一个未解决的旧物品 A，且候选图中 d 对 A 是唯一可行候选；
4. d 不能同时合理匹配另一未解决旧 C；若有第二个可行旧 C，回到第 4.1 节保持
   多方 alias/未决，不强行映射；
5. d 与手操作有直接关联，并已沿现有无手连续规则稳定出现；连续确认帧数仍使用
   `FLOW3_NO_HAND_D_CONFIRM_FRAMES`，不得降低；
6. 不存在第二个独立同类 D 候选，也不存在业务允许而视觉上不可区分的“旧同类 OUT
   与新同类 IN 同时发生”场景。后者一旦允许，单摄像头框和类别信息无法可靠区分，
   必须继续未决。

满足条件时，固定走以下路径：

```text
候选 d 预约给旧 A
-> 复用 A 的 reappear / 两帧无手自匹配证据
-> confirm_rearrange_()
-> confirmed_moved_ids_
-> 正常 MOVED 结算
-> 撤销、合并或回收仅代表同一物体的临时 D
-> 不生成 IN
```

不满足任意一项时，保持现有 C-D alias / D 防线和 `defer-commit` 行为。安全地等待
更多证据，比把一个新 D 错写成旧 MOVED 更重要。

候选图和残余归属 helper 应放在现有无手/所有权处理边界中，不能塞进遮挡几何函数，
也不能让遮挡关系参与它的身份判断。

## 5. 第二层的遮挡重算规则

遮挡关系不能在 HAND 阶段按每个临时框即时写入，也不建议把一次 MOVED 机械地
拆成“先执行一次 OUT 删除关系，再执行一次 IN 增加关系”。正确的代码边界是：

```text
先完成本帧所有物品的身份、最终 box、pending IN / MOVED / OUT；
再对 final_items 中的所有目标统一重算 blocker 关系；
最后运行既有无手未决判断并决定是否提交。
```

### 5.1 生成 blocker 候选

对于每一个目标物品 C，候选 blocker 由两部分组成：

```text
historical_blockers = C 上一轮已经确认并保存的 block_ids；
new_fronts = 本轮已确认 IN / MOVED、当前无手帧直接出现的物品。
```

过滤规则：

- blocker 必须仍在本轮 `final_items` 中；
- blocker 不能是 C 自己；
- `pending_out_ids_` 中的物品不能继续解释遮挡；
- 新关系只能由已经确认身份的 IN / MOVED 建立，未确认 suspect D 不得持久化；
- 本轮 MOVED 的 blocker 使用新的最终 `base_box`；
- 与 C 没有正面积交集的 blocker 从 C 的关系中移除；
- 不把当前自身是 OCCLUDED、身份未决或只由其他遮挡关系推导出的物品当作新的
  前景 blocker，避免递归遮挡和循环依赖；
- 历史 blocker 不能因为一张无手帧漏检就立即删除。只要它没有正式 OUT，或没有
  正式确认移动到不再覆盖 C 的位置，历史关系就保留到下一次有效重算。

这里的“新物品 / 已确认移动物品位于前方”就是本项目的业务因果规则；但是它的
入口必须是 `new_fronts`，不能是“检测框只要和 C 相交就直接加入”。

### 5.2 C 被直接观察到

如果当前无手帧成功把检测框唯一认领给 C：

```text
C.status = VISIBLE
```

如果 C 之前是 OCCLUDED，正式提交时生成一次 `REVEALED`。C 的 `item_id`、
可靠 `base_box` 和正常身份不能因为重新出现而新建或替换。

直接观察 C 时不要无条件清空所有 `block_ids`：

- blocker 已 OUT、已移动到不相交位置或不再是有效关系时，移除；
- blocker 仍是已确认的前景物品且仍与 C 相交时，保留这条部分前景关系；
- C 只要已经直接可见，就必须是 `VISIBLE`，不能继续保持 `OCCLUDED`；
- 只有目标重新直接出现、并且之前的完整遮挡解释已经失效时，才是完整的
  `REVEALED` 场景。

这样 `block_ids` 始终表示“当前已确认的前景关系”，而 `status` 表示“是否被
完整遮挡”。二者不能混用。

### 5.3 C 未被观察到

先使用历史 blocker 和本轮新确认 blocker 的最终框，统一调用现有
`fully_covered_by(C.base_box, cover_boxes)`：

```text
覆盖并集完整
    -> 保留 C.item_id
    -> 保留 C.base_box
    -> C.status = OCCLUDED
    -> C.block_ids 写入本次有效前景关系
    -> 清零 C 的直接无手缺失证据

覆盖并集不完整
    -> 只移除已经 OUT、移出覆盖范围或身份失效的 blocker
    -> 仍相交的已确认前景关系可以保留在 C.block_ids
    -> 不能把 C 改成 VISIBLE
    -> 不能产生 REVEALED
    -> 部分前景关系不能单独阻止 OUT；C 按既有 OUT 证据链继续处理
    -> 缺失计数从完整遮挡解释失效后重新开始
```

多个 blocker 必须先全部收集，再做覆盖并集。不能遇到某一个 blocker 的局部
覆盖就提前判定，也不能把单个交集面积直接相加。

### 5.4 blocker OUT 或 MOVED

当 blocker A 正式 OUT 时，遍历所有目标 C：

```text
从 C 的关系集合移除 A；
重新计算剩余 blocker 是否仍完整覆盖 C；
```

当 blocker A 正式 MOVED 时，必须基于移动后的最终 `base_box` 统一重算：

```text
A 与 C 新位置有交集
    -> A 可以成为 C 的前景关系

A 与 C 新位置无交集
    -> A 从 C 的关系中移除
```

不能只在 A 的旧位置执行一次删除，再在 A 的新位置执行一次增加。所有物品的
最终位置准备好后一次重算，才能正确处理：

```text
A 移走，但 B 仍完整覆盖 C
    -> C 继续 OCCLUDED，不产生 REVEALED

所有有效 blocker 都移走，C 直接出现
    -> C VISIBLE，并产生一次 REVEALED

所有有效 blocker 都移走，C 仍未出现
    -> 不产生 REVEALED，才允许进入 OUT 证据链
```

### 5.5 遮挡解释失效后的 OUT

在完整遮挡期间，C 的无手缺失计数必须保持为零。只有最后一个有效 blocker 被
正式移除、移出覆盖范围或失效后，C 才能开始新的连续缺失计数。

如果 C 没有现成的 `OperationTrack`，可以增加一个仅存在于本轮事务中的独立
遮挡失效计数；不能复用 D 的计数、`visible_count_missing_counts_` 或其他已有
计数器。这个内部计数不是新的正式库存状态，也不能改变现有
`FLOW3_NO_HAND_OUT_MISSING_FRAMES`。

计数规则：

```text
C 仍被完整遮挡                  -> 计数清零
C 直接出现                      -> 计数清零，按 REVEALED 处理
遮挡解释刚失效且 C 未出现         -> 从 1 开始
连续达到现有 OUT 阈值             -> 才加入 pending_out_ids_
手重新出现或本轮回滚              -> 丢弃本轮计数
```

不能因为 blocker 移走就把 C 立即设为 VISIBLE，也不能把遮挡期间累计的缺失帧
直接带入 OUT。

## 6. 推荐的代码修改边界

### 6.1 `session_settlement.cc`

遮挡重算应放在无手帧身份绑定和最终 `base_box` 更新之后、
`has_unresolved_no_hand_state_()` 判断之前。

当前代码中以下区域需要重点处理：

- `refresh_confirmed_blockers_()` 目前是空实现；
- 当前 `confirmed_front_ids` 只包含本轮新确认的直接前景物品；
- 当前对观察到的物品会清理 `block_ids`；
- 当前提交前又用 `!confirmed_front_ids.count(*blocker)` 清理历史 blocker；
- 当前 `fully_covered_ids` 只由本轮前景集合计算。

建议把这些逻辑收敛为一个统一的遮挡关系重算 helper，至少明确输入和输出：

```text
输入：
  final_items
  operation_start_inventory_
  observed_ids
  本轮已确认 IN / MOVED 集合
  pending_out_ids_

输出：
  每个物品最新的工作 block_ids / status
  fully_occluded_item_ids
  遮挡解释刚失效、需要进入 OUT 证据的 item 集合
```

不要让 helper 直接修改正式库存，不要在 helper 中生成正式事件。事件生成和
`replace_all()` 继续使用现有结算边界。

### 6.2 `session_hand.cc`、`session_no_hand.cc`、`session_ownership.cc`：同类候选冲突图

同类残余唯一归属属于身份仲裁，不属于遮挡几何。应在现有严格原位预约之后、
suspect D 创建之前新增一个没有正式副作用的 candidate-context helper，供有手和
无手阶段共同使用。它的最小输入/输出应明确为：

```text
输入：
  当前同类 detection d
  operation_start_inventory_
  working_inventory_
  track_buffer_
  本帧已建立的直接 owner 预约
  现有 suspect / pending D runtime

输出：
  direct_old_owners
  viable_unresolved_old_ids
  matching_suspect_d_ids
  是否为“唯一旧 A / 多旧 C 歧义 / 可独立 D”
```

实现边界固定如下：

1. 在 `scan_or_update_suspects_()` 中，先调用 helper 收集完整关系，再决定是否创建
   `alias_old_item_ids` 和 suspect D。当前“只收集已有另一 detection 的旧 C”这一
   窄分支必须改为完整候选图；尤其不能在集合非空后提前 `continue`，让没有直接
   detection 的活动旧 A 被跳过。
2. 现有直接 owner、手阶段保护期、CONTACT、D quarantine 与 C-D alias 规则继续
   有效。helper 只补充“哪个旧 C 对 d 仍有合理身份主张”，不改变严格 owner 的
   优先级，也不把局部框变成全局 owner。
3. 在无手 `unique_no_hand_reappear_detection_for_track()` 之前，若 d 已被一个
   suspect/pending D 几何命中，但候选图仍把 d 指向旧 A，必须先把 A 纳入该 D 的
   冲突关系或先把 d 预约给 A。不能仅因 `belongs_to_existing_d` 就跳过 d。
4. 在 `confirm-independent-d` / 提升 working item 之前，复核完整候选图：任何
   同类别未决旧 A 仍可能拥有 d 时，D 都不能提升。D 必须等待 A 获得自己的直接框、
   被正常确认 MOVED/OUT/OCCLUDED，或被路径证据明确排除。
5. 当关系图给出“唯一旧 A + 唯一稳定 d”时，复用现有 reappear、连续无手和
   `confirm_rearrange_()` 语义确认 A；临时 D 只能被合并/撤销，不能先 `IN` 后再
   补救为 MOVED。

在 `FLOW3_DEBUG_TRACE_LOG` 下，为每个进入 helper 的 d 增加一条只读 trace，至少输出
`candidate`、类别、直接旧 owner、全部 `viable_unresolved_old_ids`、匹配 D runtime、
最终决策和是否允许 D 提升。这个 trace 不能影响预约或状态机，但必须让后续实机日志
可以直接回答“是谁在竞争这一框”，避免再次只能从最终 `ambiguous` 反推原因。

不要修改普通 `track_match_box()`、`reappear_candidate_path_matches()`、全局匹配阈值、
D 确认帧数或正常 MOVED 门槛，除非另有独立设计和回放证明。根因是候选关系漏边，
不是几何阈值过紧。

### 6.3 遮挡感知静态局部认领的代码边界

这部分可以放在 `session_settlement.cc` 的无手绑定阶段，或者由
`session_ownership.cc` 提供一个只负责预约的 helper；它不能和同类残余身份回收
混成一个“宽松匹配”入口。实现前先明确以下输入：

```text
旧库存 C（operation_start_inventory_）
当前尚未占用的 detection
历史有效 block_ids
本轮已经确认的 IN / MOVED 前景集合
已被更高优先级 owner 预约的 item/detection 集合
```

建议的预约顺序是：

1. 保留现有已确认移动/轨迹终点、普通严格、路径和原位置严格阶段；这些阶段的
   优先级和双向唯一绑定不能变。
2. 对满足第 3.3 节全部条件的旧静态 C，运行遮挡感知的 `partial_match_box()`
   双向唯一预约。
3. 再进入现有普通局部回退和未决处理；普通局部回退不能借此获得更高优先级，
   也不能修改 D、C-D alias 或 OUT 的保护条件。
4. 预约成功后沿现有 `update_seen()`、`observed_ids`、事件生成和事务提交路径
   继续处理；helper 不直接写正式库存、不生成正式事件、不刷新 `base_box`。

如果现有最后的普通局部阶段已经能安全覆盖某个案例，不要重复绑定或重复更新；
应通过遮挡上下文和日志确认它是否满足第 3.3 节的安全条件，再决定是否只补充
保护过滤。目标是补足遮挡场景的缺口，而不是复制一套匹配器。

### 6.4 头文件和库存结构

优先只增加 `SessionManager` 私有 helper 声明以及必要的事务内计数容器/候选上下文。
`InventoryItem` 已经有 `item_id`、`box`、`base_box`、`status`、`block_ids`，
第一步不需要新增公共库存状态，也不需要修改 `inventory.h` 的正式结构。

## 7. 必须先写的最小失败回放

回放应加入 `tests/session3_replay_no_hand.cc`，并保留所有既有 55 个回放。
至少覆盖：

1. A 移到 C 前，C 消失且 A 的最终框完整覆盖 C：C 保留 item_id，变为
   OCCLUDED，`block_ids` 含 A；
2. 下一次操作 A 仍停在 C 前，A 有直接稳定框，C 仍不可见，但本轮没有新的
   MOVED / IN：C 仍是 OCCLUDED，历史 `block_ids` 不能清空，也不能重复产生事件；
3. A、B 联合覆盖 C，A 移走后 B 仍完整覆盖：C 不得 REVEALED；
4. 全部 blocker 移走，C 连续直接重新出现：C 保留原 item_id，只产生一次
   REVEALED；
5. 全部 blocker 失效且 C 仍未出现：第一张无手帧不 OUT，达到现有连续阈值后
   才 OUT，不产生 REVEALED；
6. 单个部分覆盖和多个框覆盖并集不完整：不能产生 OCCLUDED；
7. 已确认 blocker 使旧静态 C 只剩局部框：在有遮挡上下文且双方唯一时，C 能保留
   原 item_id 被认领，`box` 可更新但 `base_box` 不被小框覆盖；没有遮挡上下文、
   存在第二个同类候选或 owner 已被占用时，不能强行局部认领；
8. 当前实机同类苹果案例的最小失败回放：`item=1`、`item=4` 在无手帧各自拥有
   独立严格原位框，`item=5` 没有直接框但其 reappear/path 可到达剩余苹果框 d。
   断言 d 的候选冲突图必须含 `item=5`；不能仅因 `item=1` 已有另一框就把 d 建成
   只关联 `item=1` 的 alias D；d 不能先提升为 `item=6` 并反过来阻止 `item=5`；
9. 续接第 8 项的第二张无手帧：在既有连续帧数下，d 复用 `item=5`、产生一次正常
   MOVED，不产生 IN、没有 `pending-d=6 + unresolved-old=5` 的 defer-commit；只有
   `item=5` 身份确认和最终 `base_box` 就绪后，它才能成为橙子的 blocker；
10. 真实新 D 对照：同类所有旧 C 都已各自有独立直接框或正式终态时，新 D 仍可按
    既有确认帧数创建、提升和正式 IN，不能被候选图永久阻塞；
11. 多旧 C 歧义对照：同一同类 d 可合理属于两个未决旧 C 时，两个 C 都进入完整
    alias/未决关系，不能强行 MOVED、IN 或 OUT；后续有额外直接证据后才收敛；
12. 继续回放已有 HAND、CONTACT、D、C-D alias、同类检测顺序、灰区恢复、
   正常 MOVED、OUT 和已有遮挡/揭示测试。

每个新回放都必须断言：

```text
item_id、status、base_box、block_ids、事件种类、事件次数、是否提交
```

## 8. 禁止的实现方式

- 不能把任意检测框交集直接写入正式库存的 `block_ids`；
- 不能让未确认 suspect D 直接成为正式 blocker；
- 不能用 OCCLUDED 结论替代旧物品身份确认；
- 不能让遮挡模块绕过 C-D alias、D 确认帧或同类唯一归属保护；
- 不能只把“已有另一 detection”的旧 C 写入 C-D alias，然后在仍有无直接框的活动旧 A
  时提前创建或提升 D；
- 不能让一个 `conflicting_old_item_ids` 漏掉 A 的 suspect/pending D 反过来排除 A 的
  唯一 reappear/path 候选；
- 不能只证明 D 与已记录冲突集合的部分旧 C 不同，就把它视为独立 D；必须先排除
  全部可行未决旧 C；
- 不能为了修复这个 identity 漏边而放宽 `track_match_box()`、reappear 容差、局部
  匹配阈值或 D 确认帧数；
- 不能把普通物品局部匹配整体提前到严格/轨迹 owner 之前；
- 不能把“结算卡住”作为统一放宽局部匹配的触发条件；
- 不能因为 C 当前没有检测框就立即生成 OUT 或 REVEALED；
- 不能因为 blocker 移走就立即把 C 改成 VISIBLE；
- 不能在单个 blocker 的局部交集后提前停止并集计算；
- 不能把遮挡期间的缺失计数带入遮挡失效后的 OUT 计数；
- 不能修改 YOLO/NMS、手阈值、D 确认帧数、正常 MOVED 门槛或门状态流程；
- 不能删除、合并或改写现有已验证的 NORMAL、HAND、CONTACT、D、C-D alias、
  灰区恢复、IN、OUT、MOVED 和无手提交逻辑。

## 9. 实施和验收顺序

1. 保存当前完整模块化 replay、ASAN/UBSAN replay、关键库存和事件序列作为基线；
2. 先新增第 7 节第 8-11 项的同类候选冲突图回放，确认当前版本会复现“只关联
   item=1 的 alias D、item=5 被 pending D 排除”的失败；同时固定真实新 D 和多旧 C
   歧义的对照，防止修复只对一个录像有效；
3. 先实现完整 candidate-context / alias 关系收集和 D 提升门控，不实现 blocker
   生命周期、不改局部匹配；运行同类回放和完整既有 replay；
4. 再实现严格残余唯一归属，确认唯一旧 A 可复用旧 item_id 走两帧无手 MOVED，且
   临时 D 被正确回收；重新运行真实新 D、C-D alias 与多旧 C 歧义回放；
5. 再实现遮挡感知的静态局部认领，验证叠放后 B/C 的小框不会制造新的 owner 抢占；
6. 身份确认链稳定后，新增跨操作遮挡失败回放并实现 blocker 生命周期重算；
7. 再实现遮挡解释失效后的 OUT 排除与重新计数，运行完整回放；
8. 重新运行当前实机案例对应的主机回放，确认 item=5 的身份先完成，随后
   item=5 才能以已确认 MOVED blocker 参与橙子遮挡；
9. 每一步完成完整 replay、ASAN/UBSAN、`git diff --check`，并检查关键日志；
10. 若某一步改变了原有正常入库、出库、移动、D 或 alias 回放，停止在上一个
   通过点定位原因，不得通过放宽阈值或删除保护逻辑来恢复通过。

## 10. 完成条件

本轮只有同时满足以下条件才算完成：

- 跨操作历史 blocker 能正确保留、更新、移除；
- 单个覆盖、联合覆盖、遮挡持续、部分移开、全部移开和重新出现均有回放；
- C 只有在直接重新出现时才产生 REVEALED；
- C 只有在没有有效遮挡解释后才进入原有 OUT 证据链；
- 每个同类候选 d 在创建/提升 D 前都经过完整候选冲突图；不存在“D 未关联旧 A，
  却能阻止 A 认领 d”的漏边状态；
- 当前实机中的同类移动不能再无限期保持无出口，但也不能牺牲 D 防线；
- 当前实机中 `item=1`、`item=4` 有独立框、`item=5` 是唯一剩余旧 A 时，最终框
  必须复用 `item=5` 并产生 MOVED，不能生成 `item=6` 的假 IN 或 defer-commit；
- 真实新 D 和多旧 C 真实歧义仍分别保留既有 IN 确认与未决保护，不能被残余规则
  误合并为 MOVED；
- 叠放造成的旧静态局部框，在有已确认遮挡上下文且双方唯一时可以安全认领，
  且不会刷新不可靠的 `base_box`、生成假 IN 或抢占动态 owner；
- 现有正式库存、事件、item_id、`base_box` 和正常 MOVED 行为没有回归；
- 完整模块化 replay、ASAN/UBSAN 和 `git diff --check` 全部通过；
- 没有为了通过新回放而改变 YOLO/NMS、手阈值、确认帧数、门状态或原有有效功能。

本文件的核心要求只有一句话：

```text
先为每个同类候选框确认“它可能是谁”的完整旧 C 关系，再确认“这个 A 到底是谁”；
只有已确认移动/新入库物品才能按业务顺序维护 blocker。遮挡关系可以保护 C 不被
误判 OUT，但绝不能替身份证据做决定，也不能让临时 D 替身份证据做决定。
```
