# 细节 13：静态旧 C 被消失的隔离 D 互相等待，导致整理永久不提交的窄修复（计划 r16）

## 0. 本文件的用途与首要约束

本文件是下一次修改代码时的指导说明。它只处理已经由实机详细日志和当前源码共同证实的
一个极窄漏洞：**旧库存物品 C 已经稳定回到原位，但一个短暂出现、随后消失的隔离候选 D
仍与它保持 C-D alias；D 等 C 完全结算才允许删除，而 C 又因为 D 尚未解除而不能结算，
最终整轮操作永久停在 `defer-commit`。**

**最重要的原则：当前版本的正常入库、出库、整理、遮挡、接触、同类相邻物品处理已经
表现很好。下一次修改必须只补这个“静态旧 C + 已消失 runtime-only D”的收尾死锁，
不得借本例改宽任何已有主流程。**

尤其禁止把这次压力测试中的一次低分 YOLO 候选，当成“应当整体提高阈值”或“同类物品
匹配规则应放宽”的理由。那样会损害被手遮挡、物品相邻、低分但真实的入库/出库/整理
证据，风险远大于收益。

本文件不是要求回退 `3.0-r15`。r15 已正确修复了另一种 stale alias 终态，并补齐了
“业务实际输入框 = OSD 可见框”的排障能力。本次是在 r15 的保守保护仍然正确的前提下，
补它尚未覆盖的一条静态收尾子分支。

### 0.1 当前版本已经有效的能力，必须完整保留

下列能力已经经过较多测试，下一次代码修改后必须保持原有语义和表现：

```text
1. 正常 IN：真实新物品 D 必须先走既有 staged IN / 连续直接无手证据链，
   不能因本补丁被提前删除或漏报。

2. 正常 OUT：旧 C 的缺失、数量不足、遮挡、连续无手确认、回归撤销等逻辑不变。

3. 正常 MOVED / 整理：旧物品由既有 original / reappear / observed path /
   CONTACT_* 证据确认移动；本补丁不能改变其匹配范围、确认帧数或 item_id。

4. 遮挡与恢复：OCCLUDED / REVEALED 仍由原有遮挡判断处理，不能被 alias 清理
   误写为 OUT、IN 或静态。

5. 同类相邻物品：细节 9、10、11、12 中已有的一框一物品、静态邻居排除、
   claim grace、共享框与独立框仲裁必须原样保留。

6. CONTACT_CANDIDATE / HAND_CONTACT / HAND_PARTIAL_BLOCKED / HAND_FULL_BLOCKED：
   有手阶段仍只积累证据，不可因本补丁提前给出整理、出库或入库结论。
```

若实现过程中发现必须修改上述任一主流程、几何阈值或确认帧数，说明补丁范围已经失控。
此时应停止修改并重新分析，不能为了让这一个实机案例通过而扩散风险。

### 0.2 本轮版本边界

```text
当前基础版本：3.0-r15
下次目标版本：建议 3.0-r16
修改类型：状态机收尾完整性补丁，不是模型、NMS 或阈值调参
预计超参数变更：无
```

除非实现时发现一个未记录的既有超参数被实际改动，否则不应修改
`超参数位置与调节说明.txt`。本次不应新增“静态 alias 清理帧数”之类的新数值；直接复用
已有的 `FLOW3_NO_HAND_D_CONFIRM_FRAMES`（当前为 2），并保持其数值不变。

## 1. 本次实机问题：已经确认的事实

### 1.1 操作场景

本次初始库存有 7 件物品：4 个苹果、1 个苏打罐、2 个橙子。物品之间放得很近。
用户从中间取走一个苹果并放到另一侧。画面开启镜像，因此口头的“左/右”不用于判断；
应以日志中的 item id、类别、状态和坐标为准。

操作前的连续无手帧 `1296` 至 `1304` 都满足：

```text
foods=7
库存=7
每个框都稳定、合理
```

这说明操作前的库存和检测输入本身没有数量异常。

### 1.2 关键时间线

| 阶段 | 已确认事实 | 正确含义 |
| --- | --- | --- |
| `frame=1309`，有手 | YOLO 业务输入中出现 `cls=25 score=0.266 box=(870,485,961,627)` | 短暂低分苏打罐候选；物理上不一定有新苏打罐 |
| 同一帧 | 程序创建 `suspect#-2`，并与旧苏打罐 `item#12` 建立 C-D alias | 正确的保守隔离，尚未产生 IN |
| `frame=1312`，无手 | 被移动的苹果 `item#11` 已为 `MOVED_CONFIRMED`，位置为 `(800,412,981,590)` | 整理识别实际已经成功 |
| `frame=1312` 以后 | `item#12` 有自己的稳定检测，状态为 `NORMAL + STATIC_CONFIRMED` | 旧苏打罐仍在原位，并非 OUT 或 MOVED |
| `frame=1312` 至 `1318` | `suspect#-2` 没有自己的检测框，也没有与 C 共用检测框 | 临时候选 D 应进入“连续无证据后回收”路径 |
| 同一期间 | 不断出现 `[SETTLE] defer-commit`，无 `[EVENT]` | 不是 MOVED 判错，而是提交被未决 D 卡住 |

因此，本次结果的精确描述是：

```text
苹果 item#11 的整理判断正确；
真实苏打罐 item#12 的原位状态也正确；
错误的是：一个已经消失的运行时临时 D 永远不被清理，
从而阻止整个 operation 正式提交和输出 [EVENT]。
```

### 1.3 这不是“本地多生成了一个框”

`suspect#-2` 是状态机根据 YOLO 输入创建的运行时身份，但它不是本地凭空制造出来的
第八个 YOLO 框。第 `1309` 帧的 `[FOOD-DETECTION]` 已明确记录了输入来源：

```text
input-index=6
cls=25
score=0.266
box=(870,485,961,627)
business-input=1
osd-business-visible=1
```

这表示：模型/检测后处理确实在那一帧给出了一个低置信度的候选，且它达到当前食品业务
输入阈值 `0.25`，所以进入了状态机。r15 已让这类业务输入在 OSD 上可见，这正是本次能够
直接定位的原因。

正确处理方式不是把所有分数低于 `0.50` 的框一律拒绝。低分框有时是被手遮挡时仍有价值的
真实证据。健壮的业务层应做到：**允许谨慎观察低分候选，但当它没有获得连续独立证据并且
已经消失时，必须安全收尾，不能让它永久卡住操作。**

### 1.4 与 r15 已修复问题的关系

两次问题的外部现象相同，都是“已经完成操作，却没有 `[EVENT]` / 新库存输出”；内部终态
不同：

| C-D alias 的无手终态 | r15 的处理 | 本次是否覆盖 |
| --- | --- | --- |
| 旧 C 已 `MOVED_CONFIRMED` 或其他真正终态，D 无独立框且无共享框 | D 连续缺失两帧后被回收 | 已覆盖 |
| D 与 C 连续共用同一个检测框 | 沿用共享框连续确认，D 作为重复 runtime 身份回收 | 已覆盖 |
| C 与 D 均有各自独立框 | C 正常 MOVED/STATIC，D 沿原 staged IN 链路确认 | 已覆盖 |
| **旧 C 静态原位、已有直接框，但 `needs_settle=1` 仅因 D 未解除而未完全结算；D 同时又在等 C 结算** | **r15 的前置条件不成立，双方永久等待** | **本次必须修复** |

因此，r15 的设计不是错误的，也不应回退。它故意要求“旧 C 已独立结算”才允许清理消失的
D，以免误删真实的新物品。本次只是发现：当旧 C 的最后一个未结算原因恰好就是该 D 时，
原先的定义过于严格，造成了循环依赖。

## 2. 根因：代码中的循环依赖，而不是整理主流程失效

### 2.1 当前 r15 的正确但不完整的保护

当前 `session.cc` 中，r15 的 stale alias cleanup 要先调用类似以下语义的判断：

```text
all_conflicting_old_c_independently_settled(D)
```

对一个静态旧 C，现有“已独立结算”定义大意是：

```cpp
old.resolution == STATIC_CONFIRMED &&
!old.needs_no_hand_settlement &&
old.state == NORMAL &&
old.contact_state == NONE
```

这条规则对于已真正结束的 C 是对的。它保护真实 D：若 C 还在等待路径、遮挡、共享框、
接触或其他无手结算，绝不能仅凭 D 暂时没框就删除 D。

### 2.2 本次循环如何产生

本次实机日志已经逐帧证明以下关系：

```text
旧 C = item#12（真实苏打罐）
D     = suspect#-2（有手时短暂出现、随后消失的 cls=25 临时候选）

item#12：
    NORMAL + STATIC_CONFIRMED
    有自己的无手检测框
    但 needs_settle=1，alias-d=1

suspect#-2：
    no-direct-pair
    runtime-only=1
    all-conflicting-old-settled=0
    missing-count=0/2
    keep-unresolved
```

它形成的逻辑环是：

```text
item#12 未完全结算
    原因：仍关联着未决 D
        ↓
D 不允许开始“连续无直接证据”计数
    原因：要求 item#12 已完全结算
        ↓
D 永远不删除
        ↓
item#12 永远带着 alias，整轮永远 defer-commit
```

这不是苹果的 MOVED 匹配失败，也不是库存数量、镜像方向或同类邻居主仲裁发生错误。
苹果 `item#11` 已经是 `MOVED_CONFIRMED`，正是这个无关的 C-D alias 死锁挡住了最终提交。

### 2.3 必须避免的错误修法

以下做法都会伤害现有正确功能，禁止采用：

```text
1. 直接把所有 score < 0.50 的食品框从业务层丢弃。
2. 把 YOLO_OBJECT_SCORE_THRESH 从 0.25 全局提高到 0.50。
3. 在任意 D 首次无手缺失时立即删除 D。
4. 修改 strict match、partial match、reappear、同类邻居距离或 IoU 阈值，
   让本例“碰巧”不再建立 alias。
5. 直接把所有 STATIC_CONFIRMED 的旧 C 当作完全结算。
6. 直接调用特殊的强制 commit、手写 [EVENT] 或直接改 inventory_ 绕过 settlement。
7. 修改通用 old_c_has_independently_settled_identity() 的语义，使所有调用点
   都把仍 needs_settle 的静态 C 当作已结算。
```

第 7 点尤其重要。这个通用帮助函数还参与“D 是否只是已结算 C 的重复框”和“C、D 是否
拥有独立框”的其他判断。若全局放宽，会把此次极窄修复扩散到真实 D、共享框、相邻同类
物品和 IN 判断中。

## 3. r16 的唯一目标状态与安全语义

### 3.1 核心思想：只为 stale alias cleanup 引入“可安全视为静态已证实”

r16 不应宣称 `item#12` 已经在全局意义上“完全结算”。它只能在**判断是否允许清理这个
消失的 D**时，被视为“已经有足够的独立静态证据”。

建议引入一个只服务于本分支的窄帮助判断，名称可按现有代码风格调整，例如：

```cpp
bool old_c_is_directly_static_for_stale_alias_cleanup(
    const OperationTrack& old,
    int target_suspect_runtime_key,
    const std::vector<Detection>& detections,
    const std::map<int, OperationTrack>& tracks,
    const std::map<int, int>& independent_static_owner_by_detection);

bool all_conflicting_old_c_safe_for_stale_alias_cleanup(
    const OperationTrack& suspect,
    int suspect_runtime_key,
    const std::vector<Detection>& detections,
    const std::map<int, OperationTrack>& tracks,
    const std::map<int, int>& independent_static_owner_by_detection);
```

名称不是重点，边界必须严格：这个帮助函数不得替换或放宽通用的
`old_c_has_independently_settled_identity()`。

### 3.2 旧 C 可以作为“cleanup 安全静态 C”的必要条件

对 D 所关联的每一个旧 C，以下条件必须在**当前同一张有效无手帧**全部成立，才可在
stale alias cleanup 中把它视为安全：

```text
1. C 是 operation-start old C：不是 suspect，item_id 有效，类别与库存一致。

2. C 的状态严格为：
       state == NORMAL
       contact_state == NONE
       resolution == STATIC_CONFIRMED
   不能是 MOVED/OUT/OCCLUDED 的半途状态，也不能是 HAND_*、CONTACT_*。

3. C 在当前无手帧已经获得它自己的直接检测归属：
       no_hand_detection_index 有效；
       index 指向当前 detections 内同类别框；
       该框被现有的“独立静态旧物品所有权”逻辑唯一归属给 C。
   优先复用 build_independent_no_hand_static_owner_by_detection()、现有 claimed
   结果和已有匹配语义；不得另写一套更宽松的几何判断。

4. C 当前没有其他未决原因：
       没有 reappearance_pending；
       没有 b_claim_ambiguous；
       没有 contact_path_ambiguous；
       没有 no_hand_candidate_ambiguous；
       没有正在进行的 CONTACT、遮挡、OUT、路径或 claim grace 证据链。

5. C 的 needs_no_hand_settlement == true 只能由待解除的 quarantined alias 导致。
   C 的 conflicting_suspect_keys 中不得存在除当前待清理 D 以外的其他未决
   QUARANTINED_PENDING_D；若有另一个 alias、普通 pending D 或任何未知未决关系，
   必须返回 false，继续等待。

6. 当前 D 没有自己的独立 detection，也没有与 C 共用 detection。只要 D 有任意
   直接无手证据、共享框证据或尚未完成的独立 D 仲裁，本帧就不是“D 已消失”。
```

第 3、4、5 条共同保证：不是因为“C 看起来静止”就放行，而是因为 C 已被现有主流程用
自己的、唯一的、当前帧直接证据确认；它唯一剩下的障碍恰好是目前这个 D。

### 3.3 所有关联旧 C 都必须通过

一个 D 理论上可能关联不止一个同类旧 C。因此不能只检查第一个 C：

```text
所有关联 C 都必须满足下列二选一：

A. 已经按既有通用规则真正独立结算；或
B. 满足本文件 3.2 的“仅供 stale alias cleanup 的安全静态 C”条件。
```

只要有任意一个关联 C：找不到、仍在移动、还在遮挡、正在等待候选、没有自己的唯一静态框、
或有别的 alias 未决，D 的缺失计数必须清零或保持为 0，绝不能删除。

### 3.4 D 可以开始“消失计数”的必要条件

在旧 C 满足第 3.2、3.3 节后，D 还必须同时满足：

```text
1. D 是 is_suspect_new == true 且 pending_d_quarantined_by_old_c == true；
   普通 pending D 不进入本分支。

2. D 仍是 runtime-only：未 promoted_to_working_inventory，item_id <= 0；
   已提升为正式工作库存的 D 绝不可以被本分支删除。

3. 当前是有效直接无手帧；手一旦重新出现，连续缺失证据立即失效。

4. D 当前没有 direct no-hand detection，且 alias_no_hand_matched_this_frame == false；
   有独立框、共享框、重新出现候选或未完成仲裁都必须停止计数。

5. 以上条件连续满足既有 FLOW3_NO_HAND_D_CONFIRM_FRAMES 帧，当前为 2。
```

### 3.5 达到两帧后的唯一动作

达到条件时，唯一允许做的事是：

```text
1. 将该 D 放入既有 discard / erase 路径；
2. 使用既有 unlink_quarantined_suspect_() 解除 D <-> C 的双向 alias；
3. 只删除 runtime track；
4. 不写 working_inventory_；
5. 不写 pending_in_ids_；
6. 不产生 IN、OUT 或伪造 MOVED 事件；
7. 不直接修改任何旧 C 的位置、类别、库存 id；
8. 不调用强制提交。解除障碍后，让既有无手 settlement 按原有顺序完成提交。
```

删除 D 的当帧是否恰好能提交，取决于现有 C 处理和 settlement 的执行顺序；允许在下一张
正常无手帧由既有静态收尾自然完成。验收标准是“不再无限 defer-commit”，不是为了追求
少一帧而绕过原本的安全收尾步骤。

### 3.6 计数重置规则

沿用 r15 的保守原则。`alias_no_hand_missing_count` 必须在以下任一情况发生时清零：

```text
1. 手重新出现；
2. D 有自己的直接无手 detection；
3. D 与任一关联 C 共用 detection；
4. D 出现尚未完成的独立 D 证据或仲裁；
5. 任一关联 C 不再满足“通用已结算”或“本轮直接安全静态”条件；
6. C 出现 reappear、CONTACT、遮挡、claim grace、路径或同类歧义；
7. alias 被解除、D 被删除、D 被提升为正式库存；
8. 当前帧不是有效直接无手帧。
```

不得把被手、共享框、独立框或歧义打断的两个短暂缺失片段拼成“连续两帧”。

## 4. 推荐的实现位置、顺序与伪代码

### 4.1 不修改通用 helper；新增 cleanup 专用 helper

当前通用的 `old_c_has_independently_settled_identity()` 继续保持原语义。它要求静态 C
已经 `!needs_no_hand_settlement`，这是对其他 C-D 分支的必要保护。

在其旁边新增一个**仅给 stale alias cleanup 调用**的帮助函数。该函数可以把“已真正结算”
与“当前帧静态直接证实、仅被本 D 卡住”分开记录，例如：

```text
old C 的 cleanup 资格：
    final-settled          = 现有 old_c_has_independently_settled_identity(old)
    static-direct-evidence = 细节13新增的窄条件
    cleanup-safe           = final-settled || static-direct-evidence
```

这样可读性和审查性都更好，也能避免把 `needs_settle=1` 的静态 C 在其他路径中误当作完全
结案。

### 4.2 依赖当前帧归属，不能在 C 处理前抢跑

`observe_no_hand_frame_()` 已明确分两阶段：先处理已有旧 C，再处理 suspect D。该顺序必须
保留，因为 D 的 cleanup 判断需要读取已经建立好的旧 C 当前帧信息，例如：

```text
old.no_hand_detection_index
当前 detection 的唯一静态归属
old 的本帧 ambiguity / reappearance 状态
```

因此，新帮助判断必须在旧 C 的 no-hand 认领、原位/路径匹配、共享框仲裁之后执行；不能在
`process_frame()` 入口或有手阶段预先凭上一帧状态做判断。

建议把 `independent_static_owner_by_detection` 作为输入传给 cleanup 专用 helper，复用已有
“独立静态旧物品所有权”结论。不要从头复制 strict / partial / track 几何逻辑。

### 4.3 推荐伪代码

下面是语义伪代码，变量名可按现有代码风格调整：

```cpp
if (is_quarantined_c_d_alias(track)) {
    if (d_has_shared_or_independent_direct_no_hand_evidence(track)) {
        track.alias_no_hand_missing_count = 0;
        // 完全沿用现有 shared-detection / distinct-detections 逻辑。
        // 本分支绝不删除 D。
    } else {
        const CleanupOldCStatus old_c_status =
            inspect_all_conflicting_old_c_for_stale_alias_cleanup(
                track, runtime_key, detections, track_buffer_,
                independent_static_owner_by_detection);
        const bool runtime_only =
            !track.promoted_to_working_inventory && track.item_id <= 0;

        if (runtime_only && old_c_status.all_cleanup_safe) {
            ++track.alias_no_hand_missing_count;
            if (track.alias_no_hand_missing_count >=
                FLOW3_NO_HAND_D_CONFIRM_FRAMES) {
                discard_keys.insert(runtime_key);
                discard_stale_alias_keys.insert(runtime_key);
            }
        } else {
            track.alias_no_hand_missing_count = 0;
            // 继续既有 keep-unresolved；不可删除 D。
        }
    }
}
```

`CleanupOldCStatus` 不一定必须是新结构体；也可以由多个局部 bool 和详细日志实现。但代码
必须能区分：

```text
all-final-settled
all-cleanup-safe
存在 direct-static C 的个数
阻止 cleanup 的 C id 与具体原因
```

不能只打印一个难以解释的 `all_conflicting_old_settled=0/1`，否则下次仍难以判断是 C 缺框、
C 有歧义、C 有别的 alias，还是正好属于本次“静态但被 D 卡住”的情形。

### 4.4 不要直接篡改 C 的结算状态

下列写法禁止出现：

```cpp
old.needs_no_hand_settlement = false;  // 仅为了让 D 能删除，禁止
old.resolution = STATIC_CONFIRMED;     // 仅为了让 D 能删除，禁止
force_commit();                        // 不存在也不得新增
```

理由是：C 的全局结算必须仍由既有的 `release_not_held_()`、MOVED/OUT/OCCLUDED 判断和
`settle_no_hand_frame_()` 完成。r16 只在 D 的回收资格判断中承认“C 当前有足够独立静态
证据”，随后解除 D 这个运行时障碍。

实现后必须验证：D 被删除后，旧 C 会在现有无手主流程的正常时序内完成；若仍出现
`normal-track-still-needs-settlement`，要先查清它是否还有真实未决原因。不能用强制写字段
把这个日志简单压掉。

### 4.5 文件范围

预计只需修改：

```text
src/session.cc
tests/session3_replay_test.cc
可能：include/session.h（仅当为测试/状态诊断确有必要增加非超参数字段时）
```

通常不应修改：

```text
src/main.cc                         # r15 的 OSD 与业务输入同源逻辑保持
检测/NMS 后处理                     # 本次不是 NMS、分数阈值或画框问题
超参数常量                          # 无需改变数值
run.sh                              # RTSP 日志过滤属于独立的输出体验事项
```

## 5. 严格的不可退化边界

下一次实现和代码评审必须逐项检查：

```text
1. 不得改动 YOLO_CANDIDATE_SCORE_THRESH、YOLO_OBJECT_SCORE_THRESH、
   YOLO_HAND_SCORE_THRESH、NMS_THRESH 或 OSD 低分颜色阈值。

2. 不得改动 FLOW3_TRACK_*、strict / partial match、reappear、CONTACT、
   同类邻居、可见数量不足 OUT 的几何条件和确认帧数。

3. 不得改动 FLOW3_NO_HAND_D_CONFIRM_FRAMES 的数值和普通 D 的含义；
   只允许在本文件的精确交集中复用它。

4. 不得把普通 pending D、已提升 D、独立 D、共享框 D 都归入 stale alias cleanup。

5. 不得把任意 STATIC_CONFIRMED 的 C 都视为 cleanup-safe；必须有当前帧自己的
   唯一直接静态框、无其他歧义、且仅被当前 D 卡住。

6. 不得改动细节9的同类数量不足 OUT 保护、细节10的静态邻居 fallback、
   细节11的相邻同类身份仲裁和细节12的 r15 stale alias 分支。

7. 不得修改工作库存和正式事件生成顺序来掩盖未决 track；D 删除必须走统一 unlink /
   erase，最终 event 必须仍由 settle_no_hand_frame_() 产生。

8. 不得删除或弱化既有回放测试。新测试必须叠加在已有测试之上。
```

若变更 diff 出现范围外的 `main.cc`、阈值文件、匹配函数或大量无关重构，应在提交前主动
重新审查。这个问题的正确解法应当是小而清楚的补丁，而不是广泛调整。

## 6. 日志要求：足够定位，但不扩大日常噪声

### 6.1 本次新增/调整的详细 trace

当 `FLOW3_DEBUG_TRACE_LOG = true` 时，C-D alias 的 `no-direct-pair` 日志应至少包含：

```text
[C-D-ALIAS]
suspect=<runtime key / suspect id>
phase=NO_HAND
relation=no-direct-pair
runtime-only=<0/1>
all-final-settled=<0/1>
all-cleanup-safe=<0/1>
old-static-direct=<old item id 列表或 none>
old-blockers=<id:reason,... 或 none>
independent-detection=<D index 或 -1>
shared-detection=<0/1>
missing-count=<n>/<FLOW3_NO_HAND_D_CONFIRM_FRAMES>
action=<keep-unresolved / wait-stale-alias-evidence /
        reset-stale-alias-evidence /
        discard-stale-alias-after-direct-static-old-c-no-hand-missing>
```

对于每个不允许 cleanup 的 C，原因应是可读的枚举，例如：

```text
missing-direct-static-detection
not-static-confirmed
other-quarantined-alias-pending
reappearance-pending
claim-or-contact-ambiguity
shared-or-independent-d-evidence
```

这样下次日志出现 `keep-unresolved` 时，可以马上分辨“这是正确的保护”还是“又出现了新的
循环依赖”，无需从大量逐帧状态中反推。

### 6.2 日常日志不应因此继续膨胀

当前大量 `[FOOD-DETECTION]`、`[HAND-DETECTION]`、`[STATE]`、`[MATCH]`、`[NO-HAND]`
输出，是 `FLOW3_DEBUG_TRACE_LOG = true` 的深度排障模式；本次正是借它定位了问题，暂不应
删除其排障能力。

但 r16 不应在 trace 关闭时新增逐帧 `printf` 噪声。规则应为：

```text
FLOW3_DEBUG_TRACE_LOG = false：
    保留既有 [EVENT]、[INVENTORY]、真正关键的最终 alias 回收提示；
    不新增每帧状态细节。

FLOW3_DEBUG_TRACE_LOG = true：
    输出本节完整的 C-D cleanup 判断原因，方便复现问题时诊断。
```

RTSP 的 `[DEBUG rtsp_msg...]` 是 RTSP 库输出，与状态机无关；不应混进本次状态机补丁。
仓库的 `run.sh` 已有过滤规则。若后续需要改善启动输出，应另行做一个独立、可验证的脚本
调整，不能与本次 alias 逻辑修改混在一起。

## 7. 必须新增的回放测试

### 7.1 新的最小可重复场景

在 `tests/session3_replay_test.cc` 新增一个专门覆盖本次死锁的回放。建议名称：

```text
test_quarantined_same_class_static_old_c_stale_alias_commits_after_cleanup
```

测试必须构造以下语义，而不是依赖随机检测顺序：

```text
初始库存：
    至少一个会移动的旧苹果 A；
    一个保持原位的旧同类/相关 C；
    一个旧苏打罐 C_static（对应实机 item#12 语义）。

有手阶段：
    A 建立真实的移动证据；
    额外创建一个与 C_static 同类别的 QUARANTINED_PENDING_D；
    D 只存在于运行时，未提升、未写入库存。

无手第 1 帧：
    A 获得其移动后的直接框并按既有逻辑成为 MOVED_CONFIRMED；
    C_static 获得自己的唯一静态直接框；
    D 没有直接框，也没有共享框；
    断言 D 的 stale missing-count 为 1，不能提前删除或提交。

无手第 2 帧：
    保持 C_static 自己的唯一静态框；
    D 继续没有直接框、没有共享框；
    断言 D 被 unlink 并从 runtime track 删除。

后续正常无手帧（若现有时序需要）：
    断言 operation 不再永久 defer-commit；
    正常产生 A 的 MOVED 事件，库存数量保持正确。
```

### 7.2 新测试必须断言的结果

```text
1. 移动的 A 保持原 item_id，最终产生一次 MOVED / 整理事件。
2. 静态 C_static 保持原 item_id、原类别和原位；不得变成 OUT、MOVED 或 IN。
3. 假 D 从未写入 working_inventory_、pending_in_ids_ 或正式 inventory_。
4. 最终库存总数不因假 D 变化。
5. 第 1 张有效无手帧不能过早删除 D，也不能过早提交。
6. 第 2 张连续有效无手帧后，D 必须解除 alias 并被删除。
7. 在现有正常收尾时序允许的帧数内，不能继续无限 defer-commit。
8. 旧 C 的 `needs_settle` 不得被本补丁用强制赋值伪造为 false。
9. 删除 D 后，最终事件仍来自既有 settlement，而非新增强制事件路径。
```

### 7.3 必须补充的反向保护测试

新分支最危险的风险是误删真实 D。因此至少补充或确认下列回放仍通过：

```text
1. D 有连续独立无手框：
   -> C 正确结算，D 正常 IN，不能被 stale cleanup 删除。

2. D 与 C 连续共享同一个框：
   -> 保持 r15 的 shared-detection 连续确认，不能走 missing cleanup。

3. 手在缺失计数中间重新出现：
   -> missing-count 清零；下一段无手帧必须重新从 0 开始。

4. C 仍存在 reappear / CONTACT / claim / 邻居歧义：
   -> D 不得开始 stale missing-count。

5. C 除目标 D 外还有第二个未决 quarantined alias：
   -> 不能只删除其中一个并假装 C 已安全结算。

6. r15 已有“旧 C 已 MOVED_CONFIRMED 后 D 消失”的回放：
   -> 仍应按原逻辑通过，不能被 r16 改慢或改坏。
```

### 7.4 全量回归与构建验收

实现后按以下顺序验证：

```text
1. 新增最小回放，先确认修复前能稳定复现 defer-commit / 修复后通过。
2. 运行主机端全量 session3 replay。
3. 运行 ASan/UBSan replay（环境支持时）。
4. 直接交叉编译受影响的 main/session 目标，确认嵌入式构建无误。
5. 执行 git diff --check。
6. 实机复测本案例：密集物品中移动一个苹果，且制造低分瞬时框场景。
7. 实机回归：正常入库、出库、整理、遮挡、同类相邻、手接触和手重新进入。
```

旧测试只要有任何失败，都不能以“实机这一次成功了”替代。应先查清新分支是否把 alias
cleanup 扩大到了真实 D 或正常 C。
