# 细节17：在不改变业务行为的前提下模块化拆分会话代码

## 0. 文件用途

本文件是下一次拆分代码时的实施指导。当前 `3.0-r18` 代码已经完成了
《细节16.md》要求的修改，并经过主机端回放和 ASAN/UBSAN 回放，当前阶段
虽然不是绝对完美，但业务能力已经基本满足需要。本次工作的目标是把过长的
`session.cc` 拆成职责清晰的多个实现文件，降低耦合、提高可读性，并让后续
阅读和维护不必每次加载一个 6800 多行的文件。

本次只改变物理文件组织，不改变业务规则。拆分完成后，程序看到的输入、状态
变化、库存结果、事件顺序和日志语义都应与拆分前一致。

> 原先代码已经具备并验证过很多有效功能，本身是很好的。本次拆分绝不能把
> 原先正确的 NORMAL、HAND、CONTACT、D、C-D alias、遮挡、揭示、IN、OUT、
> MOVED、OCCLUDED、REVEALED、无手提交和同类仲裁功能改坏。拆分不是重写，
> 不能借机“顺手优化”业务逻辑。

## 1. 当前基线和事实

当前主要文件规模如下：

```text
src/session.cc                    约 6821 行
include/session.h                 约 458 行
tests/session3_replay_test.cc     约 2800 行
src/inventory.cc                  约 140 行
include/fridge_config.h            约 361 行
```

当前业务实现目录已有：

```text
include/
  cloud_uploader.h  fridge_config.h  geometry.h  inventory.h
  luckfox_mpi.h     session.h        snapshot.h  tracker.h
src/
  cloud_uploader.cc inventory.cc luckfox_mpi.cc main.cc postprocess.cc
  session.cc       snapshot.cc  tracker.cc      yolov5n.cc
tests/
  session3_replay_test.cc
```

`session.h` 同时承载对外事件/结算结构、状态枚举、`OperationTrack` 运行时
状态、`HandDirectOldOwnerPlan` 所有权计划以及 `SessionManager` 的 public/private
声明。第一轮拆分不要改变这些结构的字段含义、可见性和默认值。

当前 `tools/luckfox_pico_rkmpi_example/CMakeLists.txt` 使用：

```cmake
file(GLOB SRC_FILES "${SRC_DIR}/*.cc")
add_executable(${PROJECT_NAME} ${SRC_FILES})
```

这意味着 `src/` 根目录下新增的 `.cc` 会被当前构建发现；放入
`src/session/` 等子目录则不会自动发现，必须同步调整 CMake。主机端回放的
手工编译命令也必须使用拆分后的全部实现文件。

## 2. 不可违反的拆分原则

1. **只移动定义，不改行为。** 函数体应尽量原样移动；除必要的声明、命名空间
   和 include 调整外，不修改阈值、判断顺序、状态枚举、计数器含义、事件类型、
   日志标签、库存字段和确认帧数。
2. **不重写总流程。** `SessionManager::process_frame()` 的阶段顺序、手出现/手
   离开入口、无手连续收尾和最终提交逻辑保持原样。不要把“拆文件”变成重写状态机。
3. **不做无关重构。** 本轮不顺手改名、不统一格式、不删除看起来重复但尚未证明
   无用的代码、不调参、不改变数据结构，不修与模块化无关的问题。
4. **不要通过包含 `.cc` 拆分。** 禁止使用 `#include "session_hand.cc"` 等方式把
   多个实现拼成一个翻译单元；每个函数只能在一个 `.cc` 中定义。
5. **保持封装。** `SessionManager` 的私有字段不应因拆分而变成 public 或全局变量。
   如果模块需要大量直接访问私有状态，优先保留为成员函数，而不是为了“解耦”破坏
   类封装。
6. **适度拆分。** 目标是约 5 至 7 个实现模块，不是把每个小 helper 拆成一个文件，
   也不是留下新的超大单文件。单个模块仍应围绕一项完整职责组织。
7. **优先保持现有路径兼容。** 第一轮优先把新 `.cc` 放在现有 `src/` 根目录，减少
   CMake、板端脚本和测试链接变化；只有依赖边界已经清晰且构建规则同步更新后，才考虑
   建立 `src/session/` 子目录。

## 3. 推荐的模块边界

下面是候选边界，实际移动前必须以函数调用依赖为准，不能机械按行号切割。

### 3.1 `src/session.cc`：总入口和跨阶段编排

最终只保留：

- `SessionManager` 构造函数和对外 public API；
- `process_frame()` 及其必须保持完整的阶段编排；
- 会话生命周期、初始化入口、最终清理等无法独立归属的薄编排函数；
- 需要同时调用多个阶段模块、且本身没有独立业务语义的协调代码。

它不应继续容纳所有几何 helper、所有 HAND 分支和全部无手结算细节。

### 3.2 `src/session_geometry.cc`：纯几何、匹配和位移 helper

候选内容包括：

- `strict_match()`、`partial_match()` 及其框匹配辅助；
- 中心距离、边缘距离、IoU/IoM/cover ratio、框大小差等纯几何计算；
- `move_box()`、`total_move()`、`estimated_box()`；
- `final_motion_reference_diagonal()`、`normalized_final_motion_distance()`、
  `boxes_differ_as_move()`；
- 手框与物体的相交、覆盖、接触判断；
- 只依赖参数和传入对象、没有副作用的枚举/状态名称转换（若它们不需要
  `SessionManager` 状态）。

这些函数应保持无副作用，不修改工作库存、claimed 集合、证据计数或事件列表。
能继续留在单一模块的 helper 不要为了数量而外露。

### 3.3 `src/session_ownership.cc`：直接所有权和匹配仲裁

候选内容包括：

- STRICT / LOCAL_CONTINUOUS / LOCAL_WEAK 的排序与候选比较；
- `build_mutually_unique_hand_direct_old_owner_by_detection_()`；
- 静态预约 `reserve_visible_known_detections_()` 及其无副作用计算版本；
- 旧 C 原位置所有权计划、同类唯一仲裁和歧义集合处理；
- `strict_owner_blocks_old_c()`、直接 owner 计划相关的纯判断。

该模块必须保留现有优先级：旧物体自己的严格原位证据，高于自己的局部连续
证据，高于其他物体的 estimated/path/tentative/reappear 猜测。原位置歧义框
不能按 `map` 遍历顺序强行分配，也不能被 D/suspect 当作升级证据。

细节14/15 中已经验证过的“静态旧 C 预约”和 HAND/CONTACT 直接原位置所有权
必须继续存在，不能因为移动函数而删除或合并掉。

### 3.4 `src/session_hand.cc`：HAND_* / CONTACT_* 有手阶段

候选内容包括：

- `begin_working_operation_()`；
- `append_move_to_existing_hand_tracks_()`；
- `update_existing_contact_tracks_()`、`mark_new_contact_candidates_()`；
- `update_existing_hand_tracks_()`、`reopen_released_static_tracks_()`；
- `scan_or_update_suspects_()`、`mark_newly_hand_blocked_items_()`；
- `apply_suspect_cover_evidence_()`、`advance_claim_grace_()`；
- `process_effective_hand_frame_()`；
- HAND/C-D alias、tentative B、hold/drop 连续证据相关的成员函数。

移动这些函数时，保持当前的严格匹配、局部连续匹配、claim grace、唯一认领、
连续确认和可撤销临时 MOVED 逻辑，不改变状态机分支条件。

### 3.5 `src/session_no_hand.cc`：手离开后的直接观察和恢复

候选内容包括：

- `observe_no_hand_frame_()`；
- `register_post_hand_reveal_suspects_()`；
- 无手原位置恢复、stable gray zone、reappear、直接无手证据和连续计数相关
  的内部逻辑；
- `has_unresolved_no_hand_state_()`（若其只服务无手收尾）。

必须保留细节16已实现的入口修复：找到的原位置候选不能因为 CONTACT 的
`12px` 原位判断而在进入灰区/静态恢复前被清除。身份归属、静止/待确认/移动
判定、最终事件提交仍是三层独立步骤。

### 3.6 `src/session_settlement.cc`：结算、遮挡和事件生成

候选内容包括：

- `prepare_visible_count_settlement_()`、`clear_visible_count_settlement_()`；
- `refresh_confirmed_blockers_()`；
- `settle_no_hand_frame_()`；
- `mark_pending_out_()`；
- 同类数量结算、遮挡并集、IN/OUT/MOVED/OCCLUDED/REVEALED 事件生成和无手
  最终提交所需的纯结算辅助。

事件生成必须继续使用现有工作库存隔离：有手阶段只写 working inventory，
连续无手帧满足条件后才更新正式库存并输出结果。不得因拆到新文件就把临时
状态提前写成正式事件。

### 3.7 `src/session_runtime.cc` 或 `src/session_trace.cc`：可选

只有当依赖边界非常清楚时，才单独拆出：

- `rebuild_persistent_item_index_()`、`reset_operation_runtime_()`、
  `clear_runtime_after_commit_()` 等纯运行时清理；
- `trace_()`、`trace_track_()`、状态名称和调试输出。

如果拆出后需要跨模块共享大量私有字段，或者只是把几十个短函数搬走，宁可
留在 `session.cc`，不要为追求文件数量增加耦合。

## 4. 跨模块共享 helper 的处理方式

匿名命名空间中的 helper 如果只被一个新模块调用，就继续留在该 `.cc` 的匿名
命名空间中。只有确实被两个或更多模块使用的内部 helper，才考虑建立：

```text
include/session_internal.h
```

这个头文件只能暴露最小的内部接口，例如纯几何匹配、框移动或 owner 计划的
小型数据结构；不要把所有原匿名函数一股脑变成全局 API。内部头文件也不能
暴露 `SessionManager` 的私有成员布局。

如果跨模块函数必须访问大量 `SessionManager` 私有状态，优先选择以下顺序：

1. 保留为 `SessionManager` 成员函数，只移动定义；
2. 通过已有成员函数传递必要数据；
3. 只有真正纯函数才提取为内部 helper。

不要为了拆文件引入全局单例、friend 大面积开放、重复状态副本或新的业务抽象。

## 5. 推荐的实际拆分顺序

每一步只移动一个职责模块，完成后立即编译和回放；不要一次性移动全部 6800 行。

1. **建立基线。** 在任何移动前保存当前完整 session3 replay、ASAN/UBSAN replay
   的退出码、关键事件序列、库存数量和 item_id 结果。
2. **先拆 `session_geometry.cc`。** 只移动无副作用几何/匹配 helper，确认链接
   没有重复定义、所有调用仍指向同一实现。
3. **再拆 `session_ownership.cc`。** 先移动 owner 计划和唯一仲裁；重点回放
   同类检测数组顺序变化、HAND_VISIBLE_D、C-D alias。
4. **再拆 `session_hand.cc`。** 只移动 HAND/CONTACT 成员函数，保持原函数体和
   调用顺序；重点检查手进入、手移动、手遮挡、手离开四类边界。
5. **再拆 `session_no_hand.cc`。** 保留灰区连续证据、原位恢复和 reappear；重点
   回放 item#7 轻微框变化不会卡住、item#8 正式移动仍产生 MOVED。
6. **最后拆 `session_settlement.cc`。** 结算和事件最容易受链接顺序/声明影响，
   应在前面模块稳定后处理。
7. **可选拆 runtime/trace。** 只有在不增加共享私有状态后才做。

若某一步出现业务行为差异，先回到该步之前最后一个通过版本的文件组织并定位
差异；禁止通过改变阈值、放宽匹配、减少确认帧或删除事件来“修复”拆分回归。

## 6. 构建系统和目录要求

### 6.1 首选低风险布局

第一轮建议使用现有 `src/` 根目录：

```text
src/session.cc
src/session_geometry.cc
src/session_ownership.cc
src/session_hand.cc
src/session_no_hand.cc
src/session_settlement.cc
```

这样当前 `file(GLOB SRC_FILES "${SRC_DIR}/*.cc")` 可以发现新文件，板端构建
脚本的源目录参数也不需要改变。

### 6.2 需要子目录时

如果后续确实需要 `src/session/` 子目录，必须同步修改
`tools/luckfox_pico_rkmpi_example/CMakeLists.txt`，使用显式 `set(SRC_FILES ...)`
或 `file(GLOB_RECURSE ...)`，并确认：

- 主程序构建包含且只包含一套拆分后的实现；
- 主机回放测试链接同一套实现文件；
- 板端 uclibc/glibc 两种构建都能找到新目录头文件；
- 不再编译旧的完整 `session.cc` 片段和新的重复定义；
- 其他示例工程不会意外捡到本业务模块。

不要依赖构建系统“自动递归发现”这一假设。

## 7. 回归验证标准

主机端回放应根据实际拆分后的文件列表编译，例如：

```bash
g++ -std=c++11 -Wall -Wextra \
  -Itools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/include \
  -Itools/luckfox_pico_rkmpi_example/include/rknn \
  tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/tests/session3_replay_test.cc \
  tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/src/session.cc \
  tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/src/session_geometry.cc \
  tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/src/session_ownership.cc \
  tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/src/session_hand.cc \
  tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/src/session_no_hand.cc \
  tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/src/session_settlement.cc \
  tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/src/inventory.cc \
  -o /tmp/session3_replay_modular
```

命令中的文件要按实际存在的文件调整，不能把一份 `.cc` 重复链接，也不能漏掉
必要实现。每个阶段至少运行：

- 完整 `session3_replay` 回放，退出码必须为 0；
- ASAN/UBSAN 版本回放，不能出现 sanitizer 错误；
- `git diff --check`；
- 关键事件序列、库存数量、item_id、最终框和事件类型与基线逐项对比；
- 检测数组顺序变化相关的同类仲裁测试；
- HAND、CONTACT、HAND_FULL、C-D alias、遮挡/揭示、IN、OUT、MOVED 和无手
  最终提交的已有回放。

验证重点不是“能编译”而已，而是拆分前后结果一致。日志中的阶段标签和必要
的诊断信息也应保持可追溯；不要因为移动 `trace_()` 就删掉日志。

## 8. 版本和文档

纯文件拆分不应引入超参数变化，因此本次不要修改任何阈值，也不要同步改动
`超参数位置与调节说明.txt` 的参数值。所有模块化回放通过后，为了区分二进制
来源，可以把 `FLOW3_BUILD_TAG` 从 `3.0-r18` 升到 `3.0-r19`，并同步更新
`另另一种业务流程(3.0var)/版本说明.md`。如果拆分本身没有形成可运行的新版本，
不要提前修改版本号。

## 9. 完成条件

只有同时满足以下条件，才算本轮拆分完成：

1. `session.cc` 不再承担所有功能，模块职责和依赖关系清晰；
2. 每个函数只有一个定义，未使用 `#include .cc` 拼接；
3. `session.h` 公共接口和私有状态语义未被无必要改变；
4. CMake、主机回放和板端构建使用同一组实现文件；
5. 拆分前后的回放事件、库存和关键状态一致；
6. 主机端完整回放、ASAN/UBSAN、`git diff --check` 全部通过；
7. 没有为了通过测试而调阈值、放宽 NORMAL 匹配或删除原有有效功能。

如果依赖图显示某个模块无法在不破坏封装的情况下独立出来，应保留它在
`session.cc`，并在拆分说明中记录原因；“少拆一个文件”比引入隐式耦合更安全。
