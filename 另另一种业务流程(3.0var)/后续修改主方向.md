# 后续修改主方向：先稳住单手业务，再扩展实时与多手能力

## 1. 本文件的用途

本文件是后续修改的总方向和实施顺序，不直接代替每次实际编码前的
`细节X.md`。每次具体修改仍必须单独说明：问题事实、修改范围、不变量、
回归测试和验收标准。

当前的首要原则是：以已经验证较稳定的**细节14基线**为继续开发的基础。
正常 IN、OUT、直接 MOVED、CONTACT、同类一对一认领、C-D alias、假 D 防线和
已有遮挡能力均有实际价值；后续功能不能为了处理新场景而破坏它们。

细节15的“从相邻关系和最终框反推整条间接推动链”的方案已在实机测试中证明不适合
当前业务：它没有稳定解决推动，且会影响原本正常的直接整理。细节15只保留为失败方案
和分析记录，不能作为后续代码修改的直接依据。

---

## 2. 需要解决的四类问题

### 2.1 遮挡优化

当前已有 `OCCLUDED` / `REVEALED`、前景物品 `block_ids` 和覆盖判断，但还没有针对
实际复杂场景完成系统优化和验收。

需要解决的是：一个旧物品 C 暂时看不见时，系统必须可靠区分以下情况：

```text
被已确认前景物品完整遮挡       -> C 保留原 item_id 和原位置，状态为 OCCLUDED
前景物品移开、C 再次露出       -> C 恢复 VISIBLE，产生正确的 REVEALED
手或物品只部分覆盖 C           -> 不把 C 错当 OUT，也不伪造 OCCLUDED
多个前景物品联合覆盖 C         -> 依据覆盖并集判断，不因单个框不足而误判
C 实际被拿走                    -> 在没有有效遮挡解释后，才允许进入 OUT 证据链
```

本阶段的目标不是增加更多状态，而是先把“看不见不等于出库”的遮挡解释做准确、可回归。

### 2.2 单手实时连续多动作

这里的“实时”不是每一帧都立刻不可逆地修改正式库存，而是：一只手持续在冰箱内时，
系统可以让不同物品分别完成自己的动作，并继续处理下一件物品。

目标场景例如：

```text
同一只手进入
    -> 移动并放下 A
    -> 继续移动并放下 B
    -> C 被临时遮挡
    -> 最后拿走 D
```

当前动态快照和工作库存已经是这项能力的基础，但顶层状态机仍把“手从出现到离开”视为
一段总操作；无手阶段才统一做最终结算。因此 A 即使已经稳定放下，也没有独立的动作
完成边界，后续 B/D 的操作仍与 A 共享同一轮全局收尾。

本阶段需要建立的是**逐物品动作生命周期**：

```text
物品受手影响 -> 形成可撤销候选 -> 获得自身连续直接证据
    -> 在工作库存中独立完成本次动作
    -> 后续帧以该物品的新工作位置继续处理

同一物品尚未获得可靠放下/离开边界时的重复接触
    -> 仍属于同一个动作，只继续补充或修正该动作的证据

同一物品已经在工作库存中独立完成一次动作，之后又被重新接触
    -> 从该物品当前工作位置建立新的动作轮次
    -> 不复用已经结束的旧轨迹、旧原始位置或旧确认计数
    -> 两次动作在内部记录上彼此独立
```

正式库存和对外事件可以继续保留严格确认与回滚边界；“实时”首先要求工作库存和物品状态
实时、正确地向前推进，不能靠整只手离开后才识别前面发生的多个动作。

本阶段的主要实机目标是**同一只手依次处理多个不同物品**，例如 A 完成后处理 B、
再处理 D。实际使用中通常不会连续多次处理同一个物品；但状态模型不能因此强制合并
已经完成后再次发生的真实动作。只有未完成动作内的重复观测才合并；已经完成后的重新
接触应视为新的物品动作。正式事件是立即输出还是在本段总操作最终提交时统一输出，
可以由后续的事件事务策略决定，但两次动作的证据和结果不能互相覆盖。

### 2.3 间接推动/意外碰撞（延期）

手直接移动 A 时，A 可能碰到 B/C，使 B/C 小幅或明显位移。它们没有直接 HAND/CONTACT
证据，因而可能被静态结算、保持未决或造成整轮阻塞。

这是一个独立问题，不是遮挡、实时或多手完成后自然消失的附属问题。尤其多手会使
“哪只手、哪件物品带动了 B/C”的因果归属更复杂。

当前明确延期，原因是：

```text
现有细节15方案没有通过实机验证；
不能用“操作开始时相邻 + 最终框同向偏移”推断真实物理推动；
不能让邻居候选抢占原本成熟的普通无手结算路径；
```

以后重新处理时，必须从细节14真实失败日志定位 B/C 在哪个具体分支未能收尾，做窄补丁。
不得重用细节15的全局相邻移动簇、全局抢框或由最终几何关系猜测整条推动链的做法。

### 2.4 多手同时处理

多手不是“把两个手框同时传入”即可实现的功能。当前流程只选择一只主手作为动作依据，
第二只手没有独立轨迹、身份和物品归属。

需要支持的场景包括：

```text
两只手分别放入两个物品；
两只手分别拿走两个物品；
两只手分别整理不同物品；
两只手共同接触同一物品；
双手交换冰箱中的两个物品。
```

这要求维护跨帧稳定的 `HandTrack`，让物品轨迹记录关联手，而不是继续依赖单一
`old_hand_box_` 和单条公共手轨迹。共同接触同一物品时还必须允许共享归属，不能强行
指定唯一主手。

## 3. 推荐实施顺序

```text
阶段 0：固定细节14稳定基线
    -> 阶段 1：遮挡优化
        -> 阶段 2：单手实时连续多动作
            -> 阶段 3：重新评估间接推动/意外碰撞
                -> 阶段 4：多手同时处理
```

### 阶段 0：固定稳定基线

目的：先确保当前可用能力不再被新方案回归破坏。

要求：

1. 以细节14对应代码作为当前可测试基线。
2. 保留现有主机回放测试和已验证的实机操作。
3. 每次新功能先在这一基线上增加最小补丁；不进行无关重构。
4. `细节15.md` 不删除，但标记为历史分析，不作为实现说明使用。

### 阶段 1：遮挡优化

先做遮挡的原因：它是“物品暂时不可见”的安全解释。若遮挡不可靠，实时处理会把
暂时看不见的 C 错误推进到 OUT，随后所有连续动作都建立在错误库存之上。

本阶段边界：

```text
只优化 C 被前景物品遮挡、前景移动后 C 露出、覆盖并集和 OUT 排除关系；
不同时实现动作分段、间接推动或多手归属；
不改全局 YOLO/NMS、D 确认帧数、正常直接 MOVED 逻辑。
```

最低验收：完整遮挡、部分遮挡、多个前景物品联合遮挡、重新露出、真实出库、同类相邻
遮挡均有回放测试；现有 IN/OUT/MOVED/D 防线回归通过。

### 阶段 2：单手实时连续多动作

这一阶段只支持一只手，但必须让一只手持续在画面内时，A 的完成不会阻塞 B/D 的开始。

关键原则：

```text
动作边界属于物品，不属于“手是否已经离开画面”；
每个物品的候选、确认、放下/离开和重新接触必须独立管理；
尚未完成的同一物品重复接触属于同一动作；已完成后再次接触属于新动作；
工作库存可以逐物品前进，正式库存仍使用严格的确认策略；
遮挡中的 C 继续保留遮挡解释，不因为 A/B 已结算而进入 OUT。
```

最低验收：单手连续完成“移动 A -> 移动 B -> 遮挡 C -> 拿走 D”时，A/B/D 的 item_id
和结果均正确，C 不产生伪 OUT；A 在完成后再次被接触时，应从 A 的当前工作位置开始
新的独立动作，不能沿用旧轨迹或污染 B/D；单一直接操作的原有行为不退化。

### 阶段 3：重新评估间接推动/意外碰撞

只有阶段2稳定后才重新讨论本项。此时系统已经有逐物品动作边界，能够从实际日志判断：

```text
B/C 是否在有手阶段得到过自身检测；
B/C 是在哪个状态或所有权规则中被卡住；
无手时是否存在连续、唯一且属于自身的框；
真正失败的是身份、遮挡、动作结束，还是位移判定。
```

实现前必须先写新的细节说明和对应回放。设计目标是只补真实失败的分支，不能把所有
相邻物品都纳入移动候选，也不能改变正常直接整理的认领和收尾顺序。

### 阶段 4：多手同时处理

最后才扩展为多手。推荐按风险从低到高推进：

```text
两只手远距离、分别处理不同物品
    -> 两只手分别执行 IN / OUT / MOVED
        -> 两只手短暂交叉但仍处理不同物品
            -> 两只手共同接触同一物品
                -> 双手交换两个物品位置
```

多手阶段不能通过“面积最大手为主手”或“把两个手框合并成一个大手框”实现；那会破坏
物品的因果归属、遮挡解释和动作边界。

## 4. 所有阶段共同的不变量

1. 不因新问题而放宽全局 YOLO 分数、NMS、匹配、手接触或 MOVED 距离阈值。
2. 每个库存物品始终保留自身 `item_id`；检测框不是永久身份。
3. 单帧框抖动、短暂漏检或类别抖动只能形成可撤销候选，不能直接写正式库存事件。
4. 同一检测框不能同时被多个物品当作确认依据；同类身份不唯一时保持未决，不猜测。
5. `OCCLUDED` 不是 OUT；HAND/CONTACT 也不等于 MOVED。
6. 新物品 D 必须继续经过既有独立连续证据链，不能借旧 C 的框确认自己。
7. 每次修改必须保留既有回放，并新增只覆盖本次问题的最小回放用例。
8. 不需要为上述开发重新训练 YOLO、重做数据集或进行人工标注；实际失败时优先使用
   现有日志定位状态机分支。

## 5. 后续文档规则

每次开始新功能前，先新建一份 `细节X.md`，至少写清：

```text
本次只解决什么问题；
哪些现有能力绝对不能改变；
允许修改哪些源文件和状态；
不允许修改哪些全局阈值和流程；
需要新增哪些回放/实机验收场景；
何时判定“暂缓”而不是继续扩大修改范围。
```

本文件优先级高于之前关于细节15的实现建议；当旧文档与本文件冲突时，以“稳定基线、
窄修改、遮挡 -> 单手实时 -> 间接推动评估 -> 多手”的顺序为准。
