# 同类静止邻居误入重现候选后的无手回退匹配

> 本文是对细节 8、细节 9 的补充。
>
> 若本文与旧文档在本节定义的“旧 C 已移动、同类静止邻居 B 被错误写入 C 的
> `reappear_candidate`”这一局部场景发生冲突，以细节 10 为准。本文不改变细节
> 9 的同类可见数量不足 OUT 结算，也不改变细节 8 的防重复入库、D 防线和真实
> 身份歧义保护。

## 0. 实施结论与不可退化原则

本次问题已经由完整实机日志定位到明确的控制流漏洞，不是尚未确认的猜测：

```text
触发：A 的历史 reappear candidate 因相邻同类框抖动而指向静止 B；
正确判断：程序识别出“该框严格属于 B，不是 A”；
错误处理：程序立刻把 A 标为永久歧义并 continue；
遗漏步骤：没有继续检查 A 的预计新位置、真实路径和剩余唯一检测框。
```

因此，后续代码修改的目标也是明确且局部的：

```text
只修复“过期候选被独立静止邻居证伪后”的无手回退搜索；
不重写整个状态机；
不改变正常 IN、OUT、MOVED、遮挡或 D 的业务定义；
不通过放宽阈值、降低连续确认门槛或强行分配同类身份来掩盖问题。
```

当前版本在正常再入库、正常出库、普通整理、同类防重复入库、遮挡处理和大部分
相邻同类物品场景中已经表现良好。这些能力是本次修复的保护对象，不是可以为了
解决一个边缘分支而重新试验的范围。

修改时必须遵守以下不可退化约束：

1. 静止旧 B 的独立框仍只能属于 B；本补丁绝不能让移动 A 抢走 B，也不能让 B
   误报 OUT。
2. A 的真实新框仍必须经过既有的连续直接无手帧确认后才能 `MOVED`；本补丁
   绝不能把单帧框、路径猜测或排除 B 的事实直接当作 MOVED 结论。
3. 已有的同类 D 防线必须保持：未解决旧 C 仍阻止同类 D 进入，不能把 A 的真实
   新框或 B 的静止框重复登记为 IN。
4. 细节 9 的“同类可靠可见框持续不足 -> 连续确认后 OUT”必须保持；本补丁
   不能让原本可正确 OUT 的场景重新永久未决。
5. 已确认遮挡仍是 `OCCLUDED_CONFIRMED`，不能因为本次候选排除而变成 OUT。
6. 不同类别、无同类邻居的正常 IN / OUT / MOVED 路径不得改变行为或确认时序。
7. 任何不能同时满足本文件第 3 节适用条件的情况，都必须保留原有保守处理；
   宁可继续未决，也不能为了让本次案例通过而扩大补丁适用范围。

代码完成的最低验收条件不是“本次苹果移动成功一次”，而是：

```text
新增的本次复现回放通过；
细节 8、细节 9 相关回放全部继续通过；
既有正常 IN、OUT、MOVED、同类 D、遮挡、CONTACT_* 回放全部继续通过；
实机上本次操作只产生 A 的 MOVED，不产生额外 IN、错误 OUT 或永久 pending。
```

若局部修复使任何上述既有能力退化，则该实现不可接受；应回到候选排除的边界继续
收紧，而不是通过牺牲原有规则来换取本次案例通过。

## 1. 本次已经由实机日志确认的问题

本次不是阈值偏大、手框没有离开、镜像坐标方向相反，或 YOLO 完全漏检造成的
问题。完整日志已经确认：程序进入了一个错误的无手分支，并在该分支中永久停止了
对移动物品真实位置的继续搜索。

真实操作中有三个同类苹果：

```text
item#1：被手从右上方移动到左下方的旧 C，以下称 A
item#2：一直静止在左上方的旧 C，以下称 B
item#3：一直静止在中上方的旧 C，以下称 C
```

相关位置如下：

```text
A 原位置： (889,254) ~ (1054,416)
B 原位置： (560,249) ~ (749,441)
C 原位置： (729,263) ~ (905,441)

A 手离开后的预计新位置：
            (229,332) ~ (394,494)
```

在手仍在画面内时，A 曾暂时看不见。YOLO 框在相邻苹果之间跳动，使 A 的
`reappear_candidate_box` 先接近 C 的原位，随后变为几乎等于 B 的原位：

```text
frame=211
    A reappear=(734,265)~(901,440)
    -> 实际接近静止 C 的原位框

frame=216（已经无手）
    A reappear=(561,249)~(747,440)
    -> 实际接近静止 B 的原位框
```

第 216 帧同时已经独立确认 B、C 都仍在自己的原位置。日志中 A 的候选框被拒绝：

```text
[MATCH] item=1 detection=1 reject=strictly-belongs-to-other-old-item
```

这条拒绝本身是正确的。它的含义是：

```text
这个框属于静止的 B，不是移动后的 A。
```

错误在拒绝后的处理。当前代码把 A 标为
`no_hand_candidate_ambiguous`，随后 `continue`，因此没有继续尝试 A 的预计新位置、
真实手部路径，或本帧尚未分配的苹果检测框。操作从此一直重复：

```text
no-hand-candidate-strictly-belongs-to-other-old-item
ambiguous-no-hand-path-candidate
defer-commit
```

因此没有 `MOVED`、没有最终库存输出，也没有提交本次操作。

完整证据见：

```text
讨论用/完整的日志.md
    frame 211：A 的错误 reappear candidate 首次出现
    frame 216：手已离开；B/C 被独立认回；A 被错误候选阻断
    frame 217 以后：同一阻断分支反复执行，操作永不提交
```

## 2. 必须明确区分的两种语义

以下两个判断不能再混为一谈：

```text
情况一：A 的候选框严格属于已有独立证据的静止旧 B
    正确含义：这个框不是 A，应从 A 的候选中排除。

情况二：一个框可能同时属于多个尚未独立确认的同类旧 C
    正确含义：真实身份仍不唯一，应保持 UNRESOLVED。
```

细节 8 所保护的是情况二，不能削弱。此次漏洞属于情况一：B 在当前无手帧有自己的
独立原位框，A 不应再把 B 的框视为“也许是自己”。

正确业务结论应为：

```text
B 使用自己的框，保持 STATIC_CONFIRMED；
A 不能拿走 B 的框；
但 A 仍有权继续在自己的预计位置和实际路径上寻找真正的新框。
```

不能把“B 不是 A”错误翻译成“所以 A 永远无法继续结算”。

## 3. 本次修改的严格适用范围

本补丁只能在同时满足以下条件时启用：

1. 当前正在一次已经开始的手操作中，且当前帧已无手。
2. 当前处理的是旧库存 C，不是疑似新物品 D。
3. C 有一个历史 `reappear_candidate_box`，或本帧候选搜索先命中了该候选。
4. 命中的检测框与另一件同类旧物品 B 严格匹配。
5. B 在当前无手帧中具有独立、可信的归属证据，例如唯一原位框、当前帧一对一静态
   保留关系，或等价的已确认直接观测；不能只因几何上靠近 B 的旧位置就排除。
6. 该框不是 A 自己的原位置，也不是 A 已确认的移动终点。

只有此时，该框才是 A 的“排除证据”。

下列情况仍必须保留现有的保守歧义逻辑，不能套用本补丁：

- B 自己没有当前帧独立原位/移动证据，只是 A 的路径碰巧经过 B 的旧位置。
- 一个同类框同时被多个尚未解决的旧 C 合理解释。
- A 与 B 的同类数量相等，但存在“取出一个再放入一个”的可能；仍需走细节 8 的
  C -> B / D 来源与连续确认链路。
- 有手阶段。手仍在时，原有 HAND_*、CONTACT_*、保护期、B 认领和 D 防线不改。
- 已确认 D 的完整框。D 仍需由自己的完整证据链管理，不能被本补丁抢走。

## 4. 无手帧的正确处理流程

### 4.1 先确认静止邻居的独立归属

在处理 A 的历史重现候选前，必须能判断当前检测框是否已真正属于 B，而不是仅靠
“它大概靠近 B”。推荐在同类旧 C 的无手处理开始前，先建立本帧的独立静态归属信息：

```text
检测框 i -> item#B
归属原因：DIRECT_ORIGINAL / 已有一对一静态保留 / 等价直接证据
```

这份信息只用于排除错误候选和保持一对一，不允许一个检测框同时归给 A、B 两件旧物。

如果现有处理顺序不便于真正提前保留，也可以使用无副作用的前瞻查询：确认该检测框
是否能唯一、严格地作为 B 当前的原位检测。无论采用何种实现，必须满足第 3 节的
“B 有独立当前帧证据”条件。

### 4.2 历史候选命中静止邻居时：清除并继续，不是终止

当 A 的 `reappear_candidate_box` 命中一个已独立属于 B 的框时，按以下顺序处理：

```text
1. 不把该检测框 claim 给 A。
2. 记录“该候选严格属于 B”的排除结果。
3. 清除 A 的这个过期 reappear candidate，或标记为本帧及后续不可再作为 A 的候选。
4. 不设置 A 的 no_hand_candidate_ambiguous。
5. 不在这里 continue。
6. 在同一张无手帧继续执行 A 的后备查找。
```

必须注意：清除的是“误指向 B 的候选”，不是清除 A 的整个活动轨迹、
`needs_no_hand_settlement`、手部路径或移动证据。

### 4.3 A 的后备查找顺序

排除错误候选后，A 仍必须在同一无手帧依次尝试现有的安全来源：

```text
1. A 自己的原位置
   若 A 真回到原位，应保持/恢复 STATIC_CONFIRMED。

2. A 的已放下位置或 estimated_box(reference)
   这是本次实机场景中应继续尝试的来源。

3. A 的真实 HAND_* / CONTACT_* observed path
   只能使用已有的唯一、连续匹配规则，不能扩大几何阈值。

4. 现有 unique_no_hand_reappear_detection_for_track() 的唯一候选扫描
   但必须跳过已经排除、且已经一对一保留给 B 的检测框。
```

同一检测框在本帧中已被确定为 B 的独立框后，不得因为第 4 步再次被 A 找到，又重新
把 A 标成歧义。因此，实现中应传递“本帧排除的 detection index 集合”，或使用等价的
所有权查询，让后续查找与歧义检查都跳过它。

### 4.4 找到 A 的真实新框后的确认

后备查找找到 A 的新位置时，不能在单帧直接提交 `MOVED`。必须保持原有连续确认：

```text
第一张直接无手帧：
    A 的真实新框成为新的 reappear candidate / 连续确认第 1 次；
    操作暂不提交。

第二张与该候选连续自匹配的直接无手帧：
    A -> MOVED_CONFIRMED；
    B、C 继续保留；
    本次操作可正常提交。
```

本次补丁只恢复“继续寻找”的机会，不降低 `MOVED` 的证据门槛。

### 4.5 本帧确实找不到 A 时的处理

若排除 B 的静止框后，仍找不到 A 的独立新框：

```text
不得强行 MOVED；
不得把 B 的框给 A；
不得创建同类 D；
不得因为一帧缺失直接 OUT。
```

后续行为按原有规则继续：

- 同类可见数量没有减少、且仍存在真正未解决的多个候选：保持细节 8 的
  `UNRESOLVED`。
- 同类可靠可见框数量持续少于旧物品数量：走细节 9 的一框一物品和连续无手 OUT
  结算。
- A 有确认遮挡解释：保持 `OCCLUDED_CONFIRMED`，不能 OUT。

关键区别是：已独立属于 B 的框只会被排除，不得单独制造 A 的永久歧义。

## 5. 需要修改和复查的代码位置

以下位置必须一起检查，不能只删掉一个 `continue`：

### 5.1 `observe_no_hand_frame_()` 的候选优先级

当前代码会优先使用已有 `reappear_candidate_box`：

```text
src/session.cc
    约 3623 行：先按 reappear_candidate_box 找 found
    约 3633 行：只有 found < 0 才继续按 reference 找
```

这条优先级本身仍合理：真正的历史 B 候选通常比“旧框加手位移”的估计更可靠。
但必须加入“候选已被独立静止旧物品占用时，候选无效，继续 fallback”的分支。

实现要求：

```text
found 来自 reappear candidate
    + found 严格且独立属于 other_old_item
        -> 清除/排除该 reappear candidate
        -> found 重置为 -1
        -> found_as_reappear_candidate 重置为 false
        -> 继续 reference/path/unique-reappear 扫描
```

不得把这个场景留在 `found >= 0` 的普通“候选已被其他旧 C 占用”分支中。

### 5.2 “严格属于另一旧物品”的分支

当前代码约 3707 行存在以下旧行为：

```text
strictly-belongs-to-other-old-item
    -> reappearance_pending = true
    -> no_hand_candidate_ambiguous = true
    -> continue
```

需要拆为两类：

```text
另一旧物品没有独立当前帧归属：
    保持原有 no_hand_candidate_ambiguous 与 continue。

另一旧物品已独立、唯一地拥有该框，且 found 来自 A 的过期候选：
    这是“排除错误候选”；
    不设置 no_hand_candidate_ambiguous；
    清除候选后继续寻找 A。
```

对于 `found` 不来自历史候选、但后备路径本身命中了 B 的独立框，也应采用同样的
“排除该框并继续下一来源”语义；不能只修复一种调用顺序后让另一条路径仍卡死。

### 5.3 `has_ambiguous_no_hand_reappear_candidate()`

该辅助函数当前遇到“严格属于另一旧物品”的检测会立刻返回 `true`。即使主流程完成
了 fallback，这个函数仍可能把同一个 B 框重新解释为 A 的永久歧义。

必须同步改为：

```text
检测框已在本帧独立保留给 B
    -> 从 A 的可行候选与歧义候选集合中跳过；
    -> 不计入 viable_count；
    -> 不返回 true。

检测框没有独立 B 所有权，只是多个未解决 C 都可能解释它
    -> 继续返回 true，保持真实歧义。
```

这项同步修改是防止“第一处修好、下一轮又被辅助函数重新卡住”的必要条件。

### 5.4 一对一所有权与 D 防线

实现不能为解决 A 的问题而让 A 抢走 B 的框，或让剩余检测框立刻变成新 D。
必须保持：

```text
B 的独立框：只属于 B；
A 的真实新框：只在 A 通过连续确认后属于 A；
未解决旧 C：继续阻止同类 D 进入；
一个 detection index：同一帧最多被一件旧 C 或已确认 D 占用。
```

现有 `reserve_unique_no_hand_static_inventory_detections()`、同类 D guard、细节 8
的 `needs_no_hand_settlement` 以及细节 9 的 visible-count 结算都必须在修改后复查。

## 6. 必须补充的诊断日志

本次实机日志已经成功定位问题，但后续实现必须把“为什么排除、排除后是否继续找到
真正 A”明确写出来。日志仍受 `FLOW3_DEBUG_TRACE_LOG` 控制，只读取状态并输出，不能
改变业务行为。

建议使用现有 `[3.0-TRACE][MATCH]` 前缀，至少记录：

```text
[MATCH]
op / frame / HAND 或 NO_HAND
item_id=A
detection index 和 BBox
candidate_source=REAPPEAR_CANDIDATE / REFERENCE / PATH / UNIQUE_REAPPEAR
other_owner_item_id=B
other_owner_evidence=DIRECT_ORIGINAL / STATIC_RESERVATION / ...
action=EXCLUDE_STALE_CANDIDATE_AND_FALLBACK
```

候选清除后，还必须有一条结果日志：

```text
[MATCH]
item_id=A
excluded_detection_indices=...
fallback_source=REFERENCE / PATH / NONE
fallback_detection=...
candidate_reset=1
ambiguous_after_exclusion=0 或 1
```

如果最终仍未找到 A，日志应区分：

```text
no-hand-no-path-candidate
    -> 真的没有 A 的可用候选

no-hand-path-ambiguous
    -> 仍存在未被独立静止邻居占用的真实同类歧义

excluded-static-neighbor-then-no-a-candidate
    -> B 已排除，但 A 本帧没有新框；后续交给正常未决/细节 9 OUT 规则
```

`NO-HAND` / `SETTLE` 日志还应说明：本帧为何继续等待，是“真实歧义”、
“A 的新候选等待第二帧”，还是“可见数量不足累计 OUT”。不要再只打印同一个
`ambiguous-no-hand-path-candidate`，否则无法区分三种完全不同的业务状态。

## 7. 必须新增的回放测试

现有 `test_active_a_moves_next_to_static_same_class_b()` 覆盖了“移动 A 靠近静止 B”
的正常路径，但没有强制制造“有手阶段 A 的 reappear candidate 先误指向 B/C”的状态。
它不足以防止本次漏洞回归。

至少新增以下测试：

### 7.1 三个相邻同类苹果，错误候选后仍正确 MOVED

建议名称：

```text
test_stale_same_class_reappear_candidate_falls_back_to_moved_a
```

场景：

```text
初始：A（右）、B（左）、C（中），三者同 cls_id
有手：A 被遮挡；构造 A 的 reappear candidate 与 B 或 C 的原位框匹配
无手：B、C 都有自己的独立原位框；A 在左下方有独立新框
下一张直接无手：三个苹果仍各有独立稳定框
```

断言：

```text
第一张无手帧：
    不提交；
    不发 MOVED / OUT / IN；
    A 不得保持 no_hand_candidate_ambiguous；
    A 的新框必须成为新的连续确认候选，而不是 B/C 的旧框。

第二张无手帧：
    正常提交；
    仅 A 触发 MOVED；
    B、C 都保留；
    总库存数量不变；
    不得出现 OUT；
    不得出现 IN 或新的同类 D。
```

测试必须确实断言 A 在进入首张无手帧前已带有指向 B/C 的
`reappear_candidate_box`；否则没有走到本次错误分支，测试没有价值。

### 7.2 排除静止邻居后，A 本帧确实不存在

场景：

```text
A 的历史候选错误指向静止 B；
B 有独立原位框；
A 的真实新框本帧没有被检测到。
```

断言：

```text
不得把 B 给 A；
不得强行 MOVED；
不得误建 D；
不得因首张无手帧直接 OUT；
后续只按细节 8 的真实歧义或细节 9 的连续数量不足规则处理。
```

该测试保证修复不会把“消除永久歧义”误做成“无证据也强行成功”。

### 7.3 真正共享且尚未独立归属的同类框

场景：两个或多个旧 C 都能合理解释一个同类框，但没有任一静止邻居获得独立当前帧
原位归属。

断言：

```text
仍保持细节 8 的真实 UNRESOLVED；
不能仅因本补丁而让其中一个 C 随意 MOVED、OUT 或把框分配成 D。
```

### 7.4 既有完整回归集

实现后必须重新运行并保持通过至少以下相关用例：

```text
test_active_a_moves_next_to_static_same_class_b
test_same_class_static_neighbor_box_allows_active_a_out
test_adjacent_same_class_real_boxes_out_only_removed_item
test_adjacent_same_class_single_frame_deficit_recovers_without_out
test_adjacent_same_class_deficit_requires_continuous_survivor_box
所有既有 IN、同类 D、CONTACT_*、遮挡、普通 MOVED 回放测试
```

尤其不能让细节 9 的“同类数量持续不足 -> 正确 OUT”重新回到永久未决。

## 8. 超参数、版本与实施限制

本次是候选排除和控制流修复，不需要放宽或收紧任何几何/时间阈值。因此：

```text
不新增数值超参数；
不修改 FLOW3_TRACK_*；
不修改 FLOW3_REAPPEAR_CANDIDATE_*；
不修改 OUT/MOVED 的连续帧门槛；
不以调阈值掩盖这个逻辑漏洞。
```

下一次真正修改代码时：

1. 更新 `fridge_config.h` 中的 `FLOW3_BUILD_TAG`。
2. 在 `超参数位置与调节说明.txt` 的“固定规则”和诊断日志说明中，同步说明：
   “已独立保留给静止同类旧 C 的框，对移动 C 是排除证据；排除后会继续做路径/预计
   位置匹配，不会永久标为歧义。”
3. `FLOW3_DEBUG_TRACE_LOG` 继续只是日志开关，不得成为匹配行为开关。
4. 先运行主机回放测试，再交叉编译并部署到板端做实机验证。

## 9. 最终验收标准

针对本次实机复现操作，修复后的预期日志链路应接近：

```text
frame N，无手：
    A 的旧 reappear candidate 命中静止 B
    -> EXCLUDE_STALE_CANDIDATE_AND_FALLBACK
    -> B 保留自己的原位框
    -> A 在左下方真实框开始无手连续确认
    -> 本帧等待第二帧，不提交

frame N+1，无手：
    A 再次匹配自己的左下方真实框
    -> A MOVED_CONFIRMED
    -> B/C STATIC_CONFIRMED
    -> commit
    -> 只发出 A 的 MOVED 事件
```

而不应再出现：

```text
同一个静止 B 框被反复写为 A 的 reappear candidate
-> strictly-belongs-to-other-old-item
-> ambiguous-no-hand-path-candidate
-> defer-commit 无限循环
```
