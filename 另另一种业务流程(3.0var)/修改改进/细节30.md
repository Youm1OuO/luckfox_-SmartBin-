## 0. 文件性质与最高约束

本文是下一次修改 3.0 业务代码的实施指导说明。本次只修“双手同时各移动一个物品”暴露的
证据窗口过紧问题，不推翻细节22~29 任何已接入方向，不新增业务概念。

**当前已经有效的功能必须保持有效，绝对不能为了修这个问题而改坏：**

- 单手入库、出库、整理、静态回原位；单手连续操作多个物品；
- 两只手分别操作不同物品，各自按 `hand_id` 用各自 `move_value`；
- 手框合并/漏检/拆分/顺序变化时暂停错误手位移（`no-delta` 保护），不借用另一只手 delta；
- 两只手共同接触同一物品时的歧义保护；多物品入库/出库/整理；
- CONTACT、严格遮挡、因果遮挡、遮挡解除、REVEALED、正常 D/IN、C-D alias、原子提交；
- 细节27 类别无关 shadow 与全局一对一归属；细节28 统一实体图与启动保护；
- 细节29 刚修好的“因果遮挡证明对归属歧义免疫”（本次绝不能回退它）。

**特别禁止（本次绝不允许发生）：**

- 把“看到位置变了”直接判成 MOVED；把“框消失”直接判成 OUT；
- 放宽 `boxes_differ_as_move`、`strict_match`、手框匹配、OUT/遮挡阈值来强行凑结果；
- 用 detection 数组顺序、item_id、左右位置、“最近的手”来消除真实的同类归属歧义；
- 让某个物品抢先提交并清空同一 operation 中其他未结案 runtime（破坏原子提交）；
- 削弱双手合并/歧义期的 `no-delta` 保护，或让 merged 手的位移写进任何物品。

若改动或复用任何超参数，必须同步更新 `超参数位置与调节说明.md`（原值/新值/用途/风险）。
本次目标是**尽量不新增超参数**，只放开一条已有的、明显不一致的证据门槛（见第 3 节）。

## 1. 复现场景与现象

初始库存 2 件：item#1=橙子(cls=2)、item#2=苹果(cls=0)，两者相邻。
操作：双手各抓一个，一手把苹果往一侧移、另一手把橙子往另一侧移（一手一物，同时进行）。
理想结算：`[苹果 MOVED]` + `[橙子 MOVED]`。
实际：**两个 MOVED 都没出**；提交后苹果位置更新了但没有整理事件，橙子连位置都停在旧值。

（用户开了镜像，方向描述与坐标左右相反，不影响分析。）

关键日志（见《测试后的结果与发现的问题.md》）：

```text
frame155  create hand=2 / create hand=3          ← 两只手几乎同时出现
frame155-157  merged-or-ambiguous hand=2,3 ...   ← 先被判互相合并/歧义，全程 no-delta
frame158  recover hand=2,3 (action=no-delta)     ← 才分离，但恢复首帧仍不给 delta
frame159  update hand=2 delta / update hand=3 delta   ← 到这里两手才真正有可靠位移
frame161  HAND-ASSOC runtime=2 item=2 hand=3 → item#2 进入 CONTACT_CANDIDATE
          （全程没有任何 item=1 的 HAND-ASSOC bind：橙子那只手从没绑上橙子）
frame162  手离开(NO_HAND)。苹果 item#2 CONTACT_CANDIDATE，橙子 item#1 无 runtime
frame162  candidate=0 cls=2(橙子新框) → keep-unresolved（同类旧 C 未解决）
frame163  commit events=0；item#2 state=NORMAL contact=CONTACT_CANDIDATE resolution=NONE
```

两个现象、三个根因，见下。

## 2. 根因分析（均已从代码层面确认）

### 2.1 共同上游：双手同时启动，身份分离慢，压缩了移动证据窗口

两只手几乎同时进入、空间接近，`update_hand_tracks_`（`src/session_hand.cc:446~460`）先把它们
判为 `MERGED_OR_AMBIGUOUS` / `TEMP_LOST`，期间全部 `action=no-delta`（正确的保护，见
`session_hand.cc:428~443` 恢复首帧也不补 delta）。直到 frame 159 两手才真正分离出可靠 delta。
于是：真正能“用手位移驱动物品”的帧只剩 frame 159~161，随后 frame 162 手就离开了。

这一段保护本身是对的，不能削弱。问题在于**下游的“移动确认”把证据门槛设得太死**，在这种
被压缩的窗口下攒不够证据。以下 2.2 / 2.3 是两个具体的、可安全放开的门槛。

### 2.2 现象一（苹果有位移却无 MOVED）：CONTACT 状态下 reappear 确认没有被接受为移动证据

苹果 item#2 在 frame 161 进入 `CONTACT_CANDIDATE`，frame 162/163 无手帧被 `directly-observed`
连续看到新位置（`reappear=1/4`，已达 `FLOW3_REAPPEAR_CANDIDATE_CONFIRM_FRAMES=2` 门槛）。
但它始终 `resolution=NONE`，从未升级 MOVED_CONFIRMED。原因在无手帧确认整理的判据
`src/session_no_hand.cc:1190`：

```cpp
if ((track.hold_and_move || has_meaningful_hand_move(track)) &&
    boxes_differ_as_move(track.original_box, d.box) && ...) {
    confirm_rearrange_(track, d.box, d.score, trace_frame_id_);
}
```

它只认 `hold_and_move` 或 `has_meaningful_hand_move`。而：

- `hold_and_move` 在 CONTACT_CANDIDATE 下没被置位（手没握住足够久就离开）；
- `has_meaningful_hand_move`（`session_geometry.cc:452`）只看 `track.move_values`，但
  **CONTACT 状态的手位移根本没写进 move_values**：见 `session_hand.cc:993~998`——
  CONTACT 时 delta 只 push 进 `hand_move_values`（注释明写“仅作调试/未来扩展记录”），
  紧接着 `if (!is_hand_track) continue;` 跳过，不写 `move_values`。
- 因此条件 1 永远为假，即使 `boxes_differ_as_move` 与 reappear 连续确认都成立，也不 MOVED。

**不一致的证据在同文件已有先例**：`session_no_hand.cc:1312~1317`（遮挡上下文里判断某 C 是否
“真的移动过”）已经把 `has_reappear_candidate_box && reappear_candidate_is_confirmed(...)`
当作合法的 `has_real_move_evidence`。也就是说系统别处已经承认“无手帧连续确认的新位置”是可靠
移动证据，只有 1190 这一处没纳入，属遗漏而非有意从严。

### 2.3 现象二（橙子位置停在旧值）：被移动的旧 C 从未被任何手绑定，新框归属长期未决

橙子那只手在 merged/ambiguous 期没能绑上橙子，`begin operation` 后也没有出现任何
`HAND-ASSOC bind item=1`。因此橙子 item#1 全程**没有 runtime**、没有 CONTACT、没有 reappear
候选。手离开后，右侧那个橙子新框在无手帧被判为 `independent-d-candidate`，又因
`session_no_hand.cc:262` 的 D-GUARD “同类旧 C 尚未解决”而 `keep-unresolved`：既不敢把 item#1
位置更新到新框（怕误判），也不敢当新物品 IN。

结算阶段的三条兜底指派——`forced_detection_by_item`（`session_settlement.cc:1459`）、
`visible_count_detection_owner_`（1482）、原位置证据（1505）——都要求该 item 有 runtime 计划
或有 visible-count 保留。橙子 item#1 二者皆无，于是这些兜底都跳过它，item#1 位置保持
`operation_start` 的旧值。这就是“橙子连位置都不对”。

**注意**：这里不能靠“放宽 D-GUARD 直接把橙子新框当 item#1 更新”来修——那正是第 0 节禁止的
“用位置/顺序强消同类歧义”。正确方向是让被移动的旧 C **在有手期就能建立起可信的 owner 关系**
（哪怕手身份分离得晚），从而拥有 runtime 与移动证据，走正常 MOVED 路径。

## 3. 解决方法

分两步。**第一步（修 2.2）是主修，改动小、风险低、单独就能救活“苹果有位移却无 MOVED”这类
最常见的双手整理**；第二步（修 2.3）更结构化，先落第一步、验证稳定后再评估是否需要。

### 3.1 主修：把“无手帧连续确认的 reappear 新位置”纳入 confirm_rearrange_ 的移动证据

**唯一改动点：`src/session_no_hand.cc:1190` 的 `confirm_rearrange_` 触发条件。**

把移动证据判据与本文件 1312~1317 已有的先例对齐，新增“reappear 候选已连续确认”这一支：

```cpp
// 现状（1190）：只认 hold_and_move / has_meaningful_hand_move
if ((track.hold_and_move || has_meaningful_hand_move(track)) &&
    boxes_differ_as_move(track.original_box, d.box) && (...alias 门槛...)) {
    confirm_rearrange_(track, d.box, d.score, trace_frame_id_);
}

// 改为：补上“连续确认的 reappear 新位置”作为等价的移动证据
const bool reappear_move_evidence =
    track.has_reappear_candidate_box &&
    reappear_candidate_is_confirmed(track);   // 已达 FLOW3_REAPPEAR_CANDIDATE_CONFIRM_FRAMES
if ((track.hold_and_move || has_meaningful_hand_move(track) ||
     reappear_move_evidence) &&
    boxes_differ_as_move(track.original_box, d.box) && (...alias 门槛原样保留...)) {
    confirm_rearrange_(track, d.box, d.score, trace_frame_id_);
}
```

**为什么安全（不会把静止物 / YOLO 抖动误判成 MOVED）：**

- `boxes_differ_as_move(track.original_box, d.box)` 门槛**原样保留**：位移必须达到正式移动
  阈值，YOLO 小抖动（`LOW_MOTION_STATIC` / `STATIC_GRAY_ZONE`）不会触发。
- `reappear_candidate_is_confirmed` 要求连续 `FLOW3_REAPPEAR_CANDIDATE_CONFIRM_FRAMES` 帧
  在同一新位置稳定自匹配，单帧误检不算数。
- 该 track 必须已经是本 operation 内被绑定过的旧 C 的 runtime（有 reappear 候选说明它经历过
  HAND/CONTACT 关联并在无手期重新出现），不是凭空的新框。
- 只补一个“或”分支，不删除、不放宽原有两条证据，也不动 alias 门槛
  （`shared_quarantined_alias` 相关判断原样保留）。

**不新增超参数**：复用既有 `FLOW3_REAPPEAR_CANDIDATE_CONFIRM_FRAMES`。

### 3.2 结构修（修 2.3，可作为第二步，先评估再实施）

现象二的根：被移动的旧 C 因双手身份分离晚，整个有手期没能建立 owner 关系，于是无 runtime、
无移动证据，新框只能挂在 D-GUARD 的 keep-unresolved。主修 3.1 只能救“已经绑定上手”的物品
（苹果），救不了“从没绑上手”的物品（橙子）。

修 2.3 的正确方向（**不放宽同类归属、不按位置强指派**）：

- 在有手阶段，当一个旧 C 因两手 merged/ambiguous 而暂时拿不到唯一 hand owner 时，只要它自己的
  完整框在其原位置持续消失、且存在一个“同类、达到 reappear 连续确认、且不被任何其它旧 C 严格
  占用”的新框，允许在**无手结算**阶段把它作为该旧 C 的 reappear 候选接手（走 3.1 的 MOVED
  路径），而不是停留在 D-GUARD keep-unresolved。
- 关键约束：该新框必须唯一地对应到这个旧 C（同类且无其它旧 C 能严格解释它），否则保持未决
  ——绝不能在“两个同类新框、两个同类旧 C”彼此无法区分时按位置/顺序硬配。
- 这本质是把细节28“统一实体图 + 物品路径确认”用到“owner 建立晚于物品移动”的场景，属于对
  现有 reappear/global-owner 机制的延伸，不是新机制。

因为 3.2 触及归属仲裁，风险高于 3.1。**建议：先实施并验证 3.1；若单手及“双手各移一物”里被
绑定上的那一侧已恢复正常，再单独立项做 3.2**，避免一次改动面过大牵连同类仲裁。

#### 3.2 的结构确认（已读代码核实，供后续实施）

- 橙子 item#1 全程无 runtime。`build_global_ownership_plan`（`session_ownership.cc:443`）为
  无 runtime 的旧 C 只用它的**旧 base_box** 建边（466 行），配对函数
  `record_reference_assignment_edges`（229 行）要求 `strict/track/partial_match_box` 命中；
  橙子移远后全不命中 → **无边 → 该 item 拿不到任何 detection → 位置冻结在旧值**。
- 即便让它拿到 detection：结算里 `forced_detection_by_item`（`session_settlement.cc:1459`）
  只更新位置，注释明确“不单独生成 MOVED”（1481）。所以 3.2 若只放开建边，最多修好
  **位置**，仍不会为橙子发 MOVED（因为我们从没跟踪到搬运它的手，没有移动证据）。

#### 3.2 的安全实施约束（真要做时必须遵守）

- **只在结算调用处放开“最后手段”同类边，不能改共享函数的默认行为。**
  `build_global_ownership_plan` 同时被有手期 `record_direct_object_exit_evidence_`
  （`session_hand.cc:660`）和结算调用——直接改建边会双向波及。必须新增一个默认关闭的参数，
  仅在结算调用点为“无 runtime 且原位已空的旧 C”开启一条高代价 last-resort 同类边。
- **唯一性由既有 `forced` 判定兜底**：仅当移除该配对会降低基数（唯一必需）才 `forced`；
  两个同类旧 C 对两个同类新框且对称时会落入 `ambiguous_item_ids`，保持未决——绝不按位置硬配。
- **position-only，不伪造 MOVED**：无移动证据的旧 C 只更新位置，不进 `confirmed_moved_ids_`。
  是否为这类“未跟踪到手”的搬运补发 MOVED，属独立business 决策，本文件不擅自开启。

#### 本次实施范围

**本次只实施 3.1。** 原因：3.1 小而安全、与同文件既有先例一致、可用回放充分验证；3.2 触及
归属仲裁（回归高发区）且 `build_global_ownership_plan` 双向被调用，本环境无法运行回放套件证明
无回归，按第 0 节“不破坏既有功能”的最高优先级，3.2 留作**验证过 3.1 之后的独立跟进**。若你要
一并做 3.2，必须补齐第 5 节的所有回放（含对称同类不乱配的反向用例）并逐项通过后才能合入。
