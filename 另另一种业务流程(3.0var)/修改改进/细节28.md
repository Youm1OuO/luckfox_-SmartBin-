# 细节28：统一操作实体图、启动保护与物品路径确认

## 0. 文件性质与最高约束

本文是下一次修改 3.0 业务代码的实施指导说明。本次只针对测试记录中的两个问题补齐证据链，不推翻细节27已经接入的整体方向。

**当前已经有效的功能必须保持有效，绝对不能为了修这两个问题而改坏：**

- 单手入库、出库、整理和静态回原位；
- 一只手连续操作多个物品；
- 两只手分别操作不同物品，并按各自 `hand_id` 使用各自的 `move_value`；
- 手框合并、漏检、拆分、输出顺序变化时暂停错误手位移，不借用另一只手的 delta；
- 两只手共同接触同一个物品时的歧义保护；
- 当前已经较稳定的多物品入库、多物品出库和整理路径；
- CONTACT、严格遮挡、因果遮挡、遮挡解除、REVEALED、正常 D/IN、C-D alias 和原子提交；
- 细节27中的类别无关 shadow、全局一对一归属、`direct_object_exit_evidence`、`hand_group_exit_witness`。

特别禁止：

- 按当前识别到的手数量决定物品数量或是否启动操作；
- 因为一次压力测试卡住就放宽手框匹配、OUT/MOVED 帧数或遮挡阈值；
- 看到一个移动框就直接生成 MOVED，看到一个消失框就直接生成 OUT；
- 按 detection 数组顺序、物品 ID、左右位置或“最近的一只手”强行消除真实歧义；
- 让任意一个物品先提交并清空同一 operation 中其他尚未结案的 runtime。

代码可以按职责拆分到不同文件中。若修改或新增任何超参数、帧数、面积比例、距离或上限，必须同步更新 `超参数位置与调节说明.md`，记录原值、新值、用途和风险；若复用已有参数，则明确写出本次未改超参数。

## 1. 统一机制：所有类别、所有实体共用一张证据图

本文件不能被实现成“给三件同时出库加一个条件、给两个同类橙子再加一个条件”。两个测试只是暴露了同一个架构缺口：操作启动、物品路径、局部 owner 和最终结算没有始终使用同一个实体级事实来源。

下一次实现必须以一个统一的 operation candidate graph 为中心，而不是分别维护“同类方案”“异类方案”“单手方案”“双手方案”。手的数量、类别是否相同、检测数组顺序和物品所在左右位置都只提供候选信息，不能决定业务结论。

### 1.1 统一实体图

每一帧在本 operation 内维护同一组节点和关系：

```text
E = 实体节点
    - operation-start 的旧库存 C
    - 已存在但未正式 IN 的候选 D
    - 已确认、仍在本 operation 中参与遮挡/归属的物品

B = 当前食品 detection
H = 当前内部 hand_id / hand group
S = 重复观测 shadow（诊断关系，不是库存实体，不创建 E）
```

所有 `E -> B`、`E -> H` 和 `B -> S` 关系都应进入同一张图，并带有：

```text
source            strict / original / object-path / contact / hand-context /
                  shadow / occlusion / count-auxiliary
class-relation    compatible / unstable-class / incompatible
geometry          strict / partial / track-path / contained-duplicate
continuity        first-frame / last-frame / consecutive-streak
ownership         forced / ambiguous / blocked / none
conflict          alias / stronger-owner / occlusion / independent-history
```

`E` 的结论只由自己的边和自己的证据账本导出。一个物品不能因为同批另一件物品已经 MOVED/OUT/IN 而继承证据，也不能因为另一件物品的手发生合并而丢失自己的直接检测路径。

### 1.2 类别是兼容性事实，不是算法分叉

同类和不同类必须走同一套候选图、全局一对一归属和连续确认流程。类别只影响某条 `E -> B` 边能否存在、以及它的初始强度：

- 类别一致：普通强兼容边，可由严格框、部分框、连续对象路径等已有几何事实加强；
- 类别不同：默认不把 B 继承为旧 C 的身份，但仍进入同一张图，作为真实 D、类别抖动、跨类别重复 shadow 或竞争实体的候选；
- 类别暂时变化：必须有连续几何、已有 hand/contact 上下文、shadow/独立历史等证据，才能从 `incompatible` 升到 `unstable-class`；
- 低分近同框：无论类别相同还是不同，都先走细节27的 shadow 复核，不分别开同类/异类特例；
- 真实新物品：只要它与旧 C 分离、具有独立连续路径或独立 hand/contact 上下文，就必须从 shadow/竞争关系释放，按原有 D/IN 链路处理。

因此，“不同类物品同时移动”与“同类物品相贴后同时移动”的差异只能体现在图中候选边的多少和强弱，不能体现在后续改用另一套判断算法。

### 1.3 统一证据账本，不复用语义混乱的布尔值

每个实体 E 都要维护一份本 operation 有效、可撤销的事实账本。建议把“物品自己的路径事实”与“由它导出的 MOVED/OUT 资格”分开：

```text
capture-start evidence       手接触/覆盖、数量缺额、局部框等启动事实
hand-path evidence           可靠 hand_id 的 delta 路径；中断时冻结，不伪造
object-path evidence         连续、全局唯一的 E -> B 自匹配路径
global-owner evidence        当前及连续帧的 forced / ambiguous 归属结果
occlusion / missing evidence 已有正式遮挡或连续无手缺失事实

object-path-move-ready       由 object-path + owner + capture context 导出
object-path-exit-ready       由 object-path/exit witness + 后续缺失链导出
```

不要把 `direct_object_exit_evidence` 直接扩展成“看到任何对象路径就可 OUT/MOVED”的万能布尔值。实现时可以保留现有字段兼容旧逻辑，但应明确拆出或推导出上述两个不同资格：

- `object-path-move-ready` 只允许进入已有 MOVED 确认；
- `object-path-exit-ready` 只允许作为已有 OUT 缺失链的入口；
- capture-start、hand context、数量缺额、单帧 global assignment 都不能单独生成事件。

任何反向事实都必须撤销对应临时资格：原位恢复、owner 变为 ambiguous、候选框变 shadow、出现更强独立 owner、正式遮挡 proof 改变、operation 结案/回滚/重开。

### 1.4 全局归属是统一仲裁，局部规则只作 fallback

每帧先由统一候选图生成全局一对一归属计划，再让原有局部流程补充严格原位、CONTACT、遮挡和 D/IN 细节。

```text
严格 owner / 已确认遮挡与 endpoint
    -> 所有 C 与 D 对所有非-shadow B 的统一候选图
    -> 最大基数、最小代价、可解释的全局一对一计划
    -> forced / ambiguous / no-plan
    -> 每个实体自己的连续确认与联合原子提交
```

如果全局计划连续给出唯一实体关系，局部 `reserved-by-stronger-old-c`、同类局部抢框或跨类别防抖只能记录诊断，不能反向夺走已 forced 的物理终点。反过来，若全局计划真正对称、每帧改变或缺少连续性，局部规则也不能用 item_id、左右位置、检测 index 或最近手强行补全。

全局计划跨帧的稳定性必须按“实体与物理路径/框的连续关系”判断，不能按每帧 detection 数组下标是否相同判断，因为检测输出顺序本来可以变化。

## 2. 测试问题 A：三件物品同时出库却完全没有 OUT

### 2.1 日志事实

失败回放的关键顺序是：

```text
frame=153  一只手进入，operation 尚未建立物品轨迹
frame=154  识别到两只手，tracks=0
           skip-stationary-hand-no-active-track
frame=155/156 手 merged-or-ambiguous，继续 no-delta
frame=157  无手结算 tracks=0，inventory-after=3，events=0
```

这说明问题发生在结算前：操作启动阶段没有为将被拿走的旧 C 建立任何 `HAND_*`/`CONTACT_*` runtime。进入无手阶段时已经没有对象级 OUT 候选，因此后面的缺失计数、direct-object 证据和 hand-group witness 根本无从累计。不是 OUT 阈值单独太高，也不是最后的原子提交把事件吞掉了。

### 2.2 根因

当前 `skip-stationary-hand-no-active-track` 的前提过窄：当没有活动 runtime 且当前 hand delta 不可靠时，它把整帧视为“无业务意义”。但实机中可能出现：

- 第一张手框只覆盖物品的一部分，尚未达到旧逻辑的创建条件；
- YOLO 第一帧漏掉或低分输出被遮住的物品；
- 手数量从一只变成两只，或者两只手被合并为一个框；
- 物品数量先减少，而手的 `hand_id` 还没有建立稳定连续性。

因此“没有活动物品轨迹”不等于“没有物品正在被操作”。手数量和单帧 hand delta 都不能承担这个判定。

### 2.3 修改方向：增加捕获启动保护

在 `session.cc` 的有手帧早期跳过判断之前，增加一个只负责**启动/补建 runtime** 的保护阶段。它不直接产生事件，只确保后续帧有可继续验证的对象轨迹。

#### A. 启动保护的触发条件

当以下任一条件成立时，不得直接执行 `skip-stationary-hand-no-active-track`：

1. 当前 hand 框与任意 operation-start 旧 C 的原始框存在合法 `hand_touches`、`hand_affects` 或覆盖关系；
2. 当前食品检测数量少于 operation-start 可见旧 C 数量，且缺少的 C 尚未被正式遮挡 proof 或已有终点解释；
3. 当前检测框相对某个旧 C 出现了合法的局部/部分路径，但尚未形成完整 `HAND_*` 轨迹；
4. 已有的 `carrier_capture_context`、可见数量辅助证据或当前候选图表明本 operation 可能已开始。

这些条件只表示“需要继续观察”，不能单独判定 OUT/MOVED。

#### B. 启动保护的建轨规则

对每个可能受影响的旧 C：

- 以 operation-start 的 `original_box/base_box` 为稳定参考，不用尚未确认的 `estimated_box` 反推初始身份；
- 建立 `HAND_PARTIAL_BLOCKED`、`HAND_FULL_BLOCKED` 或已有 CONTACT 语义对应的 runtime；
- 保存当前帧的 detection index（若有）、手覆盖上下文、`carrier_hand_id` 候选和本帧证据来源；
- 若当前 hand_id 尚不稳定，允许创建 runtime，但必须把 `carrier_hand_ambiguous`/`hand_delta_interrupted` 置为保护状态，禁止写入不可靠的 `move_values`；
- 若多个旧 C 共享同一个手框，给每个 C 建立独立的候选 runtime，但不把同一只手的 delta 自动写给所有物品；后续由物品自身路径、统一全局一对一归属或严格 hand-group witness 分别确认；
- 若当前没有可靠 food detection，也可以先建立“被手捕获、当前不可见”的旧 C runtime，使后续连续无手缺失能够开始计数。

启动保护只为旧 C 建立捕获事实，不能借机创建 D 或产生 IN。真实 D 仍必须按统一候选图中的独立路径、shadow 释放和原有 D/IN 连续确认建立，避免“手一进入就把被挡住的旧物品误建成新物品”。

#### C. 何时仍可跳过

只有同时满足以下条件，才允许保留原来的 `skip-stationary-hand-no-active-track`：

- 当前手框与所有 operation-start 旧 C 都没有合法接触/影响关系；
- 当前检测数量没有异常减少，也没有未解释的局部/消失路径；
- 没有待处理的 D、CONTACT、遮挡或可见数量辅助候选；
- 没有任何 `carrier_capture_context` 或其他本 operation 证据。

这样可以避免无意义的静止手帧增加负担，同时不漏掉“轨迹尚未建成但操作已经开始”的场景。

## 3. 测试问题 B：两个同类橙子同时向中间移动后卡住

### 3.1 日志事实

该回放中手框曾合并、漏检并重新绑定：

```text
item=1 state=AMBIGUOUS action=suspend-delta
item=3 old-hand=2 candidate-hand=4 state=AMBIGUOUS action=suspend-delta
```

这部分行为是正确的：不能把不确定的手位移写给任意物品。

但后续又已经出现了足够强的物品级证据：

```text
DIRECT-OBJECT item=1 ... streak=2/2
DIRECT-OBJECT item=3 ... streak=2/2 或更高
GLOBAL-OWNER item=1/item=3 ... force-global-one-to-one-observation
```

随后 item 3 仍被旧的直接恢复门挡住：

```text
DIRECT-RECOVERY ... first-hand=0 ... reject
SETTLE ... reason=defer-directly-observed-still-unresolved
```

所以不是检测完全没有跟上，而是“物品自身路径证据已经成立，却没有被允许进入 MOVED 确认”；旧的 `hand_delta_interrupted` barrier 仍把它当成必须恢复手路径的对象。

### 3.2 根因边界

当前代码同时存在两类证据：

- 手级路径：`hand_id + move_value + estimated_box`；
- 物品级路径：连续 detection、全局唯一归属、相对原位置的移动。

手级路径中断时，暂停 delta 是必要的；但这不应自动抹掉物品级路径。现在的结算条件把“手级中断”和“所有移动证据都无效”混在一起，造成可见物品路径被重复拦截。

### 3.3 修改方向：统一的 object-path MOVED 入口

增加一个狭窄的“物品自身路径确认”分支。它复用现有 `confirm_rearrange_` 和原子提交，不新建另一套事件系统。

#### A. 必须全部成立的条件

只有以下条件全部成立，才允许 `direct_object_exit_evidence` 作为 MOVED 确认证据：

1. C 是 operation 开始时已有的旧库存物品，不是临时 D；
2. 当前 detection 与 C 的类别关系符合第 1.2 节的统一兼容规则，且相对 `original_box/base_box` 明显发生移动；
3. 当前 detection 在连续帧中稳定自匹配，达到已有的直接确认窗口；
4. 细节27的全局一对一计划把该 detection 唯一、稳定地分配给该 C；不能处于真正对称或未决匹配；
5. 该 C 在本 operation 中有真实接触/覆盖上下文、CONTACT 路径或已确认的 hand capture context；不能只凭远处偶发框，无论它是否同类；
6. 没有 `b_claim_ambiguous`、`contact_path_ambiguous`、`no_hand_candidate_ambiguous`、未解决 alias、遮挡冲突或更强 owner 保留；
7. 该 detection 不是 shadow，也没有被其他 C/D 共享；
8. 终点不只是原位置附近的静态邻居，且满足现有 `boxes_differ_as_move`/路径几何门。

`hand_delta_interrupted`、`carrier_hand_ambiguous` 或缺少 `first_hand_block_box` 本身不能否决这条分支；它们只表示不能使用手级 delta，不表示物品级证据无效。

#### B. 仍然不能直接提交

direct-object 分支只允许：

- 把该 C 标记为 `MOVED` 候选/恢复移动确认；
- 写入已有的 `placed_box`、连续路径和待结算状态；
- 进入原有 `confirm_rearrange_` 的连续确认和 operation 原子提交。

它不能：

- 单帧直接生成 `MOVED` 事件；
- 直接生成 `OUT`；
- 绕过遮挡 proof、C-D alias 处理或统一全局归属；
- 把这条证据复制给同批的其他 C。

#### C. 与局部 `reserved-by-stronger-old-c` 的关系

局部旧逻辑只有在全局计划尚未形成唯一稳定关系时，才能继续作为保守 fallback。若同一无手帧已经由全局一对一计划明确给出 `E1 -> B1、E2 -> B0`，则局部“另一个旧 C 更强”的临时保留不能再次夺走该框；应记录冲突日志，但以全局稳定关系进入各自的直接确认链。这里的 E 可以是不同类别的旧 C，也可以是旧 C 与已经合法建立的 D；不得只针对同类物品实现。

如果全局计划在下一帧变成真正对称或失去连续性，则撤销本帧的临时 direct-object 确认，恢复未决，不能沿用上一帧强行结案。

## 4. 两个问题的联合处理与提交边界

### 4.1 证据独立、结算联合

每个 C 必须维护自己的证据状态：

```text
启动保护 -> 捕获/接触上下文
          -> 手级路径（可能中断）
          -> 物品级连续路径（可能成立）
          -> 无手缺失或 MOVED 确认
```

一个 C 的手中断不能清空另一个 C 的物品路径；一个 C 的 MOVED/OUT 也不能提前清空同 operation 其他 C 的 runtime。

### 4.2 OUT、MOVED、IN 使用同一图上的不同结论门

- 旧 C 可见且有连续移动框：优先走 object-path MOVED 入口；
- 可见但没有足够移动证据：保持未决或走原有静态/CONTACT 路径；
- 完全不可见：只能使用已有手级/CONTACT 移动证据、严格 `hand_group_exit_witness`、正式遮挡 proof 或原有缺失链；不能因为启动保护曾建立过 runtime 就直接 OUT；
- 新 D 可见且有独立、非-shadow 的连续路径：仍只走原有 D/IN 确认；不能因为与某个 C 同时移动、同类相贴或手数量变化而绕过 D 链路；
- C 与 D 竞争同一 B，或不同类别 B 竞争同一 E 时：统一图无 forced 解就保持未决，不能为某一类别单独开后门。
- 各类证据都必须继续满足既有连续无手窗口和原子提交 barrier。

### 4.3 真正歧义仍保持未决

以下情况不得强行确认：

- 两个或更多 E（同类或不同类）对终点存在完全对称、等强的可行路径；
- hand_id 中断后没有连续物品路径，也没有严格 hand-group witness；
- detection 既可能是旧 C 又可能是真实 D，且没有全局唯一解；
- 只有可见数量缺额，没有对象级来源。

此时应保留 `needs_settle=1`，输出明确的 unresolved reason，并等待新的独立帧或安全 operation 边界。

## 5. 推荐修改边界与文件职责

- `session.cc`：调整有手帧早期跳过条件，增加捕获启动保护；不改 hand tracker 的匹配阈值和 delta 计算规则。
- `session_hand.cc`：为启动保护创建/补建旧 C runtime；维护统一 capture/object-path 事实；继续在 hand_id 歧义时中断手 delta；不得按类别复制分支。
- `session_no_hand.cc`：允许稳定 object-path 事实进入现有 MOVED 恢复入口；局部 owner 只作为全局计划缺失时的 fallback；对 C/D、同类/异类统一使用候选图结果，保持缺失窗口和 D/IN 规则。
- `session_settlement.cc`：在最终结算前把 direct-object 确认纳入现有 `confirm_rearrange_` 条件；统一检查所有同 operation runtime 是否已结案，维持原子提交。
- `session_ownership.cc` / `session_internal.h`：把细节27的 shadow/global ownership 结果提升为统一候选图计划，明确返回“forced / ambiguous / no-plan”，并保存 class-relation、物理路径连续性和冲突来源；不要用检测顺序补全缺失归属。
- `session.h`：只增加本 operation 的统一 capture/object-path 事实、导出的 move/exit readiness 和诊断原因；必须在结案、回滚、重开、reset 时清理。
- 测试：增加启动阶段第一张手框不完整、随后手合并并取走多个物品的回放；增加两个同类 C 在手 delta 中断后仍凭连续物品路径分别 MOVED 的回放；同时增加不同类别物品交叉/相贴后分别 MOVED、C 与真实 D 独立进入、同类和异类重复框 shadow 释放、真正对称保持未决的回放；保留所有旧回放。

本次不应修改 `超参数位置与调节说明.md`，除非实现确实新增/改变阈值。优先复用细节27已有的连续确认窗口、几何匹配和全局归属门。

## 6. 诊断日志要求

新增或调整日志时，至少记录：

```text
CAPTURE-START item=... trigger=hand-affects / count-deficit / partial-path action=create-runtime / skip
CAPTURE-START item=... hand_ids=[...] identity=stable / ambiguous
ENTITY-GRAPH entity=... detection=... class-relation=compatible / unstable / incompatible owner=forced / ambiguous / none
OBJECT-PATH item=... detection=... streak=... move-ready=0/1 exit-ready=0/1 reject reason=...
MOVED-RECOVERY item=... source=hand-delta / direct-object action=confirm / defer reason=...
SETTLE barrier=pass / defer unresolved=[...] reason=...
```

日志只能帮助定位证据，不能作为状态机的唯一依据。尤其要能区分：

- 根本没有建立 runtime；
- runtime 已建立但 hand delta 被安全暂停；
- 物品路径证据已成立但被旧 barrier 错误拦截；
- 真正没有足够唯一证据而合理未决。

## 7. 验证顺序与完成标准

建议分阶段实施，每阶段先编译并跑旧回放，再进入下一阶段：

1. 只接入捕获启动保护，验证三件同时出库场景至少建立三个独立旧 C runtime；确认无手静态帧仍可跳过。
2. 只接入 object-path -> MOVED 的确认入口，验证两个同类橙子、两个不同类物品在手 delta 中断后都能按各自连续路径分别确认 MOVED；确认真正对称场景仍未决。
3. 验证两者联合运行：一件完全消失、两件部分可见、手框合并/重新绑定时，仍按各自证据独立处理并最后原子提交。
4. 回归同类与不同类的单手、双手独立、双手共同接触一个物品、CONTACT、遮挡、D/IN、静态回原位和已有细节27测试。

完成标准：

- 第一个测试中，操作启动后不再出现“应被捕获但 `tracks=0`”的情况；即使 hand_id 不稳定，也有可继续验证的旧 C runtime；
- 第二个测试中，手位移被中断仍不写错 delta，但任意类别的多个物品只要各自拥有连续、全局唯一的 object-path，就能进入原有 MOVED 确认和原子提交；
- 真实对称/身份不足的场景继续保持未决；
- 现有单手、多手、遮挡、入库、出库、整理和原子提交回放全部通过；
- 没有降低既有安全阈值，没有按手数量或检测顺序猜测身份；
- 未改超参数，或已同步更新 `超参数位置与调节说明.md`。

本次修改的核心不是“放宽判断让测试通过”，而是让所有类别、所有旧 C 和合法 D 都在同一张实体图中建立、竞争、确认和撤销证据：先保证操作开始时建立对象级 runtime，再让已经证明属于某个实体 E 的连续物品路径进入相应的 MOVED/OUT/IN 确认门。手身份不可靠时仍拒绝错误手 delta，证据不足时仍宁可未决。
