# 细节25：多手独立轨迹与物品关联，支持多物品同时操作

## 0. 本文性质、目标与首要约束

本文是下一次修改 3.0 业务代码时的实施指导，不代表本次已经修改或验证过代码。

本轮目标是在现有“连续手操作事务”的基础上，支持下列情况：

- 一只手连续移动多个物品，手不离开冰箱；
- 一只手同时带动多个物品；
- 多只手同时、向不同方向移动不同物品；
- 多个物品同时入库、出库、整理，以及后续的交换位置；
- 手检测框的输出顺序变化、面积变化、短暂漏检、靠近或合并时，不能把错误的手位移写给错误物品。

**首要约束：当前已经有效的功能必须保留，绝不能为了多手/多物品功能把它们改坏。**

特别要保护已经能正确工作的：单手入库、单手出库、单手整理、严格遮挡、遮挡解除、C-D alias、同类物品的一框一物品保护、静态邻居保护、CONTACT_* 的实际物品路径、无手连续确认、工作库存事务与正式库存一次性提交。

本轮不是把原有单手逻辑推翻重写，而是把其中错误的“整段操作只有一个手轨迹、一个 hand delta”的前提替换为：**每个 OperationTrack 只使用自己可靠关联的 HandTrack 的位移。**

不得借本轮修改去做下列事情：

- 不放宽 YOLO/NMS 的基础策略；
- 不把手框数量、面积排序或 YOLO 本帧输出顺序当作手身份；
- 不因为多手检测不稳定就降低 MOVED、IN、OUT、OCCLUDED 的现有确认门槛；
- 不把手框合并、漏检或手身份歧义强行解释为任意一只手的连续位移；
- 不把“多个框/多个物品发生变化”直接当成多个正式事件；
- 不修改现有有效单手路径的几何阈值来迁就多手场景。

代码不必全部挤在一个文件。数据结构、手轨迹匹配、物品关联、无手结算和测试应按现有工程职责拆分。若新增或修改任何可调阈值、帧数、比例、距离、丢失窗口或代价间隔，必须同步更新 `另另一种业务流程(3.0var)/超参数位置与调节说明.md`，写明位置、原值/新值、用途、适用场景和调节风险。若没有改超参数，也应明确记录“本次未改超参数”。

## 1. 已确认的根因

当前实现仍保留单手假设：

1. 每张有手帧从 `hand_boxes` 中选择一个 `choose_primary_hand()`；
2. 由当前主手框与上一帧主手框计算唯一 `MoveValue delta`；
3. 将同一个 `delta` 追加给所有 `HAND_PARTIAL_BLOCKED` / `HAND_FULL_BLOCKED` 的 `OperationTrack::move_values`；
4. 每个物品的 `estimated_box` 都是自己的锚点框加上 `move_values` 的累计和。

因此，若 A 手带 a 物品向左移动、B 手带 b 物品向右移动，当前代码只能得到其中一个主手的位移，并错误地把它写入 a、b 两条轨迹。例如主手选中 A 手时：

```text
A 手 delta = (-50, 0)
a 的 estimated_box = 正确向左移动
b 的 estimated_box = 错误向左移动；真实终点实际在右侧
```

更危险的是，若相邻两帧“面积最大的手框”从 A 手切换为 B 手，计算出来的是：

```text
B 手当前框中心 - A 手上一帧框中心
```

这不是任何真实手的位移，却会污染全部活动 HAND_* 物品的预测轨迹。

所以问题不仅在最后无手帧的物品匹配；在有手阶段，多个物品的预测路径已经可能被同一个错误 `move_value` 带偏。

## 2. 核心结论：需要稳定 hand_id，但不能依赖检测顺序

用户提出的核心方向正确：应维护多条独立的手轨迹，并让每个被手操作的物品记录“自己关联的是哪一条手轨迹”。这样 a 只使用 A 手的移动记录，b 只使用 B 手的移动记录，c 只使用 C 手的移动记录。

但必须严格区分两件事：

```text
当前帧 hand_boxes 的下标：YOLO 输入顺序，逐帧临时，不是身份。
hand_id：系统自己创建并持续维护的内部身份，跨帧稳定。
```

`old_hand` 的理解应当是正确的：它不是直接保存 YOLO 的当前输出列表，而是系统维护的“上一张已确认手轨迹状态”。建议概念上改为：

```text
old_hands[hand_id] = HandTrack
```

其中 `old_hands` 可以使用与现有工程风格一致的 `std::map<int, HandTrack>`。当前帧检测框只是在该帧中被匹配到某个 `hand_id`；匹配成功后，才把该检测框更新到 `old_hands[hand_id]` 的上一帧状态。

**绝不能用 `old_hand` 列表的第 0、1、2 个位置对应当前 YOLO 列表的第 0、1、2 个位置。** 即使两只手都一直被正确检测，输出排序也可能因置信度、NMS、坐标排序、框面积变化而改变。

当前业务接口传入的是 `std::vector<BBox> hand_boxes`，手框本身没有可区分左右手的 `cls_id`。即使以后上游暴露手类别，通常所有手仍属于同一类。因此“类别一致”最多是附加检查，不能成为区分不同手的主要依据。

## 3. 建议的数据职责

### 3.1 HandTrack：独立于当前检测顺序的手轨迹

每条内部手轨迹至少需要表达：

```text
hand_id
last_box                         # 上一张可靠有手帧的手框
previous_box / 近期历史框         # 用于方向连续性和诊断
last_delta                        # 本 hand_id 本帧唯一确认后的位移
history                           # 本手自己的轨迹，不与其他手共用
last_seen_frame
missing_frame_count
state = OBSERVED / TEMP_LOST / MERGED_OR_AMBIGUOUS
```

名称可服从现有代码风格，但职责必须保持：`hand_id` 稳定、`last_box` 只属于该 hand_id、`last_delta` 只在本 hand_id 的当前匹配唯一可靠时更新。

不需要预先规定“只能有两只手”或“最多三只手”。当前帧有多少个可可靠关联的手框，就维护多少条活跃 HandTrack；当前帧手框数量变化本身不构成事件。

### 3.2 OperationTrack：记录物品与手轨迹的关联

每个由手影响的已有 C 或候选新物品 D，应在运行时记录手关联信息，例如：

```text
carrier_hand_id                  # 当前唯一可靠关联的 hand_id；无关联时为无效值
hand_association_state           # UNIQUE / AMBIGUOUS / NONE / TEMP_LOST
hand_track_start_index           # 该物品在 carrier_hand_id 自己 history 中的开始位置
```

一只手可以关联多个物品。这是允许“一只手同时带动多个物品”所必需的，不应限制一条 HandTrack 只能服务一个 OperationTrack。

一个物品通常只应有一条唯一的 `carrier_hand_id`。若同一帧有两只手都覆盖/接触该物品，或发生接手但没有独立物品观察证据，则标为 `AMBIGUOUS`，不能根据“更近”“列表更靠前”强行选择其中一只。

候选新物品 D 也需要记录自己的 hand_id 关联。它的“贴手出现”证据可以由任意当前手框触发；但若要使用手位移推算 D 的路径，也必须先得到唯一可靠的 carrier hand。

### 3.3 手覆盖与手位移必须分开

以下两类事实不能混为一谈：

```text
手覆盖/接触事实：任意当前手框是否覆盖或接触物品。
手位移来源：哪一条唯一可靠的 HandTrack 可给该物品提供 delta。
```

前者可对所有当前手框求“任意一个命中”或几何并集，用于 `HAND_*`、`CONTACT_*`、贴手 D、手+前景遮挡等既有逻辑。两只手合并为一个框时，这个覆盖事实仍可能成立。

后者必须是 item -> unique hand_id 的关联；若关联不唯一、手框合并或暂时丢失，则不得用任何 hand delta 推算该物品位置。

## 4. 每张有手帧的 HandTrack 匹配流程

### 4.1 不要逐个贪心匹配

对上一帧所有 `OBSERVED` / 可恢复 `TEMP_LOST` 的 HandTrack，与当前帧所有手框，先建立完整的候选关系，再统一做一对一匹配。不能先处理 H1，抢走一个当前框后，再处理 H2。

每个候选 pair 的可用证据可以包括：

- 手框中心的归一化距离；
- IoU 或几何连续性；
- 宽高比例的近似连续性；
- 上一帧及更早历史推导出的运动方向连续性；
- 若有可靠物品关联，可作为辅助诊断证据，但不能让物品反过来伪造手身份。

“框大小相近、移动距离小”是正确的候选条件，但不能要求完全相等；手靠近摄像头、转动、靠近画面边缘时，检测框大小会自然变化。

对于一个小规模手集合，优先采用全局一对一的最小总代价/最高总连续性分配。必须检查最优分配是否唯一；如果不同分配同样合理，则不是可靠匹配。

示例：

```text
              当前框 A'     当前框 B'
旧 HandTrack H1    低代价          高代价
旧 HandTrack H2    高代价          低代价

=> H1 -> A'，H2 -> B'，两条 delta 分别计算。
```

若两行两列代价都接近，表示双手靠近、交叉或检测不稳定：

```text
              当前框 A'     当前框 B'
旧 HandTrack H1    接近           接近
旧 HandTrack H2    接近           接近

=> 不选择，不生成本帧 H1/H2 的可靠 delta。
```

### 4.2 只有完成整张匹配计划后才能更新 old_hands

正确顺序应为：

```text
读取 old_hands（上一帧稳定状态）
        ↓
根据所有当前 hand_boxes 建立候选与全局匹配计划
        ↓
对唯一可靠 pair 计算各自 delta
        ↓
为相关物品写入各自 hand_id 的 delta
        ↓
最后统一更新 old_hands[hand_id].last_box
```

不能在处理 H1 时立即覆盖 `old_hands[H1].last_box`，否则后续 H2 的匹配会混入当前帧信息，导致结果依赖遍历顺序。

当前帧检测框下标到 hand_id 的映射只在本帧有效，例如：

```text
current_detection_index -> hand_id
```

它不能替代 `old_hands`，也不能跨帧保存为身份依据。

### 4.3 新出现、暂时丢失、合并和重新分开

必须有明确但保守的状态处理：

- 当前手框没有可匹配的旧 HandTrack：创建新的 `hand_id`；首帧没有 delta，不能伪造位移。
- 旧 HandTrack 本帧没有可匹配的当前框：进入 `TEMP_LOST`；保留历史与关联物品，但不追加 delta。
- 多条旧 HandTrack 只能对应同一个当前手框，或全局匹配不唯一：进入 `MERGED_OR_AMBIGUOUS`；相关物品暂停手位移推算。
- 一个旧 HandTrack 面对多个当前框且无法唯一选择：不把它复制成两个旧身份；最多选择唯一连续的一条，其余作为新/未决手框处理。
- 合并后的手重新分开时，只有历史位置、方向和当前几何能唯一恢复时才恢复各自 hand_id；否则保持未决，等待物品自身直接观察或无手帧结算。

临时丢失和合并不是物品已出库、已移动或新物品入库的证据。它们只能使相关物品停止追加 hand delta、继续保持待确认。

若为了 `TEMP_LOST` 引入新的帧数窗口或距离阈值，必须按第 0 节同步超参数说明；初期优先复用已有连续帧和几何工具，避免无必要新增大量参数。

## 5. move_value 与 estimated_box 的正确使用

### 5.1 保留现有单手成功路径

当某个 `OperationTrack` 有唯一可靠的 `carrier_hand_id`，且对应 HandTrack 本帧的匹配唯一可靠时：

```text
track.move_values += old_hands[carrier_hand_id].last_delta
track.track += estimated_box(track)
```

这样单手场景的语义不变：物品锚点框加上该手从物品开始被影响后积累的位移，仍得到原有的 `estimated_box`。一只手带动多个物品时，这些物品都关联同一个 hand_id，因此仍可共享这只手的 delta。

### 5.2 不再把同一个 delta 广播给全部 HAND_* 物品

现有“遍历全部 HAND_*，无条件 `move_values.push_back(delta)`”的行为是本轮必须消除的单手遗留假设。新的追加条件必须是：

```text
本物品关联的 hand_id == 本帧唯一可靠匹配的 HandTrack
```

不是“当前有手”，不是“主手移动了”，也不是“任意手移动了”。

### 5.3 没有可靠 hand delta 时的保守规则

若物品的 carrier hand 暂时丢失、合并、交叉或关联不唯一：

- 不追加任何其他手的 delta；
- 不把别的手的路径当成本物品的 `estimated_box`；
- 保留此前已经可靠积累的 `move_values` 和 `track`；
- 若物品仍有实际检测框，继续按自己的局部框、`last_seen_box`、`reappear_candidate_box`、`observed_track` 更新；
- 若物品完全不可见，则只保持“正在操作但位置暂时未知”，等待后续重新出现或无手帧的全局匹配；
- 不因这一帧没有可预测框而累计 OUT，不把它当作新 D，也不强行结束 HAND_*。

这比用错误手位移生成一个看似精确的错误估计框更安全。

`CONTACT_*` 当前依赖物品实际观测路径、而非手位移来推算位置的原则必须继续保留。多手改造不应把 CONTACT_* 退回为“跟随某只手的估计框”。

## 6. 物品关联、接手和实时状态

### 6.1 首次关联

某个 C 因任意当前手框覆盖而进入 `HAND_*`，或因相贴进入 `CONTACT_*` 时：

1. 使用所有当前手框判断“是否受手影响”；
2. 查询当前帧 hand detection -> hand_id 匹配结果；
3. 若恰有一条可靠 HandTrack 对该物品形成适用覆盖/接触，写入 `carrier_hand_id`；
4. 若没有或多条均可解释，记录 `NONE` / `AMBIGUOUS`，不能猜测。

### 6.2 手与物品的关系不是一对一

```text
一个 hand_id -> 可以关联多个物品。
一个 OperationTrack -> 正常情况下只关联一条唯一 hand_id。
```

这既支持一只手同时拿起两个物品，也不会让两只不同方向运动的手共享 delta。

### 6.3 物品被另一只手接手

物品从 H1 转交给 H2 是可能发生的，但不能只因 H2 更近就立即换 `carrier_hand_id`。至少应有物品实际检测框、持续接触、原 hand 失去接触、或连续帧几何证据中的一项可靠支持。过渡阶段若不唯一，应暂停 hand delta；不得把 H1 与 H2 的两段向量无条件拼接成同一条物品路径。

### 6.4 实时识别与正式提交仍分开

有手阶段可继续使用 `POSSIBLE_MOVED`、`PLACED` 等临时状态，供实时显示或工作库存内部决策使用。正式 `MOVED`、`IN`、`OUT`、`OCCLUDED` 仍必须等既有的无手直接观察、连续确认、身份仲裁与遮挡证明完成后，按整段事务一次性提交。

多手轨迹只改进实时的物品预测来源，不能成为提前发布正式库存事件的理由。

## 7. 多物品最终结算：手轨迹不是全部答案

多条 HandTrack 解决的是“每个物品在有手阶段使用哪个 move_value”的问题，但最终仍须保留和扩展现有的一框一物品、alias 与无手结算规则。

在无手帧中，应逐步形成当前事务的联合结算计划，例如：

```text
A -> MOVED 到 d3
B -> MOVED 到 d7
C -> OUT
D -> IN
E -> OCCLUDED by A
```

必须满足：

- 同一个 detection 最多属于一个物品；
- 每个 MOVED 有自己的移动证据和唯一终点；
- 每个 IN 都保留自身的贴手出现与连续无手直接确认链；
- 每个 OUT 都保留自身的移动/缺失证据，不能仅因少了多个框一起删除；
- MOVED/IN 的前景物品确认后，才允许按既有因果遮挡 proof 得出 OCCLUDED；
- C-D alias、同类竞争、静态邻居严格 owner、遮挡 proof 的现有保护规则继续优先；
- 任一关键分配不唯一时，保持相关对象未决，不能按 `item_id`、hand_id 或 detection index 强行裁决。

两个物品交换位置是一个闭环移动，不应被实现为 `OUT + IN`：

```text
A 的自身路径 -> B 的旧位置
B 的自身路径 -> A 的旧位置
两个终点框不同且全局分配唯一
两者各自有独立移动证据
=> 同时确认 MOVED(A) 与 MOVED(B)
```

但若两个同类物品在全过程完全遮挡，最终画面又无法区分二者，单摄像头与当前 YOLO 框信息无法证明物理身份交换。这种情况必须保持保守，不得虚构两个 MOVED；若业务必须识别，需要额外外观 ReID、标签/RFID 或多摄像头证据。

## 8. 建议的代码职责划分

实际文件名以当前工程结构为准，但不应把全部逻辑塞进一个函数。可按职责拆分：

- `include/session.h` 或适当的内部头文件：`HandTrack`、hand_id、物品手关联状态、只读访问接口；
- `session_hand.cc`：当前 hand_boxes 与 `old_hands` 的全局匹配、每条 HandTrack delta、C/D 与 hand_id 的关联、只向关联物品追加 delta；
- `session_ownership.cc`：如需要，放置纯粹的全局一对一匹配辅助函数，避免把匹配算法散落在状态机分支内；
- `session_geometry.cc`：继续复用已有 `MoveValue`、`estimated_box`、几何连续性函数，不另造不一致的距离规则；
- `session_no_hand.cc` / `session_settlement.cc`：保持现有无手身份仲裁与事务提交职责，只在需要时消费更准确的每物品路径；
- `tests/`：增加确定性回放，不使用日志人工判断替代断言。

现有全局 `old_hand_box_`、全局 `hand_track_` 和“所有 HAND_* 共用 delta”的路径应被替换或降级为单手兼容层，但不能保留两套同时写入同一 `move_values` 的机制。任何一帧、任何物品只能有一个明确的 move_value 来源。

## 9. 必做测试与回归范围

测试应首先覆盖手轨迹身份和 move_value 是否正确，再覆盖库存事件。断言不能依赖当前 hand_boxes 的数组顺序、`std::map` 遍历顺序或日志文本。

| 场景 | 必须验证的结果 |
| --- | --- |
| 单手移动一个旧 C | 保持当前 MOVED、放下、无手确认行为不变。 |
| 一只手同时带动两个 C | 两条 OperationTrack 都关联同一 hand_id，均只使用该手 delta。 |
| 两只分离的手反向移动 a、b | a 只累计 H1 delta，b 只累计 H2 delta；两个 estimated_box 方向正确。 |
| 当前手框输出顺序交换 | hand_id 不交换，物品 move_values 与最终事件不变化。 |
| 手框面积/置信度变化导致排序变化 | 不产生“当前右手减上一帧左手”的伪 delta。 |
| 两只手短暂合并为一个检测框 | 相关物品暂停追加 delta；不写入错误方向，不误 MOVED/OUT/IN。 |
| 一只手短暂漏检后恢复 | 旧 HandTrack 可保守恢复；漏检期间不伪造 delta。 |
| 两手交叉且关联代价不唯一 | 不按 hand_id 或 index 强选，相关物品保持未决。 |
| 一只手移动 A 后继续移动 B | 同一事务内 A 的临时结果保留，B 继续建立自己的路径，最终可同时结算。 |
| 双手同时多入库/多出库 | 每个 D/C 都保留独立证据链，不因手数量或检测数量直接生成事件。 |
| 同类双移动与交换位置 | 一框一物品、alias、全局唯一分配仍成立；歧义时不虚构身份。 |
| 移动物品遮挡另一个物品 | 现有 `MOVED -> OCCLUDED` 因果关系、provisional causal proof 和最终提交不退化。 |
| 既有单手、遮挡、REVEALED、C-D alias 回放 | 现有全部回放继续通过。 |

建议增加可读诊断日志，例如：

```text
HAND-TRACK create hand=H1 detection=0
HAND-TRACK plan H1->d0 cost=... H2->d1 cost=... unique=1
HAND-TRACK update hand=H1 delta=(-50,0)
HAND-ASSOC item=5 hand=H1 state=UNIQUE
HAND-ASSOC item=6 state=AMBIGUOUS action=suspend-delta
HAND-TRACK merged hands=[H1,H2] detection=0 action=no-delta
```

日志只用于诊断，不能通过日志分支偷偷改变业务状态。

## 10. 完成标准

下一次代码修改只有同时满足下列条件才算完成：

1. 当前帧手框数量、顺序、面积变化不再决定手身份；内部 `hand_id` 才是跨帧身份。
2. 不再存在“一个主手 delta 写入全部 HAND_* 物品”的路径。
3. 每个 HAND_* 物品只在 carrier hand 唯一可靠时累计该 hand_id 的 delta。
4. 手框合并、漏检、交叉和匹配歧义时，系统暂停错误推算而不是猜测；不会由此误报 MOVED、IN、OUT 或破坏库存。
5. 一只手多物品、双手反向多物品、连续多次整理等目标场景能在既有事务语义下正确收敛。
6. 已有效的单手、遮挡、alias、同类身份、入库、出库和揭示功能均有回归证据，不能退化。
7. 若改动超参数，`超参数位置与调节说明.md` 已同步更新；若未改，实施说明和提交说明明确写出“本次未改超参数”。
8. 所有代码修改、测试与实机日志都能说明系统是在“区分每个物品自己的可靠手位移”，而不是通过放宽规则、跳过检查或强行提交来伪造多物品成功。
