# 细节26：多物品同时操作的联合结算与手关联中断恢复

## 0. 本文性质、修改范围与最高约束

本文是下一次修改 3.0 业务代码时的实施指导，**不是本次已经完成的代码修改**。

本次要解决三个已经由实机日志复现的问题：

1. 两只手同时取出苹果和橙子后，事务长期 `defer-commit`，没有产生两个 `OUT`；
2. 两只手同时把苹果和橙子整理到中间后，只产生其中一个 `MOVED`；
3. 两只手交换苹果和橙子的位置后，只产生其中一个 `MOVED`。

这次不是推翻细节24、细节25，也不是重新引入“整段操作只跟一只主手”的旧逻辑。
细节25已经建立的内部 `hand_id`、每物品 `carrier_hand_id`、手框歧义时暂停写入
`move_values` 的原则是正确的，必须保留。细节24已经有效的事务内因果遮挡 proof 也必须保留。

**首要约束：已经可行的功能，尤其是单手功能，绝不能被改坏。**

必须回归保护的能力至少包括：

- 单手入库、单手出库、单手整理；
- 一只手连续操作多个物品；
- 当前已实现的多手独立 `hand_id`、每物品独立 `move_values`；
- 严格遮挡、因果遮挡、遮挡解除和细节24的 provisional causal-occlusion proof；
- 同类物品的一框一物品、静态邻居保护、C-D alias、隔离 D、正常 D/IN；
- `CONTACT_*` 的真实物品观测路径；
- 无手连续确认、工作库存事务和一次性正式提交；
- 手框短暂漏检、合并、拆分、输出顺序变化时“不写错误手位移”的保护。

特别禁止为了让这三个多物品场景看起来成功，而做以下事情：

- 不放宽 `HAND_TRACK_MATCH_*`，不靠增大 hand matching 范围把不确定的手框硬接成同一只手；
- 不在手框合并、交叉或歧义时按最近距离、检测下标、面积或左右位置强行换手；
- 不降低 `MOVED`、`OUT`、`IN`、遮挡、C-D alias 的现有确认门槛；
- 不把“物体不见了”直接等同于 `OUT`；
- 不把“当前看到一个移动后的框”直接等同于 `MOVED`；
- 不修改 YOLO/NMS 全局策略来掩盖状态机问题；
- 不因为交换位置时两个框有重叠，就放宽遮挡判定或把可见物误判为 `OCCLUDED`；
- 不对已经确认的一个物品先局部提交、再清空另一个尚未结案物品的运行时状态。

代码不必全部挤在一个文件中。应按状态、物品证据、无手匹配、事务结算和测试的职责拆分。

本说明计划**不修改任何超参数**。应优先复用已有的：

- `HAND_TRACK_MATCH_*` 的多手身份保护；
- `TRACK_HAND_MOVE_EPS` 和 `boxes_differ_as_move()` 的移动判定；
- `FLOW3_REAPPEAR_CANDIDATE_CONFIRM_FRAMES` 的连续自匹配；
- `FLOW3_NO_HAND_OUT_MISSING_FRAMES` 的连续无手缺失确认；
- 当前跨类别重复框提示参数；
- 当前遮挡、alias、静态恢复的既有阈值。

若实现中确实不得不新增或修改任何阈值、帧数、比例、距离、计数上限或其他可调参数，
**必须同步更新** `另另一种业务流程(3.0var)/超参数位置与调节说明.md`：说明位置、原值/新值、用途、适用场景和调整风险。若没有改超参数，应在实现/测试说明中明确写出“本次未改超参数”。

## 1. 三个场景中已经确认的事实

### 1.1 同时取出：不是单纯“多等几帧”就能恢复

苹果和橙子同时被取出后，无手帧中已经连续没有食品框；但两个旧 C 都没有进入
`OUT_CONFIRMED`。

日志已经显示两条独立阻塞链：

```text
苹果 #10：missing-without-sufficient-out-evidence
橙子 #11：hold-out-for-pending-disappearance-supported
             C-D alias / quarantined pending D
```

苹果的问题是：手框在操作初期发生 `temporary-lost`、创建新的 hand id、随后又
`merged-or-ambiguous`。为了避免把另一只手的位移写给苹果，现有代码正确地暂停了
`move_values`。但暂停后苹果没有保留足够的“自己的直接移动/离开证据”，因此无手阶段
不能开始原有 `OUT` 缺失计数。

橙子还有额外问题：开始操作的帧中，橙子同一位置同时出现了一个橙子检测和一个低分苹果检测。
这个低分异类重叠框被误当成独立疑似 D，随后与橙子旧 C 形成 C-D alias。alias 合理地拒绝
在证据不足时直接出库，但这里的 D 很可能只是同一实物的跨类别重复/误分类，不应在有手初期
就成为独立 D。

因此，同时取出需要两种修复同时成立：

```text
每个旧 C 自己有可靠的“被操作并离开”证据
    +
连续无手缺失确认
    +
没有伪 D / 未解决 alias 阻塞
=> OUT
```

不能因为两个物品一起消失，就直接一次性宣布两个 `OUT`。那会把普通漏检、真实遮挡或
仅仅把手放在物品前面的场景误报成出库。

### 1.2 同时整理：两个终点都已被可靠观察，但其中一个没有升级为 MOVED

两个物品分别从左右整理到中间时，手框在有手阶段也发生了暂失、合并或身份歧义；因此其中一条
物品轨迹没有积累到可靠 hand delta。无手帧中，两个物品却都已经被各自稳定地直接匹配：

```text
item=1 detection=1 source=no-hand-reappear ... count=6 ready=1
item=3 detection=0 source=no-hand-reappear ... count=6 ready=1
```

其中苹果成功得到 `MOVED_CONFIRMED`，橙子仍是：

```text
state=HAND_PARTIAL_BLOCKED
resolution=NONE
needs_settle=1
reason=directly-observed
```

这说明“物品自己的无手直接终点”已经足够稳定，但当前确认路径仍把完整的手移动量当作必要条件。
手关联歧义时暂停错误 delta 是对的；错误在于暂停后，稳定且唯一的物品直接证据没有被用作
受限的恢复证据。

随后系统立即提交了苹果的一个 `MOVED`，并清空了整个 operation runtime，导致橙子永远没有
下一张无手帧继续完成结算。这是第二层独立 bug。

### 1.3 交换位置：与同时整理同源，遮挡计划不是根因

苹果和橙子交换位置时，第一个有手帧只检测到一个很大的手框，两个旧 C 都临时关联到它；
第二只手出现后，苹果的 hand association 变为 `AMBIGUOUS`，因此正确地停止追加 hand delta。

最后无手帧中，苹果和橙子都已经有稳定、不同类别、互不竞争的直接终点：

```text
苹果 #1：reappear count=5 ready=1，终点在右侧
橙子 #2：reappear count=5 ready=1，终点在左侧，MOVED_CONFIRMED
```

苹果仍保持 `resolution=NONE / needs_settle=1`，随后系统只提交橙子的 `MOVED` 并清空运行时。

日志中的遮挡计划虽然看到橙子框和苹果框有约 `0.829` 的几何覆盖，但因为苹果本身有合法直接观察，
它给出了 `coverage-direction-not-satisfied` 并拒绝遮挡。这一保守结论是正确的，**不应修改遮挡
阈值来修复交换问题**。

## 2. 根因总结：三个问题共享什么，不共享什么

### 2.1 共同根因 A：hand_id 歧义正确地暂停了错误位移，但没有给物品留下恢复通道

细节25后的行为：手框身份不唯一、合并、拆分或发生不可靠接手时，`carrier_hand_ambiguous` 会使该
物品停止使用当前 hand delta。这个机制必须保留，因为它避免了“右手当前框减左手上一帧框”这种伪位移。

但当前 `carrier_hand_ambiguous` 是一个短期状态：手框后来又能匹配时，它可能恢复为 false；而此前已经
丢失的 hand delta 不会补回来。最终物品即使有稳定的直接 B/终点框，确认逻辑仍主要检查：

```text
hold_and_move || has_meaningful_hand_move(track)
```

所以出现了“物品真的在新位置，但因为手框保护机制工作得太保守，正式 MOVED 不产生”的情况。

### 2.2 共同根因 B：无手结算把“被看到”误当成“已经结案”

当前 `has_unresolved_no_hand_state_()` 对一个仍满足 `existing_item_needs_settlement()` 的旧 C，若它在
当前无手帧被观察到，并且重新出现候选已经连续确认，就记录 `directly-observed` 后继续；它没有要求
该 C 已经进入 `MOVED_CONFIRMED`、`OUT_CONFIRMED`、`OCCLUDED_CONFIRMED` 或正式静态结案。

之后 `settle_no_hand_frame_()` 看到“没有未决状态”便提交 `final_items`，并调用
`clear_runtime_after_commit_()`。这正是“一个物品已有 `MOVED`，另一个仍
`needs_settle=1 / resolution=NONE` 却被丢弃”的直接原因。

因此，**不能只把提交门收紧**：只收紧会把同时整理和交换从“漏一个事件”变成“永远卡住”。
必须先让拥有充分直接物品证据的旧 C 能够恢复为 `MOVED_CONFIRMED`，再由联合提交门保证所有对象
一起结案。

### 2.3 同时取出的额外根因：伪 D / C-D alias 与 OUT 证据缺口

同时取出和两个整理场景共享 hand association 中断，但同时取出没有最终可见终点，不能套用
“直接终点恢复 MOVED”。它还需要：

1. 低分异类同框不能在有手初期直接升级为独立 D；
2. 每个旧 C 要在 hand delta 中断后保留严格的、物品级的“离开”证据；
3. 只有该证据加上既有连续无手缺失窗口，才能确认 `OUT`。

## 3. 这次修改的总体方案

本次应在保留当前单手/多手正常路径的基础上，补齐三件事：

```text
有手阶段：记录每个物品自己的可靠直接证据，hand delta 中断时不污染它
        ↓
无手阶段：先对全部物品做全局一对一终点/缺失/遮挡仲裁，再补恢复确认
        ↓
提交阶段：所有相关旧 C 与 D 都已结案后，才一次性生成事件并清空 runtime
```

三个部分必须在同一次修改中一起实现和测试：

1. **物品级直接恢复证据**：解决同时整理、交换中“终点已看见但没确认”；
2. **物品级离开证据**：解决同时取出中“没有手 delta 就永远不能开始 OUT”；
3. **联合结算提交门**：禁止一个物品先成功就抛弃未决同伴。

跨类别重复框/D-alias 的修复是同时取出所需的第四个窄保护，必须和第 2 项一起完成。

## 4. 新增或复用的运行时证据

### 4.1 不要复用“当前帧歧义”作为历史事实

`carrier_hand_ambiguous` 仍应保留为“当前帧能否使用 hand delta”的短期判断。它恢复为 false 后，
系统仍不能忘记本次操作中发生过 hand delta 空档。

建议在 `OperationTrack` 中新增一个**仅本事务有效、一次置真直到结案才清除**的历史标记，概念如下：

```text
hand_delta_interrupted
```

建立条件：该物品已进入 HAND_*，且其 carrier hand 发生 `TEMP_LOST`、`MERGED_OR_AMBIGUOUS`、
接手候选不唯一，或与原 carrier 不同且无法安全确认接手，导致本帧未向该物品追加 hand delta。

这个标记的含义仅是：

```text
本物品曾因保护性暂停而缺少手位移，允许它在后续使用严格的物品直接恢复路径。
```

它**不是移动证据**，不能单独生成 `MOVED` 或 `OUT`，也不能让任意当前框跳过身份仲裁。

初始化新 track、明确回到原位并正式静态结案、事务提交/取消时必须成对清除它，不能跨事务残留。

### 4.2 直接终点恢复证据：只补“被手关联中断损失的移动确认”

新增一个统一的纯判断辅助函数，名称可按现有代码风格确定，例如：

```cpp
can_confirm_direct_recovered_move(track, original, endpoint, global_assignment)
```

它只能在无手阶段、全局一对一归属已经完成后被调用。返回 true 至少必须同时满足：

1. `track` 是 operation-start 的旧 C，不是新 D；
2. `track.hand_delta_interrupted == true`；
3. 该 C 在本次有手操作中有真实的物品级受手影响上下文：例如已有 `first_hand_block_box`，或已经按
   现有 CONTACT/HAND 规则记录了自己的直接观察；不能只因为画面中曾出现一只手；
4. 当前 detection 已被全局唯一地分配给这个 C，且同一个 detection 没有被任何 C/D 共用；
5. 该 detection 与 C 自己的 `reappear_candidate_box` / `observed_track` 连续自匹配，已达到现有
   `FLOW3_REAPPEAR_CANDIDATE_CONFIRM_FRAMES`；
6. endpoint 相对 operation-start 的 `base_box` 确实满足既有 `boxes_differ_as_move()`；
7. 不存在 `b_claim_ambiguous`、`contact_path_ambiguous`、`no_hand_candidate_ambiguous`、
   `no_hand_candidate_reserved_by_stronger_owner`、未解决 C-D alias 或 claim grace；
8. 当前没有已成立的遮挡解释把该 C 合法地解释为不可见；对当前可见 endpoint 不得用遮挡覆盖；
9. endpoint 不是该 C 的严格原位/已确认静态恢复框。

条件全部满足时，调用现有 `confirm_rearrange_()`，使工作库存、`placed_box`、
`MOVED_CONFIRMED`、`confirmed_moved_ids_` 和日志沿已有成功路径一次更新。不要复制一份
“半套 MOVED 写字段”的代码。

这个恢复路径只对 **hand delta 被保护性中断过** 的 C 开启。正常单手、正常多手唯一 hand_id 的
`hold_and_move` / `has_meaningful_hand_move()` 路径必须保持原样，不能被替换或降低门槛。

### 4.3 直接离开证据：为没有最终框的 OUT 保留物品自己的最后可靠事实

同时取出没有可见 endpoint，因此不应把第 4.2 节的规则滥用于 OUT。需要新增一个独立的、临时的
物品级 `direct_exit_evidence`，可作为 `hand_out_evidence` 的窄补充。

建议至少保存：

```text
has_direct_exit_evidence
direct_exit_box
direct_exit_frame
```

建立它的条件必须严格：

1. C 是 operation-start 的旧物品，已经按现有规则进入 HAND_*；
2. 已出现 `hand_delta_interrupted`，因此不能再依赖缺失的 hand delta；
3. 有手阶段中，该 C 自己获得过一个按现有 C 归属规则唯一可解释的直接 B / reappear candidate；
4. 这个直接框相对 C 的原位置满足既有 `boxes_differ_as_move()`；
5. 该直接框出现时与当前相关手框实际接触/覆盖，或者它来自已经记录的 C 自己的连续 hand/contact
   路径；不能用一张远处、与手无关的同类框作为离开证据；
6. 没有真实同类竞争、C-D alias、跨类别重复冲突或被更强旧 C 预约的情况。

现有的 `reappear_candidate_box`、`reappear_candidate_started_touching_hand`、`observed_track`、
`first_hand_block_box`、`last_hand_block_box` 等字段应优先复用。若它们会在第一张无手缺失帧中被清掉，
才新增上面的不可变快照；不要重复维护两套不一致的物品路径。

`direct_exit_evidence` 的作用只有一个：在无手且该 C 没有被直接观察、没有正式遮挡、没有 alias 时，
让该 C 进入**原有** `no_hand_missing_count` 累计逻辑。仍然必须等待既有
`FLOW3_NO_HAND_OUT_MISSING_FRAMES`，达到门槛才调用现有 `mark_pending_out_()`。

它绝不能做到以下事情：

- 单帧建立后立即 `OUT`；
- 代替无手连续缺失确认；
- 覆盖真实 `OCCLUDED`、`REVEALED`、C-D alias 或同类歧义；
- 让只被手擦过、最后仍在原位的 C 出库；
- 让没有手关联中断的正常单手路径改走新的宽松分支。

如某个真实场景没有满足这些严格条件，系统可以保持未决，不能为了避免“卡住”而造出错误 OUT。
本文件的目标是让当前三份日志中已存在的物品级证据被正确使用，而不是让所有缺失都自动结案。

### 4.4 跨类别同框重复检测：在创建 D 之前做窄保护

当前已有跨类别重复框提示参数和排除集合，但本次日志说明它没有在最早的 HAND_VISIBLE_D 创建阶段阻止
低分异类同框框成为独立 D。应在 `session_hand.cc` 的“候选是否创建为新 D”之前增加窄检查，概念如下：

```text
低分候选 X 与高分异类检测 Y 几乎同框
    +
Y 被当前 operation-start 的旧 C 唯一、直接地拥有
    +
X 没有与 Y 分离的独立空间/无手连续证据
=> X 仅作为跨类别重复候选，不创建 D，不建立 C-D alias，不占用 C 的 detection
```

判断必须复用现有的：

- `FLOW3_CROSS_CLASS_DUPLICATE_LOW_SCORE_MAX`；
- `FLOW3_CROSS_CLASS_DUPLICATE_SCORE_GAP_MIN`；
- `FLOW3_CROSS_CLASS_DUPLICATE_IOM_MIN`；
- `FLOW3_CROSS_CLASS_DUPLICATE_CENTER_NORM_MAX`；
- `FLOW3_CROSS_CLASS_DUPLICATE_SIZE_RATIO_MAX`。

这不是删除检测框，也不是全局 NMS。被暂时抑制的候选仍可保留诊断信息；若后续它与旧 C 分离，或在
无手帧中持续获得自己的独立直接观察，必须仍能按现有 D/IN 证据链成为真实 D。

下列情况不能触发抑制：

- 两个不同类别物品只是部分重叠、不是几乎同框；
- 高分框本身没有被一个旧 C 唯一直接拥有；
- 低分框已经在无手帧中连续表现为独立物体；
- 当前是复杂但真实的两物体遮挡，不能仅按分数压掉其中一个。

## 5. 联合无手结算：禁止半轮提交

### 5.1 一轮 operation 只能有一个最终结算计划

当前的错误流程近似为：

```text
苹果 -> MOVED_CONFIRMED
橙子 -> 已看到但 resolution=NONE / needs_settle=1
has_unresolved_no_hand_state_ 误认为橙子可放行
=> 提交苹果事件
=> clear_runtime_after_commit_
=> 橙子运行时证据被丢弃
```

正确流程必须是：

```text
所有检测框先完成全局一对一归属
    ↓
逐个旧 C/D 计算本轮结果：MOVED / OUT / IN / OCCLUDED / STATIC / UNRESOLVED
    ↓
所有相关对象都不是 UNRESOLVED
    ↓
一次性生成全部事件、replace_all、clear_runtime_after_commit_
```

不要选择“先提交已经确认的事件，同时保留其余 runtime”等折中方案。当前工作库存、原始库存快照、
blocker lifecycle、C-D alias 和下一轮身份匹配都假设一轮 operation 是原子的；部分提交会引入比当前
漏事件更难修复的库存/身份不一致。

### 5.2 正确的结案集合

对 operation-start 旧 C 而言，只有下列情况之一才算本轮已结案：

```text
MOVED_CONFIRMED
OUT_CONFIRMED
OCCLUDED_CONFIRMED（有现有正式因果/覆盖证明）
正式 STATIC 结案（已按既有原位或静态灰区规则完成，不再 needs_settle）
```

对新 D 而言，必须按已有逻辑处于：

```text
已直接连续确认的 pending IN
或已被安全丢弃 / 回收的候选
```

以下状态**都不是结案**：

```text
当前帧 directly-observed，但 resolution=NONE 且 needs_settle=1
HAND_* / CONTACT_* 仍活动
reappear candidate 尚未连续确认
未解决 C-D alias
no_hand_candidate_ambiguous
no_hand_candidate_reserved_by_stronger_owner
普通 missing 但尚无足够 OUT 证据
```

### 5.3 修改 `has_unresolved_no_hand_state_()` 的具体边界

当前的 `observed_item_ids.count(track.item_id)` 分支，不能再因为“已经看到 C”就无条件跳过未决判断。
应按下面顺序处理：

1. 无手全局匹配先完成；
2. 第 4.2 节的 direct recovered move 尝试执行；
3. 已完成正式静态恢复的 C 沿现有静态逻辑结案；
4. 已确认遮挡的 C 沿细节24/既有 blocker lifecycle 结案；
5. 若此时 `existing_item_needs_settlement(track)` 仍为 true，则该 C 必须令
   `has_unresolved_no_hand_state_()` 返回未决，并留下明确日志，例如：

```text
directly-observed-still-unresolved
```

只有在该 C 已变为第 5.2 节的正式结案状态时，才可以通过提交门。

**第 4.2 节和本节必须同时实现。** 不能只改第 5.3 节，否则当前同时整理/交换只会从漏事件变成
持续 `defer-commit`。

### 5.4 推荐的无手阶段顺序

实际函数拆分应遵循现有工程边界，但本帧的因果顺序应保持为：

1. 处理已有的无手 C/D 候选、alias、静态原位、reappear 自匹配；
2. 计算所有 C/D 与当前 detections 的全局一对一归属；
3. 对未结案旧 C 执行 direct recovered move；
4. 依据所有已确认 MOVED/IN 的前景物体重新计算既有 blocker / occlusion lifecycle；
5. 对不可见旧 C 按普通 OUT 或第 4.3 节 direct exit evidence 累计既有缺失计数；
6. 对所有 operation-start C、D 运行统一的未决检查；
7. 仅在未决集合为空时，生成 `MOVED/OUT/IN/OCCLUDED/REVEALED` 事件、提交库存并清除 runtime。

不能在第 3 步确认第一个物品后就立即产生正式事件，也不能在第 4 步用遮挡关系把当前已直接观察到的
目标覆盖掉。

## 6. 建议的代码职责划分

实际文件名以当前项目代码边界为准，但建议按职责拆开：

- `include/session.h`：增加仅事务期的 `hand_delta_interrupted`、必要的 direct exit snapshot；明确它们的初始化/清理语义；
- `session_hand.cc`：仅负责 hand_id 连续性、设置中断历史标记、记录物品自身的直接离开候选、在创建 HAND_VISIBLE_D 前做跨类别同框抑制；
- `session_geometry.cc` 或 `session_internal.h`：放置纯判断辅助函数，例如“直接恢复 MOVED 是否满足全部条件”；不要在多个状态机分支复制条件；
- `session_no_hand.cc`：继续负责 C/D 的无手连续自匹配、alias、普通 OUT 计数；在 direct exit evidence 窄条件成立时允许走原有 OUT 缺失链；
- `session_settlement.cc`：在全局一对一分配之后执行 direct recovered move，构造联合结算计划，阻止未结案 C 被提前提交；
- `tests/`：增加可重复的 replay 测试和回归断言，不能仅依赖人工查看 trace 日志。

不要在 `session_hand.cc`、`session_no_hand.cc` 和 `session_settlement.cc` 各自写一份略有不同的
“直接证据可以确认移动”的条件。应有一个权威辅助函数或权威结算入口；否则很容易出现有手阶段说可以、
无手阶段说不可以、提交阶段又提前清空的状态矛盾。

## 7. 必做测试与验收

### 7.1 本次三个实机问题的确定性回放

至少新增或完善以下测试，每个都要断言库存、事件和 runtime，而不是只匹配日志文本。

| 场景 | 必须结果 |
| --- | --- |
| 两手同时取出不同类别的苹果、橙子 | 连续无手确认后得到 `OUT(apple)` 和 `OUT(orange)`；无伪 D、无永久 alias、无无限 `defer-commit`。 |
| 两手同时把不同类别物品整理到中间 | 同一事务得到两个 `MOVED`；不能第一个 MOVED 后清空第二个 C。 |
| 两手交换苹果、橙子位置 | 同一事务得到两个 `MOVED`，不是 `OUT + IN`；苹果/橙子的 `item_id` 保持；不把可见苹果误判为 `OCCLUDED`。 |

每个测试还要断言：提交前不存在任何旧 C 为
`needs_settle=1 && resolution=NONE`；提交后 `operation_pending()` 为 false；提交前 runtime 没有被提前清空。

### 7.2 新分支必须有的反向测试

| 场景 | 不允许发生的错误 |
| --- | --- |
| 手框短暂合并、但物品最终仍在原位 | 不得因 `hand_delta_interrupted` 直接 MOVED 或 OUT。 |
| 手擦过物品，物品未移动 | 不得建立足以 OUT 的 direct exit evidence。 |
| 手框歧义后出现一张远处同类噪声框 | 不得把噪声当作 direct recovered move endpoint。 |
| 同类两个物品最终身份不可区分 | 不得按 item_id、hand_id、检测下标强行生成两个 MOVED。 |
| 真实新增 D 与旧 C 部分重叠 | 不得因跨类别重复框保护而丢失真实 D/IN。 |
| 低分异类框与高分旧 C 几乎完全同框 | 不得创建伪 D 或伪 C-D alias。 |
| 移动前景物遮挡旧 C | 细节24的 `MOVED -> OCCLUDED` proof 仍能建立、续验、失效和正常提交。 |

### 7.3 必须完整回归的旧能力

下列全部需要保持原有结果，尤其是单手：

- 单手 MOVED、OUT、IN；
- 单手手框轻微抖动、短暂漏检、手不离开连续移动多个物品；
- 一只手带动多个物品；
- 两只手分离反向移动、手框输出顺序交换、合并后再分开；
- CONTACT_CANDIDATE、CONTACT_MOVING、手擦过后恢复原位；
- 同类一框一物品、同类 alias、静态邻居 owner；
- D quarantine、D 的连续无手确认、同时放入多个物品；
- 严格遮挡、部分遮挡、因果遮挡、遮挡解除、REVEALED、多 blocker；
- 普通 OUT、可见数量结算、无手静态灰区恢复。

“同时放入”目前尚未复现错误，因此不应为它重写现有 D/IN 路径；但它必须作为回归测试，确认本次
联合提交门没有破坏当前对未确认 D 的阻塞行为。

### 7.4 建议增加的诊断日志

日志仅用于验证和定位，不能作为业务状态的替代来源。建议至少包括：

```text
HAND-ASSOC item=... action=mark-hand-delta-interrupted reason=...
DIRECT-RECOVERY item=... result=confirm-moved / reject reason=...
DIRECT-EXIT item=... result=record / reject reason=...
CROSS-CLASS-DUPLICATE candidate=... owner=... action=suppress-d-creation
SETTLE item=... action=defer-directly-observed-still-unresolved
SETTLE barrier=pass / defer unresolved=[...]
```

日志应含 item id、runtime key、detection index、hand id（若适用）、帧号和拒绝原因。这样可以确认
系统是凭物品自己的证据结案，而不是通过放宽规则或强行提交“看起来成功”。

## 8. 完成标准

下一次实现只有同时满足下列条件，才算完成：

1. 三个实机场景都能在既有确认窗口后正确收敛；
2. 同时整理和交换能在同一事务中输出两个 `MOVED`；
3. 同时取出能在每个旧 C 都具备独立证据时输出两个 `OUT`，而不是只因一起消失就误报；
4. 没有任何 `needs_settle=1 / resolution=NONE` 的旧 C 被 `clear_runtime_after_commit_()` 丢弃；
5. hand_id 歧义仍然只会暂停错误 delta，不会被阈值放宽或最近手重绑掩盖；
6. 直接恢复路径只在严格的物品级条件下运行，不能把噪声、同类歧义、手擦过或静态框升级为 MOVED/OUT；
7. 跨类别同框误检不会创建伪 D/alias，但真实 D 的既有证据链仍完整；
8. 单手、已有多手、遮挡、alias、同类身份、入库、出库、揭示和静态恢复的回归测试全部通过；
9. 未修改超参数；若实施中修改了，`超参数位置与调节说明.md` 已同步更新。

本次问题的正确方向不是“让系统更容易判定”，而是：在手框身份不可靠时继续保守地拒绝错误手位移，
同时让已经由物品本身稳定观察到的事实，经过严格全局仲裁后，能够完成整轮事务的正确结案。
