# 旧 C 提前失活时的身份闭环与防重复入库

> 本文是对细节 7 的补充。若两者有冲突，以细节 8 为准。

## 1. 本次真实问题

冰箱里原本有两个同类旧物品：苹果 A 和苹果 B。

```text
操作前：A + B
操作：  把 A 移到 B 旁边，二者不堆叠
实际结果：仍然只有 A + B
错误结果：旧位置的 A + B + 新 item#6（其实是移动后的 A）
```

这不是“两个苹果太近，所以无法区分”本身造成的正常未决，而是程序发生了两个互相矛盾的结论：

```text
对旧 A：没有按移动、没有按 OUT，默认保留在原位置
对真实 A：又按新的 D，正式 IN
```

同一个实体被记了两次，库存数量因此从 5 错误变成 6。

本次实际日志已经能确认的是“旧 C 被提前视为已解决后，错误放行新 D”的问题。
但不能因此把所有风险都归咎于提前失活。还必须独立验证另一条链路：**当旧 A 始终保持活动轨迹时，它能否在手离开后认回路径附近的 A；真的找不到时，能否正确 OUT；同类框无法唯一判断时，能否保持未决。**

这两类问题必须分别修复、分别测试：

```text
问题一：C 提前失活
    -> 可能造成“旧 C 保留 + 同一实体被新 D IN”的重复库存

问题二：C 始终活动但最终 B 不易唯一匹配
    -> 不得把任意附近同类框强认给 C
    -> 不得把检测歧义误当成 C 真的离开而直接 OUT
    -> 正确结果可能是 MOVED、OUT 或 UNRESOLVED
```

## 2. 必须成立的核心约束

一次手操作中，每一个旧物品 C 必须在提交库存前得到且只得到一种结论：

```text
1. STATIC_CONFIRMED：有独立检测证明 C 仍在自己的原位置
2. MOVED_CONFIRMED：C 已唯一匹配到移动后的最终 B
3. OUT_CONFIRMED：有足够的手操作证据，且连续直接无手帧证明 C 缺失
4. OCCLUDED_CONFIRMED：已确认前景物品完整遮挡 C
5. UNRESOLVED：以上四项都未成立，继续等待，不能提交
```

以下不是结论，也绝不能替代上述五种结论：

```text
- C 的运行时状态恰好是 NORMAL
- C 的轨迹暂时断开
- 当前框没有被 C 认领
- 同类物品数量看起来够用
- 结算时把 C 的旧框原样写回库存
```

特别是：`NORMAL` 只能表示“当前没有活动的 HAND/CONTACT 状态”，不能自动表示“已经证明 C 仍在原位”。

## 3. 同类 B / 新 D 的硬性仲裁规则

手离开后，对一个未认领的同类完整框 B，建立疑似新物品 D 之前，必须逐个检查所有同类旧 C。

只有当每一个同类旧 C 都已经满足下列任一条件时，B 才可能进入 D 链路：

```text
- C 在当前直接无手帧有自己的独立静态检测框；或
- C 已确认 MOVED；或
- C 已确认 OUT；或
- C 已确认完全被遮挡。
```

下列任一情况都说明 C 仍未解决，必须阻止 B 创建 D：

```text
- C 有活动的 HAND_* / CONTACT_* 轨迹；
- C 仍在 B 认领保护期；
- C 的 B 归属或 contact 路径存在歧义；
- C 没有运行时记录，也没有自己的独立静态检测框；
- C 有运行时记录，但该记录是 NORMAL，且 C 没有自己的独立静态检测框；
- C 的运行时轨迹刚被释放，但尚未完成一次直接无手结算。
```

最后两条是本次 bug 的直接修复点。现在的实现把“运行时记录存在但为 NORMAL”误当成已解决：它既不算活动轨迹，也不算“没有运行时记录”，从而错误放行 `POST_HAND_REVEAL_D`。

正确的处理不是把 B 强行归给某个 C，而是：

```text
保持 UNRESOLVED
-> 不创建 D
-> 不发 IN
-> 不默认删除旧 C
-> 继续等待下一张直接无手帧
```

若最终只检测到一个合并框，或者两个同类 C 都合理解释同一个 B，也同样保持未决；宁可暂不提交，不能制造额外库存。

## 4. C 的运行时生命周期要求

从旧 C 第一次因手进入 `CONTACT_*` 或 `HAND_*` 起，到该次操作提交/取消前，必须保留“这个 C 是否仍需要无手结算”的明确语义。

建议在 `OperationTrack` 中增加独立的结算标记或枚举，例如：

```text
needs_no_hand_settlement
resolution = NONE / STATIC_CONFIRMED / MOVED_CONFIRMED /
             OUT_CONFIRMED / OCCLUDED_CONFIRMED
release_reason
```

字段名可以调整，但语义必须保留。不要再仅靠 `state == NORMAL` 推断旧 C 是否已经结案。

### 4.1 `release_not_held_()` 的限制

`release_not_held_()` 目前会把运行时记录改为 `NORMAL` 并清掉轨迹、候选 B、手部锚点等信息。修改后必须区分两种情况：

```text
有直接证据：当前帧唯一检测框明确证明 C 仍在原位置
    -> 可以标记 STATIC_CONFIRMED
    -> 可以结束本次 C 的活动追踪

没有直接证据：只是路径暂时断开、候选不唯一、手框变化、或根据遮挡作推断
    -> 不得把 C 当作已解决
    -> 保留可用于无手收尾的轨迹/候选，或至少保留 needs_no_hand_settlement
```

对于“旧位置未看到 C”的情况，不能调用会抹掉 C 身份链路的释放逻辑。C 应继续处于待确认移动/待确认 OUT 状态，直到得到第 2 节中的正式结论。

### 4.2 无手收尾的限制

无手收尾中，旧 C 未被当前检测框绑定时，可以暂时把操作前的旧库存作为显示兜底，但这不是观察证据。

因此：

```text
旧 C 未绑定 + needs_no_hand_settlement = true
    -> 本帧不能正式提交
    -> 继续累积移动确认或 OUT 缺失证据

旧 C 未绑定 + 没有 OUT/遮挡/移动结论
    -> 不能因为回写 original_box 就视为 C 已存在
```

只有在 C 已得到静态、移动、OUT 或完全遮挡结论后，整个操作才允许提交。

绝不允许在同一次提交中同时出现：

```text
旧 C 仅靠 original_box 兜底保留
    +
同类未认领框 B 被正式 IN 为新 D
```

这条是防止“旧 A 还在 + 新 C 又进来”的最终一致性断言。

### 4.3 活动 C 在手离开后的匹配与 OUT 规则

本节适用于 C 仍为活动 `HAND_*` / `CONTACT_*` 轨迹的正常情况；它与“提前变成 NORMAL”的 bug 是两条独立逻辑。

手离开后的旧 C 必须优先于新 D 处理。对活动 C，直接无手帧的查找顺序应保持为：

```text
1. C 自己的原位置检测框
2. 有手阶段已经记录的 reappear candidate
3. C 的预计终点框
4. C 的整条历史轨迹附近的唯一候选框
5. 以上均无有效结果，才进入缺失/OUT 判断
```

这里的“路径附近”不是无限制地拿任意同类框匹配。候选 B 至少必须：

```text
- 与 C 同类；
- 尺寸和位置能接上 C 的候选框、估计轨迹或历史轨迹；
- 不被另一个旧物品的独立静态框更合理地解释；
- 对当前成熟 C 是唯一归属，而不是多个同类 C 的共享候选。
```

若首张无手帧找到符合条件的 B，B 只能先成为 C 的重新出现候选；必须在后续直接无手帧与自己连续匹配后，才确认 `MOVED`。这避免一张跳动框把 A、B 的身份互换。

若找不到 B，处理必须按 C 的证据强度区分：

```text
活动 HAND_* C，且已有有效手移动/持有证据：
    第一张直接无手缺失 -> UNRESOLVED，不能提交
    第二张连续直接无手缺失 -> OUT_CONFIRMED

CONTACT_CANDIDATE 但尚无足够真实移动证据：
    不能仅因缺失直接 OUT
    -> 保持 UNRESOLVED，等待路径、原位置或后续证据
```

若检测器把相邻的 A、B 合并成一个框，或该框同时合理属于多个旧 C，则它不是“真的找不到 A”的 OUT 证据。此时应保持 `UNRESOLVED`；不得强认 MOVED，不得新建 D，也不得因连续歧义框直接 OUT。

## 5. 需要修改的代码位置

以下是实现位置，不要求机械照抄；重点是满足前述语义。

### 5.1 `OperationTrack` / 状态辅助函数

- 为旧 C 增加可区分的“是否仍需要无手结算”或“结算结论”信息。
- `is_active_runtime_track()` 不能成为“是否已结案”的唯一判断。
- 运行时记录虽然为 `NORMAL`、但还没有独立静态证据时，仍要能被识别为未解决旧 C。

### 5.2 `release_not_held_()` 及其调用点

- 为每一次释放记录明确原因，例如：`ORIGINAL_DETECTION`、`CONFIRMED_OCCLUSION`、`CONTACT_RETURNED_ORIGINAL`、`OTHER`。
- 只有 `ORIGINAL_DETECTION` 等真正能证明 C 未移动的原因，才允许标记 `STATIC_CONFIRMED`。
- 逐个检查目前所有调用点，确认它们是否真的有“C 仍在原位”的直接检测证据；没有时不得清空 C 的无手结算资格。

### 5.3 `register_post_hand_reveal_suspects_()`

修改同类旧 C 的保护判断：

```text
旧 C 没有独立检测框
    + 旧 C 没有已确认的静态/移动/OUT/遮挡结论
    -> 该旧 C 未解决
    -> 禁止创建 POST_HAND_REVEAL_D
```

特别要覆盖：`runtime != nullptr && runtime->state == NORMAL`。
它在“没有独立检测框”时必须与 `runtime == nullptr` 一样阻止 D，而不是穿过当前条件。

### 5.4 `has_unresolved_no_hand_state_()` 与最终结算

- 不要因为 `is_active_runtime_track(track) == false` 就直接跳过旧 C 的未决检查。
- 对 `needs_no_hand_settlement` 为真的旧 C，即使运行时状态为 `NORMAL`，也必须阻止本帧正式提交，或继续按规则累计 OUT。
- `original_box` 回写只允许作为未决期间的临时显示/工作库存兜底，不能让它绕过未决检查。
- 提交前增加一致性检查：若某个旧 C 未解决，而同类 D 要 IN，则拒绝提交并保留未决状态。

## 6. 诊断日志要求

本节是本次代码修改的**必做项**，不是仅供分析的建议。以后状态机出现错误时，必须能从日志还原“哪一个旧 C、在哪一帧、因什么条件、从什么状态变成什么状态”，而不能只看到最终多出了一个 D。

日志必须是可开关的调试追踪，例如通过 `fridge_config.h` 中的调试常量、编译开关或明确的运行时配置启用。默认运行时不应无节制地逐帧刷屏；但一旦开启，单次操作的完整证据链必须保留。日志代码只能读取状态和输出信息，不能改变匹配、计数或结算行为。

### 6.1 统一日志上下文

每一条追踪日志都必须带有：

```text
operation_id / session_id
frame_id
有手或无手阶段
事件标签
```

建议统一使用可检索的前缀，例如：

```text
[3.0-TRACE][STATE]
[3.0-TRACE][MATCH]
[3.0-TRACE][RELEASE]
[3.0-TRACE][D-GUARD]
[3.0-TRACE][NO-HAND]
[3.0-TRACE][SETTLE]
```

这样一段真实测试日志可以按操作号和 `item_id` 直接筛选，不会混入上一轮操作。

### 6.2 必须记录的状态转换

旧 C 和疑似 D 每次发生下列变化时，必须输出一条事件日志：

```text
创建 CONTACT_* / HAND_* / suspect D
CONTACT_* <-> HAND_*
进入或结束 B 认领保护期
开始、更新、清除 reappear candidate
进入 MOVED / PLACED / OUT_PENDING / OCCLUDED
调用 release_not_held_()
运行时记录被删除或被同 item 的新记录覆盖
```

每条状态转换至少包含：

```text
item_id 或 suspect_id
old_state -> new_state
old_contact_state -> new_contact_state
resolution / needs_no_hand_settlement
触发分支的明确 reason 枚举或字符串
```

`release_not_held_()` 的日志尤其不能只写“释放”。必须记录：

```text
release_reason
调用位置或调用方名称
当帧是否存在 C 的原位置独立检测框
该检测框索引和 BBox（若有）
hold_evidence_count / not_hold_evidence_count
```

这样才能判断“释放 C”究竟是合理的原位确认，还是路径断开、遮挡推断或错误匹配。

### 6.3 C -> B 匹配与同类仲裁日志

对每个活动旧 C，在有手帧和无手帧都需要记录实际使用的参考信息：

```text
原始框 original_box
预计框 estimated_box
last_seen_box / last_hand_block_box
reappear_candidate_box 及连续次数
历史 track / observed_track 的有效末端
```

若当前同类检测框被尝试或拒绝，日志必须说明结果，而不是只打印“没有匹配”：

```text
检测框 index、cls、BBox、score
匹配来源：原位置 / 预计终点 / candidate / 历史路径
接受原因：唯一且满足几何阈值
拒绝原因：超出路径阈值 / 尺寸不符 / 已被认领 /
          严格属于另一旧物 / 多个 C 同时合理 / 仍在保护期
```

对于同类苹果贴近的场景，这一组日志必须能够回答：最终框是完全没进入 A 的候选列表，还是进入后因与 B 冲突而被保留为歧义。

### 6.4 新 D 防线日志

每次调用 `register_post_hand_reveal_suspects_()` 时，对每一个未认领的候选框都应记录：

```text
候选检测框 index、cls、BBox
是否触及本次手轨迹
是否匹配旧库存
是否冲突活动 C/D
是否被保护期 C 阻止
逐个同类旧 C 的结论：STATIC / MOVED / OUT / OCCLUDED / UNRESOLVED
最终结果：CREATE_D 或 KEEP_UNRESOLVED
```

若决定创建 `POST_HAND_REVEAL_D`，日志必须明确写出“所有同类旧 C 为什么被视为已解决”。这能直接暴露 `NORMAL` 记录被错误放行之类的问题。

### 6.5 无手 OUT 与最终提交日志

每张直接无手帧必须记录每个仍需结算的旧 C：

```text
是否绑定到实际检测框，以及绑定来源
是否被完全遮挡、遮挡者是谁
no_hand_missing_count 的旧值和新值
为何本帧是 UNRESOLVED / OUT_PENDING / OUT_CONFIRMED
是否只是 original_box 临时兜底；若是，明确标记“不是实际观测”
```

提交或拒绝提交时，还必须输出本轮摘要：

```text
每个旧 C 的最终 resolution
每个 D 的来源、连续确认次数和最终结论
库存数量变化
产生的 MOVED / IN / OUT / OCCLUDED / REVEALED 事件
未提交的具体阻塞 item_id 与原因
```

日志的目的不是长期刷屏，而是定位这次“旧 A 何时从待处理变成 NORMAL”的第一个错误状态转换。该具体前置分支目前无法只凭现有日志严格确认；完成本节后，下一次实机复测应能直接定位它。

## 7. 必须新增的回归测试

### 7.1 本次真实场景：同类旧 A 移到同类旧 B 旁边

```text
初始：两个苹果 A、B，位置分开
操作：手遮挡并移动 A，B 保持原位
结束：检测到 B 的原位完整框 + A 在 B 旁边的完整框
前提：A 的 HAND_* 轨迹在整个过程中保持活动，未被提前 release 为 NORMAL
期望：库存仍为 2；A 为 MOVED；没有 IN；没有 OUT
```

该测试要验证的不是“禁止 D”而是活动 C 的完整身份链：无手首帧能在 A 的路径附近找到正确框，后续无手帧连续确认后提交 MOVED。B 的原位框必须保持属于 B，不能被 A 抢走。

### 7.2 本次已发现的提前释放场景

```text
初始：两个同类旧物品 A、B
操作：A 被手影响后，运行时记录错误或模拟地变为 NORMAL
结束：A 的原位置没有独立检测，手路径附近出现同类完整框
期望：该框不得创建 POST_HAND_REVEAL_D；本轮保持 UNRESOLVED
```

该测试专门验证本次“旧 A 仍保留 + 新 D 又 IN”的防线，不能与 7.1 的活动轨迹 MOVED 测试混为一条。

### 7.3 活动轨迹丢失候选但旧 C 仍未结案

```text
初始：旧 C 被手影响
结束首帧：未能唯一匹配 C，出现手路径附近的同类完整框 B
期望：不创建 D、不提交 IN；操作保持 UNRESOLVED
```

后续帧应分别验证：

```text
B 与 C 建立连续身份链 -> MOVED
C 连续直接无手缺失且有足够手操作证据 -> OUT
始终无法确定 -> 保持未决，不制造库存
```

### 7.4 同类相邻框的真实歧义

```text
初始：两个同类旧物品 A、B
操作：A 被移动到 B 附近
结束：YOLO 只给出一个合并框，或同一个框同时合理属于 A、B
期望：不提交 MOVED、不提交 OUT、不创建 D；操作保持 UNRESOLVED
```

此测试确保“找不到唯一 A”不会被错误解释成“物理上 A 已出库”。

### 7.5 合法新物品不能被误伤

```text
初始：旧苹果 B 有自己的独立原位检测框
操作：真正放入新苹果 D，D 紧挨 B
期望：B 保留；D 经过完整 D 证据链后 IN
```

这保证“同类旧物未决时阻止 D”不会退化成“同类物品永远不能入库”。

### 7.6 原有回归用例

继续保留并运行：

```text
- 快速移动后 C 重新出现，仍认回 C
- 多个成熟同类 C 竞争同一 B，保持未决
- 手离开后首次显现的真正全遮挡新 D，可以连续确认后 IN
- 连续两张直接无手缺失，旧 C 正确 OUT
- 完整遮挡与重新显现的库存状态正确变化
```

## 8. 验收标准
