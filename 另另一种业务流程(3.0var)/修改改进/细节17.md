# 细节17：在不改变业务行为的前提下进行全工程模块化拆分

## 0. 文件用途

本文件是下一次拆分代码时的实施指导。当前 `3.0-r18` 代码已经完成了
《细节16.md》要求的修改，并经过主机端回放和 ASAN/UBSAN 回放，当前阶段
虽然不是绝对完美，但业务能力已经基本满足需要。本次工作的目标是把过长的
会话状态机、主循环、推理后处理、云端上报实现和主机回放测试，按职责拆成
适度数量的模块，降低耦合、提高可读性，并让后续阅读和维护不必每次加载一个
6800 多行的文件。

本次只改变物理文件组织，不改变业务规则。拆分完成后，程序看到的输入、状态
变化、库存结果、事件顺序和日志语义都应与拆分前一致。

> 原先代码已经具备并验证过很多有效功能，本身是很好的。本次拆分绝不能把
> 原先正确的 NORMAL、HAND、CONTACT、D、C-D alias、遮挡、揭示、IN、OUT、
> MOVED、OCCLUDED、REVEALED、无手提交和同类仲裁功能改坏。拆分不是重写，
> 不能借机“顺手优化”业务逻辑。

**本轮执行规则已经固定：表中标为“必须拆”的文件必须按本文件给出的边界拆开；
标为“本轮保持完整”的文件不得拆开。不存在“拆到一半再临时决定”的情况。若
实施时发现一个既定边界会破坏已验证行为，应停止在上一个通过点定位依赖，不能
以改变业务逻辑、阈值或状态语义来强行完成文件拆分。**

### 1.1 全工程文件的拆分取舍

本次不是“只拆 `session.cc`”，也不是把每个文件机械切成更小的碎片。下表是
所有当前相关文件的明确处理决定；需要拆分的文件必须在后续实施中落实，保持
完整且已经高内聚的文件则不要为了行数而硬拆。

| 文件 | 决定 | 目标组织 |
|---|---|---|

| `tests/session3_replay_test.cc` | 必须拆 | 测试辅助/fixture、基础移动与出入库、HAND/CONTACT、同类所有权、无手灰区与结算分别成测试文件，保留一个轻量 runner |
| `src/main.cc` | 必须拆 | `main.cc` 保留启动、关闭、后台库存 stub 和顶层帧循环；固定移出预处理/坐标、门状态纯 helper、OSD/事件打印，不拆出帧流水线和推流 owner |
| `src/postprocess.cc` | 必须拆 | 保持 `post_process()`、`init_post_process()`、`deinit_post_process()` API 不变；固定按标签生命周期、量化/浮点框解码、排序/NMS/结果整理拆分，避免再复制 YOLO 逻辑 |
| `src/cloud_uploader.cc` | 必须拆 | 保持 `CloudUploader` 对外接口和线程语义不变；固定按 JSON/base64、HTTP socket、队列/worker/heartbeat 移动定义 |
| `include/session.h` | 本轮保持完整 | 它是 `SessionManager` 与运行时类型的单一契约；本轮不新建 `session_types.h` 或 `operation_track.h`，避免在实现拆分时同时改变头文件依赖和封装 |
| `include/fridge_config.h` | 本轮保持完整 | 全局参数集中管理本身是高内聚设计；本轮不按常量类别拆散 |

| `include/cloud_uploader.h` | 本轮保持完整 | `CloudUploader`、`UploadJob`、上传枚举属于一个对外契约，本轮不拆 |
| `include/inventory.h`, `src/inventory.cc` | 本轮保持完整 | 库存容器和其操作规模小且职责集中 |
| `include/snapshot.h`, `src/snapshot.cc` | 本轮保持完整 | 快照职责集中，约 274 行不构成需要拆分的风险 |
| `include/tracker.h`, `src/tracker.cc` | 本轮保持完整 | 旧 ByteTrack-Lite 实现是独立整体，当前业务只保留兼容用途，不为拆分而扩大影响面 |
| `src/yolov5n.cc` | 本轮保持完整 | 模型初始化/推理生命周期规模较小且边界清楚 |
| `include/luckfox_mpi.h`, `src/luckfox_mpi.cc` | 本轮保持完整 | 硬件封装职责集中，拆分会增加板端依赖面 |
| `src_capture/capture_dataset.cc` | 本轮保持完整 | 独立采集工具，不属于主程序 `src/*.cc` 构建；约 206 行且职责集中 |

因此，“改拆开的都拆”在本文件中具体指：`session.cc`、回放测试、`main.cc`、
`postprocess.cc` 和 `cloud_uploader.cc`；其余文件经过判断必须保持完整，而不是
遗漏或留待本轮临时决定。

## 2. 不可违反的拆分原则

1. **只移动定义，不改行为。** 函数体应尽量原样移动；除必要的声明、命名空间
   和 include 调整外，不修改阈值、判断顺序、状态枚举、计数器含义、事件类型、
   日志标签、库存字段和确认帧数。
2. **不重写总流程。** `SessionManager::process_frame()` 的阶段顺序、手出现/手
   离开入口、无手连续收尾和最终提交逻辑保持原样。不要把“拆文件”变成重写状态机。
3. **不做无关重构。** 本轮不顺手改名、不统一格式、不删除看起来重复但尚未证明
   无用的代码、不调参、不改变数据结构，不修与模块化无关的问题。
4. **不要通过包含 `.cc` 拆分。** 禁止使用 `#include "session_hand.cc"` 等方式把
   多个实现拼成一个翻译单元；每个函数只能在一个 `.cc` 中定义。
5. **保持封装。** `SessionManager` 的私有字段不应因拆分而变成 public 或全局变量。
   如果模块需要大量直接访问私有状态，优先保留为成员函数，而不是为了“解耦”破坏
   类封装。
6. **适度拆分。** 每个大型职责域使用约 3 至 7 个实现模块，不是把每个小 helper
   拆成一个文件，也不是留下新的超大单文件。单个模块仍应围绕一项完整职责组织。
7. **固定保持现有路径。** 本轮所有新生产 `.cc` 放在现有 `src/` 根目录，所有新
   回放测试放在 `tests/` 根目录；不建立源码子目录，不改变 CMake 的源码发现策略。

## 3. 固定的模块边界

下面是本轮固定的职责边界。移动函数前仍须核对调用依赖，但这只能决定必要的
内部声明和 include，不能改变“哪个职责文件必须存在”这一决定。

### 3.1 `src/session.cc`：总入口和跨阶段编排

最终只保留：

- `SessionManager` 构造函数和对外 public API；
- `process_frame()` 及其必须保持完整的阶段编排；
- 会话生命周期、初始化入口、最终清理等无法独立归属的薄编排函数；
- 需要同时调用多个阶段模块、且本身没有独立业务语义的协调代码。

它不应继续容纳所有几何 helper、所有 HAND 分支和全部无手结算细节。

### 3.2 `src/session_geometry.cc`：纯几何、匹配和位移 helper

本模块包含：

- `strict_match()`、`partial_match()` 及其框匹配辅助；
- 中心距离、边缘距离、IoU/IoM/cover ratio、框大小差等纯几何计算；
- `move_box()`、`total_move()`、`estimated_box()`；
- `final_motion_reference_diagonal()`、`normalized_final_motion_distance()`、
  `boxes_differ_as_move()`；
- 手框与物体的相交、覆盖、接触判断；
- 只依赖参数和传入对象、没有副作用的枚举/状态名称转换。

这些函数应保持无副作用，不修改工作库存、claimed 集合、证据计数或事件列表。
能继续留在单一模块的 helper 不要为了数量而外露。

### 3.3 `src/session_ownership.cc`：直接所有权和匹配仲裁

本模块包含：

- STRICT / LOCAL_CONTINUOUS / LOCAL_WEAK 的排序与候选比较；
- `build_mutually_unique_hand_direct_old_owner_by_detection_()`；
- 静态预约 `reserve_visible_known_detections_()` 及其无副作用计算版本；
- 旧 C 原位置所有权计划、同类唯一仲裁和歧义集合处理；
- `strict_owner_blocks_old_c()`、直接 owner 计划相关的纯判断。

该模块必须保留现有优先级：旧物体自己的严格原位证据，高于自己的局部连续
证据，高于其他物体的 estimated/path/tentative/reappear 猜测。原位置歧义框
不能按 `map` 遍历顺序强行分配，也不能被 D/suspect 当作升级证据。

细节14/15 中已经验证过的“静态旧 C 预约”和 HAND/CONTACT 直接原位置所有权
必须继续存在，不能因为移动函数而删除或合并掉。

### 3.4 `src/session_hand.cc`：HAND_* / CONTACT_* 有手阶段

本模块包含：

- `begin_working_operation_()`；
- `append_move_to_existing_hand_tracks_()`；
- `update_existing_contact_tracks_()`、`mark_new_contact_candidates_()`；
- `update_existing_hand_tracks_()`、`reopen_released_static_tracks_()`；
- `scan_or_update_suspects_()`、`mark_newly_hand_blocked_items_()`；
- `apply_suspect_cover_evidence_()`、`advance_claim_grace_()`；
- `process_effective_hand_frame_()`；
- HAND/C-D alias、tentative B、hold/drop 连续证据相关的成员函数。

移动这些函数时，保持当前的严格匹配、局部连续匹配、claim grace、唯一认领、
连续确认和可撤销临时 MOVED 逻辑，不改变状态机分支条件。

### 3.5 `src/session_no_hand.cc`：手离开后的直接观察和恢复

本模块包含：

- `observe_no_hand_frame_()`；
- `register_post_hand_reveal_suspects_()`；
- 无手原位置恢复、stable gray zone、reappear、直接无手证据和连续计数相关
  的内部逻辑；
- `has_unresolved_no_hand_state_()`。

必须保留细节16已实现的入口修复：找到的原位置候选不能因为 CONTACT 的
`12px` 原位判断而在进入灰区/静态恢复前被清除。身份归属、静止/待确认/移动
判定、最终事件提交仍是三层独立步骤。

### 3.6 `src/session_settlement.cc`：结算、遮挡和事件生成

本模块包含：

- `prepare_visible_count_settlement_()`、`clear_visible_count_settlement_()`；
- `refresh_confirmed_blockers_()`；
- `settle_no_hand_frame_()`；
- `mark_pending_out_()`；
- 同类数量结算、遮挡并集、IN/OUT/MOVED/OCCLUDED/REVEALED 事件生成和无手
  最终提交所需的纯结算辅助。

事件生成必须继续使用现有工作库存隔离：有手阶段只写 working inventory，
连续无手帧满足条件后才更新正式库存并输出结果。不得因拆到新文件就把临时
状态提前写成正式事件。

### 3.7 运行时清理和 trace：本轮不额外拆文件

`rebuild_persistent_item_index_()`、`reset_operation_runtime_()`、
`clear_runtime_after_commit_()`、`trace_()` 和 `trace_track_()` 本轮保留在
`session.cc`。它们横跨多个阶段并且直接依赖大量 `SessionManager` 私有状态；
为了拆出一个很小的文件而外露状态，会增加耦合并提高回归风险。

因此本轮**不创建** `session_runtime.cc` 或 `session_trace.cc`。这些函数仍应按
原有顺序和语义执行，日志标签不能改变或删除。

### 3.8 主机回放测试模块

`tests/session3_replay_test.cc` 约 2800 行，已经同时包含测试 fixture、帧注入
辅助、事件断言和大量互相独立的业务场景。它也需要拆分，否则生产代码拆完后
测试仍然是新的超大单文件。本轮固定目标布局如下：

```text
tests/session3_replay_support.h
tests/session3_replay_support.cc       # det/item/frame/settle/事件断言
tests/session3_replay_basic.cc         # 基础 MOVED、OUT、身份保持
tests/session3_replay_hand_contact.cc  # HAND_*、CONTACT_*、放下与覆盖
tests/session3_replay_ownership.cc     # 同类旧 C、D、alias、检测顺序
tests/session3_replay_no_hand.cc       # 无手恢复、灰区、遮挡/揭示、连续收尾
tests/session3_replay_main.cc          # 唯一 main，调用各测试注册函数
```

文件名和职责按上表固定，必须满足以下边界：

- 每个测试函数只在一个测试 `.cc` 中定义；
- 通用的 `det()`、`item()`、`send_frame()`、`settle_after_hand()` 和事件断言
  只能有一份实现；
- 测试仍链接拆分后的生产实现，不能为测试复制一套简化业务逻辑；
- 每个测试的输入帧、检测顺序、断言和日志语义保持不变；
- 测试 runner 只负责调用测试，不在其中重新实现业务流程。

测试 runner 直接按固定顺序调用各测试注册函数，保持 C++11 兼容，不引入新的
测试框架或宏式注册机制。所有测试函数移动完成并通过回放后，原
`tests/session3_replay_test.cc` 被这些拆分文件完全替代，不再保留旧测试源或
重复的 `main()`。

### 3.9 `src/main.cc`：硬件主循环的适度拆分

`main.cc` 约 854 行，职责横跨硬件初始化、开关门状态、图像预处理、YOLO 调用、
业务会话、OSD、编码和 RTSP。本轮固定按以下边界移动定义：

```text
include/app_preprocess.h     # 预处理/坐标转换的最小声明
include/app_door_state.h     # 门状态纯辅助函数的最小声明
include/app_display.h        # OSD 与事件打印的最小声明
src/main.cc                  # main、资源初始化/释放、门状态转移、顶层帧循环
src/app_preprocess.cc        # letterbox、mapCoordinates 及相关坐标转换
src/app_door_state.cc        # 像素差、亮度、暗像素比例、中位数、关闭候选判断
src/app_display.cc           # 颜色、业务检测框、HAND 输入和事件 OSD 输出
```

本轮不创建 `app_frame_pipeline.cc` 或 `app_backend.cc`。`while (1)` 内的门状态
转移、RKNN 调用、`SessionManager` 调用、编码和 RTSP 顺序共享大量运行时对象，
强行拆出会使参数和生命周期分散，反而增加耦合。`request_backend_inventory()` 也
继续留在 `main.cc`，直到真实后台协议落地后再单独设计接口。

移出的三个模块只包含独立 helper；门状态变量、RTSP 句柄、帧缓冲和
`SessionManager` 生命周期仍由唯一的 `main.cc` owner 管理，不能复制成多个全局状态。

必须保持：

- 关门暗帧不会进入 YOLO、tracker、session、快照或结算；
- 开门/关门确认帧数和恢复入口不变；
- 传给 `SessionManager` 的检测顺序、类别、分数和 hand_boxes 不变；
- 业务 OSD 与业务输入仍使用同一批检测，不能因显示模块拆出而丢低分业务框；
- 编码、RTSP 发送和资源释放顺序不变。

### 3.10 `src/postprocess.cc`：YOLO 后处理拆分

该文件约 522 行，虽然比 `session.cc` 小，但同时包含标签生命周期、NMS、排序、
量化转换和三种输出解码路径。本轮固定拆成三个模块：

```text
include/postprocess_internal.h     # 仅声明 decode helper，不暴露 labels 可变状态
src/postprocess_labels.cc       # readLine/readLines/loadLabelName/标签释放与名称
src/postprocess_decode.cc       # process_i8/process_i8_rv1106/process_fp32 及量化 helper
src/postprocess.cc              # post_process 总编排、排序/NMS、最终结果填充
```

标签数组只由 `postprocess_labels.cc` 持有，`coco_cls_to_name()` 继续提供现有公共
查询接口；不要把 `labels` 暴露为公共全局变量。`anchor`、类别阈值和输出结构的
含义保持不变，不能因为拆分顺手改置信度、NMS 或坐标裁剪。

### 3.11 `src/cloud_uploader.cc`：端云上报拆分

该文件约 446 行，具备三个清晰职责，但线程和网络状态必须继续归
`CloudUploader` 管理。本轮固定拆成以下三个模块：

```text
src/cloud_uploader.cc           # CloudUploader 构造、start/stop、队列与线程编排
src/cloud_json.cc               # upload_kind_to_str、base64、JSON 组装/字段提取
src/cloud_http.cc               # socket/DNS/HTTP POST 的实现
```

`http_post()` 继续作为 `CloudUploader` 私有成员函数，定义移动到 `cloud_http.cc`；
`build_json()` 继续作为私有成员函数，定义移动到 `cloud_json.cc`。只把真正纯的
JSON/base64 helper 提取出去；不要为了跨文件访问而公开网络凭据、
队列或线程字段。必须保持队列满时的丢弃策略、重试次数、心跳周期、停止时 join
行为和离线模式行为不变。

### 3.12 `session.h`：本轮保持完整

`session.h` 约 458 行描述的是同一业务契约，且 `OperationTrack` 与
`SessionManager` 私有字段耦合很深。本轮不新建 `session_types.h` 或
`operation_track.h`，也不改变字段默认值、枚举数值、字段顺序或
`SessionManager` 的 public/private 边界。

这样实现文件可以被模块化，而最敏感的状态定义仍保持一份、一个入口和一套
依赖。本轮的 `session.h` 拆分工作到此为止。

## 4. 跨模块共享 helper 的处理方式

本轮固定创建：

```text
include/session_internal.h
```

它只暴露 `session_geometry.cc`、`session_ownership.cc`、`session_hand.cc`、
`session_no_hand.cc` 和 `session_settlement.cc` 确实共同需要的最小内部接口，
例如纯几何匹配、框移动、最终归一化位移、状态名称和 owner 计划辅助。只被一个
模块调用的 helper 继续留在该 `.cc` 的匿名命名空间中；不要把所有原匿名函数
一股脑变成全局 API。内部头文件也不能暴露 `SessionManager` 的私有成员布局。

跨模块函数若必须访问 `SessionManager` 私有状态，固定使用以下顺序：

1. 保留为 `SessionManager` 成员函数，只移动定义；
2. 通过已有成员函数传递必要数据；
3. 只有真正纯函数才提取为内部 helper。

不要为了拆文件引入全局单例、friend 大面积开放、重复状态副本或新的业务抽象。

## 5. 固定的全工程实施顺序

每一步只移动一个职责模块，完成后立即编译和回放；不要一次性移动全部生产代码
或 2800 行测试。

1. **建立基线。** 在任何移动前保存当前完整 session3 replay、ASAN/UBSAN replay
   的退出码、关键事件序列、库存数量和 item_id 结果。
2. **先拆 `session_geometry.cc`。** 只移动无副作用几何/匹配 helper，确认链接
   没有重复定义、所有调用仍指向同一实现。
3. **再拆 `session_ownership.cc`。** 先移动 owner 计划和唯一仲裁；重点回放
   同类检测数组顺序变化、HAND_VISIBLE_D、C-D alias。
4. **再拆 `session_hand.cc`。** 只移动 HAND/CONTACT 成员函数，保持原函数体和
   调用顺序；重点检查手进入、手移动、手遮挡、手离开四类边界。
5. **再拆 `session_no_hand.cc`。** 保留灰区连续证据、原位恢复和 reappear；重点
   回放 item#7 轻微框变化不会卡住、item#8 正式移动仍产生 MOVED。
6. **最后拆 `session_settlement.cc`。** 结算和事件最容易受链接顺序/声明影响，
   应在前面模块稳定后处理。
7. **保留 runtime/trace。** 不创建 `session_runtime.cc` 或 `session_trace.cc`；
   这些跨阶段、强依赖私有状态的函数继续留在 `session.cc`。
8. **拆回放测试。** 生产 session 模块稳定后，按 3.8 的场景边界拆测试；每拆
   一个测试模块就运行完整测试集合，确保不是只编译未被调用的测试。
9. **拆 `main.cc` 的独立 helper。** 只创建 `app_preprocess`、`app_door_state` 和
   `app_display` 模块；顶层帧循环、后台库存 stub 和所有资源 owner 继续留在
   `main.cc`，每一步都做板端依赖检查。
10. **拆 `postprocess.cc`。** 固定完成 labels、decode、总编排三个模块；保持三种
    RKNN 输出路径分别可用。
11. **拆 `cloud_uploader.cc`。** 固定完成 JSON、HTTP、uploader 编排三个模块，运行
    离线模式、重试、心跳和关门库存快照相关检查。
12. **保持 `session.h` 完整。** 本轮不创建额外 session 类型头文件，也不改变
    现有封装；这是本轮固定的不执行项。

若某一步出现业务行为差异，先回到该步之前最后一个通过版本的文件组织并定位
差异；禁止通过改变阈值、放宽匹配、减少确认帧或删除事件来“修复”拆分回归。
