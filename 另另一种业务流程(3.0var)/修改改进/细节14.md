# 细节 14：阻止不可靠 D 候选借旧 C 证据确认，避免 YOLO 瞬时噪声升级为库存事件（计划 3.0-r17）

## 0. 本文件的用途与首要约束

本文件记录一次实机整理测试已经定位的状态机漏洞，并定义下一次代码修改的
唯一目标、实现边界和回归要求。

本次问题发生在一次本应只有 `MOVED item#8 orange` 的整理操作中，最终却错误
输出了：

```text
MOVED    item#8  orange     正确
OCCLUDED item#6  apple      错误
IN       item#11 apple      错误
```

问题不是正常整理、正常入库、正常出库、正常遮挡或同类仲裁的通用逻辑失效。
它是一个非常具体的时序/所有权缺口：**一个已经存在的 `HAND_VISIBLE_D` 疑似新物品，
在有手阶段先于普通旧库存预约检测框，并把一个本应由当前帧“双向唯一静态预约”
给 operation-start 旧 C 的框当成自己的连续确认帧。**

从业务上抽象，本补丁的目标是抵御 YOLO 的单次不可靠候选，而不是消除 YOLO 的所有
误检。这里的“不可靠候选”包括短暂假阳性、类别抖动/跨类别重复框、框位置跳动，以及
由手、遮挡或反光造成的局部错误观测。它们都可以先作为可撤销的 D 存在；但在没有
独立连续证据前，不能借用静态旧 C 的唯一检测证据升级为库存事件。

本轮实现范围仍然是有手阶段已存在的 `HAND_VISIBLE_D` 更新路径。不得借此原则未经
测试地改写所有 D 来源、所有 NMS 行为或整个操作流程；将来若有其它来源出现同类漏洞，
应复用同一所有权不变量并单独增加回放测试。

下一次修改必须是一个窄补丁：在 D 候选增加 `self_match_count`、更新自身位置或
提升为工作库存之前，阻止它认领“双向唯一静态属于旧 C”的检测框。不得为了通过本例而修改
全局分数阈值、全局轨迹匹配阈值、手接触阈值、移动阈值或既有 C-D alias 机制。

### 0.1 必须完整保留的现有能力

以下能力在当前版本已有价值，细节14的修改不得改变其业务语义或确认帧数：

```text
1. 正常 IN：手边出现的真实 D 仍可经过已有 D 链路、无手连续直接证据后入库。

2. 正常 OUT：旧 C 的连续无手缺失、可见数量不足、遮挡、重新出现撤销逻辑不变。

3. 正常 MOVED / 整理：已有 C 的 original、reappear、HAND_*、CONTACT_* 路径
   与最终 MOVED 确认不变。

4. 正常遮挡与恢复：只有确认的前景物品完全覆盖旧 C 时才可产生 OCCLUDED；
   本补丁不能把普通缺失改成遮挡或出库。

5. 同类相邻物品：细节9至细节13的一框一物品、静态邻居排除、claim grace、
   C-D alias、独立 D 与共享框仲裁必须保留。

6. C 旧位置替代 D：真实 D 放在已移动/被遮挡 C 的旧位置时，仍可走
   C_POSITION_REPLACEMENT_D 和已有的隔离/无手仲裁链路。

7. CONTACT_CANDIDATE：手仅从物品旁经过、或确实低覆盖率推拉物品时，
   仍允许建立可撤销 CONTACT 候选；不能因本例而一概关闭该能力。
```

### 0.2 版本、范围与超参数边界

```text
基础版本：细节13完成后的当前 3.0 实现（r16；实际版本号以工程版本说明为准）
下一目标：3.0-r17
代码范围：src/session.cc + tests/session3_replay_test.cc
预期修改：一个有手 D 所有权防护点 + 一个回放测试
预期超参数修改：无
```

以下数值在本次不得修改：

```text
FLOW3_TRACK_CENTER_NORM = 0.75
NEW_ITEM_CONFIRM_FRAMES = 2
FLOW3_HAND_ATTACH_DISTANCE = 28 px
FLOW3_CONTACT_OBJECT_MOVE_EPS = 12 px
FLOW3_COMMIT_MOVE_CENTER_DISTANCE = 28 px
YOLO 候选分数阈值、业务分数阈值、NMS 阈值
所有 IN / OUT / MOVED / reappear / claim grace 的确认帧数
```

因此，正常情况下**不需要**修改 `超参数位置与调节说明.txt`。若实现中新增或
更改了 `constexpr`，才必须同步更新说明；本文件建议的方案不需要新增数值参数。

## 1. 本次测试中已经确认的事实

### 1.1 物理操作与正确业务结果

测试开始时库存有 6 个物品，其中包括：

```text
item#3   apple
item#4   soda can
item#6   apple
item#7   orange
item#8   orange
item#10  orange
```

用户只移动了 `item#8 orange`。正确结果应当是：

```text
仅 MOVED item#8
库存数量仍为 6
item#6 仍为可见苹果
没有任何 apple IN
没有任何 apple OCCLUDED
```

镜像画面的左右方向不影响这一结论。物品的真实身份、类别和事件数量是判断依据。

### 1.2 已确认的关键时间线

| 帧 | 日志事实 | 正确解读 |
| --- | --- | --- |
| `833` | 在 `item#8` 原位置附近同时输出 `cls=0 score=0.565` 和 `cls=2 score=0.542` 两个几乎重合的框 | YOLO 对被手影响的橙子产生了短暂的跨类别苹果候选；这只是模型输入，尚不是库存事件 |
| `833` | 创建 `suspect#-1 cls=0 source=HAND_VISIBLE_D` | 将手边未知苹果框先作为可撤销 D 候选，原则上可以接受 |
| `834` 至 `836` | 假 D 没有得到可证明属于自己的稳定苹果观测 | 它本应继续保持 provisional，不能写入工作库存 |
| `837` | `suspect#-1` 被提升为 `item#11`，其 `last` 却变成 `(374,252,556,447)` | 该框正是旧苹果 `item#6` 的稳定严格检测框；假 D 错误吃掉了它 |
| `837` | `item#6` 进入 `CONTACT_CANDIDATE` | 手与旧苹果完整参考框相距约 14 像素，低于 28 像素的接触距离；这只是保守接触候选，并不等于真实遮挡 |
| `840` 至 `852` | `item#8` 得到正常 MOVED 确认，`item#11` 却继续以苹果身份参与无手结算 | 真正的整理已识别正确；错误是已经提升的假 D 污染了一框一物品分配 |
| `852` | 输出 `OCCLUDED item#6`、`MOVED item#8`、`IN item#11` | 假 D 被当作前景苹果，进而把本应拥有唯一苹果框的 `item#6` 变成了遮挡物 |

### 1.3 这不是“橙子实际遮挡苹果”的直接判断

用户的猜测有一半正确：最终确实发生了“旧苹果的框被新苹果身份占用，旧苹果
被输出为遮挡”。但真正的因果顺序是：

```text
移动橙子附近的 YOLO 跨类别假苹果框
        ↓
创建 HAND_VISIBLE_D 的 provisional suspect
        ↓
假 D 的宽松手轨迹匹配到远处稳定旧苹果 #6
        ↓
假 D 达到 2 次 self match，被提升为 item#11
        ↓
item#11 与 item#6 争同一无手苹果框
        ↓
结算把 #11 当作前景，#6 被标记为 OCCLUDED
```

因此，`item#6` 的遮挡事件是错误 D 身份造成的**后果**，不是系统一开始看见
橙子覆盖苹果就直接作出的结论。

### 1.4 为什么橙子与苹果的 `cls_id` 不同，仍会出现这条错误链路

这里必须区分“物理物品身份”和“某一次检测候选的类别预测”。`cls_id` 是 YOLO 对
**一个候选框**给出的当前帧分类结果；它不是物理物品的永久身份证，也不会让不同
候选框天然互斥。手、遮挡、反光、角度变化或物品与手组成的局部外观，都可能让不同
候选框对同一视觉区域给出不同类别。

本例不是业务状态机把已有橙子 `item#8` 的 `cls_id=2` 改写成了苹果。日志直接证明，
检测器在 `frame=833` 已经把同一位置作为两个独立候选输出：

```text
无手前 frame=832：
  cls=2  score=0.880  box=(740,289,901,449)    <- 已知橙子 #8

手出现的 frame=833：
  cls=0  score=0.565  box=(741,289,903,418)    <- 苹果候选
  cls=2  score=0.542  box=(743,289,901,418)    <- 橙子候选
```

两个 `frame=833` 框的 IoU 约为 `0.975`，并且都与 `item#8` 的操作起始框
`(740,287,901,443)` 高度重合；在该位置没有一件独立的已知苹果。因此，基于现有日志，
最合理且足够用于修复的结论是：这是手边橙子视觉区域产生的跨类别重复候选，而不是
出现了一件真实苹果。若需要追溯到具体 YOLO anchor 或原始 tensor，还要额外记录模型
原始输出；那不是判定本次业务漏洞所必需的条件。

两个候选会同时进入业务层也符合当前后处理实现。`postprocess.cc` 的 `nms()` 只比较
`classIds[n] == filterId` 的同类候选，随后又对每个类别分别调用一次 NMS。因此：

```text
同类重叠候选：会互相 NMS 抑制。
异类重叠候选：不会互相 NMS 抑制，可同时保留。
```

这不是 NMS 本身的错误。类别感知 NMS 常用于允许真正重叠的不同物品同时存在。问题在于，
业务层将 `cls=0` 的低分候选合理地暂存为可撤销 D 后，又错误把旧苹果 #6 的严格框
当成它的第二次“自身连续观测”。因此本次修复针对的是**D 的确认所有权**，而不是把
所有跨类别重叠候选一律删除。后一种做法会误杀真实的不同类别重叠、遮挡或交接场景。

## 2. 具体根因

### 2.1 假 D 的手轨迹宽松匹配刚好覆盖了旧苹果 #6

`frame=837` 的日志给出：

```text
假 D 的预测框：    (526.5,330.0,688.5,459.0)
旧苹果 #6 检测框： (374.0,252.0,556.0,447.0)
```

两框中心距离约为 `149` 像素；相对于较小框对角线的归一化距离约为 `0.72`。
当前 `track_match_box()` 允许：

```text
normalized_nearby_distance <= FLOW3_TRACK_CENTER_NORM = 0.75
width ratio difference        <= FLOW3_TRACK_WIDTH_RATIO = 0.65
height ratio difference       <= FLOW3_TRACK_HEIGHT_RATIO = 0.65
```

因此，纯几何的宽松 HAND 轨迹匹配会接受这个框。这种宽松容差本来是为了处理：

```text
手持物体的框跳动、局部框、手移动后完整框重新出现、物品中途放下。
```

它本身不应被收紧。问题是：**在它被用于 D 的确认之前，没有先检查该检测框
是否已被当前帧的双方唯一静态预约规则分配给 operation-start 旧 C。**

同一帧中，旧苹果 #6 的原始框与该检测框几乎重合：

```text
旧 #6 原始框：     (374,250,550,440)
当前苹果检测框：   (374,252,556,447)
中心距离：约 5 像素
```

它完全满足严格旧库存身份匹配，应该优先属于 `item#6`，不应成为 D 的第二帧
自身证据。

### 2.2 有手阶段的处理顺序暴露了所有权缺口

`process_effective_hand_frame_()` 的现有顺序为：

```text
update_existing_contact_tracks_()
update_existing_hand_tracks_()      <- 已存在 D 在这里更新并可能 promote
reopen_released_static_tracks_()
reserve_visible_known_detections_() <- 普通静态旧 C 到这里才预约自己的严格框
mark_new_contact_candidates_()
mark_newly_hand_blocked_items_()
scan_or_update_suspects_()
```

`frame=837` 时，`item#6` 还没有运行时 HAND/CONTACT 轨迹；而 `suspect#-1`
已在 `track_buffer_` 中。`update_existing_hand_tracks_()` 先执行，并且 D 的
runtime key 为负数，map 遍历时会先被处理。它先取走了检测框；后面的静态库存
预约自然无法再把同一框交给 `item#6`。

当前 D 分支的危险动作是：

```cpp
claimed_detection_indices->insert(observed_index);
++track.self_match_count;
track.last_seen_box = d.box;
if (!track.promoted_to_working_inventory &&
    track.self_match_count >= NEW_ITEM_CONFIRM_FRAMES) {
    promote_keys.push_back(...);
}
```

假 D 创建时 `self_match_count = 1`；本帧错误拿到旧苹果框后加到 `2`，正好达到
`NEW_ITEM_CONFIRM_FRAMES = 2`，因而提升为 `item#11`。

### 2.3 为什么 `CONTACT_CANDIDATE` 不是应当修改的根因

`item#6` 的完整参考框底边约为 `y=440`，手框顶边约为 `y=454`，边缘距离约为
14 像素。`hand_is_near()` 使用：

```text
box edge distance <= FLOW3_HAND_ATTACH_DISTANCE = 28 px
```

所以系统将它标为“可能低覆盖率接触/推拉”的 `CONTACT_CANDIDATE`。这是合理的
保守输入状态：手从旁边经过时不能立刻断言物品完全静止。它不会单独产生 IN 或
OCCLUDED。

本例之所以后来出现伪遮挡，是因为假 `item#11` 抢走了同一个苹果框。降低 28 像素
接触阈值只能掩盖这一次路径，还会损害真正低覆盖率推拉与贴边接触的检测能力。

## 3. 通用业务不变量与本轮落点

在一次有手操作中，若当前检测框已经被本帧的“静态旧 C 预约计划”唯一分配给
operation-start 旧 C，则：

```text
这个检测框不得作为当前 `HAND_VISIBLE_D` suspect D 的自身确认帧。
```

这是“单次不可靠候选不得升级为库存事件”的具体可执行形式：D 可以保留、等待、在
后续拿到独立证据后继续确认；本帧仅禁止它把该旧 C 框洗成自己的确认依据。本轮仅在
`update_existing_hand_tracks_()` 的既有 `HAND_VISIBLE_D` 分支执行这一约束。

这里的“唯一分配给静态旧 C”必须同时满足以下条件，缺一不可：

```text
1. C 是 operation-start 旧库存，仍在 working_inventory_ 中，状态可见，且不是 pending IN。

2. C 当前没有活动的 HAND_* / CONTACT_* / PLACED runtime；活动 C 必须继续由自己的
   动态路径、C_POSITION_REPLACEMENT_D 或 C-D alias 逻辑处理，不能被当作静态 C。

3. 当前手没有达到对 C 完整可靠参考框的 e2 覆盖，即：
       !hand_affects(hand_box, reference)
   “手离得近”不等于覆盖；本例 #6 虽然可以进入 CONTACT_CANDIDATE，但覆盖率为 0，
   仍可作为静态预约候选。

4. C 与当前 detection 使用现有 strict_match_cost() 计算严格候选关系。

5. C 在所有未认领严格候选中唯一最偏好该 detection；同时该 detection 在所有
   静态旧 C 中也唯一最偏好 C。必须是双方互相唯一的最低成本 pair。

6. 该 C 本帧没有已拥有另一 detection 的 known_item_owner。若它已经有自己的独立框，
   则当前未认领框不能仅因几何上也接近 C 就被强行让渡给 C。
```

只有这种“当前帧双向唯一、未被手覆盖的静态旧 C 所有权”才是细节14的阻断依据。
它不是“任意旧 C 能 strict match 这个框”的同义词。

具体而言，suspect D 不得使用被该计划分配给旧 C 的框去：

```text
1. 写入 claimed_detection_indices；
2. 增加 self_match_count；
3. 覆盖 last_seen_box / last_hand_block_box；
4. 进入 PLACED；
5. 触发 promote_suspect_()；
6. 在已提升后继续把自己的 placed_box 漂移到该旧 C 框。
```

## 4. 推荐实现：复用静态预约语义，为有手 D 加“互相唯一旧 C”让渡保护

### 4.1 修改位置与范围

文件：

```text
tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/src/session.cc
tools/luckfox_pico_rkmpi_example/example/luckfox_pico_rtsp_yolov5n/tests/session3_replay_test.cc
```

主要修改函数：

```cpp
SessionManager::reserve_visible_known_detections_()
SessionManager::update_existing_hand_tracks_()
```

实现应把 `reserve_visible_known_detections_()` 现有的“严格匹配 + 双方唯一最小成本 +
未被手覆盖”的选择规则抽取为一个**无副作用的预约计划 helper**。该 helper 可在不修改
`claimed_detection_indices` 与 `known_item_owner` 的前提下，回答：

```text
本帧的某个 detection，若等现有静态预约逻辑执行，它是否应当唯一归属某个普通静态库存 item？
```

建议 helper 名称可表达其语义，例如：

```cpp
build_mutually_unique_hand_static_owner_by_detection_()
```

名称不是硬要求；“纯计划、复用预约规则、返回 detection -> item_id 的映射”才是硬要求。
在 D 防护点再额外确认该 item 是 operation-start 旧 C，而不是本轮 pending D。

### 4.2 必须复用的预约计划语义

当前 `reserve_visible_known_detections_()` 已实现了正确的基本思想：

```text
对每个普通旧库存 C：找严格候选中的唯一最低成本 detection；
对每个 detection：找严格候选中的唯一最低成本 C；
只有双方相互选择时，才保留该 pair。
```

细节14不应写一套近似但不同的判断。推荐做法是将这一套迭代过程提取为纯 helper：

```cpp
// 输入是本帧的初始 claimed / known owner 副本；函数只在副本上运行。
// 返回新增的 detection_index -> 静态 working item_id 映射。
std::map<int, int> build_mutually_unique_hand_static_owner_by_detection_(
    const BBox& hand_box,
    const std::vector<Detection>& detections,
    const std::set<int>& claimed_seed,
    const std::map<int, int>& known_owner_seed);
```

其内部必须沿用 `reserve_visible_known_detections_()` 的全部关键筛选：

```text
1. 排除已 claimed detection；
2. 排除已有 known_item_owner 的 item；
3. 保持 reserve_visible_known_detections_() 对 working item 的现有筛选语义；
4. 排除有活动 runtime 的 item；
5. 排除 hand_affects(hand_box, reference) 的 item；
6. 用 strict_match_cost() 建候选；
7. 只保留双方唯一的最低成本 pair；
8. 反复在副本上推进，直到没有新的静态预约 pair。
```

然后使 `reserve_visible_known_detections_()` 也调用同一 helper 并实际写入这些预约，
或保证其后续实际写入与 helper 的计划完全一致。不能让“D 防护的预约规则”和“真正
静态预约的规则”以后逐渐分叉。D 防护仅消费其中 owner 位于
`operation_start_inventory_` 且不在 `pending_in_ids_` 的 pair。

### 4.3 推荐 D 防护伪代码

在 `update_existing_hand_tracks_()` 开头、遍历 `track_buffer_` 之前，基于已经由
`update_existing_contact_tracks_()` 写入的当前 `claimed_detection_indices` 与
`known_item_owner`，构造一次纯预约计划：

```cpp
const std::map<int, int> static_owner_by_detection =
    build_mutually_unique_hand_static_owner_by_detection_(
        hand_box, detections, *claimed_detection_indices, *known_item_owner);
```

然后在已计算出 `observed_index`、但即将进入 D 的 claimed / self-match / promote 分支
之前加入：

```cpp
// 只限制 D。旧 C 的 HAND_* 路径、CONTACT_* 路径保持原样。
if (track.is_suspect_new && observed_index >= 0) {
    const Detection& candidate = detections[observed_index];
    const std::map<int, int>::const_iterator static_owner =
        static_owner_by_detection.find(observed_index);

    const bool owner_is_operation_start_old_c =
        static_owner != static_owner_by_detection.end() &&
        operation_start_inventory_.count(static_owner->second) > 0 &&
        pending_in_ids_.count(static_owner->second) == 0;
    if (owner_is_operation_start_old_c) {
        trace_(
            "D-GUARD",
            "suspect=%d item=%d candidate=%d cls=%d phase=HAND "
            "action=yield-to-mutually-unique-static-old-c old-item=%d "
            "self-match=%d promote=0 claimed-write=0",
            track.suspect_id, track.item_id, observed_index, candidate.cls_id,
            static_owner->second, track.self_match_count);

        // 不认领、不加 self_match、不更新 D 的位置。保留当前检测框，
        // 后面的 reserve_visible_known_detections_() 会按同一计划把它交给旧 C。
        observed_index = -1;
    }
}

if (track.is_suspect_new) {
    if (observed_index >= 0) {
        // 保留现有 D 更新逻辑，不改阈值。
        ...
    }
    continue;
}
```

### 4.4 为什么不能只调用 `strict_owner_for_detection()`

`strict_owner_for_detection()` 的含义是“存在某个旧 C 可以 strict match 这个框”。
这对无手路径的保守排除有用，但**不足以**作为本次有手 D 的阻断条件。

例如现有回放 `test_adjacent_same_class_new_item_gets_its_own_d_chain()` 中：

```text
旧苹果： (800,100,1000,300)
新苹果： (740,100,940,300)
```

两框中心相距 60 像素，对 200x200 苹果框的归一化中心距离约为 `0.21`，确实可能
同时落入旧 C 的 strict 容差。但该帧旧苹果还有一个位于原位置、成本更低的独立框，
并且手本身也覆盖旧苹果。因此新苹果框不应被静态预约给旧苹果，必须继续走真实 D
链路。

若简单使用：

```cpp
strict_owner_for_detection(...).kind == StrictOwnerKind::START_OLD_C
```

就会错误阻止该相邻同类新苹果入库，违反当前已经通过的回归测试。

同理，也不能直接把 `detection_matches_old_working_inventory()` 复制到此处；它还包含
`partial_match`，范围更宽，会进一步误伤局部 D、相邻 D 和 C 位置替代 D。

细节14必须用“双方唯一静态预约计划”而不是“任意 strict owner”来限定本次补丁。

### 4.5 对真实 C 位置替代 D 与同类相邻 D 的正确影响

需要特别保证如下场景不被误伤：

```text
1. 旧 C 被手带离，而真实 D 被放在 C 的旧位置；
2. 旧 C 仍有自己的原位检测框，旁边贴手放入同类 D；
3. D 只露出局部框，随后无手才显示完整框；
4. 同类 C / D 在画面中相邻甚至部分重叠。
```

细节14的预约计划会正确区分：

```text
旧 C 被手覆盖或已有活动轨迹：
    不作为静态 C 预约；现有 HAND_*、C_POSITION_REPLACEMENT_D、C-D alias 接管。

旧 C 有自己的成本更低严格框：
    只预约自己的那个框，不预约附近真实 D 的框；D 链路不受阻。

多个旧 C 或多个框无法形成双方唯一 pair：
    不强行所有权让渡，保持原有同类歧义/候选逻辑。

本例 #6：
    未被手覆盖、没有活动 runtime、只有自己的唯一严格苹果框；
    因此 detection=3 应唯一预约给 #6，假 D 必须让渡。
```

这是库存场景中正确的保守取舍：单一检测框只有在“静态旧 C 的双方唯一证据”成立时，
才足以阻断 D 的确认；仅有几何接近不能作为阻断依据。

## 7. 明确禁止的错误修法

下列做法不应采用：

```text
1. 把所有 score < 某个更高值的检测框删除。
   本例误分类苹果为 0.565，同帧真实橙子也只有 0.542；调高阈值会伤害手遮挡
   下本应保留的真实业务证据。

2. 收紧 FLOW3_TRACK_CENTER_NORM 或其它全局轨迹阈值。
   这会影响真实手持、局部框、放下中途、重现路径等已经通过的业务能力。

3. 降低 FLOW3_HAND_ATTACH_DISTANCE。
   #6 的 CONTACT_CANDIDATE 只是保守接触状态，不是伪 IN 的根因。

4. 在看到旧 C 严格框后直接删除 suspect D。
   D 可能是真实物品的局部/过渡观测；正确做法仅是本帧不允许它使用该框确认自己。

5. 在最终结算阶段硬删 item#11，或针对 event=IN 事后打补丁。
   错误身份已经在有手阶段写入 working_inventory；必须在身份确认源头阻止。

6. 修改 C-D alias 的通用独立结算条件，或让 D 一缺失就删除。
   这些规则保护真实独立 D、共享框 D 和同类相邻场景，与本次 root cause 无关。

7. 重排整个 process_effective_hand_frame_ 的流程，以静态预约全面提前为代价解决问题。
   这会改变已有 HAND_* / CONTACT_* / C_POSITION_REPLACEMENT_D 的优先级。
   本次只需在 D 认领点加严格所有权让渡，风险更低。
```
