# 细节29：同类多实例遮挡时，归属歧义误杀因果遮挡证明导致永不提交

## 0. 文件性质与最高约束

本文是下一次修改 3.0 业务代码的实施指导说明。本次只修一个明确的死锁回归，不推翻
细节22~28 已经接入的任何方向，不新增业务概念，不放宽任何匹配/帧数/面积/距离阈值。

**当前已经有效的功能必须保持有效，绝对不能为了修这个问题而改坏：**

- 单手入库、出库、整理、静态回原位；
- 一只手连续操作多个物品；两只手分别操作不同物品，各自按 `hand_id` 用各自 `move_value`；
- 手框合并/漏检/拆分/顺序变化时暂停错误手位移，不借用另一只手 delta；
- 两只手共同接触同一物品时的歧义保护；
- 多物品入库、多物品出库、整理路径；
- CONTACT、严格遮挡、因果遮挡、遮挡解除、REVEALED、正常 D/IN、C-D alias、原子提交；
- 细节27 的类别无关 shadow、全局一对一归属；细节28 的统一实体图与启动保护。

**特别禁止（本次绝不允许发生）：**

- 放宽因果遮挡证明的几何条件（覆盖率 `ratio`、连续性、witness 必须是确认前景物）；
- 看到一个消失框就直接判 OUT，或看到一个移动框就直接判 MOVED；
- 按 detection 数组顺序、item_id、左右位置、"最近的手"来强行消除真实的身份歧义；
- 让某个物品先提交并清空同一 operation 中其他尚未结案的 runtime（破坏原子提交）；
- 因为要解开这一处死锁，就全局关闭 `no_hand_candidate_ambiguous` /
  `b_claim_ambiguous` / `contact_path_ambiguous` 的置位或它们在别处的作用。

若改动或复用任何超参数，必须同步更新 `超参数位置与调节说明.md`；本次预期**不新增、不修改
任何超参数**（见第 5 节），若最终引入了参数，必须在该文档记录原值/新值/用途/风险。

## 1. 复现场景与现象

初始库存 6 件：2 个橙子(cls=2)、3 个苹果(cls=0，item#3/#4/#5)、1 个洋葱(cls=15)。
操作：把一个橙子(item#2)移动过去，遮挡其中一个苹果(item#3)。
理想结算：`[橙子 MOVED]` + `[苹果 OCCLUDED]`，然后原子提交、operation 结束。
实际：**卡死，永不提交**，两个事件都发不出来，operation_active 一直为 1。

关键日志对比（见《测试后的结果与发现的问题.md》）：

```text
frame=166  target=3 ... observation-conflict=0 ... allow-occluded=1   ← 遮挡成立，正常
           OCCLUSION target=3 causal-proof-established witnesses=[2] ratio=0.926 required=0.300
frame=167+ target=3 ... observation-conflict=1 ... allow-occluded=0   ← 之后每帧都这样
           OCCLUSION target=3 causal-proof-invalidated reason=strong-observation-conflict
           NO-HAND   item=3 ... reason=hold-out-for-pending-disappearance-supported
           SETTLE    defer-commit inventory=6 ... pending-out=0        ← 永远停在这里
```

橙子(item#2)本身已 `MOVED_CONFIRMED / PLACED`，苹果(item#3)几何上已被 0.926 覆盖率的
确认前景物遮挡。但结算每帧把这份因果证明作废，于是 item#3 一直 HOLD，整笔事务无法收敛。

**与本次无关的澄清：** 这不是 reclassify（YOLO 输出后 egg/orange/apple/onion 手动纠正层）
引入的。日志里那些 `cls=18(egg)` 是移动橙子途中的误检幻影(suspect D)，框面积占比约
0.0149，未达 `RECLS_EGG_TO_ORANGE_AREA_RATIO=0.020`，纠正层全程未改任何类别。本问题是
双手能力接入后，在"单手 + 同类多实例 + 遮挡"组合下暴露的结算回归。

## 2. 根因：归属歧义与"消失原因"两件正交的事被混为一谈

代码位置 `src/session_settlement.cc`（refresh_confirmed_blockers_ 内 per-target 循环）：

```cpp
// 约 824~829 行：把"同类归属歧义"打包进 strong_proof_conflict
target_has_lifecycle_identity_conflict =
    target_runtime->no_hand_candidate_ambiguous ||
    old_track_has_unresolved_alias_(*target_runtime);
target_has_strong_proof_conflict =
    target_has_lifecycle_identity_conflict ||
    target_runtime->b_claim_ambiguous ||
    target_runtime->contact_path_ambiguous;

// 约 923~929 行：只要 strong_proof_conflict，就作废已成立的因果遮挡证明
} else if (target_observed) {
    invalid_reason = "target-direct-observed";
} else if (target_has_strong_proof_conflict) {
    invalid_reason = "strong-observation-conflict";   // ← 死锁的元凶
} else if (target_has_confirmed_exit_now) {
    invalid_reason = "target-confirmed-independent-exit";
}
```

事件链：

1. 橙子移动完、手离开，item#3 进入纯无手结算；
2. 场上还有另外两个苹果(item#4/#5)，同类仲裁无法唯一确定"消失的是不是 #3"，于是
   `session_settlement.cc:1418` 附近给 item#3 置 `no_hand_candidate_ambiguous=true`
   （全局 owner 计划把它列为 `ambiguous_item_ids`）；
3. 该"归属歧义"经由 `target_has_strong_proof_conflict` 每帧作废 item#3 那份几何上
   已充分成立的 `CAUSAL_FRONT_MISSING` 证明（witness=确认移动过的橙子，ratio=0.926）；
4. 证明失效 → `lifecycle_observation_conflict` 保持 true → `plan.observation_conflict=1`
   → `allow_occluded_transition=0`（见约 993~1000、1038、1042 行）；
5. item#3 落入 `OutDisposition::HOLD_FOR_PENDING_OCCLUSION` →
   `has_unresolved_state=true`（约 1650 行）→ `defer-commit`（约 1661 行）永远返回。

**核心矛盾**：因果证明回答的是"item#3 是否被前景物遮挡而消失"（存在性/消失原因），
而 `no_hand_candidate_ambiguous / b_claim_ambiguous / contact_path_ambiguous` 回答的是
"某个框归哪个 item"（归属）。这两件事正交。用归属歧义去一票否决一份**几何+连续性已经
充分**的因果遮挡结论，就误伤了"单手把一个同类物体移过去遮挡另一个同类物体"这个在旧版
单手逻辑里本来能收敛的场景。

**为什么"加了双手后单手变差"**：`strong-observation-conflict` 这类严格判据是为双手多同类
场景加的身份保护——双手同时操作多个同类时归属确实要严守。但它没区分上面两件正交的事，
于是连累了单手同类遮挡。

## 3. 解决方法（本次采用方案 B：让因果证明对"归属歧义"免疫，但保留真正矛盾的否决）

方向：把"归属歧义"从"作废因果遮挡证明"的判据里剥离，只保留真正与遮挡结论矛盾的两条否决
（目标又被直接观察到 / 目标有确认的独立离场证据）。归属歧义只应影响"这个可见框最终登记
给哪个 item"，不应影响"这个 item 是否被确认前景物遮挡而消失"。

### 3.1 精确改动点

**改动仅限 `src/session_settlement.cc` 的因果证明失效判定（约 923~929 行）。** 新增一个
"因果证明可免疫归属歧义"的守卫条件，只有在**几何证明足够强**时才免疫：

```text
causal_proof_immune_to_ownership_ambiguity =
    该 target 的 provisional 记录 proof.kind == CAUSAL_FRONT_MISSING
 && proof.witness_blocker_ids 全部满足：属于 confirmed_front_ids
      且 effective_block_ids 且 (confirmed_moved_ids_ 或 pending_in_ids_)
 && 本帧 witness 覆盖率 provisional_coverage.covered_ratio >= required_coverage_ratio
 && front_witness_boxes_are_continuous(...) 为真
```

这几个条件在现有代码 933~964 行本来就会逐一计算（用于其它 invalid_reason 判定）。实现时
应**先算这些几何/连续性条件，再决定是否因 strong-observation-conflict 作废**，即把
`strong-observation-conflict` 这条判定改成：

```cpp
// 伪代码，示意判定顺序，不是最终代码
} else if (target_observed) {
    invalid_reason = "target-direct-observed";              // 保留：真矛盾
} else if (target_has_confirmed_exit_now) {
    invalid_reason = "target-confirmed-independent-exit";   // 保留：真矛盾
} else if (target_has_strong_proof_conflict
           && !causal_proof_immune_to_ownership_ambiguity) {
    invalid_reason = "strong-observation-conflict";         // 仅在几何不够强时才作废
}
```

同时，在约 993~1000 行 `provisional_causal_proof_valid` 成立时清 `observation_conflict`
的逻辑保持不变——它本来就是把"更强邻居的弱保留"从冲突里排除的正确出口，方案 B 只是让
"归属歧义"也走到这个出口。

### 3.2 为什么这样安全（不会放行双手误判）

- 免疫的前提是 `CAUSAL_FRONT_MISSING` 证明**本身几何很强**：witness 必须是本 operation 内
  确认移动/确认入库的前景物、严格覆盖目标、且连续多帧成立。双手乱抓、拿走、换位不会轻易
  同时满足"确认前景物 + 严格覆盖 + 连续"，所以双手场景的身份保护不被削弱。
- `target-direct-observed`（目标又被直接看到）和 `target-confirmed-independent-exit`
  （目标有 MOVED/OUT 等独立离场证据）两条**真矛盾**否决**原样保留**。也就是说：如果
  item#3 其实是被拿走或自己移走了（有独立离场证据），证明照样会被正确作废，不会误判成遮挡。
- 免疫**只作用于因果证明是否失效**，不改 `no_hand_candidate_ambiguous` 等标志的置位，也不
  改它们在"可见框归属登记 / 全局一对一 / OUT 判定"里的其它作用。归属该歧义时依然歧义。

### 3.3 明确不做的事

- 不动 `session_settlement.cc:1418` 等处 `no_hand_candidate_ambiguous` 的**置位逻辑**；
- 不动 `session_ownership.cc` / `session_no_hand.cc` 里 `b_claim_ambiguous`、
  `contact_path_ambiguous`、`no_hand_candidate_reserved_by_stronger_owner` 的置位；
- 不降低 `FLOW3_CONFIRMED_OCCLUSION_DISAPPEARANCE_MIN_COVER_RATIO` 或因果证明的
  `required_coverage_ratio`、连续性要求；
- 不改原子提交边界（`replace_all()`），不让任何单个物品抢先提交。

## 4. 备选方案（未采用，仅记录，便于回溯）

- **方案 A：僵局打破器。** 检测到因果证明连续 N 帧在"成立↔strong-conflict"之间抖动、
  且几何始终满足时，以几何为准提交。改动小，但属打补丁，未解决正交性根因，且引入新阈值 N。
- **方案 C：缩小 `no_hand_candidate_ambiguous` 的触发面。** 在已有充分因果遮挡证明的
  target 上不置该标志。风险大：该标志被多处共用，容易牵连"可见框归属登记"等其它路径。

方案 B 精准解开死锁、保留真矛盾否决、不新增阈值、改动面最小，故采用。
