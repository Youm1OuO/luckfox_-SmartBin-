# 细节29：长条物品局部框、原位误判与 C-D alias 解环

## 0. 文件性质与最高约束

本文是下一轮 3.0 业务代码修改的实施指导说明。本文在细节27、细节28已经接入的统一实体图、启动保护、物品自身路径和原子提交方向上继续修正，不另起一套“长条物品算法”。

**当前已经可行、稳定或正在保护中的功能必须保持有效，绝对不能为了修复本次问题而改坏：**

- 单手入库、出库、整理和静态回原位；
- 一只手连续操作多个物品；
- 两只手分别操作不同物品，并通过各自 `hand_id` 使用各自的 `move_value`；
- 两只手共同接触同一物品时的歧义保护；
- 手框合并、漏检、拆分、重新绑定、检测输出顺序变化时暂停不可靠手 delta，不能借用另一只手的位移；
- 当前已经较稳定的多物品入库、出库、整理和最后的原子提交；
- CONTACT、HAND、严格遮挡、因果遮挡、遮挡解除、REVEALED、正常 D/IN、C-D alias、shadow 和全局一对一归属；
- 细节28已经接入的捕获启动保护、`object-path-move-ready`、`object-path-exit-ready` 和联合结算边界。

特别禁止以下做法：

- 按“长条/圆球”、类别、物品 ID、左右位置或检测数组顺序复制两套算法；
- 按当前识别到的手数量决定物品数量、是否开始操作或是否出库；
- 用一只手的 `move_value` 推断另一件物品的移动；
- 把任意一个局部检测框直接当成 MOVED 或 OUT；
- 把“检测框与原框部分重叠”直接当成“物品仍在原位”；
- 因为本次测试卡住就降低 OUT/MOVED 帧数、放宽 hand 匹配、降低歧义门槛或扩大静态判定范围；
- 看到 pending D 就无条件清除 C 的所有路径，或看到 C 有一张路径框就无条件删除 D；
- 让同一 operation 中某一件物品先提交并清空其他尚未结案的 runtime。

代码可以按职责拆分到不同文件中，不必把所有逻辑挤在一个文件里。若实际修改或新增任何超参数、帧数、面积比例、距离、IoM、尺寸比例或上限，必须同步更新 `超参数位置与调节说明.md`，记录原值、新值、用途、适用范围和风险；如果完全复用已有参数，也要在修改说明和诊断中明确写出“本次未改超参数”。

## 1. 本次测试的正确理解

最新测试是：初始库存有橙子、节瓜和苦瓜，两只手同时分别拿走节瓜和苦瓜。圆球类或较短物品之前经常可以正常操作，但长条形物品容易卡住。

这不是因为“长条形类别需要另一套识别算法”，而是长条形物品在被手抓住时更容易产生以下视觉情况：

```text
原始完整物品框 C
        |
        | 手遮住中间或大部分区域，仍露出一端/一块局部
        v
移动后的局部检测框 B
```

移动后的局部框 B 仍可能与原始完整框 C 有很大的交集，甚至满足 `partial_match_box()` 和旧位置重叠条件。但 B 只代表物品的可见部分，不代表物品整体的中心、边界和原位置没有改变。

因此本次问题的第一层根因是：当前逻辑把“局部可见”与“原位静态”混用了。具体表现是，节瓜在有手阶段被一个部分检测框触发 `ORIGINAL_DETECTION`，从 `HAND_PARTIAL_BLOCKED` 转成了 `NORMAL + STATIC_CONFIRMED + needs_settle=1`。手离开后它已经没有活动 HAND 轨迹可以继续积累出库证据，于是被结算保护门阻塞。

本次问题的第二层根因是：苦瓜的局部框进入 C-D alias 后，后续全局 owner 已经有“该框属于旧 C”的迹象，但代码遇到 unresolved alias 就清空旧 C 的 object-path；pending D 又被要求等待旧 C 先结案，最终形成：

```text
C 要先解决 alias 才能结案
        ^
        |
pending D 要等 C 先结案才允许回收
```

这两个问题是连锁关系。长条物品的局部原位误判会丢掉一条 C 的证据，另一条 C 的 alias 歧义又会阻塞它自己的物品路径，最后原子提交正确地拒绝提交整轮 operation。

## 2. 统一实体和证据模型

本轮继续使用细节28的统一 operation candidate graph，不能新建“长条物品分支”。每个 operation 中维护：

```text
E = 旧库存 C、已有但未正式 IN 的 D、已经确认仍参与本 operation 的实体
B = 当前食品 detection
H = 当前 hand_id / hand group
S = 重复观测 shadow，不是库存实体，不产生 IN
```

每条 `E -> B` 关系至少区分以下事实：

```text
coverage      full / partial / unknown
geometry      original / last-object / hand-estimate / track-path
continuity    first / current / consecutive
ownership     forced / ambiguous / blocked / none
class         compatible / unstable-class / incompatible
source        strict / partial / object-path / hand-context / shadow / alias
```

必须把“看到了一部分物品”与“证明物品仍在原位”分开：

```text
partial-visible       只证明物品仍有一部分可见或路径可能连续
original-static-ready  只在独立、稳定的原位证据成立后导出
object-path-ready      只在连续物品路径和唯一 owner 成立后导出
exit-ready             只作为现有缺失 OUT 链的入口
```

这些资格都必须可撤销。检测恢复到严格原位、owner 变 ambiguous、路径成为 shadow、出现更强独立 owner、遮挡关系改变、operation 回滚或结案时，必须撤销相应的临时资格。

## 3. 局部检测不能直接触发静态原位

### 3.1 原始框、路径框和可见局部框必须分开

每个旧 C 至少保留以下参考，不得互相覆盖：

```text
original_box          operation-start 的不可变完整框
hand_estimate_anchor  手级路径开始时的锚点；不能用它改写 original_box
last_object_box       最近一次可信食品检测框
last_hand_block_box   最近一次与手覆盖相关的食品框
object_path_history   连续食品框及其 owner/来源
```

初次建立 HAND 旧 C 时，即使当前只看到完整框或局部框，也要建立等价的路径锚点。不能只在 CONTACT 转 HAND 时设置 `hand_estimate_anchor_box`，而让初次 HAND 轨迹在后续移动时没有路径锚点。

如果当前 hand delta 可靠，可以追加该物品自己的手级路径；如果 hand delta 不可靠、hand_id 合并或重新绑定，则冻结手级 delta，不能写入伪造位移。但此前已经确认的 object-path、last object box 和 capture context 不能因此被清空。

### 3.2 “原位证据”必须有反证检查

有手阶段或无手阶段找到一个与原框有交集的检测框时，不能只调用宽松的旧位置匹配就执行 `release_not_held_()`。必须先建立以下事实：

1. 该框是否是完整、严格且唯一的原位检测；
2. 该框是否只是被手遮挡后露出的局部；
3. 该框是否同时与 `last_object_box`、`last_hand_block_box` 或移动后的 estimated/object path 连续；
4. 当前是否有可靠手移动、CONTACT 路径、capture context 或 object-path 证据；
5. 该框是否被其他 C/D 共享，或只是 pending D/shadow 的重复观察。

如果框同时满足“原框部分重叠”和“移动路径连续”，结论必须是 `ambiguous / path-observation`，不能是静态原位。不能用 item_id、检测顺序或最近手解决这个冲突。

### 3.3 静态回原位仍然必须可用

本轮不是要取消静态回原位，而是收紧错误的静态入口：

- 完整、严格、唯一的原位检测，且没有矛盾移动路径时，继续沿原有静态释放流程；
- 手离开后，已有稳定近原位灰区仍可使用现有连续无手确认窗口；
- 手仍接触物品时的局部框，不能单独触发最终静态释放；
- 有手 delta 或 object-path 显示物品可能已移动时，即使检测框和原框部分重叠，也必须等待路径或无手稳定证据；
- 真正回到原位的物品仍应能通过现有 `STATIC_CONFIRMED` 及原子结算，不得因为本轮保护而永久冻结。

静态判断最好采用“连续且独立的原位事实”，而不是调大或调小某个全局 IoM/面积阈值。对于仅一张局部框、同时存在原位和移动两种解释的情况，保持未决是正确结果。

## 4. 物品自身路径必须独立于手路径

### 4.1 物品路径的建立

当食品 detection 连续出现，并满足以下条件时，可建立 object-path：

- 类别关系兼容，或通过连续几何和已有 hand/contact 上下文被判定为 `unstable-class`；
- 检测框与该实体上一张真实物品框或可验证路径连续；
- 全局一对一 owner 唯一、稳定，不是 shadow；
- 该实体确实有本 operation 的 capture/contact/hand context；
- 不是与其他 C/D 完全对称的共享候选。

物品检测可以是完整框，也可以是手遮挡下的局部框；但局部框只能作为连续路径的一部分，不能单帧产生 MOVED 或 OUT。

### 4.2 手 delta 中断时的处理

以下行为必须保留：

- hand_id 合并、丢失、拆分、重新绑定时，暂停当前不可靠的 `move_value`；
- 不把另一只手的 delta 借给当前物品；
- 不因为两只手数量变成一只或新建了 hand_id 就强行重置物品身份。

同时必须新增或修正以下行为：

- hand delta 中断只冻结手级证据，不清空已经成立的物品级连续路径；
- 只要 object-path 仍有连续、唯一 owner，继续累积 `move-ready` 或 `exit-ready`；
- 物品完全消失后，只有此前的 object-path/hand/contact 证据才能进入现有缺失 OUT 链；没有证据则继续未决。

### 4.3 MOVED 与 OUT 入口不能混淆

```text
object-path-move-ready  -> 现有 MOVED/整理确认入口
object-path-exit-ready  -> 现有无手缺失 OUT 入口
```

这两种资格都必须满足已有连续帧和全局 owner 条件，不能看到一张移动框就立即产生事件。不能因为长条物品检测框变小、类别分数变低或暂时只剩局部，就直接把物品判为 MOVED/OUT。

## 5. C-D alias 的统一解环规则

### 5.1 pending D 的定位

当一个局部框既可能属于旧 C，也可能是新 D 时，继续建立 pending D 是必要的保护；但 pending D 不能永久冻结旧 C。

每个 alias 候选必须保存：

```text
conflicting_old_c_ids
alias_detection_history
old_c_path_history
owner_plan_history
d_independent_path_history
shadow/duplicate reason
```

### 5.2 允许 C 继续路径的窄条件

只有以下事实同时成立时，才允许旧 C 在存在 pending D 的情况下继续累计自己的 object-path：

1. 全局候选图连续给出唯一的 `C -> B` forced owner；
2. 该 B 与 C 的上一张真实框或 object-path 连续；
3. C 有明确 capture/contact/hand context；
4. B 不是 shadow，也没有被其他 C/D 独立占用；
5. pending D 没有自己的独立、连续、非共享路径；
6. 当前不是对称匹配或 owner 在帧间反复变化。

这不是“忽略 alias”，而是把 alias 明确标记为“等待 C 的连续路径确认的重复解释”。C 的路径未达到现有确认窗口时，仍不能提交；一旦达到窗口，pending D 才能按 duplicate/shadow 回收。

### 5.3 alias 回收和恢复

- C 的 object-path 连续确认达到现有 `FLOW3_NO_HAND_D_CONFIRM_FRAMES` 后，且 D 没有独立路径：回收 pending D，不产生 IN；
- C 的路径中断、owner 变 ambiguous、D 建立了独立路径或出现更强 owner：撤销本次 alias 回收资格，恢复未决；
- 不能按 `all_conflicting_old_c_settled` 单一条件无限等待，因为 C 可能正需要 alias 解析后才能结案；
- 也不能只凭一张全局 owner 框就删除 D，必须使用现有连续确认窗口；
- 同类 C-D 和不同类/类别抖动的 C-D 必须走同一套 alias/shadow 生命周期，类别只影响候选边强度。

### 5.4 当前测试场景的预期状态

对苦瓜这条链，正确的状态转移应类似：

```text
HAND_PARTIAL_BLOCKED
    -> partial object-path + pending alias
    -> forced C owner 连续确认
    -> pending D 识别为 duplicate/shadow
    -> object-path-exit-ready 或 object-path-move-ready
    -> 进入现有 OUT/MOVED 结算
```

对节瓜这条链，正确的状态转移应类似：

```text
HAND_PARTIAL_BLOCKED
    -> 局部框只更新路径，不触发 ORIGINAL_DETECTION
    -> 保留有效手/物品路径
    -> 手离开后按 object-path 或 hand-path 进入缺失链
    -> OUT/MOVED 在现有原子提交中确认
```

如果实际帧仍不能区分“旧 C 移动”和“真实 D”，则两条链都应保持未决，不能为了让本次测试通过而强行选边。

## 6. 全局候选图与局部流程的顺序

本轮实现不能让局部 map 遍历顺序先决定身份，再让全局计划事后补救。建议逻辑顺序为：

```text
1. 收集 C、D、B、H、shadow 的候选边
2. 先计算全局一对一 owner 及 forced/ambiguous/no-plan
3. 根据 owner 计划标记 full/partial/path/shadow/alias 关系
4. 更新每个实体自己的 object-path 和 hand-path 账本
5. 由局部 CONTACT/HAND/静态规则补充细节
6. 仅把 move-ready/exit-ready 送入已有 MOVED/OUT 入口
7. 最后统一检查 operation 中所有实体并原子提交
```

如果当前代码结构不适合一次性移动所有调用，可以先建立一个只读的本帧 owner/path 计划，再让现有局部函数消费它；不能让不同类别、不同手数或不同文件各自重新猜一遍 owner。

## 7. 结算边界和不可绕过的安全条件

### 7.1 可以提交的情况

- 旧 C 有连续、唯一、非-shadow 的移动路径，满足现有 MOVED 确认；
- 旧 C 已有有效手/CONTACT/object-path exit 证据，并完成现有无手缺失窗口；
- pending D 已通过独立连续路径确认 IN，且与所有冲突旧 C 的身份关系已经解除；
- 正式遮挡 proof、遮挡解除和 REVEALED 仍满足原有因果条件；
- 同一 operation 中所有旧 C、D、遮挡关系和临时事件都能形成一致的最终计划。

### 7.2 必须继续未决的情况

- 只有一张局部框，没有连续 object-path 或 hand/contact 证据；
- 框同时等强地匹配两个实体；
- alias C/D 没有唯一 owner；
- hand_id 中断后也没有物品级连续路径或严格 hand-group witness；
- 仅有可见数量减少，没有对象级来源；
- 某一物品已经有结论，但同 operation 其他 runtime 仍有未解决 alias、owner、遮挡或 D/IN 关系。

### 7.3 原子提交不得削弱

修复不能通过提前把 `needs_no_hand_settlement` 置为 false、直接清空 `track_buffer_`、提前删除 pending D 或提前写入 `pending_out_ids_` 来绕过结算门。任何临时结论都必须可撤销，正式事件仍只能由现有统一原子提交产生。

## 8. 推荐代码职责

可以按以下职责拆分修改，避免把所有判断写在一个函数中：

- `session_hand.cc`：初始化和维护 HAND 轨迹的原始/路径锚点；区分局部观察和静态原位；手 delta 不可靠时冻结手证据但保留物品路径；
- `session_ownership.cc` / `session_internal.h`：构建 full/partial/path/shadow/alias 候选关系和全局 forced/ambiguous/no-plan 结果；不按类别复制算法；
- `session_no_hand.cc`：消费 object-path/exit-ready 和 alias 解环结果，继续复用现有无手缺失、静态灰区、D/IN 和遮挡生命周期；
- `session_settlement.cc`：把 object-path move-ready 纳入已有 MOVED 确认门，只放行满足唯一 owner、连续路径、capture context 和无冲突条件的实体；维持最终联合结算；
- `session.cc`：只负责本帧流程顺序和 operation 边界，不根据手数量直接下业务结论；
- `session.h`：若需要新增字段，增加可撤销的 coverage/path/owner/alias 事实，并在 reset、rollback、reopen、operation 结案时清理。

本轮优先复用现有 `partial_match_box()`、`track_match_box()`、`strict_match_box()`、`boxes_differ_as_move()`、现有连续确认窗口和全局 assignment。除非测试证明已有参数无法表达必要事实，不要新增或修改超参数。

## 9. 诊断日志要求

下一轮必须能够从日志区分以下情况：

```text
OBJECT-COVERAGE item=... detection=... coverage=full/partial/unknown
OBJECT-RELATION item=... detection=... original=0/1 path=0/1
STATIC-GATE item=... decision=release/defer reason=partial-path-conflict/
            strict-original/no-independent-owner/hand-contact
OBJECT-PATH item=... detection=... streak=... owner=forced/ambiguous/none
            move-ready=0/1 exit-ready=0/1
C-D-ALIAS old-item=... suspect=... relation=shared/duplicate/shadow
            owner=forced/ambiguous action=keep/reconcile/discard reason=...
SETTLE unresolved-items=[...] unresolved-alias=[...] barrier=pass/defer reason=...
```

至少要能回答：

- 当前框是完整框还是手遮挡后的局部框；
- 它更接近原位、上一张真实物品框还是移动路径；
- 为什么没有静态释放；
- 为什么 object-path 被保留、撤销或进入 move/exit-ready；
- pending D 是真实独立物品，还是已经被旧 C 连续路径解释的重复框；
- 最终 defer 是哪一条实体证据未闭合，而不是只打印“卡住”。

## 10. 验证顺序和完成标准

实现后按以下顺序验证，避免一次改动同时掩盖多个问题：

1. 先回放本次节瓜+苦瓜日志，确认节瓜的局部框不再触发错误 `ORIGINAL_DETECTION`，苦瓜的 pending D 能在唯一连续 owner 下解除 alias；
2. 验证长条物品静止不动但被手短暂接触时，仍然能够静态回原位，不会被误判为 MOVED/OUT；
3. 验证长条物品从中部、末端、不同方向抓取，部分框持续露出时，能够保留自己的 object-path；
4. 验证圆球/小物品原有单手、双手独立、多物品入库、出库、整理和静态回原位回放全部不退化；
5. 验证同类 C-C、异类 C-C、C-D alias、跨类别重复 shadow 和真正对称匹配；
6. 验证 hand_id 合并、漏检、重新绑定时仍暂停错误 delta，不借用另一只手；
7. 验证完全没有足够唯一证据的场景继续保持未决，而不是用更宽松的规则强行产生事件；
