# 细节24：事务内因果遮挡证明，避免已正确判断的遮挡在延期帧中被推翻

## 0. 本文的性质和修改边界

本文是下一次修改代码时的指导说明，不代表本次已经修改或验证过代码。

本次要解决的是一个很具体的问题：前景物体已经确认移动到目标物体的旧位置，并且已经正确得出 `OCCLUDED` 后，事务因为其他轨迹尚未结案而多经历了几张无手帧；在这些后续帧中，原本正确的遮挡结论又被弱的候选框预约信息推翻，最终持续 `defer-commit`、卡住不提交。

**首先必须保护当前已经有效的功能。** 当前已有的直接检测、正常移动、正常出库、入库、揭示、严格遮挡、同类物品的身份处理、手部短暂接触后的恢复等行为中，已经能正确工作的部分是很重要的。修改只能针对下面说明的矛盾链路收口，不能为了让这一个场景提交，而把原来能正确识别的功能改差、放宽或绕过。

尤其不要借本问题去修改或整体放宽以下基础规则：

- 不修改 YOLO/NMS 的基础策略。
- 不全局修改匹配阈值、普通 `OUT` 阈值、手边缘接触范围或遮挡覆盖率。
- 不因为目标已经出现过 `OCCLUDED` 就无条件提交整个事务。
- 不把所有身份冲突都当成可忽略的噪声。
- 不跳过已遮挡目标后续帧的检测和验证；目标重新出现、遮挡物移走、真实身份歧义等反证仍然必须被发现。

代码不必强行全部挤在一个文件中。应按职责把数据、记录、验证和决策分别放到合适的文件；具体建议见第 6 节。

如果本次修改到任何超参数、阈值、帧数、比例、计数上限或其他可调参数，**必须同步更新** `另另一种业务流程(3.0var)/超参数位置与调节说明.md`：写明参数位置、原值/新值、作用、适用场景和调整风险。若没有改超参数，也应在实现和提交说明中明确“本次未改超参数”。

## 1. 需要复现的真实场景和正确结果

场景中有苹果 `#2/#3/#4` 与橙子 `#1/#5`：

- 苹果 `#2` 是被遮挡的目标 A。
- 橙子 `#5` 从原位置移动到苹果 `#2` 的旧位置，最终对其旧 `base_box` 的覆盖约为 `0.939`。
- 苹果 `#3/#4` 仍各自保有合法、较强的原位直接检测框。
- 橙子 `#1` 曾由于手框边缘接触短暂进入 `CONTACT_CANDIDATE`，但后来已经恢复正常；它不是持续卡住的根因。

该场景应得到的事务结果是：

```text
MOVED(#5) -> OCCLUDED(#2) -> 其他轨迹结案 -> 提交
```

其中必须满足：

- 不应产生 `OUT(#2)`。
- `#2` 应保留原来的 `item_id`，不是被取出后再新增的物品。
- `#2` 的遮挡关系应指向已确认移动的 `#5`。
- `#1` 不应因为一次已恢复的短暂手部边缘接触而误判为 `MOVED` 或 `OUT`。
- 经过既定的无手确认窗口后，事务必须收敛并提交，不能无限重复 `defer-commit`。

## 2. 已从日志确认的事实

这不是“第一张无手帧完全识别不出遮挡”的问题。第一张无手帧已经做对了因果遮挡判断。

在 `frame=579`：

```text
#5: MOVED_CONFIRMED
#2: observed=0
    observation-conflict=0
    effective=[5]
    ratio=0.939
    allow-occluded=1
    reason=confirmed-front-missing-target
```

此时 `#2` 已正确进入 `OCCLUDED_CONFIRMED`。也就是说，“已确认移动的 #5 覆盖未被直接看到的 #2”这一条因果判断本身是成立的。

真正出错发生在事务尚未提交、继续处理后续无手帧时（例如 `frame=581/582/585`）：

```text
#2: state=HAND_PARTIAL_BLOCKED
    resolution=OCCLUDED_CONFIRMED
    needs_settle=0
    reason=no-hand-path-reserved-by-stronger-old-c
```

随后同一目标又被新的生命周期结算计划写成：

```text
observation-conflict=1
visibility=4
out=1
allow-occluded=0
reason=coverage-direction-not-satisfied
```

最终反复出现：

```text
hold-out-for-pending-disappearance-supported
defer-commit
```

因此，这是真实的持续不收敛，不是简单多等一帧无手图像即可解决的问题。

## 3. 根因：正确的遮挡结论没有跨延期帧保存为可验证的事务证明

第一次无手帧把 `#2` 判为 `CAUSAL_FRONT_MISSING` / `OCCLUDED_CONFIRMED` 后，这个结论只停留在当帧运行时 `resolution` 或 `final_items` 层。

事务尚未提交时，`#2` 的活动轨迹仍带着 `HAND_PARTIAL_BLOCKED` 等历史状态。因此每个后续无手帧仍会重新进入路径匹配。由于苹果 `#3/#4` 有更强的原位直接证据，某个较宽松候选框会被它们保留；`#2` 不能抢走该候选框，于是得到：

```text
no_hand_candidate_reserved_by_stronger_owner
```

这个标记的含义只是“`#2` 不能把邻居已经更强地占有的宽松候选框当作自己的直接观察”。它不是 `#2` 的合法直接检测，也不是 `#2` 本身确认移动，更不等于真正的同等强度身份歧义。

但目前后续生命周期结算把这个弱预约也计入了 `target_observation_conflict`。与此同时，已确认 `OCCLUDED_CONFIRMED` 的 `#2` 会被可见数量结算排除，第一帧中暂时压住冲突的依据消失。结果是：

```text
运行时结论：#2 已确认 OCCLUDED
后续结算计划：#2 因弱 observation-conflict 不能保持 OCCLUDED
提交门：仍有未决/等待消失的轨迹
最终结果：持续 defer-commit
```

根本缺少的是：在一个尚未提交的事务中，把已经成立的因果遮挡结论保存为“可持续验证、也可被反证推翻”的临时 proof，而不是每帧完全从头把它降回普通缺失或 `OUT` 链。

## 4. 修改目标

新增“事务内临时因果遮挡证明”（下文称 provisional causal-occlusion proof）。它只服务于一个已经通过严格因果条件建立的遮挡结论，独立于：

- 正式库存状态；
- 普通运行时 `resolution`；
- 一般的 missing/disappearance 计数；
- 仅用于匹配分配的弱候选框预约标记。

它不是永久缓存，也不是忽略检测结果的开关。它的用途是在当前事务延期的连续无手帧中，维持已证实的 `KEEP_OCCLUDED`，直到事务提交或出现真实反证。

## 5. proof 的建立、内容、续验和失效

### 5.1 建立条件

只有在现有严格因果遮挡判定已经成功时才建立 proof，例如本场景满足：

- 目标没有合法唯一直接观察；
- 前景 witness（例如 `#5`）已经可靠地确认 `MOVED` 或 `IN`；
- witness 的可靠 placed/base box 对目标操作开始时的 `base_box` 有足够方向正确、比例足够的覆盖；
- 当前结论是 `CAUSAL_FRONT_MISSING`，而不是普通“检测不到”。

不要把普通 missing、手遮挡期间的猜测、单纯候选框分配失败或宽松 IoU 重叠直接写成 proof。

### 5.2 proof 至少应保存的数据

建议在事务/会话内部保存以下内容：

```text
target_id
proof_kind = CAUSAL_FRONT_MISSING
witness_blocker_ids
target_operation_start_base_box
witness_confirmed_event_frame
witness_reliable_placed_or_base_box
建立 proof 时的覆盖率、方向关系和必要连续性信息
建立/最后验证的帧号（用于诊断，不应替代实际验证）
```

多遮挡物场景可保存多个 witness，但必须仍满足既有的遮挡方向和组合覆盖规则；不能因为多个弱重叠就放宽为“任何一个都算遮挡”。

### 5.3 每张后续无手帧的续验

在事务未提交期间，每个后续无手帧都必须继续验证 proof，而不是盲目信任它。至少检查：

1. witness 仍是已确认的 `MOVED/IN` 前景物体，没有被撤销或确认移走；
2. witness 的框仍连续可信，并继续以合理比例、正确方向覆盖目标原 `base_box`；
3. 目标没有取得合法、唯一、足够强的直接观察；
4. 目标没有自己的确认 `MOVED/OUT`、唯一终点或其他独立状态证据；
5. 没有真实的同类 alias/同等强度身份冲突。

验证通过时：

- 保持 provisional proof；
- 在生命周期结算中保持目标的 `KEEP_OCCLUDED`；
- 不重复给目标增加 missing/disappearance 计数；
- 允许其他尚未结案轨迹按原有规则继续结案，全部满足后正常提交。

本场景中特别需要精确区分冲突强度：

- 可以不让 `no_hand_candidate_reserved_by_stronger_owner` 这种“邻居凭更强直接证据占用了宽松候选框”的**弱预约**推翻一个仍然验证通过的 proof。
- 不能因此忽略 `no_hand_candidate_ambiguous`、真实 C-D alias、同等强度身份竞争、目标自身直接出现、目标独立移动等**强冲突**。

换言之，proof 只能屏蔽与“目标不可抢邻居宽松候选框”有关的假冲突，不能普遍屏蔽身份冲突。

### 5.4 必须清除 proof 的情况

出现下列任一反证时，立即清除 provisional proof，并回到现有正常的检测、缺失、`OUT` 或 `REVEALED` 链路：

- witness 已移走、失去连续性，或不再覆盖目标旧 `base_box`；
- 目标重新得到合法唯一的直接观察；
- 目标被独立可靠地确认 `MOVED` 或 `OUT`；
- 出现真实的身份歧义、同等强度 owner 竞争或 alias；
- 证明所依赖的方向、覆盖或可靠性条件不再成立。

清除 proof 后不要残留已遮挡状态，也不要人为压住之后应有的 `OUT`。例如 blocker 后来移走、目标仍不出现时，系统必须能够重新走正常的缺失/出库判断。

## 6. 建议的代码职责划分

不要求把所有逻辑硬塞进一个源文件。为避免把状态结构、匹配、结算和遮挡判断混在一起，可以按现有工程结构分开实现，例如：

- `include/session_internal.h` 或 `include/session.h`：事务内 provisional proof 的数据结构、生命周期字段和只读访问接口；
- `session_settlement.cc`：首次记录 proof、后续验证、生命周期结算时的 `KEEP_OCCLUDED` 决策；
- `session_no_hand.cc`：无手帧继续观察时，对“弱 reservation”与“真实冲突”的区分；proof 失效后恢复现有普通流程；
- 如有必要，`session_occlusion.cc`：集中实现纯粹的 proof 建立条件和验证函数，避免在多个位置复制覆盖率/方向判定。

实际文件名要服从现有代码边界。重点是：数据的归属明确、建立和清除位置成对、每帧验证只有一个权威入口，避免同一帧被不同模块相互覆盖状态。

实现时优先复用已有的可靠 box、匹配结果和遮挡判断函数；不要另造一套与现有规则不一致的 IoU/覆盖率计算。

## 7. 修改时要重点检查的状态一致性

同一帧、同一目标不能同时出现下列互相矛盾的有效决策：

```text
resolution = OCCLUDED_CONFIRMED
但 lifecycle plan = OUT / 不允许 OCCLUDED
```

如 proof 仍有效，结算计划必须能明确表达“保留遮挡”；如 proof 已失效，运行时遮挡状态也必须被一致地撤销或重新计算。不能只更新日志字段或 `final_items`，却让提交门仍按另一套未决状态工作。

建议为 proof 的建立、每帧验证、忽略弱预约、强冲突失效、提交前清理分别增加可读诊断日志。例如：

```text
causal-proof-established
causal-proof-validated
causal-proof-weak-reservation-ignored
causal-proof-invalidated=<reason>
```

日志应包含 `target_id`、witness id、帧号和关键判断原因，便于确认不是“强行提交”。不要因增加日志而改变业务状态。

## 8. 必做回归测试

### 8.1 本次实机拓扑

复现：苹果 `#2/#3/#4`、橙子 `#1/#5`；`#5` 移动并约 `0.93` 覆盖 `#2`；`#3/#4` 继续保有原位直接框；`#1` 有短暂边缘接触后恢复。连续多张无手帧后，系统不能无限 `defer-commit`。

至少断言：

- 事件顺序为 `MOVED(#5)` 在 `OCCLUDED(#2)` 前；
- 没有 `OUT(#2)`；
- `#2` 保持原 `item_id`，并带有正确的 `block_ids`；
- `#2` 的 proof kind 是 `CAUSAL_FRONT_MISSING`；
- `#1` 没有错误的 `MOVED/OUT`；
- 在既定无手确认窗口结束后事务能够提交；
- 日志中若遇到 `no_hand_candidate_reserved_by_stronger_owner`，只能在 proof 其他条件仍成立时将其记录为弱预约，而不能将其升级成通用冲突。

### 8.2 必须保留的旧能力

以下场景都需要回归，避免为本问题牺牲原有正确能力：

- 严格全遮挡和边缘遮挡；
- 前景只部分重叠，但目标仍有合法直接检测框时，目标必须保持 `VISIBLE`；
- 目标自身真正移动或出库时，该独立结论必须优先，不能被旧 proof 压住；
- 真正同类 owner/alias 歧义必须继续保持未决，不能被 proof 绕过；
- blocker 移走后，provisional proof 必须撤销，并允许目标回到正常 `OUT` 链；
- `REVEALED`、多 blocker、D/IN、普通 `OUT`、同类邻居竞争、手短暂擦过等已有场景。

5. 若改动超参数，`超参数位置与调节说明.md` 已同步更新；
6. 修改前后均保存关键日志或测试证据，能说明这是“保留并验证正确遮挡”，而不是简单跳过检查或强行提交。
