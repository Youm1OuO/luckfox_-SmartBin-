# 细节 13：无手静态灰区使旧 C 无法独立结算，进而阻塞 r15 的 C-D alias 收尾（计划 3.0-r16）

## 0. 本文件的用途与首要约束

本文件是下一次修改代码时的指导说明。它记录了本次实机压力测试所暴露的完整根因，
以及下一次实现必须遵守的边界。

本次问题**不是**“r15 应该更快删除 D”，也不是“低分检测框都应当拒绝”。r15 对 D 的
保守保护是正确的：只有关联的旧 C 已经真正独立结算，才可把连续消失的隔离 D 当作过期
runtime identity 回收。这样才能保护真实的独立 D、共享框 D 和相邻同类物品。

本次真正缺失的是另一条能力：一个旧 C 在有手阶段被建立为轨迹后，手离开时已经有自己的
稳定无手检测框，但其框中心相对原框落入“接触原位门槛”和“正式 MOVED 门槛”之间的灰区。
现有代码既不把它安全收尾为静态，也不把它判成移动，于是 C 无法独立结算；r15 因此正确地
继续保留 D，整轮操作却再也无法提交。

**最重要的原则：当前版本在正常入库、出库、整理、遮挡、接触、同类相邻物品等方面已经
表现很好。r16 必须是一个极窄的“无手静态灰区收尾”补丁。不得为了通过本例而放宽、重写
或削弱已经成熟的主流程。**

### 0.1 当前已经有效的能力，必须完整保留

以下功能已经有良好表现，下一次修改后必须保持原有语义和测试结果：

```text
1. 正常 IN：真实新物品 D 仍须沿既有 staged IN / 连续直接无手证据链确认。

2. 正常 OUT：旧 C 的缺失、数量不足、遮挡、连续无手确认、回归撤销逻辑不变。

3. 正常 MOVED / 整理：旧 C 仍由 original / reappear / observed path / CONTACT_*
   的既有证据链确认；本补丁不能改变 item_id、匹配范围或确认帧数。

4. 遮挡与恢复：OCCLUDED / REVEALED 仍由既有遮挡逻辑决定，不能被本补丁改成
   OUT、IN 或静态。

5. 同类相邻物品：细节9、10、11、12中的一框一物品、静态邻居排除、claim grace、
   共享框与独立框仲裁必须原样保留。

6. CONTACT_CANDIDATE / HAND_CONTACT / HAND_PARTIAL_BLOCKED / HAND_FULL_BLOCKED：
   有手阶段仍只积累证据；本补丁不可提前给出整理、入库或出库结论。

7. r15 stale alias cleanup：仍要求旧 C 真正独立结算后，D 才可连续缺失两帧并删除。
   不得放宽 all_conflicting_old_c_independently_settled() 的通用语义。
```

若实现中发现必须修改上述任一主流程、全局匹配规则、全局确认帧数或大量无关文件，说明
补丁范围已经失控。应停止并重新分析，不能以一次实机成功换取系统性退化风险。

### 0.2 本轮版本与超参数边界

```text
当前基础版本：3.0-r15
下次目标版本：建议 3.0-r16
修改类型：无手静态收尾完整性修复，不是模型、NMS 或全局阈值调参
预计超参数变更：无
```

r16 不应修改以下现有数值：

```text
FLOW3_CONTACT_OBJECT_MOVE_EPS = 12 像素
FLOW3_COMMIT_MOVE_CENTER_DISTANCE = 28 像素
YOLO_CANDIDATE_SCORE_THRESH / YOLO_OBJECT_SCORE_THRESH / YOLO_HAND_SCORE_THRESH
NMS_THRESH
所有 FLOW3_TRACK_*、reappear、IN、OUT、MOVED 的确认帧数和几何阈值
```

这不表示 12/28 像素是长期最理想的架构；它们确实是后续可以单独评估的改进点。但本次
不能把“解决一个静态灰区收尾漏洞”扩大成“全系统像素阈值重构”。r16 应复用已有的
归一化身份匹配、IoM、宽高比例和连续帧证据，给灰区一个安全出口。

因此，正常情况下无需修改 `超参数位置与调节说明.txt`。只有实际实现时意外新增或改变
某个 `constexpr` 数值，才必须同步更新该说明文件；若没有数值改动，则不应为了形式修改。

## 1. 本次实机问题：已经确认的事实

### 1.1 物理库存、检测数量与低分候选的正确理解

冰箱中真实存在 7 个物品，其中包含 1 个真实苏打罐。操作前的连续无手帧 `1296` 至
`1304` 都稳定显示：

```text
库存数量 = 7
foods = 7
真实苏打罐存在且被稳定识别
```

有手阶段出现的 `foods=6`，例如 `frame=1308`、`frame=1310`，本身不构成错误证据。
物品被手遮挡、被拿起、检测框局部化、类别短暂抖动或漏检时，输入框数变少是正常现象。
不能把“物理上有 7 件物品”错误推导为“每一张有手帧都必须恰好有 7 个食品框”。

`frame=1309` 的 `foods=7` 也不能理解成“多出第 8 个物品”。该帧同时包含：

```text
真实苏打罐：
    cls=25 score=0.929 box=(141,138,396,410)

手附近的低分苏打罐候选：
    cls=25 score=0.266 box=(870,485,961,627)
```

此时一个本应识别为苹果的物品框很可能被手遮挡或未被正确分类，因此总数仍为 7。低分
`cls=25` 候选的“错误”在于类别/归属很可疑，而不是证明冰箱里不存在真实苏打罐，或证明
状态机本地凭空生成了一个 YOLO 框。

### 1.2 已确认的状态时间线

| 阶段 | 日志事实 | 正确含义 |
| --- | --- | --- |
| `frame=1308`，有手 | `foods=6`，真实苏打罐高分框仍在 | 手遮挡/检测抖动期，数量波动正常 |
| `frame=1309`，有手 | 低分 `cls=25 score=0.266` 框落在手框范围内 | 模型/后处理给出的短暂低置信候选 |
| 同一帧 | `old-item=12` 与 `suspect#-2` 建立 C-D alias | 正确的保守隔离，尚未产生 IN |
| `frame=1312`，无手 | 苹果 `item#11 -> MOVED_CONFIRMED`，新位置为 `(800,412,981,590)` | 整理判断已经成功 |
| `frame=1312` 以后 | 真实苏打罐 `item#12` 每帧均有自己的 `cls=25` 检测框 | C 没有消失，也没有真实 OUT |
| 同一期间 | `item#12` 是 `NORMAL + STATIC_CONFIRMED + needs_settle=1` | C 没有完成最终无手静态收尾 |
| 同一期间 | `suspect#-2` 无独立框、无共享框，但始终 `missing-count=0/2` | r15 还没得到“C 已独立结算”的前提 |
| `frame=1312` 至 `1318` | 持续 `[SETTLE] defer-commit` | 不是 MOVED 判错，而是收尾无法终止 |

### 1.3 关键的 12 至 28 像素灰区

`item#12` 的原始框与手离开后的稳定检测框为：

```text
原始框：       (163,138,401,400)
无手检测框：   (145,141,392,407)

原始框中心：   (282.0,269.0)
检测框中心：   (268.5,274.0)
中心距离：     14.396 像素
```

当前代码的两个绝对中心距离规则分别是：

```text
FLOW3_CONTACT_OBJECT_MOVE_EPS = 12 像素：
    CONTACT/有手轨迹相关的“仍可视为原位”及最小实际移动证据门槛。

FLOW3_COMMIT_MOVE_CENTER_DISTANCE = 28 像素：
    正式产生 MOVED / 整理事件前的最小中心位移。
```

因此本次数据满足：

```text
14.396 > 12：
    contact_detection_is_at_original() 拒绝把它作为明确原位的无手收尾。

14.396 < 28：
    boxes_differ_as_move() 也不允许把它作为正式 MOVED。
```

日志中的 `item#12 detection=0 source=REFERENCE` 正是这个结果：它仍能以一般轨迹/参考框
匹配到自己的检测，但未通过用于清除 `needs_no_hand_settlement` 的“明确原位”路径。

这不是只看像素距离的全部系统：身份匹配已经使用类别、IoM、宽高比例与归一化中心距离。
例如现有 `normalized_nearby_distance(a,b)` 定义为：

```text
中心距离 / 两个框中较小的对角线长度
```

本例苏打罐框对角线约为 `353.96` 像素，因此：

```text
14.396 / 353.96 = 0.0407 = 4.07%
```

并且两个框的 IoM 很高、宽高变化很小，后续无手帧的位置也稳定。这更像检测框抖动，
而不是一次应产生整理事件的真实移动。

### 1.4 r15 为什么没有、也不应当直接解决它

r15 的 stale alias cleanup 规则是：

```text
只有 D 关联的所有旧 C 都已经真正独立结算，且 D 连续无直接/共享无手证据，
才允许删除 runtime-only D。
```

在本次中，`item#12.needs_settle=1`，所以 r15 的
`all_conflicting_old_c_independently_settled()` 返回 false。这是符合 r15 设计的正确保护：
若 C 尚未真正独立结算，不能因为 D 暂时没有框就删掉可能真实的同类 D。

因此，这不是“r15 删除 D 的条件应该变宽”。真正应补的是：**C 必须能在不依赖 D 的前提下，
用自己的连续无手证据完成静态结算。** 当 C 真正结算后，r15 的原有 stale alias cleanup
会自然开始累计并处理消失的 D。

## 2. 完整根因：检测触发 + 静态灰区无出口 + r15 正确保护叠加

### 2.1 三层原因必须分开理解

```text
第一层，触发输入：
    手附近出现低分 cls=25 候选。它可能是类别误判、局部框或检测抖动。
    状态机正确地将其隔离为 QUARANTINED_PENDING_D，而非立即 IN。

第二层，缺失状态转换：
    真实旧 C 的无手检测框相对原框偏移约 14.4 像素。
    它超过 12 像素的 CONTACT 原位判定，却小于 28 像素的正式 MOVED 门槛。
    当前代码没有“连续稳定灰区框 -> 安全静态结算”的路径，C 因而维持 needs_settle=1。

第三层，r15 的正确保护：
    C 未真正结算时，r15 不允许 D 开始 stale missing-count。
    所以 D 留在 track_buffer_，操作继续 defer-commit。
```

真正的根因不是 `foods=6`，也不是镜像方向，更不是苹果 `item#11` 的整理匹配失败。
苹果已经 `MOVED_CONFIRMED`。问题是一个与苹果无关的旧 C 没有从“有手阶段暂时静态”
可靠地过渡到“无手阶段最终静态”，导致 r15 合理地不放行 D。

### 2.2 为什么它会表现为永久循环

目前每张无手帧都会重复相同的事实：

```text
C：有自己的框，但偏移仍约 14 像素，无法通过 12 像素原位收尾；needs_settle 仍为 1。
D：没有框，但 r15 看到 C 仍未结算；missing-count 因而保持 0/2。
SETTLE：仍有 C/D 未决状态，继续 defer-commit。
```

更多相同帧不会改变任何一个判断，因此不是“再等一会儿就会自己好”的短暂等待，而是真正
没有出口的状态机漏洞。

### 2.3 必须避免的错误修法

以下做法禁止采用：

```text
1. 将食品业务阈值从 0.25 粗暴提高到 0.50，借此隐藏低分候选。
2. 把所有 score < 0.50 的框从业务层删除。
3. 让所有 D 在第一张无手缺失帧就删除。
4. 修改 r15 的通用 old_c_has_independently_settled_identity()，让任意
   STATIC_CONFIRMED + needs_settle=1 的 C 都被视为已结算。
5. 在 stale alias cleanup 中绕过 C，直接把 D 当作假框删除。
6. 全局把 12 或 28 改为某个新数值，试图让本例“恰好通过”。
7. 直接写 old.needs_no_hand_settlement = false、强制提交或手写 [EVENT]。
8. 放宽 strict / partial / reappear / 同类邻居匹配范围。
```

这些做法会把当前已经稳定的低分真实证据、同类相邻保护、IN、OUT、MOVED 或遮挡逻辑改坏。

## 3. r16 的唯一目标：让 C 自己独立完成尺度感知的稳定静态收尾

### 3.1 正确的修复顺序

r16 必须按下面的因果顺序工作：

```text
旧 C 获得连续、唯一、稳定的无手近原位证据
        ↓
旧 C 通过既有静态 release 机制真正结算，needs_settle 变为 false
        ↓
r15 原有 all_conflicting_old_c_independently_settled() 成立
        ↓
若 D 没有独立框、没有共享框，则 r15 原有 stale missing-count 开始累计
        ↓
连续两帧后，r15 原有 unlink / discard 删除 runtime-only D
        ↓
现有 settlement 自然 commit，正常输出 MOVED / IN / OUT / INVENTORY
```

**不得反过来先强删 D 来逼迫 C 结算。** C 必须先由自己的证据独立完成结算；这正是 r15
用于保护真实 D 的安全边界。

### 3.2 r16 专用的“稳定近原位无手证据”条件

仅当同一个旧 C 在连续有效无手帧中满足以下全部条件，才允许累积新的静态收尾证据：

```text
1. C 是 operation-start old C：不是 suspect，item_id 有效。

2. C 处于有手操作后的待收尾静态状态：
       state == NORMAL
       contact_state == NONE
       resolution == STATIC_CONFIRMED
       needs_no_hand_settlement == true
       has_hand_estimate_anchor_box == true
   这保证本分支只处理“有手后尚待最终无手确认”的 C，不能碰普通稳定库存。

3. C 在当前帧有自己的直接无手 detection：
       no_hand_detection_index 有效；
       detection 的类别与 C 相同；
       detection 由现有的一框一物品/独立静态所有权逻辑唯一归属 C。
   不可只因画面里存在同类框就认定它属于 C。

4. 当前检测与 C 的原始框仍是可靠的同一物品身份：
       使用现有 strict_match_box() 的类别、归一化中心距离、宽高比例约束；
       同时使用现有 partial / IoM 约束确认存在足够空间重叠。
   不能只看原始中心的绝对像素距离。

5. 它不属于真正的正式移动：
       boxes_differ_as_move(original_box, current_box) == false。
   这不是新的移动门槛，而是保留既有 28 像素正式 MOVED 语义，避免 r16 吞掉
   已达到当前正式移动标准的 C。

6. C 没有真实移动或身份不确定证据：
       !hold_and_move；
       没有 has_meaningful_hand_move()；
       没有 CONTACT_MOVING；
       没有 reappearance_pending；
       没有 b_claim_ambiguous、contact_path_ambiguous、no_hand_candidate_ambiguous；
       没有 claim grace、遮挡、OUT 或其他未决路径。

7. 当前帧的框与上一张“稳定近原位”证据框也连续一致：
       使用现有 strict / partial / IoM / 归一化中心距离语义检查；
       不能把两张不同物品、两个远处同类框或两段被手打断的证据拼在一起。
```

第 4、7 条是本次“尺度感知”改进的关键。现有 `normalized_nearby_distance()` 以较小框对角线
作为尺度，IoM 和宽高比例又补足了中心距离单独无法判断的形状/覆盖关系。对于本例，
`14.4` 像素虽然超过原有 12 像素 CONTACT 门槛，但仅为苏打罐尺寸的 `4.07%`，且两帧框高度
重叠、位置稳定，因此可以作为“静态收尾候选”，而非直接判定 MOVED。

### 3.3 为什么 r16 不新增一个新的全局“归一化移动阈值”

从长期架构看，`FLOW3_CONTACT_OBJECT_MOVE_EPS=12` 和
`FLOW3_COMMIT_MOVE_CENTER_DISTANCE=28` 都可以在未来单独评估为尺度归一化门槛。但那会影响
CONTACT 证据、正式 MOVED、不同类别物品和所有已通过的回放，不能混入本次修复。

r16 的安全做法是：

```text
身份近似：沿用已有归一化中心距离 + 宽高比例 + IoM；
时间稳定：新增连续两张有效无手帧要求；
正式移动边界：保留现有 boxes_differ_as_move()；
有手移动证据：保留现有 hold/contact/path 规则。
```

也就是说，r16 不以“中心差小于某个新魔法数”作为唯一结论；它以多个已有尺度感知证据
加上时间连续性确认静态。这样既回应了不同尺寸物品不能只用 12 像素判断的问题，也避免
对全系统进行未经回归验证的阈值重构。

### 3.4 连续确认帧数

新的稳定近原位计数可复用已有的 `FLOW3_NO_HAND_D_CONFIRM_FRAMES`，当前值为 2：

```text
第 1 张有效无手帧：记录 C 的稳定近原位候选，计数 1/2；不结算、不删除 D。
第 2 张连续有效无手帧：再次满足所有条件，计数 2/2；允许 C 真正静态结算。
```

复用该值的理由是：它只是同一段无手收尾中的“连续直接证据确认帧数”，当前系统已经用
它保护 D 的独立/共享/消失判断。不得修改其值。若未来需要让 C 与 D 使用不同帧数，应在
独立需求中新增明确超参数、更新说明文件并重新评估全部回放；不是 r16 的范围。

### 3.5 证据计数必须重置的情况

新的 `stable_near_original_no_hand_count` 仅描述连续稳定无手证据。以下任一情况发生时必须
清零，同时丢弃保存的上一帧候选框：

```text
1. 手重新出现；
2. 当前帧不是有效直接无手帧；
3. C 没有自己的唯一直接 detection；
4. 当前 detection 不再是同类、严格/IoM/形状一致的近原位身份；
5. 当前 detection 已达到既有正式 MOVED 门槛；
6. C 出现 hold_and_move、CONTACT_MOVING、reappear、遮挡、OUT、claim 或同类歧义；
7. 当前候选与上一张稳定候选不连续；
8. C 已真正结算、轨迹删除或新一轮操作开始。
```

不得把被手、独立 D、共享框、歧义或大幅框跳动打断的两个片段拼成“连续两帧”。

### 3.6 达到两帧后的唯一动作

当 C 连续两张无手帧通过第 3.2 节的条件后，C 应通过现有的静态 release 语义真正结算：

```text
1. 先用当前 C 的直接 detection 更新 working_inventory_ 中该 C 的可见框；
2. 调用既有 release_not_held_()，且 keep_reopen_anchor 必须为 false；
3. 建议新增明确的 ReleaseReason，例如 STABLE_NEAR_ORIGINAL_NO_HAND，
   让详细日志能说明这不是普通 ORIGINAL_DETECTION，也不是强制结算；
4. 由 release_not_held_() 按既有语义清除 hand estimate anchor、
   needs_no_hand_settlement、临时轨迹和歧义状态；
5. 不直接手写 old.needs_no_hand_settlement = false；
6. 不直接提交 inventory_，不直接手写 [EVENT]。
```

这是“根据两张独立无手直接证据完成真正静态结算”，不是“为了删 D 伪造 C 已结算”。

### 3.7 C 结算后的 D 处理必须完全沿用 r15

C 真正结算后，D 的处理不新增宽松分支：

```text
D 有自己的连续独立框：
    沿既有 distinct-detections / staged IN 链路，正常确认真实 D。

D 与 C 连续共享同一框：
    沿既有 shared-detection 连续确认，D 作为重复 runtime 身份回收。

D 没有独立框，也没有共享框：
    r15 原有 alias_no_hand_missing_count 开始计数；连续两帧后，
    走既有 unlink_quarantined_suspect_() + discard 路径回收 runtime-only D。
```

因此 r16 不应改动 `all_conflicting_old_c_independently_settled()`、
`old_c_has_independently_settled_identity()` 或 r15 的 stale alias 删除条件。r16 的目标是
让真正静态的 C 达到这些既有条件，而不是改变条件的含义。

## 4. 推荐的实现位置、数据结构与顺序

### 4.1 数据结构：只增加 C 自己的窄证据，不复用 D 或 OUT 计数

在 `include/session.h` 的 `OperationTrack` 中增加仅用于本分支的字段，例如：

```cpp
int stable_near_original_no_hand_count = 0;
bool has_stable_near_original_box = false;
BBox stable_near_original_box;
```

字段含义必须固定：

```text
stable_near_original_no_hand_count：
    同一个 operation-start old C 在连续有效无手帧中，具有自身唯一、
    尺度感知近原位、无真实移动证据的直接检测次数。

stable_near_original_box：
    上一张该证据帧的 C 框，仅用于确认下一张框连续稳定。
```

不得复用以下字段：

```text
alias_no_hand_missing_count：只描述已结算 C 后，D 连续消失的证据。
alias_no_hand_match_count：只描述 C-D 共享/独立无手直接证据。
no_hand_missing_count：旧 C 的 OUT / 遮挡缺失证据。
not_hold_evidence_count：有手阶段的 not-hold 证据。
```

混用会把静态收尾改动扩散到 OUT、遮挡或真实 D 逻辑，是不允许的。

### 4.2 建议提取的窄 helper

在 `session.cc` 中增加语义清楚、只读或局部更新的帮助函数。名称可按现有风格调整，例如：

```cpp
bool old_c_has_unique_scale_aware_near_original_no_hand_detection(
    const OperationTrack& old,
    int detection_index,
    const std::vector<Detection>& detections,
    const std::map<int, int>& independent_static_owner_by_detection);

bool old_c_can_accumulate_stable_near_original_no_hand_evidence(
    const OperationTrack& old,
    const Detection& detection);

bool stable_near_original_evidence_continues(
    const OperationTrack& old,
    const Detection& detection);
```

这些 helper 应明确复用：

```text
strict_match_box()                         # 类别 + 归一化中心 + 宽高比例
partial_match_box(... FLOW3_TRACK_PARTIAL_IOM)  # IoM / 覆盖关系
normalized_nearby_distance()               # 尺度归一化中心距离
boxes_differ_as_move()                     # 保留现有正式 MOVED 边界
当前帧的一框一物品独立 owner 结果         # 防止相邻同类串身份
```

不得在这里新写一套更宽松的距离、IoU 或同类候选规则，也不得修改上述通用函数。

### 4.3 实现时机：旧 C 先处理，D 后处理

`observe_no_hand_frame_()` 已经按“已有旧 C -> suspect D”的顺序处理。这个顺序必须保留。

建议的时机是：旧 C 已经完成当前帧的 strict/original/reappear/reference 认领，已经拥有
`no_hand_detection_index`，但原有 `contact_detection_is_at_original()` 因 12 像素门槛拒绝
将它直接 release 时。此时再评估新的稳定近原位证据。

不能在以下位置提前判断：

```text
process_frame() 入口
有手阶段
旧 C 尚未完成本帧一框一物品认领之前
D 处理阶段之前读取上一帧残留的 detection index
```

原因是：r16 需要知道“当前框确实唯一属于 C”，而不是只知道画面里有同类别框。

### 4.4 推荐伪代码

下面仅表达语义，不要求逐字照抄：

```cpp
// 在 observe_no_hand_frame_() 的 existing old C 阶段，当前帧已找到 found detection 后。
if (old_c_is_provisional_static_after_hand(track) &&
    found >= 0 &&
    !original_release_was_accepted_this_frame) {
    const Detection& d = detections[found];
    const bool unique_near_original =
        old_c_has_unique_scale_aware_near_original_no_hand_detection(
            track, found, detections, independent_static_owner_by_detection);
    const bool no_real_move_evidence =
        !track.hold_and_move &&
        !has_meaningful_hand_move(track) &&
        track.contact_state == ContactState::NONE &&
        !track.reappearance_pending &&
        !track.b_claim_ambiguous &&
        !track.contact_path_ambiguous &&
        !track.no_hand_candidate_ambiguous;
    const bool not_formal_move =
        !boxes_differ_as_move(track.original_box, d.box);

    if (unique_near_original && no_real_move_evidence && not_formal_move &&
        stable_near_original_evidence_continues(track, d)) {
        ++track.stable_near_original_no_hand_count;
        track.stable_near_original_box = d.box;
        track.has_stable_near_original_box = true;

        if (track.stable_near_original_no_hand_count >=
            FLOW3_NO_HAND_D_CONFIRM_FRAMES) {
            update_seen(working_inventory_[track.item_id], d, frame_id);
            release_not_held_(track, false,
                              ReleaseReason::STABLE_NEAR_ORIGINAL_NO_HAND,
                              found, &d.box,
                              "no-hand-stable-near-original");
        }
    } else {
        reset_stable_near_original_no_hand_evidence(track);
    }
}
```

实现细节必须遵守：

```text
1. 首帧只计数，不 release；不能一帧框抖动就直接静态结算。
2. 连续性检查的第一帧需要正确初始化为 1，不能要求不存在的“前一帧”。
3. 若 C 已被原有 ORIGINAL_DETECTION 正常 release，本新分支不得重复执行。
4. 必须通过 find/update 现有工作库存项，不可用 map[] 意外创建未知库存。
5. 若不希望扩展 ReleaseReason，也必须使用能在日志中清晰区分的既有 release 路径；
   不能伪装成普通 ORIGINAL_DETECTION 而失去可追溯性。
6. 新证据只令 C 真正结算；不得直接 unlink 或删除 D。
```

### 4.5 C 已结算后，r15 必须自然接手

当 C 在第 2 张稳定无手帧通过 `release_not_held_()` 清除 `needs_settle` 后，同一帧后续的
D 处理应继续运行已有 r15 代码：

```text
第一个结果帧：
    C 已真正 independent-settled；D 无框；r15 stale missing-count = 1/2。

下一张连续无手帧：
    D 仍无框；r15 stale missing-count = 2/2；
    已有 unlink_quarantined_suspect_() + discard 删除 runtime-only D。

随后：
    既有 settlement 不再被 D 或 C 阻塞，正常 commit。
```

若 D 在任何时刻有独立框或共享框，r15 的原有逻辑必须清零 missing-count 并走正确的
IN/共享仲裁路径。r16 不得参与 D 的最终身份判断。
