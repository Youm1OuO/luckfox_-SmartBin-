# 库存身份一对一结算、跨阶段未决池与异常基线修复

## 1. 本文件解决的问题与优先级

本文件优先级高于细节7及此前所有流程说明；只有与本文件冲突的规则以本文件为准，未冲突部分继续沿用原说明。

这次实际测试暴露的不是“D 连续确认两帧还不够”：

    初始库存：
    #1 soda_can  约 (1058, 489)
    #2 apple     约 ( 651, 352)
    #3 orange    约 ( 340, 396)
    #4 apple     约 ( 653, 353)
    #5 orange    约 ( 488, 358)

    用户只把 #1 soda_can 移到约 (269, 511)

    错误结果：
    #1 仍留在旧位置
    新建 #11 soda_can，位置约 (269, 511)
    新建 #12 apple，位置约 (895, 346)

这里有两个互相放大的错误：

1. #2 与 #4 两个 apple 的库存位置相差只有约 2 像素，库存中的空间身份早已失真；单个 apple 检测框不能同时证明两个 item_id 都可见。
2. 有手阶段已经发现“同类旧 C 尚未得到独立归属”，但这个未决事实只在当前帧的局部变量中存在；手离开后，POST_HAND_REVEAL_D 又重新检查了一次，并可能把同一个旧物品的新位置当成新 D。

本文件的目标是先堵住“旧物品丢失一个身份，随后在新位置再生成一个新身份”的路径。对无法区分的情况，宁可暂不提交事件，也不能让库存数量膨胀。

本文件仍然要求 3.0 每张有效帧直接处理：

- 不引入 SnapshotBuffer。
- 不对多个检测框平均，不做快照投票。
- 连续帧只用于同一个对象的直接自匹配、缺失计数和未决状态推进。

## 2. 必须始终成立的身份约束

### 2.1 一张检测框最多属于一个对象

同一帧、同一检测索引 B，最多只能有一个正式 owner：

    一个 B -> 至多一个旧 C，或至多一个已有 D，或暂时无人认领

绝不能出现：

    一个 apple B
        -> 同时作为 #2 仍在原位的证据
        -> 同时作为 #4 仍在原位的证据

也不能出现：

    一个 soda_can B
        -> 一边被当成 #1 的可能新位置
        -> 一边又建立 POST_HAND_REVEAL_D

“检测框能分别匹配两个库存框”只说明视觉上有歧义，不说明两个库存物品都被看见。歧义时不按 item_id、map 遍历顺序或框分数强行选择 owner。

### 2.2 每个操作开始前已有的 C 必须得到一种解释

一次手操作收尾时，operation_start_inventory_ 中的每个旧 item_id 都只能处于下列一种运行时结论：

    AT_ORIGIN              在原位置被一对一检测框确认
    AT_NEW_POSITION        在自己的已确认路径/放下位置被一对一检测框确认
    OCCLUDED_CONFIRMED     被已确认前景物品的覆盖并集完全遮挡
    OUT_CONFIRMED          满足现有连续无手直接缺失规则
    UNRESOLVED             上述四种均无法唯一证明

前四种才叫“已解决”。UNRESOLVED 不是 OUT，也不是 VISIBLE，更不是可以忽略的普通状态；它表示旧身份仍可能解释某个当前 B。

现有 InventoryItem 只有 VISIBLE / OCCLUDED 两种持久状态时，UNRESOLVED 应先保存在本次操作的运行时状态中，不能伪装写成 OCCLUDED。OCCLUDED 仍只表示已经证明“完整覆盖”，不能作为“没有检测到”的通用替代。

### 2.3 新 D 的来源必须晚于旧 C 的一对一解释

一个未绑定 B 稳定存在两帧，只能证明“这个 B 真实存在”，不能证明“这个 B 从冰箱外放入”。

对于任何准备作为 D 的 B，所有可能解释它的同类旧 C 必须先得到一对一结论。若仍有一个可能的旧 C 是 UNRESOLVED，则：

    B 保持未决
    不创建 suspect D
    不提升工作库存
    不发送 IN
    不以数量变化来猜身份

这里的“可能解释”至少包括：

- C 的原位置与 B 相同或可部分匹配；
- B 落在 C 自己的 HAND、CONTACT、reappear 或 placed 候选路径上；
- C 与其他同类旧物品在操作开始时已经发生空间身份碰撞；
- C 在有手阶段曾针对该 B 进入候选、保护期或歧义状态。

距离很远、且原位置和轨迹都不可能接到 B 的同类静态 C 不应无限期阻断真实 D；阻断集合必须由候选关系决定，而不是只按类别总数粗暴判断。

### 2.4 PLACED 不是自动“已解决”

已有代码中，POST_HAND_REVEAL_D 的守卫不能仅因为某个旧 C 的 OperationTrack.state 为 PLACED 就跳过它。

PLACED 只表示“该 C 曾得到一个放下候选”。只有 placed_box 已在当前直接无手帧中获得独占的一对一检测确认，并且满足原有连续确认条件后，该 C 才能进入 AT_NEW_POSITION。

## 3. 简单移动时应怎样工作

以本次 soda_can 为例：

    t0：#1 在右侧旧位置；库存总数为 5。
    t1：手遮住或接触 #1；系统开始保存 #1 的候选路径。
    t2：手和 #1 一起移到左侧；左侧 soda B 还只能是 #1 的候选。
    t3：手离开；左侧 soda B 与 #1 的路径连续，且没有其他旧 soda 能解释它。
    t4：下一张直接无手帧仍匹配到同一个左侧 soda B。

正常结果必须是：

    左侧 B -> #1
    事件  -> MOVED #1
    库存  -> 仍然是 5 件

绝不能是：

    #1 还在右侧
    左侧 B -> 新 #11
    事件  -> IN #11
    库存  -> 6 件

若 t3 或 t4 无法唯一确认左侧 B 属于 #1，例如框跳动、漏检或出现同类冲突，则正确的短期结果是：

    #1 -> UNRESOLVED
    左侧 B -> 未决池
    事件 -> 暂不发送
    库存数量 -> 仍为 5

这会延迟一次 MOVED，但不会制造一个多出来的 soda_can。后续直接无手帧一旦给出唯一证据，再确认 #1 的 MOVED；若操作被中断或会话结束仍无唯一证据，则丢弃工作副本并保留操作前的正式库存，不强行 IN 或 OUT。

## 4. 新增的运行时数据

所有新增数据只服务于一段连续手操作，放在 SessionManager / OperationTrack 的运行时内，不写入正式 InventoryItem，也不写入后端库存。

建议增加如下概念；实际字段名可以按现有代码风格命名：

    enum class IdentityResolution {
        UNRESOLVED,
        AT_ORIGIN,
        AT_NEW_POSITION,
        OCCLUDED_CONFIRMED,
        OUT_CONFIRMED,
    };

    struct FrameOwnership {
        // item_id -> 当前帧唯一检测索引
        std::map<int, int> old_item_to_detection;
        // 当前帧检测索引 -> 唯一旧 item_id
        std::map<int, int> detection_to_old_item;
        // 当前帧未能唯一归属的旧 item_id 与检测索引
        std::map<int, std::vector<int> > item_candidates;
        std::map<int, std::vector<int> > detection_candidates;
    };

    struct UnresolvedSameClassClaim {
        int cls_id;
        BBox first_box;
        BBox last_box;
        bool has_last_box;
        int first_frame_id;
        int last_frame_id;
        int direct_self_match_count;
        bool seen_during_hand;
        bool touched_by_this_hand_track;
        std::set<int> possible_old_item_ids;
    };

其中 UnresolvedSameClassClaim 代表“一个尚不能决定是旧 C 还是新 D 的 B”，而不是“一个已经存在的 D”。

其生命周期如下：

    有手帧发现未认领 B，且存在可能旧 C
        -> 创建或更新未决 claim
    手离开后的同一个 B 继续直接自匹配
        -> 更新同一个 claim，不创建 POST_HAND_REVEAL_D
    某旧 C 获得唯一路径/原位/遮挡/OUT 结论
        -> 从 claim 的 possible_old_item_ids 中移除该 C
    claim 的所有 possible_old_item_ids 都已解决
        -> 才可把仍连续出现、且有合法手操作来源的 B 启动为 D
    claim 的 B 消失或不能自匹配
        -> 丢弃 claim；绝不能补发 IN

为了防止“D 守卫刚解除就把很久以前的任意无手框算作新物品”，claim 还必须保存首次来源证据：

- 它是否在手操作期间出现；
- 或它是否在手刚离开后的 POST_HAND_REVEAL 窗口内首次出现；
- 它是否接触本次 hand_track；
- 首次出现后是否连续直接自匹配。

未决期间的观察可证明 B 连续存在，但在旧 C 守卫解除前不能计入 D 的正式确认次数。守卫解除的当前帧才是 D 的第一张确认帧，下一张直接无手帧仍须自匹配。

## 5. 统一的每帧一对一归属表

### 5.1 先建立 FrameOwnership，再进行状态推进

每张有效有手帧和无手帧，都应先为“操作开始前的旧 C”建立一张 FrameOwnership。它是本帧唯一的归属事实来源，后续的 C 更新、D 守卫、POST_HAND_REVEAL_D 和最终结算都读取同一份结果，不能各自再扫描 detections 并得到彼此矛盾的答案。

候选边只允许同类对象之间建立，并按证据强弱分层：

    1. 已确认的 C 新位置、confirmed reappear 候选、CONTACT 的真实 observed_track
    2. C 的原位置严格匹配
    3. C 的 HAND 预计路径或尚待二次确认的 reappear 路径
    4. C 的原位置局部匹配

建立候选图后，按下列规则提交 owner：

1. 一个 C 最多获得一个 B。
2. 一个 B 最多分给一个 C。
3. 只有 C 和 B 两侧都唯一，或代价具有明确领先差距时，才提交该 pair。
4. 同类 B 对多个 C 的代价并列或都合理时，保持未决，不以 map 顺序选一个。
5. 已经分给旧 C 的 B 从候选集中消耗，不能再被 D、另一个 C 或“独立检测”检查重复使用。

现有的 bind_mutually_unique 和 bind_mutually_unique_track_paths 已经体现了“双方唯一才绑定”的方向。应把这个机制抽成可复用的 FrameOwnership 生成过程，供有手、无手和 settle_no_hand_frame_ 共用，而不是只在最终 settle 阶段使用。

### 5.2 必须替换 POST_HAND_REVEAL_D 中的独立检测扫描

register_post_hand_reveal_suspects_ 当前会对每个旧 C 单独遍历 detections 判断 independent_detection。该写法的问题是：同一个 apple 检测框可以在 #2 的循环中成为“独立检测”，又在 #4 的循环中再次成为“独立检测”。

修改要求：

    不再在每个 old C 内部独立扫描 detections。

改为：

    const FrameOwnership& ownership = 当前帧的一对一结果;

    old C 已解决的必要条件之一：
        ownership.old_item_to_detection 中存在该 C 的唯一 owner，
        或该 C 已被独立证明为完整遮挡 / OUT。

若 #2、#4 都可能对应同一个 apple B，则 FrameOwnership 不给该 B 分配两个 owner；在真正并列时可以一个都不分配。两个 C 都保持 UNRESOLVED，绝不能因为同一个 B 而让它们都被视为“独立存在”。

### 5.3 有手与无手必须共享未决结论

scan_or_update_suspects_ 中出现下列情形时：

    同类旧 C 尚未得到独立归属，B cls=...

不能只打印日志然后 continue。应当：

1. 找出能解释该 B 的所有旧 C；
2. 写入或更新 UnresolvedSameClassClaim；
3. 把对应 C 的 IdentityResolution 保持为 UNRESOLVED；
4. 不给该 B 分配 D owner；
5. 在后续有手帧、无手帧继续用同一 claim 跟踪它。

register_post_hand_reveal_suspects_ 只能读取该持久状态，不能重新以“当前帧恰好看到另一个同类框”为由绕开有手阶段的未决结论。

## 6. C、已有 D、POST_HAND_REVEAL_D 的固定处理顺序

每张无手直接帧按以下顺序处理：

    1. 用 FrameOwnership 更新旧 C 的原位、轨迹和放下位置证据。
    2. 更新已有的、在有手阶段预登记的 D。
    3. 更新已有 UnresolvedSameClassClaim 的连续匹配和候选旧 C 集合。
    4. 对剩余 B 检查是否能作为 POST_HAND_REVEAL 的来源线索；
       若仍可能属于旧 C，创建/更新未决 claim，而不是 D。
    5. 只有旧 C 守卫全部解除后，才把符合来源条件的 claim 启动为 D。
    6. 最后调用 settle_no_hand_frame_；只要存在 UNRESOLVED claim 或
       UNRESOLVED 旧 C，就不提交正式库存。

有手帧也遵守“旧 C 优先、已有 D 次之、未决 claim 再次、真正新 D 最后”的顺序。

实际代码中应统一封装一个判断，例如：

    bool can_start_new_d_for_claim(
        const UnresolvedSameClassClaim& claim,
        const FrameOwnership& ownership);

它至少检查：

1. claim 的 B 未被 old_item_to_detection 或已有 D 占用；
2. claim 有合法的本次操作来源证据；
3. claim 仍在允许的手离开确认窗口内，或它从窗口内开始后一直直接连续存在；
4. claim.possible_old_item_ids 中每个 C 都已得到 AT_ORIGIN、
   AT_NEW_POSITION、OCCLUDED_CONFIRMED 或 OUT_CONFIRMED；
5. 相关的空间身份碰撞组已经被一对一解开；
6. 本帧没有新的同类歧义。

条件不足时返回 false；不得因为“B 已出现两帧”直接创建或提升 D。

## 7. 最终结算和事件提交

settle_no_hand_frame_ 不能重新单独推导一套与 observe_no_hand_frame_ 不同的归属。它应接收或重建同规则的 FrameOwnership，并在最终提交前检查：

    has_unresolved_no_hand_state_ 必须同时检查：
    - 活动旧 C 的 UNRESOLVED；
    - b_claim_ambiguous；
    - contact_path_ambiguous；
    - 未结束的 UnresolvedSameClassClaim；
    - 空间身份碰撞组仍未解开的成员；
    - 尚未完成直接自匹配的 D。

只要其中任意一项存在：

    不 replace_all 正式库存
    不 clear_runtime_after_commit_
    不生成 IN / OUT / MOVED

只有全部旧 C 已解释、D 已完成自己的直接无手确认、每个检测框只被一个 owner 使用时，才允许提交。

提交时还应满足以下不变量：

    若 B 被确认给旧 #1：
        #1 的 base_box 更新为 B
        可以产生 MOVED #1
        不允许以同一个 B 新建 IN

    若 B 被确认给新 D：
        B 不能再作为任何旧 C 的原位、新位置或独立存在证明
        才可以产生 IN

    若 B 未决：
        正式库存数量不变
        不为 B 分配新 item_id

没有必要通过增加 D 确认帧数来解决本问题。错误的 soda_can 在左侧会稳定出现很多帧；把两帧改成五帧，只会在第五帧错误地产生 #11。

## 8. 已经损坏的同类库存基线如何处理

### 8.1 当前两个 apple 不能自动恢复出真实身份

已有的 #2 约 (651,352) 与 #4 约 (653,353) 几乎重合。仅凭一张单目 YOLO 检测图像，系统无法知道：

- 是两个真实 apple 正好遮挡；
- 是曾经把 #4 的检测框错写给 #2；
- 是同一个检测框过去同时更新了两个 item_id；
- 还是其中一个 apple 的历史位置早已丢失。

因此不能让程序“猜一个”然后继续把两个 ID 都更新到同一 B。那会继续污染后续操作。

### 8.2 运行时保护

在以下两个时机检测同类空间身份碰撞：

1. init_from_backend 后的首张无手校验；
2. begin_working_operation_ 复制 operation_start_inventory_ 后。

对同类 item_id 组，若出现“多个旧库存框都能匹配同一个检测 B，且没有足够的其他 B 形成一对一分配”，则标记为 baseline collision / identity collision。

碰撞组的规则：

- 不更新多个 item 的 box 到同一个检测 B。
- 不把任一成员仅因漏检写成 OUT。
- 不把任一成员仅因一个 B 写成 VISIBLE。
- 该组成员保持 UNRESOLVED，且阻挡与它们可能相关的同类 D。
- 只有之后出现足够的、可一对一匹配的独立同类检测框，才解除碰撞。

初始校验日志也要从“多少检测框可唯一对应”扩展为输出每个碰撞组，例如：

    [INIT-IDENTITY] cls=apple collision: item#2,item#4 share detection[3]
    [INIT-IDENTITY] baseline remains unchanged; same-class IN is guarded

### 8.3 现实数据的恢复步骤

当前已经从 5 错增为 7 的库存，不应继续作为新算法的测试基线。应先恢复到“真实数量为 5”的可信库存，再测试移动逻辑。

推荐的人工恢复方式：

1. 删除这次错误生成的 #11 soda_can 与 #12 apple，或从可信后端快照恢复到错误操作前的 5 件。
2. 让冰箱内两个 apple 在无手、无遮挡画面中分开摆放，确保 YOLO 能同时得到两个独立完整框。
3. 通过受控的后台校正/重建基线，将两个 apple 分别写入这两个真实框。
4. 保存一张无手基线日志，确认同类两个 item_id 能得到两个不同的唯一检测 owner。
5. 再进行“只移动 soda_can”的回归测试。

第 3 步是人工校正，不是运行时自动删除库存。若两个 apple 在图像中始终完全重叠，二维 YOLO 本身无法重新建立二者各自的位置；系统只能保留数量并将身份标记为未决，等待它们被分开、增加外观特征、增加视角，或由人工校正。

## 9. 需要增加的诊断日志

这类问题不能只看“进入未决池”一行日志。每个候选 B 至少要打印一次可追踪诊断，包含 frame_id、检测索引、类别、框中心、候选旧 C、最终 owner 和拒绝原因。

建议日志格式：

    [3.0][OWNERSHIP] frame=... B[3] cls=25 center=(269,511)
        candidates={item#1:path}
        owner=item#1
        result=AT_NEW_POSITION

    [3.0][OWNERSHIP] frame=... B[1] cls=0 center=(652,353)
        candidates={item#2:origin,item#4:origin}
        owner=none
        result=AMBIGUOUS

    [3.0][D-GATE] frame=... B[3] cls=25
        result=BLOCK
        unresolved_old={item#1:HAND_PATH}
        source=POST_HAND_REVEAL

    [3.0][D-GATE] frame=... B[3] cls=25
        result=ALLOW
        old_resolution={item#1:AT_NEW_POSITION}
        direct_d_count=1/2

对于每个旧 C，还应在它从守卫集合移除时打印具体原因：

    item#... resolved by unique origin detection
    item#... resolved by unique moved-path detection
    item#... resolved by full occlusion union
    item#... resolved by confirmed OUT

这样下一次若仍出现误 IN，可以直接知道到底是：

- 旧 C 没被放入 possible_old_item_ids；
- 一个检测框被重复当作独立检测；
- PLACED 被过早视为已解决；
- D 守卫被错误绕过；
- 还是基线本身已碰撞。

## 10. 必须补充的回放测试

在 tests/session3_replay_test.cc 中增加主机端回放，不依赖摄像头、RKNN 或快照模块。每个无手帧直接喂给状态机，验证对象 owner、事件和库存数量。

至少覆盖以下场景：

1. 五件库存中只移动一个 soda_can：

       旧 #1 从右侧移动到左侧
       结果只有 MOVED #1
       库存仍为 5
       不存在新 soda_can IN
       不存在无关 apple IN

2. soda_can 的新位置先处于未决：

       旧 #1 与左侧 B 暂时无法唯一匹配
       连续无手帧期间不产生 IN
       old #1 未被删除
       B 后来唯一接上 #1 路径时才产生 MOVED #1

3. 两个同类旧 apple 只看到一个同类 B：

       #2 和 #4 都能匹配 B
       B 不获得双 owner
       #2/#4 都不能因该 B 同时被视为 VISIBLE
       不产生 apple IN、OUT 或任意错误位置更新

4. 两个同类旧 apple 各有一个独立 B：

       FrameOwnership 分别建立两个不同 owner
       解除碰撞组
       两个库存位置均可安全更新

5. 真实的新 D 在同类旧 C 尚未解决时出现：

       先保存为 UnresolvedSameClassClaim
       不启动 D 确认计数
       旧 C 后来被一对一确认后
       同一个 B 再连续两张直接无手帧匹配
       才生成一次 IN

6. 真实的新 D 且所有可能旧 C 已解决：

       保留细节4 / 细节6规定的手轨迹来源条件
       两张直接无手帧自匹配后只生成一次 IN

7. 已确认移动的旧 C 与真实新 D 同类：

       旧 C 的新位置只能归旧 C
       D 的 B 只能归 D
       两个 B 不可交叉复用

8. 会话结束时仍然未决：

       不提交工作库存
       正式库存保持操作前状态
       不产生错误事件

9. 回放中确认不链接 snapshot.cc，且每张无手帧均直接调用：

       observe_no_hand_frame_
       settle_no_hand_frame_

## 11. 建议的实施顺序

1. 在 session.h / session.cc 中加入 IdentityResolution、UnresolvedSameClassClaim 和每次操作的碰撞组状态；在 reset_operation_runtime_ 与 begin_working_operation_ 正确清空、初始化。
2. 抽取 FrameOwnership 的候选构建和一对一分配，使有手、无手、最终结算共享同一规则。
3. 修改 scan_or_update_suspects_：发现同类旧 C 未解决时写入持久 claim，不再只打印后丢失状态。
4. 修改 register_post_hand_reveal_suspects_：删除逐个 old C 重复扫描 independent_detection 的做法；改读 FrameOwnership 和持久 claim；取消“PLACED 直接跳过”的捷径。
5. 修改 observe_no_hand_frame_ 与 has_unresolved_no_hand_state_：推进 claim，并让未决 claim 阻止 commit。
6. 修改 settle_no_hand_frame_：使用相同的一对一 owner，确保同一个 B 不会同时支撑旧 C 和新 D。
7. 扩展首张无手校验，识别并记录同类基线碰撞；提供受控的人工基线校正入口。
8. 增加上述回放和诊断日志后，再用真实视频测试。

实现后的首要验收标准不是“更快产生 IN”，而是以下不变量：

    任意一次单纯整理：
        旧 item_id 保持不变
        不增加库存数量
        没有证据不足时不产生 IN

    任意一张检测框：
        只能证明一个物品身份

    任意真实新物品：
        可以延迟确认
        但不会因旧 C 身份未解而抢占旧物品的位置
