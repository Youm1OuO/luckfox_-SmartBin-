# YOLO 后处理颜色判别实施指导（演示专用）

> 状态：该功能已经接入当前 `yolov5n` 板端流程。实现位于
> `src/color_postprocess.cc`，只修改四个目标类别的 `cls_id`，不修改 YOLO
> 模型、RKNN 模型、训练配置、bbox、score 或检测数量。本文同时作为实现和
> 板端调参的验收说明。
>
> 目标：仅为比赛演示中的 `egg / orange`、`apple / onion` 易混淆问题增加保守的手工后处理。要求每帧仍然立即输出结果，但不能因为新规则破坏现有检测、手部处理、库存状态机、事件上报和其他 45 类物品。

## 1. 适用范围与非目标

本功能只处理以下两对类别：

```text
egg <-> orange
apple <-> onion
```

当前类别 ID：

```text
apple  = 0
orange = 2
onion  = 15
egg    = 18
```

它不是重新训练 YOLO，也不是修改 NPU 推理模型。它只在 YOLO 已经输出 bbox、类别和分数之后，根据该 bbox 在当前画面中的颜色、面积等信息，对这两对类别进行很小范围的二次判别。

本功能不负责解决：

- 老苹果被 YOLO 判为橙子的问题。该问题属于 `apple <-> orange`，不在第一版范围内；老苹果本身可能视觉上接近橙子，不能安全地通过颜色强行改类。
- 所有类别的通用识别提升。
- NMS 参数、YOLO 置信度阈值或模型结构优化。

比赛展示时使用颜色鲜红的新鲜苹果，是处理老苹果问题的低风险方案。

## 2. 最重要的安全原则

### 2.1 YOLO 是默认结果

后处理只能在“外观证据足够强”时覆盖 YOLO 的类别。颜色、面积判断不明确时，必须保留 YOLO 原始类别。

禁止使用以下不安全逻辑：

```text
若不像 egg，则一定判 orange
若不像 apple，则一定判 onion
```

正确逻辑必须有第三种状态：

```text
EGG_LIKE / ORANGE_LIKE / UNKNOWN
APPLE_LIKE / ONION_LIKE / UNKNOWN
```

其决策应当是：

```text
若 EGG_LIKE：    输出 egg
若 ORANGE_LIKE： 输出 orange
若 UNKNOWN：     保留 YOLO 原始类别

若 APPLE_LIKE：  输出 apple
若 ONION_LIKE：  输出 onion
若 UNKNOWN：     保留 YOLO 原始类别
```

这仍然满足“每帧立即输出”，不需要等待多帧；`UNKNOWN` 不是不输出，而是输出本帧 YOLO 的原始判断。

### 2.2 只触碰两对目标类别

若 `cls_id` 不是 `egg`、`orange`、`apple`、`onion`，后处理必须完全不执行，输出的：

```text
cls_id
score
bbox
检测数量
```

都必须与原始流程保持一致。

即使属于这四类之一，也绝不允许被改成第三个无关类别。例如：

```text
egg/orange 分支只能输出 egg 或 orange
apple/onion 分支只能输出 apple 或 onion
```

### 2.3 证据不足、画面异常时不改类

以下情况必须直接保留 YOLO 原类别：

- bbox 太小，中心区域像素不足；
- bbox 被画面边缘裁断严重；
- bbox 无法裁出有效中心区域；
- 颜色特征处于两类阈值之间；
- 手框明显覆盖或重叠该物品框；
- 物品被遮挡、强反光、严重模糊或中心区域主要是冰箱背景；
- 颜色统计函数失败或得到非法数值。

不能因为新功能异常而删除检测框、改变 bbox、改变 YOLO 分数，或让库存状态机收到空结果。

## 3. 正确的插入位置

当前主流程概念上是：

```text
摄像头 BGR frame
  -> 180 度翻转
  -> letterbox 后送入 RKNN
  -> YOLO 解码 + NMS
  -> 704 letterbox 坐标映射回原图坐标
  -> detections / hand_boxes
  -> food_dets
  -> session.process_frame(...)
```

颜色二次判别应放在：

```text
坐标映射完成后
并且 hand_boxes 已经收集完成后
但在 food_dets 和 session.process_frame(...) 之前
```

建议未来的概念流程：

```text
YOLO 输出
  -> 映射为原图坐标的 detections
  -> 收集 hand_boxes
  -> 对目标类别调用颜色/面积二次判别
  -> 生成 food_dets
  -> 进入原有 session / inventory / cloud 流程
```

原因：

- 此时 bbox 与当前真实 `frame` 的坐标一致，可以正确裁剪图像。
- `frame` 在该阶段仍是 BGR 图像；不能错误地从给 RKNN 的 RGB letterbox 输入中裁剪原图区域。
- 手框已经可用，可以避免手部肤色干扰颜色判断。
- 修正后的类别会被后续库存和事件流程一致使用，而不是只修改 OSD 显示文字。

参考现有位置：

- `src/main.cc` 中 YOLO 推理、`mapCoordinates(...)` 和 `detections` 构造流程。
- `src/postprocess_decode.cc` 和 `src/postprocess.cc` 继续保留原有解码、阈值和 NMS 行为。

## 4. ROI 与颜色特征

### 4.1 使用 bbox 中心区域

不能对整个 bbox 求颜色平均值。整个框常包含冰箱背景、货架、阴影、包装物和手，容易污染结果。

应按原图坐标从 `frame` 中裁出 bbox 的中心区域，例如中心宽高约为原框的 `55%~70%`。具体比例要通过真实板端画面测试后确定。

裁剪前必须：

- 将坐标裁剪到画面范围内；
- 检查宽高大于最小像素尺寸；
- 检查中心 ROI 有效；
- 不修改原始 bbox。

### 4.2 使用 HSV 或 Lab，不直接使用平均 RGB

未来实现时可将中心 BGR ROI 转换为 HSV。建议统计的是颜色像素比例，而不是整个 ROI 的平均 Hue：

```text
red_ratio          红色像素比例
purple_ratio       紫色 / 紫红色像素比例
orange_ratio       橙红色像素比例
yellow_white_ratio 黄白像素比例
mean_saturation    平均或中位数饱和度
mean_brightness    平均或中位数亮度
```

直接平均 Hue 不可靠：红色在 HSV 中跨越色相首尾，背景和多种颜色混合也会使平均值失去意义。

亮度和饱和度应优先使用中位数、像素比例或经过裁剪的均值，避免少量阴影/反光主导结果。

## 5. egg / orange 判别规则

### 5.1 可使用的证据

```text
egg_like：
- 中心区域偏黄白；
- 饱和度低或中等；
- 通常较亮；
- 在当前固定镜头/演示距离下，bbox 面积通常较小。

orange_like：
- 中心区域有明显橙红色；
- 饱和度较高；
- 在当前固定镜头/演示距离下，bbox 面积通常较大。
```

框面积仅能作为辅助证据。真橙子离镜头较远时也可能变小；鸡蛋靠近镜头时也可能变大。因此禁止使用：

```text
box 小 -> 一定 egg
box 大 -> 一定 orange
```

### 5.2 推荐的每帧决策

```text
如果 YOLO 类别属于 {egg, orange}：
    若黄白特征强、饱和度/亮度符合 egg，且相对橙色证据有明显优势：
        输出 egg
    否则若橙红特征强、饱和度/亮度符合 orange，且相对鸡蛋证据有明显优势：
        输出 orange
    否则若两类证据接近，但框大小为当前 egg 范围且 egg 证据略高：
        输出 egg
    否则若两类证据接近，但框大小不在当前 egg 范围且 orange 证据略高：
        输出 orange
    否则：
        保留 YOLO 原类别
```

实现中的颜色比例以中心 ROI 的有效像素（`V >= 35`）为分母；当前默认起点为
`egg_tone_ratio >= 0.35`、`orange_ratio >= 0.30`、类别分差至少 `0.08`，
并附加平均饱和度/亮度约束。这里的数值只是实际板端调参起点，不能脱离真实
冰箱灯光、距离和 bbox 质量直接视为最终标定值。

## 6. apple / onion 判别规则

### 6.1 可使用的证据

```text
apple_like：
- 红色区域比例高；
- 颜色通常更鲜艳；
- 亮度通常不是很低。

onion_like：
- 紫色或紫红色区域比例高；
- 颜色通常更暗；
- 与红苹果相比，偏紫色而不是纯红色。
```

“亮”或“暗”只能辅助判断，不能单独作为结论。阴影里的红苹果可能很暗，强光下的紫皮洋葱也可能很亮；红色比例与紫色比例应是主要证据。

### 6.2 推荐的每帧决策

```text
如果 YOLO 类别属于 {apple, onion}：
    若红色比例高，且亮度/饱和度符合苹果：
        输出 apple
    否则若紫色比例高，且亮度/饱和度符合洋葱：
        输出 onion
    否则：
        保留 YOLO 原类别
```

第一版不要尝试根据框大小区分苹果和洋葱；两者尺寸和形状可能重叠，使用颜色更符合当前已知问题。

## 7. 手部与遮挡保护

当前业务已经会构建 `hand_boxes`。颜色后处理必须检查目标物品框是否与任一强手框存在明显交叠。

```text
若物品框与手框重叠明显：
    不做颜色覆盖
    保留 YOLO 原类别
```

这是必要保护：手的肤色可能被误认为苹果/橙子颜色，白色反光或手部遮挡也可能让鸡蛋颜色统计失真。

该保护不等待下一帧，也不会影响每帧输出；只是不在视觉证据不可靠时强行替换 YOLO 结果。

## 8. YOLO 分数的后续增强（非第一版必需）

当前 RV1106 解码流程在每个候选框上只保留最高类别和最终 `prop`：

```text
prop = objectness * max_class_probability
cls_id = max_class_id
```

它会丢失第二名类别分数，因此当前无法区分：

```text
orange 0.95, egg 0.02
orange 0.48, egg 0.45
```

未来若需要更稳健的规则，可以只额外保留这四个类别的原始分类分数：

```text
apple_score, onion_score, egg_score, orange_score
```

这样可以做到：YOLO 本身非常确定时少改；两类分数接近时允许颜色/面积更积极地纠正。

注意：这是增强项，不是第一版颜色规则的前置条件。第一版不得为了保存额外分数而改变 `OBJ_CLASS_NUM`、模型输出形状、模型文件、类别顺序或原有 49 类解码逻辑。

## 9. NMS、分数和 bbox 的保护要求

第一版不修改：

- `NMS_THRESH`；
- 现有 NMS 执行顺序；
- YOLO 候选框阈值；
- 原始检测 bbox；
- 原始 `score/prop` 计算；
- 检测结果数量；
- ONNX、RKNN、标签文件和类别数。

颜色规则最多修改目标 detection 的 `cls_id`，且仅在强视觉证据下修改为该目标类别对中的另一个类别。

因为修正发生在已有 NMS 之后，极少数情况下可能出现原先不同类、修正后变成同类的重叠框。第一版不要为了处理这个边缘情况而全局重写 NMS；先在真实演示画面中观察是否出现，再决定是否增加仅针对目标类别对的小范围去重。

## 10. 原有功能不可回归清单

实现后必须确认以下功能保持原样：

- 49 类类别 ID 和 `labels_list.txt` 顺序不变；
- 当前 49 类 `.rknn` 模型、模型输入尺寸 `704`、模型加载流程不变；
- 非 `apple/onion/egg/orange` 的类别、框、分数和数量不变；
- 手检测和 `hand_boxes` 的行为不变；
- 开关门检测、暗帧跳过、截图和视频编码流程不变；
- `session.process_frame(...)` 的调用时机、入参结构和库存业务逻辑不变；
- 云端上报、中文类别映射、事件类型和截图逻辑不变；
- 原有 NMS 和所有全局阈值不因本功能被修改；
- 后处理出现异常时，系统继续使用原始 YOLO 检测结果，不能崩溃、不能丢帧、不能丢检测。

实现时应把新逻辑隔离在独立的小模块/辅助函数中，并保留明确的开关或容易回退的路径。不要把颜色判断分散插入库存、追踪、云端或显示代码中。

## 11. 调参和验收顺序

在真正启用类别覆盖前，建议先只打印日志或保存调试信息，确认真实画面中的特征范围：

```text
真实类别
YOLO 原 cls_id 与 score
bbox 面积 / 宽高比
red_ratio / purple_ratio / orange_ratio / yellow_white_ratio
饱和度与亮度统计
是否与手框相交
```

建议从实际板端、实际冰箱灯光、实际摆放距离下收集每类约 20~30 个稳定样本：

```text
egg
orange
鲜红苹果
紫皮/偏暗洋葱
```

之后再设定保守阈值。阈值应优先保证“错误时不乱覆盖 YOLO”，而不是追求每一帧都强行修正。

验收至少覆盖：

1. 真鸡蛋被 YOLO 判为 orange 时，满足黄白、低饱和、小框条件后能改为 egg。
2. 真橙子即使框偏小，只要橙红和高饱和明显，仍保留/改为 orange。
3. 红苹果被 YOLO 判为 onion 时，红色证据强时能改为 apple。
4. 紫皮洋葱被 YOLO 判为 apple 时，紫色证据强时能改为 onion。
5. 手遮挡、强反光、阴影、bbox 边缘裁断、颜色不明确时，保留 YOLO 原类别。
6. 四个目标类以外的物品，输出与启用前一致。
7. 原有入库、出库、移动、遮挡、开关门、云端上报和截图流程不发生行为回归。

## 12. 实施结论

第一版应保持简单：

```text
中心 ROI + HSV 颜色像素比例 + 框面积辅助 + 手部重叠保护 + UNKNOWN 回退 YOLO
```

它不使用时间等待，不重新训练，不改变模型，也不改动全局后处理逻辑。

最重要的底线是：新规则只是对少数强证据场景进行覆盖；任何不明确、异常或不在范围内的情况，都必须回退为原有 YOLO 输出，确保现有功能不被改坏。
