# 细节22：统一遮挡生命周期、正式证据与 OUT 时序的实施说明

## 0. 本文件的结论与用途

本文件是下一次修改 3.0 状态机前的实施指导。它处理的不是两个彼此独立的
“橙子/苹果特例”，而是同一个遮挡生命周期在两个方向上都没有完整收口的问题：

```text
前景物 A 已确认离开 C 前方
    + C 重新被合法观察到
    -> 应为 REVEALED(C)，不能继续 OCCLUDED。

前景物 A 已确认进入/移动到 C 前方
    + C 随后持续没有合法直接观察
    -> 应为 OCCLUDED(C)，不能进入普通 OUT。
```

当前代码已经把这两条链的一部分做对了，但仍把“遮挡关系”“严格矩形完整覆盖”
和“普通 OUT 缺失计数”分散在多个阶段处理。因此上一次修复只补到了前一方向的
一个覆盖语义缺口；本次必须收敛为一套统一的、因果顺序正确的生命周期计划。

本文件要求下一次修改做到以下三点：

```text
1. 先完成 detection -> 旧物/新 D 的身份结算；
2. 再以已确认前景物的关系变化，统一计算遮挡/露出/OUT 的资格；
3. 最后一次性提交正式库存和事件。
```

这不是增加“橙子框差 19px 就放行”的专属补丁，也不是把“有交集”直接等价于
“完全遮挡”。它是把已经存在但分散的 blocker、观察、缺失、OUT 规则放入正确的
事务顺序中。

本文件只写设计说明，**当前这次不修改生产代码、不修改超参数文件**。实施时若按
第 11 节新增超参数，必须同步更新《超参数位置与调节说明.md》。

## 1. 最高优先级：当前已经有效的功能很好，绝对不能改坏

**当前代码已经实现了很多正确且重要的功能。下一次修改只能在这些能力之上补齐
遮挡生命周期，绝对不能把原来已经有效的功能改坏。**这不是推倒重写 3.0，也不是
为了本次案例放松所有身份、IN、MOVED 或 OUT 防线。

以下行为是不可回归基线，必须保留并继续通过已有回放：

- 正式 `inventory_`、操作期 `working_inventory_` 和
  `operation_start_inventory_` 的隔离；手操作期间绝不能提前写正式库存；
- `replace_all()` 仍是一次操作唯一的正式库存提交边界；
- `NORMAL`、`HAND_PARTIAL_BLOCKED`、`HAND_FULL_BLOCKED`、`CONTACT_*`、旧 C
  的原位恢复、灰区静态结算、reappear、轨迹与连续确认规则；
- 旧物 `MOVED` 的既有确认门槛和 `confirmed_moved_ids_` 语义；
- 新 D 的 C-D alias、quarantine、连续无手直接自匹配和“没有充分 D 证据绝不
  `IN`”的防线；
- 跨类别低分重复框的只读 identity hint；它不能删除 YOLO detection，也不能用
  遮挡结论反向认定旧物身份；
- 普通两帧无手 `OUT`、同类可见数量收尾、低置信度假 `IN` 防御、小位移容忍；
- `base_box` 是可靠完整位置，`box` 可以是最近直接观察到的局部框；
- 已有矩形差集并集 `fully_covered_by()`；绝不能退化为多个交集面积相加；
- `IN`、`OUT`、`MOVED`、`OCCLUDED`、`REVEALED` 仍只在正式无手结算提交时
  发布，不能在 HAND 阶段发事件；
- YOLO 业务输入、OSD、截图和 trace；身份或遮挡仲裁不能删检测框、改检测顺序或
  改变显示层。

以下做法明确禁止：

- 不能只把 `FLOW3_CONFIRMED_OCCLUSION_EDGE_RESIDUAL_PX` 从 8 调大到 19、20
  或更大来碰巧通过本例；这会把很多缺口较大的部分重叠误写成完整遮挡；
- 不能把 `block_ids` 非空直接当成 `OCCLUDED`，也不能让 `block_ids` 非空的物品
  永久免于 OUT；
- 不能把 `old.status == OCCLUDED` 单独当作历史完整覆盖证明；必须有已提交的
  blocker 证据；
- 不能用目标 C 自己的 detection 去反向证明 A 已移动或已入库；
- 不能让未确认 D、quarantined D、手框、预计框、路径中间点、低分重复框成为正式
  blocker；
- 不能全局放宽/收紧 `strict_match_box()`、`partial_match_box()`、
  `track_match_box()`，不能提高全局 YOLO/NMS 阈值，也不能降低 D、MOVED、OUT
  的确认帧数；
- 不能用 item_id、map 遍历顺序、detection 数组顺序或“等待太久”强行结束身份
  歧义；
- 不能把所有新条件继续堆进 `session_settlement.cc` 的大函数。遮挡几何、遮挡
  因果、无手 OUT、手期证据和正式提交必须按职责拆开。

## 2. 最新实机日志已经证明的根因

### 2.1 本次“橙子移入，苹果被 OUT”的事实链

最新回放中：

```text
item#5 orange:
    operation-start base_box ~= (878,258)-(1065,443)
    已正确确认 MOVED 到 ~= (607,269)-(845,510)

item#6 apple:
    operation-start base_box ~= (612,250)-(790,425)
    最终无手帧没有合法直接 observation
```

目标苹果的可靠框被移动后的橙子横向完整覆盖，但在顶部留下约 19px 的矩形残余。
这并不意味着实物一定露出：检测框边缘、物体轮廓、透视和前景框的尺寸都可能让
真实完全遮挡在二维矩形上留下边界带。现场画面中苹果确实已经看不见。

日志已经清楚说明当前状态机实际上完成了前景关系，但没有完成可见性结算：

```text
target=6
historical=[]
effective=[5]
added=[5]
observed=0
after=(strict=0 edge=0 full=0)
allow-occluded=0
```

也就是说：

```text
item#5 的身份正确，MOVED 正确；
item#5 -> item#6 的 block_ids 关系也已经正确写入候选；
但现有“严格覆盖或 8px 边缘残余”不成立；
于是 item#6 仍被当作 VISIBLE 的缺失旧物；
随后 visible-count / direct-missing 的两帧 OUT 链正常地把它删除。
```

最终得到的是：

```text
MOVED(item#5 orange) + OUT(item#6 apple)
```

而业务上正确的结果应为：

```text
MOVED(item#5 orange) + OCCLUDED(item#6 apple)
```

### 2.2 它和上次“blocker 移走后没有 REVEALED”是同一个问题

上次的方向是：

```text
历史上 A 已使 C 正式 OCCLUDED；
A 本轮已正确 MOVED 离开；
C 也已经有合法 direct observation；
但 before 只按严格几何重新计算，历史 edge-residual 的正式遮挡事实丢失；
所以 C 无法 REVEALED。
```

本次的方向是：

```text
A 本轮已正确 MOVED 进入 C 前方；
C 失去 direct observation；
但 after 只接受严格/极窄边缘几何，前景关系没有升级为正式遮挡；
所以 C 被普通 OUT 链删除。
```

两者共同暴露的不是身份错误：本次 `item#5` 的 `MOVED` 是正确的，新的 D 也没有
被错误入库。共同缺口是：

```text
当前实现把“已确认 blocker 关系的变化”与“目标可见性/OUT 的最终裁决”分开了；
且将正式遮挡完全等同于某一帧的严格矩形布尔结果。
```

因此此前修改并不是白做：它保住了真实移动身份、D guard、历史关系和一部分
`REVEALED` 路径。只是它还没有把“移入导致消失”和“移出导致出现”放进同一套
生命周期计划。这正是本文件要补齐的内容。

## 3. 统一后的业务模型与不变量

### 3.1 必须区分四种事实，不能继续混用

```text
Detection observation
    当前帧某个 YOLO 框，尚未必然属于某个库存 item。

Identity fact
    当前 detection 已经按既有 C/D/MOVED 规则合法归属到旧 item 或已确认 D。

Front relation
    已确认 A 位于目标 C 前方的关系，写为 C.block_ids 包含 A.item_id。

Formal visibility fact
    正式库存中 C 是 VISIBLE 还是 OCCLUDED，以及由何种已提交证据成立。
```

其中最重要的约束是：

```text
observation != identity fact
identity fact != front relation
front relation != OCCLUDED
OCCLUDED != OUT 豁免
```

只有依次完成前两层，才可建立第三层；只有第三层加上足够覆盖/消失证据，才可
建立第四层。普通 OUT 只能在第四层没有给出遮挡解释时运行。

### 3.2 `block_ids` 的固定含义

对任意目标 C：

```text
C.block_ids = {A, B}
```

表示 A、B 都是已确认、当前仍位于 C 前方并与 C 可靠 `base_box` 有正面积交集的
库存物品。它是目标侧的有向关系，不写在 A 或 B 上。

固定规则：

```text
confirmed MOVED / confirmed IN 的前景物进入并相交
    -> 可新增 C.block_ids 中的关系。

历史 blocker 未确认移动/OUT、只是当前漏检
    -> 关系不得被静默删除。

历史 blocker 已确认 MOVED 到不再相交处，或正式 OUT
    -> 从 C.block_ids 中移除。

无关操作、目标自己的 detection、HAND 临时框、未确认 D
    -> 都不能单独新增或清空正式关系。
```

`block_ids` 非空仍可以只是部分前景关系。C 是否为 `OCCLUDED`，必须由下节的
正式遮挡证据决定。

### 3.3 正式遮挡需要一个可跨操作使用的已提交证明

当前只保存 `status + block_ids`，而严格几何又会在下一操作重新计算。这会使已经
提交的“边缘残余遮挡”或“检测消失支持的遮挡”在下一操作丢失 before 事实。

下一次实现应给 `InventoryItem` 增加一个**小而明确的正式遮挡证明**。推荐形式如下，
命名可按项目风格微调：

```cpp
enum class OcclusionProofKind {
    NONE,
    STRICT_UNION,
    EDGE_RESIDUAL_UNION,
    DISAPPEARANCE_SUPPORTED,
};

struct OcclusionProof {
    OcclusionProofKind kind = OcclusionProofKind::NONE;
    std::set<int> witness_blocker_ids;
};

struct InventoryItem {
    // 既有字段保持不变。
    ...
    std::set<int> block_ids;
    OcclusionProof occlusion_proof;
};
```

它不是临时轨迹状态，不包含 detection index、手框、分数或预计框；它是随
`InventoryItem` 一起在 `replace_all()` 中提交的正式业务事实。

固定不变量（针对正式提交库存以及本轮 plan 应用后的 `final_items`；HAND/runtime
中的 provisional 状态不受这条持久不变量约束）：

```text
status == VISIBLE
    <=> occlusion_proof.kind == NONE
        && occlusion_proof.witness_blocker_ids 为空。

status == OCCLUDED
    => occlusion_proof.kind != NONE
       && witness_blocker_ids 非空
       && witness_blocker_ids 是 block_ids 的子集。
```

`block_ids` 保存全部当前前景关系；`witness_blocker_ids` 只保存当时真正支撑
“C 已完全不可见”这一正式结论的 blocker 集合。这样多 blocker、部分 blocker 和
跨操作 reveal 都不会被混在一起。

现有 `init_from_backend()` 已明确把外部快照当作新的 VISIBLE 基线，并清空
`block_ids`。在该既有业务约定下，新的 proof 也应同时清空；本轮不假装把它同步到
尚未定义的后台协议。若将来后台需要恢复遮挡关系，必须把 proof 与 `block_ids` 一起
纳入后台合同，不能只传 `status`。

对升级时已有的异常记录：

```text
status == OCCLUDED 但 proof == NONE
```

不能直接把它当作可信历史完整覆盖，也不能立刻改成 VISIBLE。应记录
`legacy-unverified-occlusion` trace，先以历史 blocker 的严格/edge 几何尝试补齐
proof；无法补齐时保持未决，等待一次有因果变化的直接观察或 OUT 证据，避免制造假
`REVEALED`。

### 3.4 遮挡的方向性不变量

```text
VISIBLE -> OCCLUDED
    必须由本轮已确认的前景 A/D 进入或移动到 C 前方引起；
    不能由 C 自己的一张缺失或历史 block_ids 凭空产生。

OCCLUDED -> VISIBLE / REVEALED
    必须由已提交 proof 的 witness blocker 移动、OUT 或被新的前景关系替代后，
    使旧 proof 失效，并且 C 有合法 direct observation；
    不能因 C 自己偶然出现一张检测框而凭空 reveal。

OUT(C)
    只能在 C 没有已经确认或仍在确认中的遮挡解释时发生；
    “被确认前景覆盖且持续消失”必须优先解释为遮挡，而不是普通缺失。
```

这正是用户提出的业务逻辑：没有物品移动走/OUT/位置变化，就不应让原本遮挡的
物品无原因露出；没有已确认物品移入/IN/位置变化，就不应让原本可见的物品无原因
变为遮挡。

## 4. 覆盖事实不能只剩一个 `bool full`

### 4.1 纯几何层应返回完整事实，不写库存

应把 `fully_covered_by()`、边缘残余和覆盖比例抽成只读几何结果。例如：

```cpp
struct CoverageFacts {
    bool strict_full = false;
    bool edge_residual_full = false;
    bool residual_is_outer_boundary_only = false;
    float covered_ratio = 0.0f;       // 目标被 cover 并集覆盖的比例
    float uncovered_ratio = 1.0f;
    std::size_t cover_box_count = 0;
};
```

几何层只接受：

```text
target 的可靠 base_box
已确认 front 的可靠 base_box 集合
```

它不看 `item_id` 顺序、D 状态、手、轨迹、事件或 observation owner，也不修改
`InventoryItem`。

`strict_full` 与现有矩形差集语义完全一致；`edge_residual_full` 继续只使用已有的
`FLOW3_CONFIRMED_OCCLUSION_EDGE_RESIDUAL_PX`。新增的 `covered_ratio` 和
`residual_is_outer_boundary_only` 只为下一节的“检测消失支持”提供输入，绝不能变成
全局身份匹配阈值。

### 4.2 三种可提交的正式遮挡证明

完成身份和前景关系后，正式 `OCCLUDED` 只能由以下三类证明之一建立：

```text
1. STRICT_UNION
   已确认 front 的可靠 base_box 并集严格覆盖 C.base_box。

2. EDGE_RESIDUAL_UNION
   严格覆盖失败，但残余全部是已有 8px 规则允许的外边缘窄条；
   且至少一个参与者是本轮已确认 MOVED/IN front。

3. DISAPPEARANCE_SUPPORTED
   已确认 front 已进入 C 前方；C 在连续无手帧中失去合法 direct observation；
   覆盖并集已达到“近完整、残余只在目标外边缘”的通用几何条件；
   C 没有独立的出库/移动终点证据。
```

第三类不是“只要缺失就遮挡”。它的完整前提见下一节。它解决的正是本例中二维框
留有 19px 边缘、但实物和检测结果都表明苹果已被橙子遮住的情况。

### 4.3 `DISAPPEARANCE_SUPPORTED` 的严格资格

对一个 operation-start 为 VISIBLE 的 C，只有全部满足时才可以建立该 proof：

1. 至少一个 front 是本轮已经完成既有身份确认、且在当前无手帧直接出现的
   `MOVED` 旧物，或满足既有所有 D guard 的确认 `IN`；
2. 该 front 的最终可靠 `base_box` 与 C 的 operation-start `base_box` 有正面积
   交集，并按本业务“后进入/已确认移动到此处的物品在前”的顺序建立关系；
3. C 本帧没有合法 direct observation；同类 owner 歧义、C-D alias、被更强 owner
   预约的框都属于“未观察确定”，不能假装成消失；
4. C 没有更高优先级的自身终局证据：例如 C 已确认 `MOVED` 到另一个终点，或有
   独立、无冲突的取出路径。仅有 `HAND_FULL_BLOCKED`、手靠近或一次普通缺失不是
   自身出库证据；
5. 可靠前景框并集的覆盖比例达到专用近完整阈值，且所有未覆盖残片只接触 C 的
   外边界，不能有内部洞或两物体之间的缝；
6. 相同 target、相同 witness 关系和连续可比的前景框，在既有
   `FLOW3_NO_HAND_OUT_MISSING_FRAMES` 张无手帧中持续成立；
7. 任一帧 C 重新获得合法 direct observation、front 身份失效、front 不再相交、
   target 有独立终局路径或出现歧义时，候选立即撤销，不能留下永久 OUT 豁免。

本例会满足上述条件：`item#5` 已正确 `MOVED`，其最终框与 `item#6` 高比例重叠，
`item#6` 连续两张无手帧都无合法 direct observation，且没有自身的移动终点。因此
应建立：

```text
item#6.block_ids = {5}
item#6.occlusion_proof = DISAPPEARANCE_SUPPORTED({5})
item#6.status = OCCLUDED
```

而不是进入 `OUT(item#6)`。

### 4.4 近完整条件不是“把部分遮挡当完全遮挡”

必须同时满足：

```text
covered_ratio 足够高
AND 所有残余只在 target 外边界
AND target 连续合法缺失
AND front 已确认且当前直接出现
AND target 没有独立 exit evidence
```

因此以下情况仍不能建立 `DISAPPEARANCE_SUPPORTED`：

- 前景只遮住 C 的 30% 或一小角，C 只是一次漏检；
- 目标框内部有明显未覆盖洞；
- front 只是未确认 D、HAND 框或低分跨类别重复框；
- C 有自己的确认移动终点、真实取出轨迹或未决 owner 冲突；
- C 下一帧重新被合法观察到；
- 只是历史 `block_ids`，本轮没有确认前景变化。

## 5. 单一的遮挡生命周期事务顺序

### 5.1 当前顺序为什么会出错

当前无手路径大致存在以下碎片：

```text
可见数量 OUT 预处理
-> detection owner / MOVED / D 结算
-> 直接把已观察 item 写成 VISIBLE
-> refresh_confirmed_blockers_()
-> 普通 OUT / visible-count OUT
-> 可能再 refresh_confirmed_blockers_()
-> 删除 pending OUT
-> 生成事件
```

这会出现两个危险窗口：

```text
1. 前景关系已经成立，但 full bool 尚未成立，目标先进入 OUT 计数；
2. 已提交 OCCLUDED 的历史事实，又被当前一帧严格几何重新否定，导致 reveal
   的 before 事实消失。
```

下一次实现必须把“关系变化、可见性决定和 OUT 资格”放入同一个只读计划中，在
任何 `pending_out_ids_` 删除 `final_items` 之前完成。

### 5.2 推荐的纯计划结构

推荐新增一个只存在于无手结算调用中的 `OcclusionLifecyclePlan`。它可以复用现有
`BlockerTransitionPlan` 的一部分字段，但不应继续让 helper 直接修改
`final_items`：

```cpp
enum class VisibilityDecision {
    KEEP_VISIBLE,
    KEEP_OCCLUDED,
    ENTER_OCCLUDED,
    REVEAL_VISIBLE,
    PENDING_OCCLUSION_EVIDENCE,
    PENDING_REVEAL_OR_OUT,
};

enum class OutDisposition {
    NORMAL_OUT_EVIDENCE,
    HOLD_FOR_PENDING_OCCLUSION,
    BLOCKED_BY_CONFIRMED_OCCLUSION,
    START_AFTER_OCCLUSION_LOSS,
    NOT_APPLICABLE,
};

struct TargetOcclusionPlan {
    int target_id = -1;
    std::set<int> historical_blocker_ids;
    std::set<int> effective_blocker_ids;
    std::set<int> added_blocker_ids;
    std::set<int> removed_blocker_ids;
    std::set<int> moved_blocker_ids;
    CoverageFacts before_geometry;
    CoverageFacts after_geometry;
    OcclusionProof before_proof;
    OcclusionProof proposed_proof;
    bool valid_direct_observation = false;
    bool observation_ambiguous = false;
    bool target_has_independent_exit_evidence = false;
    int matching_missing_frames = 0;
    VisibilityDecision visibility = VisibilityDecision::KEEP_VISIBLE;
    OutDisposition out = OutDisposition::NORMAL_OUT_EVIDENCE;
};
```

这个计划只是计算结果：不分配 detection owner、不创建 D、不写 `InventoryItem`、
不发事件。这样可以避免现在同一帧反复调用会修改 `final_items` 的
`refresh_confirmed_blockers_()`，也避免 OUT 和遮挡互相回写。

### 5.3 正确的无手结算顺序

下一次实现的实际顺序必须固定为：

```text
第 1 步：身份计划
    按现有 owner 优先级完成 detection -> old C / confirmed D 的预约，
    完成既有 MOVED、D、C-D alias 和跨类别 duplicate 防线。

第 2 步：确定自身事实
    得到当前无手帧中真正已确认的 MOVED、IN、已确认 OUT 候选、
    合法 direct observation 和各旧 C 的独立 exit evidence。

第 3 步：构建 blocker 关系图
    从 operation_start 的历史 block_ids 出发；
    删除已确认 OUT 或确认移至不相交处的 blocker；
    添加本轮已确认且当前直接出现的 MOVED/IN front；
    得到每个 C 的 effective_blocker_ids、added/removed/moved 集合。

第 4 步：构建 OcclusionLifecyclePlan
    先评价历史已提交 proof 是否仍有效，再评价本轮新的 strict/edge/
    disappearance-supported proof；同时为每个 target 得到 OUT disposition。

第 5 步：在 plan 已知后才推进 OUT 证据
    confirmed/pending occlusion 的 target 不得进入或继续普通 direct-missing、
    visible-count OUT；proof 失效且没有 direct observation 的 target 才从
    “遮挡失效后的缺失证据”重新开始。

第 6 步：一次性应用 plan
    把最终 block_ids、proof、status、base_box、pending OUT 写到 final_items/
    runtime；此前不能把 observation 直接写成正式 VISIBLE。

第 7 步：按因果顺序生成事件，再 replace_all()
    先发布 MOVED/OUT/IN 等前景自身变化，再发布 OCCLUDED/REVEALED；
    全部通过后才原子提交库存。
```

这不是单纯调整函数调用的表面顺序。第 3 至第 5 步必须使用同一份纯 plan，保证
同一个前景变化不会在“判遮挡”时存在、在“判 OUT”时又被忽略。

### 5.4 blocker OUT 与多层关系的稳定求值

一个 blocker A 的正式 OUT 会使另一个目标 B 的 proof 失效；而 B 本身又可能是
更深层 C 的 blocker。不能通过 map 顺序决定谁先删。

推荐方式是在纯 plan 内做有限的、单调的求值：

```text
初始集合：已由自身既有证据确认的 MOVED / IN / OUT 候选；
-> 计算所有 target 的 blocker 图和遮挡保护；
-> 删除“被 confirmed/pending occlusion 保护”的 OUT 候选；
-> 用剩余 OUT 候选重新计算 blocker 图；
-> 直到 OUT 候选集合不再变化，再一次性应用。
```

每轮只会移除不再合法的 OUT 候选，不靠 timeout 或 item_id 强行收敛，因此集合有限
且会停止。若某个环无法由既有证据打破，应保持未决并 defer commit，而不是强行
输出 OUT 或 OCCLUDED。

## 6. 前态、后态和两种方向的统一判定

### 6.1 前态不应重新用一帧几何否定已提交事实

对 operation-start 为 OCCLUDED 的 C：

```text
before_proof = C.occlusion_proof
before_full  = before_proof.kind != NONE
```

它的含义是“上一轮已经正式提交 C 被这些 witness 遮挡”，不是“本帧重新跑一次严格
矩形是否仍然恰好完整”。这正是上一轮 edge-residual reveal 漏掉的前态。

当然，不能只看 `status == OCCLUDED`：必须有有效 proof 和至少一个仍可解析的
witness blocker。没有 proof 的 legacy 数据按第 3.3 节保守处理。

### 6.2 后态由当前已确认关系和当前证据产生

对本轮 after：

```text
effective_blocker_ids
    = 仍有效历史 blocker
      + 本轮已确认、当前直接出现的 MOVED/IN front
      - 已确认 OUT 或确认移至不相交处的 blocker。

after_proof
    = STRICT_UNION / EDGE_RESIDUAL_UNION /
      DISAPPEARANCE_SUPPORTED 中唯一已满足的一种。
```

如果多个前景物联合覆盖 C，proof 的 `witness_blocker_ids` 必须记录真实参与的集合。
A 移走但 B 仍足够覆盖时，after proof 仍存在，C 继续 OCCLUDED，不能 reveal。

### 6.3 决策表

| operation-start C | 当前 observation 与因果事实 | 正确正式决定 | OUT 处理 |
|---|---|---|---|
| `VISIBLE` | 有合法 direct observation；即使有部分 blocker | `VISIBLE`，保留部分 `block_ids` | 不计 OUT |
| `VISIBLE` | 无 direct observation；strict/edge proof 成立 | `ENTER_OCCLUDED` | 清零/撤回未提交 OUT |
| `VISIBLE` | 无 direct observation；近完整外边缘残余 + 已确认 front + 连续消失 | `ENTER_OCCLUDED`，proof 为 `DISAPPEARANCE_SUPPORTED` | 清零/撤回未提交 OUT |
| `VISIBLE` | 无 direct observation；只有部分交集或证据歧义 | 先 `PENDING_OCCLUSION_EVIDENCE`，失败后才走既有 OUT | 不得抢先确认 OUT |
| `OCCLUDED` | 历史 proof 的 witness 仍有效，或新 proof 替代它 | `KEEP_OCCLUDED` | 不计 OUT |
| `OCCLUDED` | proof 失效，且 C 有合法 direct observation | `REVEAL_VISIBLE` | 不计 OUT，发布 REVEALED |
| `OCCLUDED` | proof 失效，C 仍无 direct observation | `PENDING_REVEAL_OR_OUT` | 从遮挡失效时重新累计 OUT，不能带入遮挡期间计数 |

这里的“连续消失”与“遮挡失效后重新累计 OUT”使用不同的运行时证据容器，不能混用
`visible_count_missing_counts_`、普通 track 的 missing count 或旧的
`occlusion_loss_missing_counts_`。

### 6.4 目标自身有移动/出库证据时的优先级

若 C 自己存在独立终局证据，则不能因为另一个 A 的框与 C 原位置重叠就把 C 强行
写成 OCCLUDED。优先级应为：

```text
C 自己已经确认 MOVED 到合法终点
    > C 的正式位置已改变，按自身 MOVED 结算。

C 有独立、无 owner 冲突的出库路径
    > 保持 OUT 未决/既有 OUT 规则；不创建 disappearance-supported proof。

C 的身份仍有 alias / owner 歧义
    > 同时不确认 OCCLUDED、不确认 OUT，继续 defer。

C 只有手覆盖、没有自身终点，且 A 已确认移入并连续解释其消失
    > 优先建立遮挡，而不是 OUT。
```

最新 `item#6` 属于最后一种，因而应该保护并最终确认遮挡。

## 7. 需要收敛或移除的现有碎片逻辑

本节不是要求一口气删除所有代码。正确实施顺序是先用新的纯 plan 覆盖全部回放，
再删除被完全替代的窄补丁，避免同时存在两套互相矛盾的遮挡/OUT 规则。

### 7.1 observation 不得直接写正式 VISIBLE

当前无手结算在 owner 绑定后会先把 observed item 写成 `VISIBLE`，随后再由
`refresh_confirmed_blockers_()` 尝试恢复 OCCLUDED。这种“先写状态、后修正”的方式
正是逻辑顺序混乱的来源之一。

修改后应区分：

```text
observed projection
    本轮候选的 box、score、base_box 更新，供 identity 和 geometry 使用。

formal visibility application
    只在 OcclusionLifecyclePlan 完成后写入 final_items.status/proof。
```

一个历史 OCCLUDED 的 C 即使有一张 observation，只要 blocker proof 未失效，也只能
把该框当作临时 observation，不能先写 VISIBLE 或刷新完整 `base_box`。

### 7.2 HAND 阶段不能直接形成正式 `block_ids/status`

必须审计并收敛 `session_hand.cc` 中所有直接写：

```text
item.status = OCCLUDED / VISIBLE
item.block_ids.insert(...) / clear()
```

尤其是 `apply_suspect_cover_evidence_()`、`confirm_rearrange_()`、回滚和 hand
release 路径。HAND 阶段可以保留现有轨迹、接触、覆盖、reappear、D 证据，但只应写
入 runtime/provisional evidence，不应直接构造将被下一操作当成正式历史的 blocker
关系或 visibility 状态。

例如可保留一个 operation-local 的：

```text
PendingFrontEvidence
    target_id
    candidate_front_id / suspect runtime
    hand-time geometry hint
```

它仅帮助无手阶段理解为何应继续收集证据，不能绕过 D/identity 确认，也不能发出
OCCLUDED 事件。最终 `block_ids`、proof 和 status 的唯一写入点应是正式无手计划应用。

移动物品自身的 `block_ids.clear()` 也必须谨慎：关系存在于被挡的目标侧，移动 A
不等于 A 自己不再被其他物品挡住。只能由统一关系图更新每个 target 的集合。

### 7.3 `prepare_visible_count_settlement_()` 必须拆分为“观察分配”和“OUT 结算”

最新错误中，`visible-count` 在遮挡 lifecycle 最终决定之前已经把 `item#6` 当成
同类缺额候选，并在第二帧确认 OUT。该机制本身用于解决同类可见实例不足，仍然有
价值；问题只是它过早拥有了 OUT 决定权。

应拆成两个职责明确的阶段：

```text
prepare_visible_count_observation_plan_()
    只完成同类可见 detection 的一对一保留/预约；
    不增加缺失计数，不写 pending_out_ids_。

apply_visible_count_missing_evidence_(out_disposition)
    在 OcclusionLifecyclePlan 已经给出每个 target 的 OUT disposition 后，
    才推进、暂停、撤回或确认该类别的缺额 OUT 证据。
```

当 target 是 `PENDING_OCCLUSION_EVIDENCE` 时，第一帧的缺失可被记录为同一份待决
证据，但不得提交 OUT；第二帧若遮挡证据成立则转为 OCCLUDED，若失败则按原两帧
缺失语义完成/继续 OUT。这样不会把所有 OUT 平白延迟，也不会让遮挡先被 OUT 删除。

### 7.4 用统一 plan 替代窄 OUT 遮挡补丁

以下函数/路径的职责应逐步合并，而不是再叠加更多 if：

```text
refresh_confirmed_blockers_()
defer_direct_missing_out_for_possible_occlusion_()
advance_occlusion_loss_out_evidence_()
fully_occluded_item_ids 的单一 bool 保护
```

推荐迁移结果：

```text
refresh_confirmed_blockers_()
    -> 纯 blocker/geometry 构建器，或由新的 occlusion 模块替代；

defer_direct_missing_out_for_possible_occlusion_()
    -> 被 PENDING_OCCLUSION_EVIDENCE 的统一 OUT disposition 替代；

advance_occlusion_loss_out_evidence_()
    -> 变成 “proof 已失效后的 OUT evidence” 的一个明确分支；

fully_occluded_item_ids
    -> 由 TargetOcclusionPlan.visibility/out 表达，不再是唯一信息载体。
```

不能先删除旧保护再写新计划。应先让新 plan 在回放中输出相同或更严格的保护结果，
切换调用点，最后删掉不再可达的旧补丁和重复 trace。

## 8. 建议的文件职责与解耦

代码不必、也不应该全部挤在同一个文件中。此次属于遮挡生命周期的实质性收敛，
推荐按以下职责拆分：

| 文件 | 应承担的工作 | 不应承担的工作 |
|---|---|---|
| `include/inventory.h` | `OcclusionProofKind`、`OcclusionProof` 和 `InventoryItem` 的正式不变量字段 | HAND 轨迹、D owner 或纯几何算法 |
| `include/session_internal.h` | `CoverageFacts`、`TargetOcclusionPlan`、`OcclusionLifecyclePlan` 的内部声明 | 持久数据库写入或 YOLO 阈值 |
| 新建 `src/session_occlusion.cc` | 纯覆盖几何、关系图构建、历史 proof/after proof 评价、生命周期 plan、trace 格式化 | detection identity 分配、直接提交库存 |
| `src/session_settlement.cc` | 组织身份结果、调用 lifecycle plan、应用 plan、安排事件、原子提交 | 重新实现手期轨迹、复制几何差集 |
| `src/session_no_hand.cc` | 保持 owner/C-D/D/MOVED 证据；把可见数量逻辑拆为观察保留和 plan 后的 OUT evidence | 根据遮挡反向认领 detection |
| `src/session_hand.cc` | 只记录 HAND/CONTACT/前景候选的 provisional evidence；移除正式 blocker/status 直写 | 发布 OCCLUDED/REVEALED 或提前写正式库存 |

项目 CMake 当前通过 `src/*.cc` 自动收集源文件；新增 `session_occlusion.cc` 后仍应核对
板端构建和主机 replay 编译列表，不能假定测试目标自动包含它。

## 9. 必须新增的日志与回放

### 9.1 统一 trace

新增或替换为一条只读 `OCCLUSION-LIFECYCLE` trace。每个存在历史/当前关系或待决
遮挡的 target 至少输出：

```text
target
start-status
historical blockers / effective blockers / added / removed / moved
before proof kind + witness ids
before geometry: strict / edge / covered ratio / boundary residual
after geometry: strict / edge / covered ratio / boundary residual
direct observation / ambiguity / independent exit evidence
pending disappearance count
proposed proof kind + witnesses
visibility decision
OUT disposition
reason
```

本次实机理想日志应能读成：

```text
target=6 start=VISIBLE
effective=[5] added=[5]
observed=0 independent-exit=0
after=(strict=0 edge=0 covered-ratio~=0.89 boundary-residual=1)
pending-disappearance=2/2
proof=DISAPPEARANCE_SUPPORTED witnesses=[5]
visibility=ENTER_OCCLUDED out=BLOCKED_BY_CONFIRMED_OCCLUSION
```

而 blocker 离开后的理想日志应为：

```text
target=4 start=OCCLUDED
before-proof=EDGE_RESIDUAL_UNION witnesses=[2]
removed/moved=[2]
observed=1
after-proof=NONE
visibility=REVEAL_VISIBLE
```

日志只能解释已经计算出的 plan，不能成为按 detection 顺序/等待时长选择 owner 的
业务依据。

### 9.2 核心新增回放

所有回放都要断言：库存数量、item_id、`status`、`base_box`、`block_ids`、
`occlusion_proof`、事件种类、事件次数、提交状态和事件顺序。

1. **本次现场逆方向回放：近完整边缘残余的移入遮挡**

   ```text
   初始：A=apple 可见，B=orange 可见。
   操作：B 按既有 MOVED 门槛确认移到 A 前方；
   几何：B 覆盖 A 约 89%，只留下 A 顶部外边缘残余；
   观察：A 连续两张无手帧无合法 detection，B 连续直接出现。
   ```

   断言：

   ```text
   MOVED(B) 存在；
   OCCLUDED(A) 存在且仅一次；
   OUT(A) 不存在；
   A.status == OCCLUDED；
   A.block_ids == {B}；
   A.proof.kind == DISAPPEARANCE_SUPPORTED；
   MOVED(B) 在 OCCLUDED(A) 之前；
   库存数量不减少。
   ```

2. **保留上次正方向回放：历史 blocker 离开后 reveal**

   使用真实第一事务建立 `STRICT_UNION` 或 `EDGE_RESIDUAL_UNION`，第二事务让
   blocker MOVED/OUT 离开且 target 有合法 direct observation。

   ```text
   MOVED/OUT(front) 在 REVEALED(target) 之前；
   target.status == VISIBLE；
   target.block_ids 只保留仍有效 blocker；
   target.proof == NONE；
   没有假 IN/OUT。
   ```

3. **部分关系对照**

   已确认 A 只覆盖 C 的一部分，C 仍有合法 direct observation：

   ```text
   C.status 仍为 VISIBLE；
   C.block_ids 可包含 A；
   不产生 OCCLUDED、REVEALED 或 OUT。
   ```

4. **一次漏检对照**

   A 近完整相交，但 C 只缺失一张无手帧、下一帧重新合法出现：

   ```text
   不产生 OCCLUDED；
   不产生 OUT；
   pending disappearance evidence 被清空。
   ```

5. **真实取出与前景相交对照**

   C 有独立、无冲突的取出路径；另一 A 只在 C 原位置部分/近完整相交：

   ```text
   不得把 C 错判 OCCLUDED；
   仍按现有 OUT 规则或保持未决，取决于既有自身证据；
   不得靠遮挡覆盖 C 的身份/OUT 证据。
   ```

6. **多 blocker 并集**

   A+B 联合遮挡 C；A 离开而 B 仍足够覆盖：C 必须继续 OCCLUDED；只有最后使
   proof 失效的 blocker 离开且 C 被观察到时，才一次 REVEALED。

7. **不变 blocker 下的假 reveal 对照**

   C 历史上 OCCLUDED，witness 未移动/OUT；检测器偶然给 C 一张局部框：

   ```text
   C 继续 OCCLUDED；无 REVEALED；base_box 不被局部框污染。
   ```

8. **D / 同类 / 跨类别保护回归**

   低分苹果/橙子近同框、真实旧 A 终点、未确认 D、C-D alias、真实 D IN、普通
   OUT、HAND、CONTACT、小位移、已有严格完整遮挡和当前 edge-residual reveal
   回放全部继续通过。

### 9.3 事件顺序不变量

正式事件由同一事务生成，但必须按因果依赖排序：

```text
MOVED(A) -> OCCLUDED(C)
IN(D)    -> OCCLUDED(C)
MOVED(A) -> REVEALED(C)
OUT(A)   -> REVEALED(C)
```

不能因为 map/item_id 遍历使 C 的 visibility 事件出现在造成它的前景事件之前。

### 9.4 位置无关性与“中间区域失败”的诊断要求

最新补充现象是：相似的遮挡/露出操作在左上、右上可以成功，而在画面中间失败。
当前源码检索没有发现按左、中、右划分业务区域的分支；因此不能直接断言是坐标条件
本身导致了错误。更可能的情况是位置改变了检测框形状、透视缩放、手框覆盖范围、
同类物品邻居数量或 owner 竞争，进而把同一操作送入了不同的身份/遮挡/OUT 路径。
这仍然属于同一套生命周期必须覆盖的输入变化，不能用“中间区域专属补丁”掩盖。

实现必须满足以下位置无关性不变量：

```text
同一个业务动作、相同的物品相对几何和相同的证据时序，
只平移到左上/中间/右上后，必须使用同一套 identity -> blocker -> visibility -> OUT 逻辑。

不得根据绝对 x/y、画面象限、镜像后的口头方向或 item_id 选择不同阈值、不同事件路径
或不同的 OUT 保护期。

位置差异只允许通过归一化几何、可靠 base_box、已确认身份和实际手/无手证据体现，
不能改变生命周期规则本身。
```

在修改生产代码前，必须把位置因素拆成可证伪的回放和 trace：

1. **平移不变量回放**：构造同一组 target/front 框、相同尺寸和相同覆盖比例的左上、
   中间、右上三组输入，逐帧保持 MOVED/IN、直接观察缺失和无手帧数一致。三组必须
   得到完全相同的 `OCCLUDED`、`REVEALED`、`OUT` 决策和事件顺序；只有坐标数值不同。
2. **拓扑隔离回放**：中间位置分别测试一个孤立物品和同类密集邻居。若孤立样本成功、
   密集样本失败，根因在同类 owner、C-D alias 或 visible-count 竞争，不在遮挡几何。
3. **几何隔离回放**：保持邻居数量和身份安排不变，只改变前后框的尺寸、边缘残余和
   覆盖比例，记录严格覆盖、edge residual、并集覆盖比例和内部空洞；确认失败是否
   只是检测框未达到既有 proof 条件。
4. **手证据隔离回放**：保持物品几何不变，比较手框是否同时覆盖多个物品、HAND/
   CONTACT 是否改变、release 后是否有相同数量的合法无手帧。不能把手框临时状态当
   正式 blocker。
5. **坐标变换检查**：对原始相机坐标、letterbox/缩放反变换后的业务框和 OSD 框做
   对照；镜像只影响显示方向，不得改变身份或遮挡计算坐标。若变换有偏差，应修复
   输入/坐标管线并单独回归，不能在生命周期中增加区域补偿。

每个 `OCCLUSION-LIFECYCLE` trace 还必须带上以下诊断字段，才能定位“中间失败”究竟
发生在哪一层：

```text
target/front 的原始与归一化框、框宽高和中心
covered_ratio、strict、edge residual、外边界残余/内部洞
历史/有效/新增/移除 blocker
同类候选数、owner kind、alias/quarantine/ambiguity
手框覆盖率、HAND/CONTACT 状态
合法 direct observation、pending missing、visible-count 是否启动
最终 visibility decision、OUT disposition 和 reason
```

禁止以下“修复”：

- 为中间 x/y 区间单独放宽 `FLOW3_CONFIRMED_OCCLUSION_EDGE_RESIDUAL_PX` 或新增
  中间专用覆盖阈值；
- 通过调高/调低全局 YOLO、NMS、owner 或 OUT 阈值来碰巧改变某个位置的结果；
- 仅凭“中间区域经常失败”把所有中间缺失都解释成遮挡，绕过 D、MOVED、身份歧义和
  独立出库证据。

如果位置无关回放证明生命周期决策一致，但实机中间区域仍系统性漏检，则应把它归类
为检测模型、光照、透视或坐标变换问题，另行处理；生命周期代码只能消费已确认的
证据，不能替模型补造 detection。无论检测层是否另有改进，本文件第 1 节列出的
当前有效身份、D guard、MOVED、OUT、HAND/CONTACT 和既有遮挡成功路径都必须保持。

## 11. 超参数约束

本次只是写指导文件，尚未修改任何超参数。实施 `DISAPPEARANCE_SUPPORTED` 时，建议
新增且仅新增一个语义明确的参数：

```cpp
// 仅用于“已确认 front + target 连续直接缺失”的近完整遮挡证明。
// 不参与 identity、D、MOVED、普通 OUT、YOLO/NMS 或 block_ids 关系建立。
constexpr float FLOW3_CONFIRMED_OCCLUSION_DISAPPEARANCE_MIN_COVER_RATIO = 0.85f;
```

`0.85` 是保守的初始建议值：它能覆盖本次约 0.89 的现场形状，但仍要求残余只在
外边界、前景身份已确认和连续缺失，不能单独把普通部分重叠变成遮挡。它必须先由
第 9 节的正反回放验证，不能只看这一次实机日志确定最终值。

仍然复用：

```text
FLOW3_CONFIRMED_OCCLUSION_EDGE_RESIDUAL_PX
FLOW3_NO_HAND_OUT_MISSING_FRAMES
```

前者继续服务于纯几何的极窄边缘残余；后者继续提供连续无手时序确认。不要把两者
调大/调小来替代生命周期重构，也不要复用 `FLOW3_D_PARTIAL_COVER_RATIO` 或手覆盖
阈值作为这个新 proof 的阈值。

实际加入该参数时必须同步更新《超参数位置与调节说明.md》，写清：默认值、只作用
于 `DISAPPEARANCE_SUPPORTED`、所需日志、与现有 edge residual 的区别、调大/调小的
误判风险和对应边界回放。若最终实现不需要新增参数，则该说明文件无需为本轮改动。

## 12. 完成条件与核心原则

本轮只有在同时满足以下条件时才算完成：

- 已确认前景物移入后，目标持续消失能被正确结算为 `OCCLUDED`，不会先被 OUT；
- 已确认 blocker 离开后，目标合法重现能正确结算为 `REVEALED`；
- 两个方向共用同一份 blocker 图、proof 和 OUT disposition，不是两个专属补丁；
- `block_ids` 跨操作只按确认前景关系维护，部分关系不伪装完全遮挡；
- 任何正式 OCCLUDED 都有可检查的已提交 proof，历史 before 不再依赖一帧严格几何；
- 未确认 D、HAND 框、低分重复框、目标自己的 detection 和历史关系都不能伪造因果；
- 目标有自身移动/取出证据或 owner 歧义时，不被遮挡逻辑强行覆盖；
- `MOVED/OUT/IN` 永远先于相关 `OCCLUDED/REVEALED`；
- 相同相对几何与证据时序平移到左上、中间、右上后，遮挡/露出/OUT 决策和事件顺序
  位置无关；若实机仍有位置差异，必须由 trace 定位到检测或坐标管线，不能用区域补丁；
- 当前已经有效的身份、D guard、C-D alias、普通 OUT、HAND/CONTACT、低置信度防线、
  小位移容忍、OSD 和完整回放均无回归；
- 新增代码按职责拆开，而不是继续把所有条件堆进一个源文件。

最终原则是：

```text
先确认是谁移动/入库/出库，
再用这些已确认变化维护前景关系，
再由“目标出现或持续消失”与可靠覆盖证据决定可见性，
最后才允许 OUT 和正式事件提交。

遮挡不是一帧矩形 bool，也不是给 OUT 打的例外补丁；
它是由已确认前景关系驱动、可跨操作保持并可被因果变化解除的正式生命周期。
```
