# 开门与关门的会话流程（2.0）

> 本文件是《另一个版本.md》《track的说明.md》和《快照的说明.md》的外层流程。
> 一次“开门 → 关门”是一个 Session；但本地 `inventory` 不会在关门时清空。


## 1. 持久状态与会话状态

```text
跨关门持续保留的本地状态：
inventory
→ 每个物品的 item_id、cls_id、box、base_box、status、block_ids。

needs_reconciliation
→ 上一次关门前是否存在尚未得到稳定快照的操作。

仅在当前开门 Session 中使用的状态：
item_by_id、track_buffer、frozen_tracks、no_hand_buffer、
track_session_is_ambiguous、operation_pending、initial_check_state。
```

`item_by_id` 只是当前 Session 的索引；每次开门都可由持久的 `inventory` 重建，关门时可以清空。

`initial_check_state` 只用于冷启动首次校验：

```text
WAITING    # 已从后台取得初始库存，尚未完成首次校验
DONE       # 已用 k 帧或 N 帧完成首次校验
SKIPPED    # 第一帧就是手，没有可用无手帧，直接采用后台初始库存
NOT_NEEDED # 本地 inventory 已存在，不需要首次校验
RECONCILE_LOCAL # 本地 inventory 存在，但上次有未结算操作；等待首个正常 N 帧快照补结算
```


## 2. 光线状态

```text
环境较暗 → 冰箱灯亮、画面持续变亮：认为开门；
环境较亮 → 冰箱灯灭、画面持续变暗：认为关门。
```

不能只凭单帧亮度变化判断。应使用两个阈值和连续帧确认，避免自动曝光、灯光闪烁造成误判：

```python
if 连续 open_confirm_frame_count 帧的亮度 > open_light_threshold:
    door_state = OPEN

if 连续 close_confirm_frame_count 帧的亮度 < close_light_threshold:
    door_state = CLOSED
```

通常应满足：

```text
open_light_threshold > close_light_threshold
```

这样会形成迟滞，避免亮度处在临界值时反复开门、关门。


## 3. 开门：优先使用本地库存

开门只执行一次会话初始化，不能在门已打开时反复初始化。

```python
def on_door_open():
    if session_active:
        return

    session_active = True

    track_buffer.clear()
    frozen_tracks.clear()
    clear_snapshot_buffer()
    track_session_is_ambiguous = False
    operation_pending = False

    if 本地 inventory 存在:
        # 本地 inventory 是上次结算后持续保存的库存，直接使用它。
        if needs_reconciliation:
            initial_check_state = RECONCILE_LOCAL
        else:
            initial_check_state = NOT_NEEDED
    else:
        # 只有冷启动、本地从未维护过库存时，才向后台申请初始库存。
        inventory = 向后台申请库存列表()
        保存为本地 inventory
        initial_check_state = WAITING

    item_by_id.clear()
    for A in inventory:
        item_by_id[A.item_id] = A
```

后台库存是本地库存结算后上传得到的。因此本地库存存在时，不需要每次开门都把后台库存与本地库存重新做视觉匹配。


## 4. 冷启动时的首次库存校验

只有 `initial_check_state == WAITING` 时需要首次校验。它的目的只是验证“快照中已经看见的物品”能否在后台初始库存中找到对应的【可见】物品；它不是普通的库存结算。

```text
快照中看见 B
→ 库存中应存在一个【可见】A 与 B 对应。

库存中有 A、但首次快照没有看见 A
→ 不能据此判 A 出库；不修改库存。
```

若快照中的 B 找不到对应可见 A，只记录“首次校验不一致”；不凭这一次校验直接入库、出库或修改 `block_ids`。

### 4.1 正常得到 N 帧首次快照

如果开门后先连续得到 N 帧无手，快照模块会正常返回 `initial_snapshot`：

```python
if initial_check_state == WAITING and initial_snapshot 已生成:
    只验证每个 B 能否对应 inventory 中的一个【可见】A
    initial_check_state = DONE
```

同一个库存 A 在首次校验中最多对应一个快照 B，避免两个快照物品同时“验证”同一个 A。
这里可复用严格匹配 / 局部匹配的候选与双向唯一规则，但它们只用于只读校验，不能写入 `affirm`、`item_id`、`box`、`base_box` 或 `block_ids`。

### 4.2 手先出现时，强行使用已有 k 帧

若首次 N 帧尚未凑满就检测到手，先在清空缓存前处理已有无手帧：

```python
def finalize_initial_check_before_hand():
    if initial_check_state != WAITING:
        return

    if no_hand_buffer 为空:
        # 第一帧就是手；没有可用画面，直接采用后台初始库存。
        initial_check_state = SKIPPED
        return

    # 此时实际只有 k 帧，1 <= k < N。
    # 以实际 k 帧进行投票、平均框和最终小框过滤，不能假装有 N 帧。
    short_snapshot = generate_snapshot_from_frames(no_hand_buffer)
    clear_snapshot_buffer()

    只验证 short_snapshot 中每个 B 能否对应 inventory 中的一个【可见】A
    initial_check_state = DONE
```

这项“用 k < N 帧生成快照”的特例只允许用于冷启动的首次校验。普通手操作结束后的快照仍必须使用连续 N 帧无手。

无论首次校验完成还是跳过，都不能再让之后的正常快照走“首次校验”分支；之后的快照应按正常 Track / 库存结算流程处理。

### 4.3 上一次关门时有未结算操作

若用户操作后立刻关门，上一轮没有得到稳定快照，`needs_reconciliation` 会保留为 `True`。下一次开门虽然本地库存存在，也不能一直跳过快照：

```text
等待首个正常的连续 N 帧无手快照
→ 使用该快照执行一次正式库存结算。
```

对于上一次未结算的操作，没有可用的旧 Track；若本次开门后又发生了新的手操作，则本次新建的 Track 仍会随快照一起冻结并参与结算。其余物品仍可通过严格匹配、局部匹配、遮挡、出库和入库逻辑更新库存。短帧首次校验不能用于这项补结算。


## 5. 开门期间逐帧处理与库存结算

```python
def process_open_frame(item_detections, hand_detections):
    if hand_detections 不为空:
        # 必须在 Track 的有手分支清空 no_hand_buffer 之前调用。
        finalize_initial_check_before_hand()

    # process_frame()：有手时更新 Track；无手时由快照模块累计帧。
    # 只有连续 N 帧无手时才返回 snapshot，否则返回 None。
    snapshot = process_frame(item_detections, hand_detections)

    if snapshot is None:
        return

    if initial_check_state == WAITING:
        # 这是冷启动且从未有手时得到的正常 N 帧首次快照。
        只验证 snapshot 中每个 B 能否对应 inventory 中的一个【可见】A
        initial_check_state = DONE
        return

    if initial_check_state == RECONCILE_LOCAL:
        # 上一轮没有结算完成；本轮必须等待完整 N 帧快照后才补结算。
        freeze_all_tracks()
        settle_inventory(
            inventory=inventory,
            snapshot=snapshot,
            frozen_tracks=frozen_tracks,
        )
        needs_reconciliation = False
        initial_check_state = DONE
        return

    if operation_pending:
        # 稳定快照已经生成；此时才冻结本次尚未结算的 Track。
        freeze_all_tracks()

        settle_inventory(
            inventory=inventory,
            snapshot=snapshot,
            frozen_tracks=frozen_tracks,
        )

        # settle_inventory() 的最后一步会调用 clear_tracks_after_settlement()
        # 并重置 track_session_is_ambiguous 与 operation_pending。
```

`settle_inventory()` 就是《另一个版本.md》中的完整流程：

```text
严格匹配
→ 局部匹配
→ Track 唯一整理配对
→ 遮挡 / 出库 / 入库
→ 隐藏物品恢复判断
```

若手在凑满 N 帧前再次出现，`no_hand_buffer` 会被清空，但 Track 尚未冻结；这视为同一次尚未结算的复合操作，Track 可以继续更新。


## 6. 关门

关门后画面变暗，不能再依靠暗帧生成快照或补做库存判断。

```python
def on_door_close():
    if not session_active:
        return

    if operation_pending:
        # 最后一次手操作没有得到连续 N 帧无手的快照。
        # 暗帧没有可靠视觉信息，不能猜测最终入库、出库或整理。
        记录本次存在未结算操作
        needs_reconciliation = True

    # 上传的是最后一次已经完成结算后的本地 inventory。
    将当前 inventory 发送给后台()

    # 只清理本次开门 Session；inventory 保留到下一次开门。
    item_by_id.clear()
    track_buffer.clear()
    frozen_tracks.clear()
    clear_snapshot_buffer()
    track_session_is_ambiguous = False
    operation_pending = False
    initial_check_state = NONE
    session_active = False
```

若用户刚移动物品就立刻关门，系统没有机会得到最终稳定快照。当前版本不使用关门后的暗帧补算；后台收到的是最后一次已确认结算后的库存，同时记录“本次有未结算操作”。
