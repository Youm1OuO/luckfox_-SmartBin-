# 开关门与后台库存接口实现说明

本文档说明冰箱视觉程序与后台库存接口之间的业务边界、状态机、容错规则和实现细节。

核心目标：

1. 开门时，系统开始一次新的冰箱业务会话。
2. 开门后优先向后台获取上一轮库存清单。
3. 如果后台没有可用库存、返回空、超时或失败，则用第一份无手稳定快照初始化本地库存。
4. 开门期间所有出入库、遮挡、整理判断都只更新本地工作库存。
5. 关门时，系统结束本轮业务会话，并把最终库存清单上传给后台。



一、基本概念
=====================================================================

1. 门状态 DoorState
---------------------------------------------------------------------

门状态由画面亮度判断：
    BRIGHT：
        画面亮，认为冰箱门打开。

    DARK：
        画面暗，认为冰箱门关闭。

实际实现时不要用单帧亮度直接切换状态，必须使用连续帧确认：
    bright_streak >= DOOR_CONFIRM -> 确认开门
    dark_streak >= DOOR_CONFIRM   -> 确认关门


建议：
    DOOR_CONFIRM = 5

这样可以避免灯光闪烁、摄像头曝光变化导致误触发。


2. 业务会话 FridgeSession
---------------------------------------------------------------------

一次开门到下一次关门，称为一个业务会话。
    开门：
        创建或恢复本地工作库存。
        开始接收 YOLO / ByteTrack / 快照输入。

    开门期间：
        只维护本地工作库存。
        不依赖后台实时参与每一次判断。

    关门：
        停止本轮业务判断。
        上传最终本地库存。
        等待下一次开门。


3. 本地工作库存 WorkingInventory
---------------------------------------------------------------------

本地工作库存是开门期间程序实际使用的库存清单。

来源有两种：
    1. 后台返回的上一轮库存清单
    2. 第一份无手稳定快照

注意：
    后台库存不是每帧都查。
    后台库存只在开门时作为初始状态。
    后续业务判断以本地工作库存为准。


4. 稳定快照 stable_snapshot
---------------------------------------------------------------------

稳定快照由多帧 YOLO 检测投票得到。
要求：
    1. 不包含手
    2. 连续多帧检测稳定
    3. 只包含食物/物品，不包含 hand 类别

第一份可用 stable_snapshot 很重要：
    如果没有可信后台库存，它就是本轮业务会话的初始库存。



二、开门流程
=====================================================================

1. 开门触发
---------------------------------------------------------------------

当亮度连续变亮：
    if door_state == CLOSED
    and bright_streak >= DOOR_CONFIRM:
        door_state = OPEN
        start_new_door_session()


2. 开门后立即请求后台库存
---------------------------------------------------------------------

开门时向后台请求上一轮关门保存的库存清单：
    request_backend_inventory(device_id, session_id)

请求应包含：
    device_id
    session_id
    open_time_ms

后台返回建议包含：
    success
    inventory_found
    authoritative
    inventory_version
    inventory_items
    timestamp_ms


3. 后台返回结果分类
---------------------------------------------------------------------

后台返回不能只看 inventory_items 数量。

必须区分以下情况：
    A. 成功返回，并且 inventory_items 非空
        认为有可用后台库存。
        使用后台库存初始化本地工作库存。

    B. 成功返回，但 inventory_items 为空
        默认不要直接认为“冰箱一定为空”。
        更稳妥的处理是：
            视为没有可信后台库存。
            等待第一份无手稳定快照初始化。

        除非后台明确返回：
            authoritative = true
            inventory_found = true
            inventory_items = []

        这才表示后台明确知道上一次关门时冰箱为空。

    C. 请求失败
        视为没有可信后台库存。
        等待第一份无手稳定快照初始化。

    D. 请求超时
        视为没有可信后台库存。
        等待第一份无手稳定快照初始化。

    E. 返回格式错误
        视为没有可信后台库存。
        等待第一份无手稳定快照初始化。


4. 关键规则：空后台库存不能阻塞快照初始化
---------------------------------------------------------------------

这是当前最容易出错的点。

错误做法：
    后台返回 []。
    程序设置 backend_initialized = true。
    后续第一份 stable_snapshot 到来时，认为已经有后台库存。
    但后台库存为空，于是没有把 stable_snapshot 中的物品加入本地库存。
    最终导致本地库存一直为空，后续拿走/整理/遮挡都无法正常判断。


正确做法：
    backend_initialized 只能表示“已有可信后台库存”。

    如果后台返回空列表，但没有明确 authoritative_empty，
    不应该设置 backend_initialized = true。

    应该设置：
        backend_status = NO_TRUSTED_BACKEND

    然后等待第一份无手稳定快照：
        init_inventory_from_first_stable_snapshot(stable_snapshot)


5. 开门初始化状态机
---------------------------------------------------------------------

建议使用明确状态，而不是只用一个 bool。
    enum InitState:
        WAIT_BACKEND
        WAIT_FIRST_STABLE_SNAPSHOT
        READY


开门后：
    init_state = WAIT_BACKEND
    backend_request_start_time = now
    working_inventory.clear()
    snapshot_baseline.clear()
    operation_context.clear()


后台成功返回非空库存：
    working_inventory = backend_inventory
    init_state = WAIT_FIRST_STABLE_SNAPSHOT

说明：
    即使有后台库存，也仍然建议等待第一份无手稳定快照。
    因为需要把后台库存与当前画面做一次对齐：

        当前能看到的 -> VISIBLE
        后台有但当前看不到的 -> OCCLUDED


后台失败、超时、返回空但不可信：
    working_inventory.clear()
    init_state = WAIT_FIRST_STABLE_SNAPSHOT


第一份无手稳定快照到来：
    if init_state == WAIT_FIRST_STABLE_SNAPSHOT:
        if has_trusted_backend_inventory:
            match_backend_inventory_with_snapshot()
        else:
            init_inventory_from_snapshot()

        baseline_snapshot = stable_snapshot
        operation_context = new OperationContext(baseline_snapshot)
        init_state = READY



三、第一份稳定快照初始化规则
=====================================================================

1. 第一份快照必须无手
---------------------------------------------------------------------

如果 snapshot.has_hand == true：
    不允许作为初始化快照。
    只记录 OperationContext 证据。
    继续等待下一份无手 stable_snapshot。


2. 第一份快照可以是 0 件
---------------------------------------------------------------------

如果开门时冰箱确实为空，第一份无手稳定快照可能是 0 件。

这种情况仍然应该进入 READY：

    working_inventory = []
    baseline_snapshot = empty_snapshot
    init_state = READY

不能因为库存是 0 件就一直等待。

否则空冰箱开门测试会永远进不了业务流程。


3. 无后台库存时的初始化
---------------------------------------------------------------------

如果没有可信后台库存：

    对 stable_snapshot 中每个物品创建本地库存记录。
    状态设为 VISIBLE。
    item_id 使用本地自增 id。
    track_id 可以先设为 -1，后续由 ByteTrack / 快照更新。

伪代码：

    for obj in stable_snapshot.objects:
        inventory.add(
            cls_id = obj.cls_id,
            bbox = obj.bbox,
            score = obj.score,
            status = VISIBLE
        )

    baseline_snapshot = stable_snapshot
    init_state = READY


4. 有后台库存时的初始化
---------------------------------------------------------------------

如果有可信后台库存：

    用第一份 stable_snapshot 和后台库存做匹配。

匹配到：

    后台 item -> VISIBLE
    更新 bbox / score / cls_id

后台有但快照没有：

    后台 item -> OCCLUDED
    保留 item_id

快照有但后台没有：

    视为新物品，加入本地库存。

注意：

    这里不能简单认为“后台没有的快照物品一定是刚放入”。
    因为开门前后台可能没有记录。
    所以开门初始化阶段新增物品只进入本地工作库存，
    不一定立刻上报 ITEM_IN 事件。


5. 初始化阶段是否上报事件
---------------------------------------------------------------------

建议：

    开门初始化阶段不上传 ITEM_IN / ITEM_OUT / MOVED 事件。

原因：

    初始化阶段是在建立本轮业务基准，不是在判断用户刚刚做了什么。

只有 READY 之后，后续 stable_snapshot 与 baseline_snapshot 的差异，
才生成事件。



四、开门期间业务流程
=====================================================================

当 init_state == READY 后，进入正常业务流程：

    1. 每帧运行 YOLO
    2. 每帧运行 ByteTrack
    3. 每帧更新 OperationContext
    4. SnapshotBuffer 生成 stable_snapshot
    5. 跳过 has_hand 快照
    6. 对无手 stable_snapshot 执行：

        diff_snapshots(
            baseline_snapshot,
            stable_snapshot,
            operation_context
        )

    7. 应用事件到本地工作库存
    8. baseline_snapshot = stable_snapshot
    9. 重建 OperationContext


重要规则：

    1. 手出现不代表进入另一套业务流程。
    2. 手只提供 OperationContext 辅助证据。
    3. 出入库/整理最终仍由 stable_snapshot diff 裁决。
    4. 同一个 stable_snapshot 只能消费一次。



五、关门流程
=====================================================================

1. 关门触发
---------------------------------------------------------------------

当亮度连续变暗：

    if door_state == OPEN
    and dark_streak >= DOOR_CONFIRM:
        door_state = CLOSED
        finish_door_session()


2. 关门时停止业务判断
---------------------------------------------------------------------

确认关门后：

    1. 停止 YOLO 业务处理
    2. 不再更新 SnapshotBuffer
    3. 不再执行 diff_snapshots
    4. 冻结当前本地工作库存


3. 上传最终库存清单
---------------------------------------------------------------------

关门时上传的是最终库存快照，而不是单个事件。

上传内容建议：

    device_id
    session_id
    close_time_ms
    inventory_version
    inventory_items

每个库存物品建议包含：

    item_id
    cls_id
    fine_class
    coarse_category
    status        # VISIBLE / OCCLUDED
    bbox
    score
    updated_time_ms


注意：

    OUT 状态物品不应该作为“当前在冰箱里”的库存上传。
    但可以保留在本地 out_stock_archive 中，用于短时间内放回匹配。


4. 上传失败处理
---------------------------------------------------------------------

关门上传可能失败，不能直接丢弃。

建议：

    1. 本地保存一份 pending_upload
    2. 后台请求失败时重试
    3. 下次开门前如果还有 pending_upload，先尝试补传
    4. 上传 payload 带 session_id，后台做幂等处理


5. 幂等要求
---------------------------------------------------------------------

后台保存库存时应按 session_id 幂等。

同一个 session_id 的关门库存重复上传：

    后台应覆盖或忽略重复请求。
    不应该生成多份互相冲突的库存记录。



六、异常与边界情况
=====================================================================

1. 程序启动时门已经打开
---------------------------------------------------------------------

程序启动时可能冰箱门已经是打开的。

建议：

    如果连续 bright_streak >= DOOR_CONFIRM，
    即使没有经历 CLOSED -> OPEN 边沿，也应启动业务会话。

否则会出现：

    用户先打开门，再启动程序。
    程序一直认为没有开门事件。
    初始化不会发生。


2. 程序启动时门已经关闭
---------------------------------------------------------------------

如果启动时画面很暗：

    door_state = CLOSED
    不运行 YOLO 业务流程
    等待开门


3. 开门后后台很慢
---------------------------------------------------------------------

后台请求不能无限等待。

建议：

    BACKEND_TIMEOUT_MS = 500 ~ 1500

超时后：

    init_state = WAIT_FIRST_STABLE_SNAPSHOT
    使用第一份无手稳定快照初始化。

如果后台稍后才返回：

    如果 init_state 已经 READY，不建议再强行覆盖本地库存。
    可以记录日志：
        late backend response ignored


4. 开门时手一直在画面里
---------------------------------------------------------------------

如果手一直在画面里：

    stable_snapshot.has_hand = true
    不能初始化库存

处理方式：

    继续等待无手稳定快照。
    UI / 日志提示：
        waiting first stable no-hand snapshot

如果长时间等不到：

    可以显示警告，但不要用有手快照初始化。


5. 开门时 YOLO 暂时识别不到物品
---------------------------------------------------------------------

如果没有后台库存，第一份无手稳定快照是 0 件：

    可以进入 READY，表示当前冰箱为空。

但为了避免刚开门曝光不稳定导致误判为空，可以加一个短暂等待窗口：

    FIRST_SNAPSHOT_GRACE_MS = 500 ~ 1000

在这个窗口内：

    如果快照是 0 件，可以继续等待下一份稳定快照。

超过窗口仍是 0 件：

    允许以空库存初始化。


6. 后台返回空库存，但当前快照有物品
---------------------------------------------------------------------

如果后台返回空库存，而第一份稳定快照检测到物品：

    默认以稳定快照为准。

原因：

    当前画面是直接观测结果。
    后台空库存可能只是没有历史记录、接口未接入、上次上传失败。


7. 后台返回非空库存，但当前快照为空
---------------------------------------------------------------------

可能原因：

    1. 物品被挡住
    2. YOLO 漏检
    3. 冰箱确实被清空但后台旧记录未更新

建议：

    不要直接删除后台库存。
    将后台物品初始化为 OCCLUDED。
    后续通过 stable_snapshot diff 再慢慢修正。


8. 关门时还有 pending_relocation
---------------------------------------------------------------------

如果关门时还有待确认整理：

    不建议继续等待。
    应根据当前本地工作库存上传。

处理原则：

    pending_relocation 未确认，不提交 MOVED。
    A / B 如果还被冻结，应在关门前按当前最新可见状态做保守恢复。



七、推荐接口定义
=====================================================================

1. 获取后台库存
---------------------------------------------------------------------

请求：

    GET /inventory/current?device_id=luckfox

或：

    POST /inventory/open

请求体：

    {
      "device_id": "luckfox",
      "session_id": "20260610_120000_luckfox",
      "opened_at": 1780000000000
    }


响应：

    {
      "success": true,
      "inventory_found": true,
      "authoritative": true,
      "inventory_version": "v123",
      "items": [
        {
          "item_id": 1,
          "fine_class": "apple",
          "class_id": 0,
          "status": "VISIBLE",
          "bbox": [100, 120, 80, 90],
          "score": 0.91
        }
      ]
    }


如果没有历史库存：

    {
      "success": true,
      "inventory_found": false,
      "authoritative": false,
      "items": []
    }


如果明确知道冰箱为空：

    {
      "success": true,
      "inventory_found": true,
      "authoritative": true,
      "items": []
    }


2. 上传关门库存
---------------------------------------------------------------------

请求：

    POST /inventory/close

请求体：

    {
      "device_id": "luckfox",
      "session_id": "20260610_120000_luckfox",
      "closed_at": 1780000060000,
      "inventory": [
        {
          "item_id": 1,
          "fine_class": "apple",
          "class_id": 0,
          "coarse_category": "fruit_veg",
          "status": "VISIBLE",
          "bbox": [100, 120, 80, 90],
          "score": 0.91
        }
      ]
    }


响应：

    {
      "success": true,
      "inventory_version": "v124"
    }



八、推荐伪代码
=====================================================================

主循环：

    while true:
        frame = read_frame()
        brightness = calc_brightness(frame)
        update_door_state(brightness)

        if door_state == CLOSED:
            continue

        detections = yolo(frame)
        tracks = bytetrack(detections)

        update_operation_context(detections, tracks)

        snapshot_buffer.push(food_detections, has_hand)

        if snapshot_buffer.full():
            snapshot = snapshot_buffer.take_snapshot()

            if snapshot.has_hand:
                continue

            if init_state == WAIT_FIRST_STABLE_SNAPSHOT:
                init_inventory(snapshot)
                baseline_snapshot = snapshot
                init_state = READY
                continue

            if init_state == READY:
                events = diff_snapshots(
                    baseline_snapshot,
                    snapshot,
                    operation_context
                )
                apply_events(events)
                baseline_snapshot = snapshot
                operation_context.reset(snapshot)


开门：

    on_door_open():
        session_id = new_session_id()
        init_state = WAIT_BACKEND
        backend_status = UNKNOWN
        request_backend_inventory_async(session_id)


后台返回：

    on_backend_inventory_response(resp):
        if init_state != WAIT_BACKEND:
            ignore_late_response()
            return

        if resp.success and resp.inventory_found and resp.authoritative:
            trusted_backend_inventory = resp.items
            backend_status = TRUSTED
        else:
            trusted_backend_inventory = []
            backend_status = NO_TRUSTED_BACKEND

        init_state = WAIT_FIRST_STABLE_SNAPSHOT


后台超时：

    on_backend_timeout():
        if init_state == WAIT_BACKEND:
            backend_status = NO_TRUSTED_BACKEND
            init_state = WAIT_FIRST_STABLE_SNAPSHOT


第一份稳定快照初始化：

    init_inventory(snapshot):
        if backend_status == TRUSTED:
            init_from_backend_and_snapshot(trusted_backend_inventory, snapshot)
        else:
            init_from_snapshot(snapshot)


关门：

    on_door_close():
        freeze_working_inventory()
        upload_inventory_close(session_id, working_inventory)
        init_state = NOT_STARTED



九、当前代码需要重点避免的问题
=====================================================================

1. 不要把空 backend_items 当作可信后台库存
---------------------------------------------------------------------

如果调用：

    init_from_backend(empty_vector)

当前实现很容易让：

    backend_initialized_ = true
    backend_items_ = []

这会导致后续第一份快照不再走“无后台库存初始化”，从而本地库存为空。

正确语义应该是：

    init_from_backend(items, trusted)

或者：

    set_backend_inventory(items)
    set_no_backend_inventory()

空列表必须能表达两种不同含义：

    1. 后台没有数据，不可信，需要本地快照初始化
    2. 后台明确知道冰箱为空，可信空库存

不能只用 vector 是否为空来表达。


2. 空冰箱也必须进入 READY
---------------------------------------------------------------------

如果第一份稳定快照是 0 件，并且没有可信后台库存：

    working_inventory = []
    baseline_snapshot = empty_snapshot
    init_state = READY

否则空冰箱开门测试会一直卡住。


3. 初始化完成日志应该无条件明确打印
---------------------------------------------------------------------

建议日志：

    [SESSION] 开门会话开始 session_id=...
    [SESSION] 后台库存请求开始
    [SESSION] 后台库存不可用，等待第一份稳定快照初始化
    [SESSION] 第一份稳定快照: N 件
    [SESSION] 使用快照初始化本地库存: N 件
    [SESSION] 初始化完成，进入 READY

不要只在 inventory.size() > 0 时打印“快照已就绪”。

因为 0 件库存也是一种合法 READY 状态。



十、最终原则
=====================================================================

1. 开门触发业务开始。
2. 后台库存只是初始参考，不是实时裁判。
3. 后台不可用时，第一份无手稳定快照就是初始库存。
4. 空后台库存不能阻塞本地初始化。
5. 空冰箱也必须能进入 READY。
6. 开门期间只维护本地工作库存。
7. 关门时上传最终库存。
8. 上传失败要可重试，接口要幂等。
9. 所有库存事件都必须发生在初始化 READY 之后。
10. 有手快照不能作为库存基准，只能作为 OperationContext 证据。
