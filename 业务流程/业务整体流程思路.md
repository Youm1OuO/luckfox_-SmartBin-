# 业务整体流程思路（重构版，未落地代码）

## 0. 最重要的总原则

系统只保留两份主要数据：

```text
库存表（InventoryDB）
    = 已确认的库存事实；只在快照对比得出结论后才允许修改。

信息处理表（ProcessStore）
    = 本次开门期间的临时工作区；其中包含 N 帧缓冲、两份快照、Track、当前帧 YOLO 结果等。
      关门或本轮快照对比完成后，临时内容会清空/重置。
```

快照不是第三张长期表，而是【信息处理表】中的数据成员。

```cpp
struct InventoryDB {
    map<int, InventoryItem> items;       // item_id -> 正式库存物品
};

struct ProcessStore {
    SnapshotBuffer no_hand_buffer;       // 连续 N 帧无手、无明显移动的 Detection
    Snapshot baseline_snapshot;          // 已确认的旧稳定快照
    Snapshot candidate_snapshot;         // 刚生成、等待对比的新稳定快照
    map<int, ItemTrack> tracks;          // item_id -> 本次 A→B 期间的临时路径
};
```

其中：

```text
InventoryItem
    item_id、cls_id、anchor_box、visible_box、status ……
    这些是确认后的结果。

ItemTrack
    start_box、latest_box、path、last_hand_box ……
    这些是临时过程证据，不放进正式库存物品中。
```

`ItemTrack` 虽然从 `InventoryItem` 中物理剥离，但仍然通过 `item_id` 属于该物品：

```cpp
InventoryItem& item = inventory.items[item_id];
ItemTrack& track = process_store.tracks[item_id];
```

手不进入库存，也不进入快照。每帧手框只在当前帧处理时使用；只有当物品被完全遮挡、需要手代理时，该物品自己的 `ItemTrack.last_hand_box` 暂时保存上一帧关联手框，用于计算位移。

## 1. 开门后的初始化

```text
根据画面亮度等信号识别冰箱门打开。
    ↓
向后台请求当前库存。
    ↓
将后台库存转换为 InventoryDB（库存表）。
```

库存状态直接继承后台已确认状态：

```text
后台是【可见】 → 本地保持【可见】
后台是【遮挡】 → 本地保持【遮挡】
后台是【出库】 → 按业务规则保留或清理，不作为当前冰箱内物品
```

同时创建空的信息处理表：

```cpp
ProcessStore process;
process.no_hand_buffer.clear();
process.baseline_snapshot.valid = false;
process.candidate_snapshot.valid = false;
process.tracks.clear();
```

首次得到 N 帧连续稳定结果时：

```text
生成第一份稳定快照。
    ↓
若没有 baseline_snapshot：
    它成为 baseline_snapshot。
    将能确认对应库存物品的 SnapshotItem 绑定 item_id。
    为当前库存物品创建本轮 ItemTrack 起点。
```

说明：若后台库存没有 bbox，首次稳定快照需要负责补齐/绑定物品位置；这个绑定不应由某一帧 YOLO 结果直接决定。

---

## 2. 每帧处理流程

```text
摄像头取一帧
    ↓
输入 YOLOv5n
    ↓
得到本帧 Detection 列表：{ cls_id, box, score }
```

这一帧的 Detection 只是临时观察结果：

```text
不能直接新增库存；
不能直接删除库存；
不能直接修改 anchor_box；
不能直接把“本帧没检测到”理解为物品拿走。
```

### 2.1 先处理手与 Track

```text
1. 从 Detection 中分离手框与食物框。
2. 手框只用于当前帧判断，不写入 Snapshot。
3. 食物 Detection 可与 ProcessStore.tracks 中同类 ItemTrack 比较。
4. 若某库存物品被手完全遮挡：
       用手的位移更新该物品的 ItemTrack.path（手代理）。
5. 若该物品重新被 YOLO 看见，且 Detection 能匹配该 Track 路径：
       将它重新认领给原 item_id；
       路径压缩为最新一个物品框；
       停止手代理。
```

注意：手代理记录的路径框必须是“物品估计框”，而不是手框本身。

```text
错误：path = [手框1, 手框2, 手框3]
正确：path = [苹果估计框1, 苹果估计框2, 苹果估计框3]
```

正确做法是保留苹果原来的宽高，只把手的位移加到苹果框上。

### 2.2 决定本帧是否参与快照生成

快照的输入条件是：

```text
本帧无手
且没有明显物品移动
且没有正在进行的手代理移动
```

其中“明显移动”是超过阈值的真实位置变化，不是 YOLO 小抖动；不能因为框偏了 1～2 像素就不断重置快照。

```text
若有手 / 有明显移动 / 有手代理：
    清空 no_hand_buffer 的 count，重新等待稳定。

若无手且稳定：
    将本帧的食物 Detection 放入 no_hand_buffer。
```

收集到连续 N 帧后：

```text
N 帧食物 Detection
    ↓
使用严格原位匹配将同一物品聚类、投票、取平均框
    ↓
生成 candidate_snapshot
```

这里生成的是稳定的“观察快照”，不是库存修改。

## 3. N 帧合成一份稳定快照

`no_hand_buffer` 中保存的是 N 帧普通 Detection。合成快照时才把它们合并为 `SnapshotItem`：

```cpp
struct SnapshotItem {
    int item_id = -1;  // baseline 中通常有效；candidate 中对比前可为 -1
    int cls_id;
    BBox box;          // N 帧投票/平均后的稳定框
    float score;
    int vote_count;
};
```

合并条件用于判断“这 N 帧中的两个框是不是同一位置的同一物品”：

```text
1. cls_id 相同；
2. 中心距离足够近；
3. 宽度相对差足够小；
4. 高度相对差足够小。
```

可使用下面的思路。阈值必须以像素或物品尺寸归一化后表示，不能直接沿用未标定的 `0.1`：

```python
def same_stable_object(a, b,
                       max_center_distance_px,
                       max_width_ratio_diff,
                       max_height_ratio_diff):
    if a.cls_id != b.cls_id:
        return False

    center_distance = euclidean(a.box.center, b.box.center)
    if center_distance > max_center_distance_px:
        return False

    width_diff = abs(a.box.width - b.box.width) / max(a.box.width, b.box.width)
    height_diff = abs(a.box.height - b.box.height) / max(a.box.height, b.box.height)
    return width_diff <= max_width_ratio_diff and height_diff <= max_height_ratio_diff
```

合并后的 box 取平均，是为了抵消 YOLO 小抖动：

```text
第 1 帧苹果框：略偏左
第 2 帧苹果框：略偏右
第 3 帧苹果框：正常
    ↓
平均后得到更稳定的苹果框
```

不是为了把“移动前框”和“移动后框”平均在一起；有手或明显移动时，N 帧缓冲早已被清空。

## 4. 两份快照的生命周期

只保留两份已合成快照：

```text
baseline_snapshot   = 上一次已确认的稳定快照
candidate_snapshot  = 当前刚合成、等待比较的稳定快照
```

```text
第一次稳定快照：
    baseline_snapshot = candidate_snapshot

之后每次新的 candidate_snapshot：
    baseline_snapshot 与 candidate_snapshot 对比
    ↓
    得出整理 / 拿出 / 放入 / 露出 / 遮挡
    ↓
    修改 InventoryDB
    ↓
    给 candidate_snapshot 中物品写入最终 item_id
    ↓
    baseline_snapshot = candidate_snapshot
    清空本轮 Track，开始下一轮
```

因此：

```text
baseline_snapshot 中的物品应尽量带 item_id。
candidate_snapshot 中新出现的物品对比前可以 item_id = -1。
快照不保存完整 Track.path；Track 独立存在于 ProcessStore.tracks。
```

---

## 5. 快照匹配：先建立候选，不立刻改库存

比较 `baseline_snapshot` 与 `candidate_snapshot`，先按“原位严格匹配”分成：

```text
same_position_objects (不变的)
    baseline 与 candidate 都有，且原位严格匹配成功。

disappeared_objects (丢失的)
    baseline 有，但 candidate 没有原位匹配。

appeared_objects (增加的)
    candidate 有，但 baseline 没有原位匹配。
```

原位严格匹配仍然使用：类别相同 + 中心近 + 宽高相近；这一步不使用 Track。

```text
注意：这一步只产生候选列表，尚未修改 InventoryDB。
```

---

## 6. 第一步：只在“消失 A + 出现 B”时尝试整理

Track 的意义只在这一小步：判断两个变化是否其实是同一件物品的移动。

```text
若只有消失，没有同类新出现物品：
    不使用 Track，按拿出流程处理。

若只有新出现，没有同类旧物品消失：
    不使用 Track，按放入流程处理。

只有同时满足：
    旧快照中 A 消失
    新快照中 B 出现
    A 与 B cls_id 相同、宽高相近
才读取 A.item_id 对应的 ItemTrack。
```

整理判定：

```text
A = baseline_snapshot 中消失的物品（应能找到 A.item_id）
B = candidate_snapshot 中新出现的物品（暂时 item_id = -1）

track = ProcessStore.tracks[A.item_id]

若 B.box 与 track.path 中至少一个“物品估计框”严格接近：
    A 很可能移动到了 B
    → 判定【整理】
    → B.item_id = A.item_id
    → 更新库存中 A.item_id 的 anchor_box = B.box
    → A、B 标记为已消费，不再参与后续拿出/放入处理
```

不能只比较 `track.latest_box`：手可能在物品已经放下后继续离开冰箱；这时真正的放下位置可能是路径中较早的点。

整理还必须满足唯一性：

```text
同一个 A 不应能同样好地匹配多个 B；
同一个 B 不应能同样好地匹配多个 A；
若候选不唯一，则本轮不强行判整理，按“拿出 + 放入”处理即可。
```

---

## 7. 第二步：处理剩余消失物品（拿出 / 遮挡）

对未被“整理”消费的 `disappeared_objects` 中每个 A：

```text
1. 通过 A.item_id 找到 InventoryDB 中对应物品。

2. 找不到 item_id：
       不修改库存。
       可能是旧快照误检或初始绑定失败。

3. 库存状态是【遮挡】：
       不直接判【出库】。
       因为它本来就不可见，candidate 中继续看不见不能证明被拿走。

4. 库存状态是【可见】：
       在 A.anchor_box 附近搜索未消费的 appeared_objects，统一裁决。
```

附近候选 C 的含义：

```text
C 能匹配库存中【遮挡】物品：
    A 被拿走后，原来被挡住的 C 露出来（reveal_candidate）。

C 能匹配库存中【可见】物品：
    C 原本就在库存中，现在仍可见（visible_inventory_candidate）。

C 不能匹配任何当前库存：
    C 可能是新放入物品，并遮挡了 A（occlusion_candidate）。
```

统一裁决优先级：

```text
1. 有 occlusion_candidate：
       A 从【可见】变为【遮挡】；仍保留库存。
       C 暂不消费，继续交给“新出现物品”步骤。

2. 没有 occlusion_candidate，但有 reveal_candidate：
       A 从【可见】变为【出库】。
       被露出的 C 从【遮挡】变为【可见】。
       消费 reveal_candidate。

3. 只有 visible_inventory_candidate，或附近没有任何 C：
       A 从【可见】变为【出库】。
```

这里的【出库】建议保留记录并写 `out_time_ms`，暂不立刻物理删除：它本身就相当于旧设计中的 `out_stock_archive`，后续若识别到放回，可恢复原 `item_id`。

---

## 8. 第三步：处理剩余新出现物品（露出 / 放回 / 放入）

对未被整理、未被第二步消费的 `appeared_objects` 中每个 B：

```text
1. 与当前库存做原位严格匹配（主框使用 anchor_box）：
       匹配到【可见】物品：说明它原本就在库存中，不新增。
       匹配到【遮挡】物品：说明旧物品露出，状态改为【可见】。

2. 若没匹配当前库存，再尝试匹配状态为【出库】但尚未过期的旧物品：
       匹配成功：说明放回；恢复原 item_id，状态改为【可见】。

3. 都匹配失败：
       说明是全新放入物品；此时才分配新的 item_id 并写入库存表。
```

本步骤同样不需要 Track。

---

## 9. 提交结果并开始下一轮

上述三个步骤完成后，才一次性提交结果：

```text
更新 InventoryDB：
    整理 → 保留 item_id，更新 anchor_box
    拿出 → 状态改 OUT，记录时间
    放回 → 恢复原 item_id，状态改 VISIBLE
    放入 → 创建新 item_id
    露出/遮挡 → 更新状态与稳定 visible_box

更新 candidate_snapshot 中每个物品的 item_id。
baseline_snapshot = candidate_snapshot。

清空本次操作的临时过程数据：
    no_hand_buffer.clear()
    tracks.clear()
    candidate_snapshot 置空

为仍在库存中的物品重新创建下一轮 ItemTrack 起点。
```

最后做例行清理：

```text
1. 清理超过保留时间的 OUT 物品；
2. 检查同一 item_id 是否意外出现重复记录；
3. 同类候选不唯一时，不强行绑定 item_id；
4. 优先保证库存数量正确，而不是勉强判定整理。
```

处理顺序必须固定：

```text
快照候选建立
    → 整理
    → 消失（拿出/遮挡）
    → 新出现（露出/放回/放入）
    → 一次性提交库存
    → 清理临时信息
```
