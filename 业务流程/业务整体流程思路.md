# 业务整体流程思路（重构版，未落地代码）

## 0. 最重要的总原则

系统只保留两份主要数据：

```text
库存表（InventoryDB）
    = 已确认的库存事实；只在快照对比得出结论后才允许修改。

信息处理表（ProcessStore）
    = 本次开门期间的临时工作区；其中包含 N 帧缓冲、两份快照、Track、当前帧 YOLO 结果等。
      关门或本轮快照对比完成后，临时内容会清空/重置。
```

快照不是第三张长期表，而是【信息处理表】中的数据成员。

```cpp
struct InventoryDB {
    map<int, InventoryItem> items;       // item_id -> 正式库存物品
};

struct ProcessStore {
    SnapshotBuffer no_hand_buffer;       // 连续 N 帧无手、无明显移动的 Detection
    Snapshot baseline_snapshot;          // 已确认的旧稳定快照
    Snapshot candidate_snapshot;         // 刚生成、等待对比的新稳定快照
    map<int, ItemTrack> tracks;          // item_id -> 本次 A→B 期间的临时路径
};
```

其中：

```text
InventoryItem
    item_id、cls_id、anchor_box、visible_box、status ……
    这些是确认后的结果。

ItemTrack
    start_box、latest_box、path、last_hand_box ……
    这些是临时过程证据，不放进正式库存物品中。
```

`ItemTrack` 虽然从 `InventoryItem` 中物理剥离，但仍然通过 `item_id` 属于该物品：

```cpp
InventoryItem& item = inventory.items[item_id];
ItemTrack& track = process_store.tracks[item_id];
```

手不进入库存，也不进入快照。每帧手框只在当前帧处理时使用；只有当物品被完全遮挡、需要手代理时，该物品自己的 `ItemTrack.last_hand_box` 暂时保存上一帧关联手框，用于计算位移。

## 1. 开门后的初始化

```text
根据画面亮度等信号识别冰箱门打开。
    ↓
向后台请求当前库存。
    ↓
将后台库存转换为 InventoryDB（库存表）。
```

库存状态直接继承后台已确认状态：

```text
后台是【可见】 → 本地保持【可见】
后台是【遮挡】 → 本地保持【遮挡】
后台是【出库】 → 按业务规则保留或清理，不作为当前冰箱内物品
```

同时创建空的信息处理表：

```cpp
ProcessStore process;
process.no_hand_buffer.clear();
process.baseline_snapshot.valid = false;
process.candidate_snapshot.valid = false;
process.tracks.clear();
```

首次得到 N 帧连续稳定结果时：

```text
生成第一份稳定快照。
    ↓
若没有 baseline_snapshot：
    它成为 baseline_snapshot。
    将能确认对应库存物品的 SnapshotItem 绑定 item_id。
    为当前库存物品创建本轮 ItemTrack 起点。
```

说明：若后台库存没有 bbox，首次稳定快照需要负责补齐/绑定物品位置；这个绑定不应由某一帧 YOLO 结果直接决定。

## 2. 每帧处理流程

```text
摄像头取一帧
    ↓
输入 YOLOv5n
    ↓
得到本帧 Detection 列表：{ cls_id, box, score }
```

这一帧的 Detection 只是临时观察结果：

```text
不能直接新增库存；
不能直接删除库存；
不能直接修改 anchor_box；
不能直接把“本帧没检测到”理解为物品拿走。
```

### 2.1 先处理手与 Track

```text
1. 从 Detection 中分离手框与食物框。
2. 手框只用于当前帧判断，不写入 Snapshot。
3. 食物 Detection 可与 ProcessStore.tracks 中同类 ItemTrack 比较。
4. 若某库存物品被手完全遮挡：
       用手的位移更新该物品的 ItemTrack.path（手代理）。
       此时只积累“可能的移动路径”，不立刻判断物品已放下，也不修改库存。
5. 若该物品重新被 YOLO 完整看见、且不再被手遮挡，且 Detection 能匹配该 Track 路径：
       将它重新认领给原 item_id；
       将路径清空后，只保留这个最新物品框；
       停止该物品的手代理；之后手再去移动其他物品，不再追加到它的路径。
```

路径压缩的实际结果是：

```text
确认放下前：path = [起点, 手代理点1, 手代理点2, ...]
确认放下后：path = [latest_box]
```

注意：手代理记录的路径框必须是“物品估计框”，而不是手框本身。

```text
错误：path = [手框1, 手框2, 手框3]
正确：path = [苹果估计框1, 苹果估计框2, 苹果估计框3]
```

正确做法是保留苹果原来的宽高，只把手的位移加到苹果框上。

### 2.1.1 不要求实时判断“已经放下”

手拿 A、放下 A 后又继续在冰箱内移动，并不需要在当时立刻判定 A 已放下：

```text
手还在画面中：
    不生成快照，不比较快照，不修改 InventoryDB；
    Track 只继续保存过程证据。

手离开后，连续 N 帧稳定：
    才生成 candidate_snapshot；
    再把“旧快照中消失的 A”与“新快照中出现的 B”统一比较。
```

若 A 重新被 YOLO 完整看见且不再被手遮挡，就能较可靠地停止 A 的手代理。
若 A 全程看不见、手又继续去移动另一个物品，则无法准确知道手在哪一帧从 A 切换到另一个物品；这时允许 A 的路径保留不确定性，但不能据此强行判定整理。

若同一物品之后又被手拿起，就从仅有的 `latest_box` 继续追加新的手代理路径点。

### 2.2 决定本帧是否参与快照生成

快照的输入条件是：

```text
本帧无手
且没有明显物品移动
且没有正在进行的手代理移动
```

其中“明显移动”是超过阈值的真实位置变化，不是 YOLO 小抖动；不能因为框偏了 1～2 像素就不断重置快照。

这里的“正在进行”指当前帧手仍在画面中、手代理仍在更新。手已经离开后，某个 Track 即使还保留一段尚未完全确认的历史路径，也不能阻止生成稳定快照；这段路径正是后续快照对比时要使用的证据。

```text
若有手 / 有明显移动 / 有手代理：
    清空 no_hand_buffer 的 count，重新等待稳定。

若无手且稳定：
    即使 tracks 中仍有未完全确认的历史路径，也允许生成快照；
    将本帧的食物 Detection 放入 no_hand_buffer。
```

收集到连续 N 帧后：

```text
N 帧食物 Detection
    ↓
使用 `match_box(..., MATCH_ORIGIN)` 将同一物品聚类、投票、取平均框
    ↓
生成 candidate_snapshot
```

这里生成的是稳定的“观察快照”，不是库存修改。

## 3. N 帧合成一份稳定快照

`no_hand_buffer` 中保存的是 N 帧普通 Detection。合成快照时才把它们合并为 `SnapshotItem`：

```cpp
struct SnapshotItem {
    int item_id = -1;  // baseline 中通常有效；candidate 中对比前可为 -1
    int cls_id;
    BBox box;          // N 帧投票/平均后的稳定框
    float score;
    int vote_count;
};
```

所有场景都只使用同一个基础匹配函数；不再实现多套“严格匹配函数 / 宽松匹配函数 / Track 匹配函数”。

```cpp
struct MatchRule {
    bool require_same_class;       // 是否要求 cls_id 相同
    float max_center_distance;     // 归一化中心距离阈值
    float max_width_diff;          // 相对宽度差阈值 [0, 1]
    float max_height_diff;         // 相对高度差阈值 [0, 1]
};

bool match_box(const Object& a, const Object& b, const MatchRule& rule) {
    if (rule.require_same_class && a.cls_id != b.cls_id) {
        return false;
    }

    // 用较小框对角线归一化，避免小苹果和大保鲜盒共用“20 像素”阈值时失真。
    float scale = max(1.0f, min(diagonal(a.box), diagonal(b.box)));
    float center_distance = distance(a.box.center(), b.box.center());
    float normalized_center_distance = center_distance / scale;
    if (normalized_center_distance > rule.max_center_distance) {
        return false;
    }

    float max_width = max(a.box.width(), b.box.width());
    float max_height = max(a.box.height(), b.box.height());
    if (max_width <= 0.0f || max_height <= 0.0f) {
        return false;
    }
    float width_diff = abs(a.box.width() - b.box.width()) / max_width;
    float height_diff = abs(a.box.height() - b.box.height()) / max_height;
    return width_diff <= rule.max_width_diff &&
           height_diff <= rule.max_height_diff;
}
```

同一函数只换参数。下面数值只是第一版起点，实际要用采集数据调参：

```cpp
// N 帧合成快照、两快照原位比较：要求非常像同一位置物品。
const MatchRule MATCH_ORIGIN  = {true,  0.25f, 0.20f, 0.20f};

// Track 路径点与新位置 B：允许检测框因部分遮挡略有变化。
const MatchRule MATCH_TRACK   = {true,  0.70f, 0.45f, 0.45f};

// “A 原位置附近是否出现 C”：不是身份判断；C 可以不同类、不同大小。
// 宽高阈值设为 1.0 表示这一步不限制宽高，只判断是否在附近。
const MatchRule MATCH_NEARBY = {false, 1.20f, 1.00f, 1.00f};
```

因此，`MATCH_ORIGIN`、`MATCH_TRACK`、`MATCH_NEARBY` 是三份参数，不是三套算法。

合并后的 box 取平均，是为了抵消 YOLO 小抖动：

```text
第 1 帧苹果框：略偏左
第 2 帧苹果框：略偏右
第 3 帧苹果框：正常
    ↓
平均后得到更稳定的苹果框
```

不是为了把“移动前框”和“移动后框”平均在一起；有手或明显移动时，N 帧缓冲早已被清空。

## 4. 两份快照的生命周期

只保留两份已合成快照：

```text
baseline_snapshot   = 上一次已确认的稳定快照
candidate_snapshot  = 当前刚合成、等待比较的稳定快照
```

```text
第一次稳定快照：
    baseline_snapshot = candidate_snapshot

之后每次新的 candidate_snapshot：
    baseline_snapshot 与 candidate_snapshot 对比
    ↓
    得出整理 / 拿出 / 放入 / 露出 / 遮挡
    ↓
    修改 InventoryDB
    ↓
    给 candidate_snapshot 中物品写入最终 item_id
    ↓
    baseline_snapshot = candidate_snapshot
    清空本轮 Track，开始下一轮
```

因此：

```text
baseline_snapshot 中的物品应尽量带 item_id。
candidate_snapshot 中新出现的物品对比前可以 item_id = -1。
快照不保存完整 Track.path；Track 独立存在于 ProcessStore.tracks。
```

## 5. 快照匹配：先建立候选，不立刻改库存

比较 `baseline_snapshot` 与 `candidate_snapshot`，先按
`match_box(..., MATCH_ORIGIN)` 分成：

```text
same_position_objects (不变的)
    baseline 与 candidate 都有，且原位严格匹配成功。

disappeared_objects (丢失的)
    baseline 有，但 candidate 没有原位匹配。

appeared_objects (增加的)
    candidate 有，但 baseline 没有原位匹配。
```

这里仍然是同一个 `match_box()`：类别相同 + 中心近 + 宽高相近；
只是传入 `MATCH_ORIGIN`。这一步不使用 Track。

```text
注意：这一步只产生候选列表，尚未修改 InventoryDB。
```

## 6. 第一步：只在“消失 A + 出现 B”时尝试整理

Track 的意义只在这一小步：判断两个变化是否其实是同一件物品的移动。

```text
若只有消失，没有同类新出现物品：
    不使用 Track，按拿出流程处理。

若只有新出现，没有同类旧物品消失：
    不使用 Track，按放入流程处理。

只有同时满足：
    旧快照中 A 消失
    新快照中 B 出现
    A 与 B cls_id 相同、宽高相近
才读取 A.item_id 对应的 ItemTrack。
```

整理判定：

```text
A = baseline_snapshot 中消失的物品（应能找到 A.item_id）
B = candidate_snapshot 中新出现的物品（暂时 item_id = -1）

track = ProcessStore.tracks[A.item_id]

若 B.box 与 track.path 中至少一个“物品估计框”满足
`match_box(..., MATCH_TRACK)`：
    A 很可能移动到了 B
    → 判定【整理】
    → B.item_id = A.item_id
    → 更新库存中 A.item_id 的 anchor_box = B.box
    → A、B 标记为【身份已处理】，不再参与后续拿出/放入处理
```

不能只比较 `track.latest_box`：手可能在物品已经放下后继续离开冰箱；这时真正的放下位置可能是路径中较早的点。

整理阶段始终只使用一条规则：`B.box` 与 `track.path` 中至少一个点匹配。

```text
已确认放下：path 只有 latest_box
    → “匹配 path 中至少一个点”等同于比较 latest_box。

尚未确认放下：path 保留完整过程
    → 仍可匹配到较早的真实放下位置，不会被手后续离开的 latest_box 误导。
```

整理不是手部操作中的实时判定，而是在手离开、生成新的稳定快照后才统一判定。因此“等待重新看见物品”带来的延迟不是问题：期间不会生成快照，也不会修改库存。

如果一次手部操作连续移动多个物品：

```text
某物品重新被看见并成功认领：
    它的手代理路径到此结束；之后的手移动不属于它。

某物品始终被完全遮挡：
    路径可能混入手后来移动其他物品的部分。
    只有最终 A → B 匹配唯一且证据足够强，才判整理；
    否则不判整理，退回“拿出 + 放入”或“遮挡”的保守结果。
```

### 6.1 整理确认后，立刻处理旧位置和新位置的遮挡变化

确认 `A → B` 整理后，不能只更新 A 的位置；还要立刻检查两处位置。

```text
A 的旧位置：A 被移走后，是否有原先【遮挡】的 C 露出来？
B 的新位置：A 移到这里后，是否有原先【可见】的 D 被挡住？
```

#### 6.1.1 检查 A 的旧位置：C 是否露出

在尚未处理的 `appeared_objects` 中扫描 C：

```text
若 C 位于 A 的旧位置附近：
    match_box(A旧box, C.box, MATCH_NEARBY)

且 C 能唯一严格匹配到一个原先【遮挡】库存物品 I：
    match_box(C.box, I.anchor_box, MATCH_ORIGIN)

则：
    I：计划【遮挡】→【可见】
    I.visible_box = C.box
    C.item_id = I.item_id
    C 标记为【身份已处理】
```

含义是：A 原来压住/挡住了 I；A 整理走后，I 在旧位置露出。

#### 6.1.2 检查 B 的新位置：D 是否被挡住

在尚未处理的 `disappeared_objects` 中扫描 D：

```text
若 D 原先是【可见】库存物品，且 D 的旧位置位于 B 新位置附近：
    match_box(D旧box, B.box, MATCH_NEARBY)

则：
    D：计划【可见】→【遮挡】
    D 标记为【身份已处理】
```

含义是：A 被整理到 B 后，覆盖了原先在 B 附近可见的 D。

必须扫描所有符合条件的 C 和 D，不只处理第一个
C、D 被标记为“身份已处理”后，不会在后面的普通【拿出】或【放入】步骤里被重复处理。

整理后的完整效果因此是：

```text
A：保留原 item_id，位置更新为 B
C：若在 A 旧位置露出，则【遮挡】→【可见】
D：若在 B 新位置被遮住，则【可见】→【遮挡】
```

整理还必须满足唯一性：

```text
同一个 A 不应能同样好地匹配多个 B；
同一个 B 不应能同样好地匹配多个 A；
若候选不唯一，则本轮不强行判整理，按“拿出 + 放入”处理即可。
```

## 7. 第二步：处理剩余消失物品（拿出 / 遮挡）

第 6.1 节已经处理了“已确认整理”引起的两种遮挡变化：

```text
A 移走后，旧位置露出 C：C 从【遮挡】变【可见】；
A 移到新位置后，挡住 D：D 从【可见】变【遮挡】。
```

所以本步骤只处理还没有在第 6 节中处理过的消失物品 A。仍保留三种可能：

```text
1. A 真的被拿走；
2. 新放入、或身份暂时不明的物品 C 出现在 A 原位置，挡住了 A。
3. 冰箱中原有的一件物品移到 A 原位置，挡住了 A。

第 3 种按正常流程已由第 6.1 节处理；这里仍再检查一次，
作为第 6 节匹配漏掉、但该物品的轨迹证据仍足够明显时的保护，避免把 A 错判为拿走。
```

下文的“改状态”都只是写入 `planned_changes`；真正修改 `InventoryDB` 仍要等第 9 节统一提交。

### 7.1 先过滤不能判出库的 A

对未被“整理”处理的 `disappeared_objects` 中每个 A：

```text
1. 用 A.item_id 在 InventoryDB 中查找库存物品 I。

2. 找不到 I：
       跳过 A。
       原因：可能是旧快照误检，或初始化时没有成功绑定 item_id。

3. I.status == 【遮挡】：
       跳过 A，不判【出库】。
       原因：遮挡物品本来就不可见；“这次仍没看见”没有足够信息。
       而且原先是【遮挡】的物品不能直接变成【出库】。

4. I.status == 【可见】：
       先在 appeared_objects 中找 A 旧位置附近的 C。
       InventoryDB 只用于确认 C 是否是原先【遮挡】的旧物品。

       4.1 附近没有 C：
              A 大概率被拿走，计划【可见】→【出库】。

       4.2 附近有 C，且 C 能唯一匹配原先【遮挡】的库存物品：
              说明 A 移走后，旧物品 C 露出来。
              C 对应库存项：计划【遮挡】→【可见】；
              A：计划【可见】→【出库】。

       4.3 附近有其他 C（不是上述“露出的旧物品”）：
              C 可能是新放入物，也可能是原有物品移动过来。
              为避免把仍在冰箱中的 A 错判出库，
              A：计划【可见】→【遮挡】。

       若附近有多个 C：全部检查；只要存在 4.3 的 C，就优先让 A 保持【遮挡】。
```

### 7.2 什么叫“附近的 C”

判断 A 旧位置是否被遮挡时，候选范围是 **`appeared_objects + InventoryDB`**：

```text
1. appeared_objects：当前稳定快照中实际看得见、位于 A 旧位置附近的物体 C。
   要扫描全部 appeared_objects；即使某个 B 已在第 6 节绑定 item_id，
   它仍可作为“现在确实有物体在 A 旧位置”的证据。

2. InventoryDB：冰箱原有物品的 item_id、状态和 ItemTrack。
   它用于判断 C 是否其实是某件原有物品移过来的，而不是新放入物。
```

```cpp
// 不要求 C 与 A 同类；新放入的牛奶也可能挡住苹果。
bool is_near_old_position = match_box(A, C, MATCH_NEARBY);
```

---

## 8. 第三步：处理剩余新出现物品（露出 / 放回 / 放入）

对未被整理、未被第二步消费的 `appeared_objects` 中每个 B：

```text
1. 与当前库存做 `match_box(B, inventory_item.anchor_box, MATCH_ORIGIN)`：
       匹配到【可见】物品：说明它原本就在库存中，不新增。
       匹配到【遮挡】物品：说明旧物品露出，状态改为【可见】。

2. 若没匹配当前库存，再尝试匹配状态为【出库】但尚未过期的旧物品：
       匹配成功：说明放回；恢复原 item_id，状态改为【可见】。

3. 都匹配失败：
       说明是全新放入物品；此时才分配新的 item_id 并写入库存表。
```

本步骤同样不需要 Track。

## 9. 提交结果并开始下一轮

上述三个步骤完成后，才一次性提交结果：

```text
更新 InventoryDB：
    整理 → 保留 item_id，更新 anchor_box
    拿出 → 状态改 OUT，记录时间
    放回 → 恢复原 item_id，状态改 VISIBLE
    放入 → 创建新 item_id
    露出/遮挡 → 更新状态与稳定 visible_box

更新 candidate_snapshot 中每个物品的 item_id。
baseline_snapshot = candidate_snapshot。

清空本次操作的临时过程数据：
    no_hand_buffer.clear()
    tracks.clear()
    candidate_snapshot 置空

为仍在库存中的物品重新创建下一轮 ItemTrack 起点。
```

最后做例行清理：

```text
1. 清理超过保留时间的 OUT 物品；
2. 检查同一 item_id 是否意外出现重复记录；
3. 同类候选不唯一时，不强行绑定 item_id；
4. 优先保证库存数量正确，而不是勉强判定整理。
```

处理顺序必须固定：

```text
快照候选建立
    → 整理
    → 消失（拿出/遮挡）
    → 新出现（露出/放回/放入）
    → 一次性提交库存
    → 清理临时信息
```
